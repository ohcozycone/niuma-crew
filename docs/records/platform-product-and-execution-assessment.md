## 1. 核心判断

当前平台是**以员工配置为导航中心、以对话为主要执行容器，已有真实运行管理和专业 CI 诊断用例的早期平台**。它具备演进基础，但“员工已配置”与“员工能持续承担工作”之间仍有距离。

建议的产品演进目标是：**让用户把一类工作放心交给数字员工，并获得可核对、可采用、可继续跟进的结果。** 员工是可复用的职责和能力，任务是一次工作的目标，对话承接沟通，配置负责维护。

| 用户问题                                            | 判断                                                                   | 建议                                                                          |
| --------------------------------------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 收藏员工点击进入配置页是否合理                      | 对维护工具合理；对日常交办工作的平台，默认动作偏离使用目的             | 近期进入可用员工的新对话；有任务能力后进入员工工作页，配置保持显式入口        |
| loop + prompt + Skill + MCP + 知识 + rules 是否合理 | 作为能力装配和认知执行基础合理，作为完整数字员工定义不充分             | 补职责、交付标准、授权与环境、执行策略、成果验收和持续运营                    |
| 对话价值是否有限                                    | 价值取决于是否减少真实工作的总投入；对话本身既不证明价值，也不妨碍价值 | 先把一项工作从资料接入做到结果被采用，再增加触发与自动化                      |
| 是否必须多 harness                                  | 需要多种执行语义，未必需要多个框架或独立引擎                           | 统一平台控制与记录，保留交互 Agent；按需增加持久流程中的 Agent 步骤及沙箱环境 |
| 宏观建设顺序                                        | 完整画布、全行业目录与多框架托管都不是当前前置                         | 当前知识助手学习迭代先行；产品化围绕单一工作闭环验证，再补后台执行            |

分析顺序应是“用户需要什么结果 → 围绕什么对象使用 → 怎样执行 → 哪些保证由平台承担 → 如何分期验证”，不能仅从一个链接或一个框架得出结论。

## 3. 第一性原理：平台应围绕什么价值组织

### 3.1 从工作结果倒推对象

一次真实工作的成本包含资料与连接准备、说明目标、等待、检查纠错、采用结果，以及后续维护。生成快了，而准备与复核更贵，并不产生净收益。

以“回复项目交付问题”为例，用户可能需要四种不同结果：

1. 看懂概念：有依据的对话回答就能完成工作。
2. 向客户解释：需要答复草稿、出处和适用版本，由负责人确认。
3. 处理一批工单：需要逐项状态、失败项、负责人及回写结果。
4. 长期维护答复：需要重复问题识别、已确认答案复用、资料变化后的复核。

它们都可以通过对话发起，但后三种不能只用一串消息表达全部状态。第一种也不需要强迫填写复杂任务表单。

建议沿用[领域术语](../architecture/domain-glossary.md)的对象分工：员工承担职责与能力，Task 保存目标及验收，Run 记录一次尝试，Conversation 保存沟通，Deliverable 保存成果。流程是可复用执行方法，触发器决定何时交办。知识导入、索引与评测保留各自作业语义，不伪装成业务聊天。

### 3.2 使用中心与维护中心可以共存

| 主要用户                 | 高频问题                 | 合适的默认中心               |
| ------------------------ | ------------------------ | ---------------------------- |
| Agent 构建者、平台维护者 | 怎样装配、调试和发布员工 | 员工配置、测试、连接与评测   |
| 业务执行者               | 这件事交给谁，结果在哪里 | 交办、任务、成果与最近沟通   |
| 业务负责人               | 哪里卡住，哪些需要我决定 | 待处理、异常、审批与采用情况 |

当前权限和导航偏第一类，数字员工愿景包含后两类。这是阶段差距，不能简单归因于链接写错。长期围绕同一员工提供使用与维护视图，按权限显示入口；早期无需建设两套门户。

商业化应优先验证工作结果。个人学习中，覆盖更多技术有独立价值，但仍应通过可运行的小闭环学习，而非一次堆满组件。

## 4. 收藏员工入口与信息架构

### 4.1 当前入口的判断

收藏通常表示希望更快再次使用对象；侧栏持续可见，更像日常快捷入口。当前点击进入“编辑员工”，而目录主按钮是“开始对话”，默认意图不一致。问题不只在 URL，而在员工详情与编辑配置合并了。

如果平台明确面向构建者，收藏用于管理待调试员工，进入配置是合理选择。如果目标是交办与跟进工作，建议默认使用，显式维护。判断依据是用户的重复动作和完成工作所需成本，不是名称里有没有“员工”。

### 4.2 按阶段调整

| 阶段           | 收藏点击后的目标                                     | 关键边界                                              |
| -------------- | ---------------------------------------------------- | ----------------------------------------------------- |
| 当前对话阶段   | 有执行权限且员工可用时，进入员工新对话交办页         | 页面读取不创建会话、不执行；“设置”显式进入配置        |
| 形成真实任务后 | 员工工作页：能做什么、交办、当前任务、最近成果与对话 | 默认展示工作；配置为独立页或显式标签                  |
| 多人使用后     | 个人常用员工与管理员共享推荐分开                     | 当前共享星标若保留，建议称推荐/置顶；个人收藏另有归属 |

不建议无条件打开最近对话：同一员工可能服务不同项目，自动延续容易串上下文。可以列出最近对话供显式继续，执行中的任务则显示“继续此任务”。

员工未配置或被停用时，呈现原因；有权限者可进入配置，无权限者看到只读说明。游客/member 当前不能执行，不能仅改链接就将其送入无权限流程。

中期建议日常导航围绕工作台/待处理、任务、对话、员工组织，技能、知识、模型、连接与规则承接管理。尚未实现的任务不先放空菜单；harness 类型、MCP 工具名也无需成为业务用户每次交办的必填项。

验收应比较从收藏到提交所需步骤、误入编辑的情况、上下文混用和运行中工作是否好找，不只检查 URL。

## 5. 对能力组合模型的多维评估

### 5.1 合理之处与缺失之处

共享执行器降低重复开发；岗位指令限定职责，Skill 复用方法，工具连接实际系统，知识提供事实依据，rules 表达共同要求。它们变化速度与维护者不同，分开管理合理。相同 loop 服务多个岗位，也有利于统一观测和模型替换。

但这仍是一份能力材料清单，尚未回答什么时候接活、以谁的身份行动、怎样知道完成、失败如何恢复、结果交给谁。

| 维度        | 组合能解决什么             | 组合本身不能保证什么                 | 建议                                                       |
| ----------- | -------------------------- | ------------------------------------ | ---------------------------------------------------------- |
| 岗位 prompt | 职责、语气、工作重点       | 岗位名称对应实际胜任力               | 定义可接任务、拒绝范围、必要输入与完成标准；按真实工作评测 |
| Skill       | 方法、参考、模板与可选脚本 | 必定遵守方法、工具必定可用、结果正确 | 方法内容与工具许可分离；标准包支持逐项验证                 |
| MCP/工具    | 外部操作发现和调用         | 权限、幂等、业务顺序、交付质量       | 受信层检查连接身份和资源范围，调用前复核                   |
| 知识        | 事实与业务背景             | 内容最新、访问合法、结论被来源支持   | 保留发布、版本、来源和实际引用，暴露资料不足               |
| rules       | 共同要求和行为偏好         | 不可绕过的制度和安全条件             | 文字规范进上下文，强制审批和阈值进程序策略                 |
| 记忆        | 减少重复交代背景           | 历史聊天自动成为可信长期记忆         | 按用户/项目/任务归属，可检查、纠正和撤销，不据此扩权       |
| 执行        | 模型判断读什么、调什么     | 长等待、恢复、持续授权和副作用安全   | 平台生命周期与持久编排负责                                 |
| 交付与评测  | 生成正文和候选结果         | 任务完成、结果采用、业务收益         | 分开记录结果检查、人工接受和实际系统状态                   |

上表是本项目的设计分析，不代表框架效果已在本项目验证。

### 5.2 一名可上岗员工需要回答六个问题

1. **职责**：接受哪类工作，何时移交人类？
2. **能力**：采用哪些方法、知识、模型和工具？
3. **授权与环境**：访问哪些项目、资料、账号，能否读写文件和运行代码？
4. **执行约定**：人交办还是事件触发，能否后台推进，何时等待？
5. **交付约定**：输出什么，如何检查，谁接受，怎样回写？
6. **运营**：如何发现失败、控制费用、停用、评测与升级？

员工无需拥有独立模型或 loop，也无需终身固定执行策略。同一个项目支持员工可以即时答疑，也可以按结构化流程处理需复核的客户答复。

### 5.3 可靠性、易用性与成本的取舍

配置自由度越高，越容易出现“岗位 × 模型 × Skill × 工具 × 知识版本”的组合爆炸。建议提供少量已验证工作模板与就绪检查，允许高级用户修改，并保存实际运行依据；不能要求业务用户都成为 Agent 工程师。

把全部 Skill、工具和知识塞进首轮上下文，会增加成本与干扰；当前按需加载方向值得保留。工具数量也不等于员工能力，发现方式、命名、输入契约和最小许可范围同样重要。

prompt 写“审批后才能执行”仍依赖模型遵守，不构成硬保证。权限、凭证、资源范围和强制审批必须独立执行。即使审批器采用插件实现，不可绕过的调用位置仍属于平台责任。

## 7. 数字员工可以怎样工作

### 7.1 对话、定时和 workflow 属于不同维度

| 维度     | 回答的问题         | 可选形式                                               |
| -------- | ------------------ | ------------------------------------------------------ |
| 交互渠道 | 人从哪里表达与查看 | 网站对话、表单、IM、邮件、API                          |
| 触发方式 | 什么时候创建工作   | 手动、定时、Webhook、业务事件、上游任务                |
| 编排方式 | 谁决定下一步       | 固定流程、Agent 动态探索、混合                         |
| 执行环境 | 在哪里采取行动     | API 工具、文件工作区、代码沙箱、浏览器、受控本地执行器 |
| 人机分工 | 哪些决定交给人     | 即时协作、草稿确认、例外升级、限权自动执行             |

它们可以组合：用户在对话中交办周报，定时器每周触发，workflow 收集指标，Agent 分析异常，负责人确认后工具发布。

Anthropic 对 workflow 与 agent 的区分也落在控制流：前者采用预定义路径，后者由模型动态决定过程。这里引用稳定概念，不将其 2024 年文章中的工具清单作为当前选型依据。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)。

### 7.2 工作形态与完成条件

| 形态               | 例子                             | 什么才算完成                             | 关键机制                               |
| ------------------ | -------------------------------- | ---------------------------------------- | -------------------------------------- |
| 即时问答           | 解释项目部署要求                 | 有依据，缺失与适用范围清楚               | 知识权限、引用与反馈                   |
| 一次性交办         | 比较三个方案，交付选型报告       | 报告、证据、未知项可查看，可接受或退回   | Task、来源、成果与验收                 |
| 事件处理           | CI 失败后生成诊断草稿            | 对应运行的证据已核对，异常有去向         | 验签、去重、固定对象、失败升级         |
| 定时作业           | 每周整理项目风险                 | 本期报告生成，缺失源可见，交付到约定位置 | 时区、错过执行策略、重叠控制与交付记录 |
| 持续监控           | 资料变化后提示需复核答案         | 检出相关变化并通知，无变化时安静         | 基线、增量游标、去重、阈值与持续授权   |
| 固定流程中的判断   | 收集申请→核对→审批→回写          | 必要步骤完成，写入状态已确认             | 持久状态机、等待、审批与幂等           |
| 批量处理           | 整理一批工单                     | 每项有结果，部分失败可单独重试           | 分片、并发配额、逐项记账与汇总         |
| 文件与代码         | 清洗数据、生成报表、提交代码修改 | 有真实制品和检查结果，后续动作符合授权   | 沙箱、依赖、制品存储、真实测试         |
| 多人/多 Agent 接力 | 研究、分析、复核分工             | 结果合并，责任与未决项明确               | 子任务、上下文隔离、共享预算与取消传播 |

监控通常用事件或周期触发短运行，保存上次基线，不让模型循环永久空转。批量逐项记账，不因一个失败重做全部。

### 7.3 用同一工作逐步验证价值

沿现有知识助手，可以验证项目支持员工的四步演进；客群和需求仍待验证：

1. **问答**：回答项目是否支持某种部署方式，引用明确版本资料。
2. **交付**：准备客户答复，提供草稿、依据和待确认项，负责人接受或退回。
3. **流程**：工单进入后整理资料，缺信息则等待，越权则升级；获准后回写草稿或记录。
4. **维护**：资料更新后，提示哪些已采用答复可能过时，请负责人复核。

这比同时增加十种岗位更容易判断平台价值：同一工作逐步减少准备、重复交代、搬运和维护。第 1 步仍可用对话完成，后续才引入 Task、等待与触发。CI 可作执行架构验证，但主打市场仍由需求决定。

## 8. Agent loop、插件与 harness 的边界

### 8.1 单 loop 的适用范围

本文将 harness 理解为让模型在真实环境受控完成工作的运行支架，包含上下文、状态、工具执行、预算、恢复、人类协作和交付检查，范围大于模型/工具循环。

Agent 可以理解“先审批再写入”，业务系统还要保证审批者身份、参数版本、有效期、重启继续和重复事件不重复写入。更多 prompt 或插件不会自动产生这些保证。

| 场景                      | 通用 loop 的适配度               | 当前需要的增量                      |
| ------------------------- | -------------------------------- | ----------------------------------- |
| 短问答、只读探索          | 高                               | 真正的知识/工具接入与结果检查       |
| 有边界的开放研究          | 高                               | 来源快照、预算、上下文与阶段交付    |
| 必须按顺序完成的流程      | 适合做步骤，整体不宜只靠模型控制 | 状态转移、强制门禁、恢复与幂等      |
| 等人/外部系统数小时或数天 | 当前不足                         | 持久等待与恢复，释放执行资源        |
| 文件/代码生成并验证       | 循环可复用，环境不足             | 隔离工作区、执行权限、制品与测试    |
| 长时间持续推进            | 只加轮数不够                     | 分阶段、进度依据、交接与完成检查    |
| 多 Agent/批量             | 可组合，不代表自动受控           | 子任务/逐项身份、全局预算与失败处理 |

当前不足是平台尚未实现，不等于 LangChain/LangGraph 没有能力。没有证据表明 Python 或 LangChain 是当前价值不足的原因。

### 8.2 一个平台内核，少量执行策略

**统一责任**：归属、提交与准入、授权与凭证、预算与取消、运行/步骤记录、成果、等待与恢复入口、审计及观察。

**允许变化**：下一步由模型还是流程决定，是否需要文件执行环境，是否分工，以及如何检查特定成果。

近期继续使用现有 `create_agent`。第一个必须等待和恢复的用例出现后，增加“持久流程 + Agent 步骤”，可共用 LangGraph/SDK 与平台授权，不必立即接两套框架。文件和代码任务再增加 sandbox 执行配置，可服务同一 Agent。

不按岗位各写一个专用 loop。相同机制共享，专业检查用受信组件复用。现有 CI 的重复模型往返可以迁入通用循环，固定仓库、来源一致性、引用和覆盖检查必须保留。这与[现有 Skill/MCP 方案](../proposals/skills-and-mcp/README.md)一致，不是要求撤销统一循环方向。

### 8.3 插件与内核的分工

| 能力       | 可扩展部分               | 平台保证                             |
| ---------- | ------------------------ | ------------------------------------ |
| Skill/SOP  | 方法、示例和模板         | 获准范围、版本依据与激活记录         |
| 连接器/MCP | 具体系统和协议适配       | 凭证、许可、资源范围、撤权与审计     |
| 校验器     | 报告结构、引用和领域规则 | 必须检查的成果无法绕过检查           |
| 工作流     | 流程定义和领域步骤       | 可靠状态、等待、恢复及副作用语义     |
| 执行环境   | 沙箱/远端 runner 适配    | 租约、隔离、能力声明、凭证与制品归属 |

平台保证不意味着全写在一个核心文件；可以调用可信插件，但不能让模型决定是否执行这些控制。

多框架托管等到必须复用客户已有 Agent，或特定 SDK 经真实用例证明明显更合适时再做。适配协议应覆盖输入、状态、事件、权限、预算、制品和取消，而不只是返回字符串。

## 9. 最需要补齐的工程语义

### 9.1 三种成功分开记录

1. **技术成功**：调用正常结束，结果持久化。
2. **交付合格**：信息、依据、结构与检查达到约定。
3. **业务采用**：负责人接受，或外部系统中的目标得到确认。

普通 Run 主要覆盖第一层，CI 有部分第二层。模型自述完成不能代替验收。低风险标准任务可以用明确机器条件确认，不要求每件事都人工点击。

### 9.2 Task、Run 与对话的归属

真实业务任务出现后，再将 Run 从必需聊天消息的约束中解耦。已有对话继续可用，轻量问答不强制复杂 Task；任务可关联交流，并在多次尝试间保留稳定目标与成果历史。

任务的待补资料/待验收/已接受，与运行的排队/执行/等待/失败/取消是不同状态，不能塞进一个 status。实施时再按用例更新详细数据与接口设计，本次不先新增完整表群。

### 9.3 后台身份与持续授权

当前 session 失效停止运行符合交互约定；后台任务则需明确谁拥有自动化、能用哪些连接、访问什么范围、何时到期、谁可撤销、异常找谁。

点击创建定时器不自动授权长期使用所有连接。建议自动化委托与单次登录分开，执行仍复核当前权限。定时/Webhook 进入相同受控准入，不伪造聊天消息绕过检查。

### 9.4 持久记录不等于断点恢复

聊天历史恢复交流，Run/Step 观察尝试，checkpoint 保存图状态与执行位置，长期记忆保存经过选择的跨任务事实。它们不可互相冒充。

LangGraph 支持持久 checkpointer，内存保存器不能跨重启。`interrupt` 可保存并等待外部输入，但恢复会重跑发生中断的节点，副作用需幂等或独立成步骤；平台仍需审批身份、具体参数绑定和过期处理。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。

先在当前规模验证一个持久流程，不立即引入 Temporal 集群。跨部署长等待、复杂补偿、规模化 worker 运维需求成立后，再比较成本。若叠加编排器，要明确谁拥有步骤状态和重试，避免两套系统各自推进相同工作。

### 9.5 外部副作用与结果未知

创建工单成功但网络响应丢失时，重试可能创建第二个。Run 落库和框架重试都不自动解决此问题。

需要业务幂等键、写入意图、返回标识、查询核对，以及结果未知时的处理。没有幂等与核对接口时，不盲目自动重试。Temporal 官方也说明在途 Activity 可能重跑，真实退款仍需接收系统的幂等检查；持久编排不提高模型判断质量。[Agent memory and state](https://docs.temporal.io/ai/featured/memory-state-stripe)。

审批绑定具体动作、参数、目标和版本；批准后修改收件人或正文，旧批准不能继续生效。取消不能承诺撤回已发生的外部动作，应记录已执行与未执行部分。

### 9.6 长任务、沙箱与多 Agent

长任务需阶段成果、稳定工作区、进度依据和完成条件，不只增加轮数。Anthropic 的实践展示跨上下文交接与增量执行，后续研究也强调随模型变化评测并删减 harness。[长任务交接](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)、[Harness 演进](https://www.anthropic.com/research/harness-design-long-running-apps)。

沙箱解决执行环境隔离，不自动解决资料注入与获准网络外传；凭证尽量留在受信工具/代理层，不放进可自由读取的工作区。[Deep Agents Sandboxes](https://docs.langchain.com/oss/python/deepagents/sandboxes)。

多 Agent 适合独立并行研究、不同权限/上下文分工与专门复核；同质角色互相聊天容易增加协调与费用。与单 Agent 比较成功率、人工修正、时延及成本，再决定保留；模型互评不替代来源核对或真实测试。

## 10. 宏观规划与推进顺序

### 10.1 学习路线与产品化判断分开

当前知识助手与可比较实验可以验证资料、权限、版本、引用和效果，也是后续工作的基础。不因讨论任务平台，就先建设调度中心和多 harness。

产品化可把已有“项目交付/支持答疑”作为首个假设，但仍需真实工作与使用者证据。候选场景按频率、输入可得、结果可检查、接入成本和分发渠道选择，技术现成不是唯一依据。

### 10.2 按证据分期

| 阶段              | 交付增量                                                   | 完成依据                                                       | 暂缓内容                           |
| ----------------- | ---------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------- |
| A：现有能力值得用 | 全文知识助手、来源问答、反馈；明确收藏使用/配置入口        | 从资料到答案采用可走通，失败可归因；完成现有学习迭代与效果对比 | 独立队列集群、完整画布             |
| B：一项工作可交办 | 一种交付任务；最小 Task、成果、接受/退回与跟进             | 非作者能找到目标、结果、依据和未决项；与当前最好做法比较总投入 | 全行业员工目录、通用项目管理       |
| C：工作能后台推进 | 该任务的定时或事件触发、持续授权、持久等待/恢复与幂等      | 重启、重复触发、撤权和响应丢失不产生错误业务状态               | 同时引入所有触发和框架             |
| D：证明可迁移     | 第二个真实场景、标准 Skill/第二个 MCP，按需 sandbox        | 主要复用机制，改变方法和连接即可承担相近工作                   | 每位员工复制专用流程               |
| E：扩大采用       | 业务角色与隔离、并发、团队运营，选择性多 Agent/外部 runner | 使用量、质量与运维约束证明收益                                 | 未验证的市场、复杂计费与全框架兼容 |

Skill/MCP 技术实验可穿插 A/B，不成为知识助手前置；C 也不提前拖住 A。按里程碑与证据推进，不在不了解人力、用户渠道和任务质量时承诺日期。

### 10.3 衡量价值与形成差异

先观察每周被接受或实际采用的任务数，按复杂度、人工参与和质量分组；记录接入、准备、交办、复核、纠错、维护耗时与模型/工具费用。

基线包含当前最好做法和“通用 Agent + 相同资料/Skill/工具”，避免把模型收益全部算给平台。释放时间不直接等于现金成本下降，未知费用保持未知。完整试点口径沿用[定位与收益验证](../proposals/product-validation.md)，不建立第二套 ROI 账本。

可验证方向包括特定工作的证据结构、已确认结果复用、资料变化后的维护，以及嵌入现有入口的体验。它们需要对照验证，不能预先称为护城河。

## 11. 验收建议与本次未完成项

下表是后续实施验收，不代表本次已执行这些测试。

| 场景               | 必须看到的结果                                           |
| ------------------ | -------------------------------------------------------- |
| 收藏与权限         | 使用者快速交办，维护者显式编辑，无权限者不误入不可用流程 |
| 来源与成果         | 资料缺失、来源不支持、结构不合格和结果被接受分别可见     |
| 运行/等待中重启    | 恢复位置明确，不假称成功，不盲目重复已发生动作           |
| 重复事件与重发     | 相同业务事件不重复建同一工作，新周期可产生新任务         |
| 批准后参数变化     | 旧批准不作用于新内容/目标，撤权持续生效                  |
| 外部成功但响应丢失 | 核对原动作或明确未知，不自动重复外发/创建                |
| 取消与迟到结果     | 终态一致，已发生外部动作如实记录                         |
| 部分失败与超预算   | 已完成项保留，失败可定位，子任务不绕过全局预算和取消     |
| 第二个场景         | 复用执行与治理机制，并有单 Agent 或人工基线比较          |

未决问题包括真实主要用户、首个任务的频率和验收责任人、资料/连接成本、持续授权范围、文件/浏览器需求、租户部署、愿付价格及分发渠道。它们影响后续优先级，不阻碍先完成现有知识助手与最小效果实验。

本次事实依据为静态审计和官方资料，没有新增模型效果、竞品使用效果或企业收益的验证结论。实施建议需在具体用例落地前进入相应方案和契约。
