# 后端架构

当前后端是 Python 模块化单体。HTTP 接入、业务操作、后台运行和 Agent 内部循环在同一应用进程协作，使用 SQLite 与同步 SQLAlchemy Session。本文描述已实施结构，改造证据见[实施记录](../records/platform-refactor-implementation.md)。

## 业务架构

理解后端先看「谁决定什么」，再看文件在哪。员工配置决定岗位使用哪些资源；技能、模型连接及工具模块各自维护资源；对话模块把一次用户输入组织成可处理工作，并决定最终如何交付。排队和动作记账交给执行宿主，模型往返交给 Agent 适配层。

| 业务或公共职责                                       | 拥有的事实                                       | 协作方式与原因                                                         |
| ---------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------- |
| auth                                                 | 登录用户、会话和权限策略                         | 先提供可信身份，业务模块再检查创建者、资源归属和当前业务条件。         |
| agents                                               | 员工资料、技能关系、工具许可、使用者账号选择     | 资源本体在其他模块，员工只保存选择关系，避免每个岗位复制技能和密钥。   |
| skills、model_connections、tools、organization_rules | 工作方法、共享模型连接、工具服务与账号、全员规范 | 各自维护内容和生命周期；准备流程通过受信入口组合已获准运行的资源。     |
| capability_catalog                                   | 跨技能和工具服务的检索结果                       | 负责可见范围及统一分页，原对象的修改和执行规则留在资源模块。           |
| conversations                                        | 对话、消息、运行关联和输入/交付规则              | 同一业务流程负责接受、准备、授权组合与发布，保证输入和成果有完整归属。 |
| execution                                            | Run、实际动作、预算和调度状态                    | 工作被接受后继续履行处理责任，独立于 HTTP 连接和具体模型 SDK。         |
| agent_runtime、llm                                   | 模型/工具循环、SDK 适配和模型客户端构造          | 运行层使用普通输入和受限控制接口；模型工厂只消费连接参数。             |
| files、sandboxes、infrastructure                     | 文件字节、临时环境责任、数据库与加密机制         | 提供公共资源能力，具体附件可见性和业务错误由业务所有者决定。           |

知识模块 `knowledge` 当前提供本人库、原件暂存、手动后台处理、词法及硅基流动向量检索业务。处理批次持久化在 SQLite，由 lifespan 管理的单文件扫描器领取，逐文件复核并原子发布正文/Chunk/FTS；关闭时等待在途文件结束，异常重启将未完成的执行标为中断。向量保存于现有 SQLite，另保留独立 Chroma/问答实验；个人员工装配、跨库召回及Run证据由knowledge模块拥有，通过bootstrap向会话准备/授权和运行资源注入接口，不在员工表保存私人库列表。业务模块、应用查询、运行机制和基础设施都是模块，但不是同一种领域对象。

## 工程架构：入口、业务、执行与资源

一次短操作沿「HTTP 路由 → 所属业务服务 → 数据库」完成。一次长处理先由对话服务接受并持久化，再由宿主领取，通过准备回调生成执行输入，调用 Agent，最后经发布回调提交结果。共同装配点是 `bootstrap.py`：它创建具体服务并把协作能力交给需要它们的模块。

依赖既包括直接导入，也包括运行时注入和同库读取，不能把「没有导入某个服务」等同完全独立。

| 关系                                    | 当前做法                               | 设计效果与代价                                                 |
| --------------------------------------- | -------------------------------------- | -------------------------------------------------------------- |
| API → 业务入口                          | 路由解析请求并调用服务或查询           | 相同业务规则可在非 HTTP 受信入口复用；业务不能只依赖路由授权。 |
| conversations → 资源与执行契约          | 组合快照、接受和最终发布               | 跨模块流程有明确业务归属；它需要了解相关资源的有效性。         |
| execution → 注入的准备/授权/发布能力    | 不直接导入对话模型和 API               | 宿主专注可靠处理；具体业务回调由启动装配负责接对。             |
| agent_runtime → 控制协议、资源接口、llm | 不取得业务数据库、身份服务或 HTTP 请求 | SDK 变化局限在适配层；平台必须显式提供所需操作。               |
| 业务模块 → infrastructure               | 共用事务、字段和加密机制               | 同一事务能维护引用一致性；当前仍与 SQLite 的隔离和锁行为有关。 |
| 资源服务 → 相关表的引用查询             | 同库检查员工或运行是否仍引用资源       | 删除保护可在同一事务完成；存在数据耦合，拆服务时必须重新设计。 |

这里没有要求每个模块都具备 controller/service/repository 三层。简单操作由服务直接使用 ORM；只有形成独立读取、状态存取或适配职责时，才拆出查询、存储或协议文件。

## 工程目录与应用包

应用入口为 [main.py](../../backend/app/main.py)，由 [bootstrap.py](../../backend/app/bootstrap.py) 创建具体依赖和生命周期。迁移、测试、实验保留在 backend 工程根。包导入不启动模型、数据库或后台任务。

```text
backend/                                # Python 工程；依赖、迁移和应用共同维护
├── app/                                # 正式应用；绝对导入统一以 app 开头
│   ├── main.py                         # 导出 ASGI 应用；不承担路由逻辑
│   ├── bootstrap.py                    # 装配并关闭服务；把共享流程注入执行宿主
│   ├── config.py                       # 汇总并校验环境与路径；不散读配置
│   ├── api/                            # HTTP 适配、安全、错误和静态交付
│   │   ├── routes/                     # 按资源组织路由，不拥有业务写事务
│   │   ├── dependencies.py             # 解析 Actor，取得已装配的服务
│   │   └── conversation_streaming.py   # 观察已提交快照，管理 SSE 连接
│   ├── conversations/                  # 内容、命令事务、查询及共享回复流程
│   │   ├── service.py                  # 创建、接受、重试和停止
│   │   ├── queries.py                  # 页面快照、历史、目录及回复读取
│   │   ├── preparation.py              # 固定依据并准备执行输入
│   │   ├── authorization.py            # 当前许可与装配组合复核
│   │   └── publication.py              # 正文、输出文件关联和终态共同提交
│   ├── knowledge/                      # 本人资料库、后台处理、三种检索与个人员工知识，另保留独立实验
│   ├── capability_catalog/             # 应用查询：组合技能与 MCP 服务的检索结果
│   │   ├── queries.py                  # 按查看权限检索两类条目，统一排序、计数和分页
│   │   └── schemas.py                  # 检索结果的概要字段，不代替源业务模型
│   ├── execution/                      # 队列、容量、预算、动作、取消和恢复
│   │   ├── scheduler.py                # 单宿主扫描和并发看护；拥有进程锁
│   │   ├── coordinator.py              # 负责一次 Run；调用准备及发布回调
│   │   ├── control.py                  # 受限运行协作与普通内容缓冲
│   │   └── store.py                    # 状态转移和持久记录；不调用业务发布器
│   ├── agent_runtime/                  # Agent 内部模型/工具循环及 SDK 适配
│   ├── agents/                         # 员工配置、装配、修订和就绪规则
│   ├── skills/                         # 共享方法、参数规范和引用保护
│   ├── tools/                          # 原生目录、MCP 连接、秘密与外部调用
│   ├── files/                          # 不可变文件字节、配额与孤立对象清理
│   ├── sandboxes/                      # 环境申请、远端身份、停止与回收
│   ├── model_connections/              # 模型连接、秘密及当前修订验证
│   ├── organization_rules/             # 单份全员工作规则及版本
│   ├── auth/                           # 身份、登录会话及访问策略
│   ├── llm/                            # 显式配置下的模型连接与协议处理
│   └── infrastructure/                 # 数据库连接、事务、字段和共用凭据加密机制
├── migrations/                         # 正式数据升级；不在启动时隐式运行
├── tests/                              # 隔离离线、竞争、迁移与进程恢复验证
└── experiments/                        # 隔离验证程序；不进入正式业务链路
```

HTTP 的完整结构和边界见 [API 模块](../../backend/app/api/README.md)；其他模块从 [后端入口](../../backend/README.md#模块架构与阅读入口)进入。上一轮逐文件设计保留在[历史目标树](../proposals/platform-refactor/target-tree.md)。

## 当前架构

HTTP 请求调用所属业务入口，服务通过有类型的 API 依赖取得。ConversationService 在对话模块组织内容与运行登记；员工、技能、规则、模型与工具的用户操作显式接收 Actor，自行检查操作权限；资源归属、修订和写入在业务事务内完成。受信内部读取使用当前 Session，不能额外要求配置管理权限。配置和跨模块引用检查回调由 bootstrap 装配。公开详情直接生成白名单读取模型。

运行准备、组合授权和最终发布归 conversations，由 bootstrap 注入执行宿主。没有全局 use_cases/application。跨模块操作的归属由它完成的业务目的决定，不因调用两个模块就再建一层。

当前目录包含业务模块、应用查询和技术实现三类职责。skills 拥有工作方法及版本，tools 拥有工具服务、账号和工具清单，agents 拥有员工装配及工具许可。capability_catalog 负责组合跨模块检索结果；共用名称、说明等检索字段不表示两类对象具有统一的维护、授权或执行模型。它完整负责跨类型搜索、计数和分页，供不同入口复用；具体分工见[检索模块](../../backend/app/capability_catalog/README.md)。

数据库写入使用短事务。接受时同时保存用户输入、空助手记录、Run 与绑定；发布时同时保存正文、输出文件关联、Run 终态和占用释放。参与者传递同一 Session，模型、工具和凭证解密在写事务外。

skills/definitions 统一解释新旧技能内容，agents/execution_config 组合装配与本次执行依据。agents/tool_account_bindings 只为员工已有许可选择当前用户自己的账号；账号与秘密仍归 tools。tools 的连接维护、工具清单和真实调用分别由 ToolConnectionService、ToolCatalogService、ToolInvocationService 负责；服务定义由 McpDefinitionService 维护。共用加密机制归 infrastructure/credentials，各业务转换自己的凭据失败。

业务规则、HTTP 接入和受控运行分开维护，当前仍同进程、同库。产品管理接口不会自动成为模型工具；模型当前使用的是已授予的工作区、MCP操作及个人知识检索/补读工具。用户业务 CLI、机器身份和独立 worker 尚未接入。

应用生命周期分层登记清理：启动尝试前登记异步停止，创建数据库和 MCP 服务后登记最终释放；部分启动失败也进入清理。知识与对话生产任务先停止，随后停止文件/沙箱维护，再关闭 MCP 与数据库。单个关闭异常不跳过后续资源，知识 worker 任务异常也释放进程锁；对应故障场景由[启动测试](../../backend/tests/test_bootstrap.py)覆盖。

## 运行调度与过程展示

调度器领取 queued 记录，协调器调用已准备的异步函数。Agent 在 agent_runtime 中运行，通过 RuntimeControl 请求动作、报告普通内容和通知存档位置，不取得执行 Store、数据库或身份服务。

模型动作开始前，当前授权、预算扣减与动作记录在同一事务中完成。保存失败就不发出调用。Agent 返回的是候选，PublishRun 复核许可后才交付。SDK 流结束、工具完成或出现一段文字均不代表业务成功。

前端通过回复快照观察已提交数据。停止是显式命令，浏览器断线不取消。当前只支持单主机单宿主进程锁；支持的普通运行按可信 checkpoint 恢复；已退役试验保留只读历史，不能重试。详见[运行契约](../reference/runtime.md)和[Agent 边界](agent-runtime.md)。
