## 行为与视觉契约

工程实现保持日夜配色、文字角色、间距、头像与品牌、页面构图和操作位置的一致性。视觉细则以[组件规范](../../frontend/src/design-system/components.md)和[颜色规范](../../frontend/src/design-system/colors.md)为准。

可交互滚动区和裁切区按[焦点与裁切边界](../../frontend/src/design-system/components.md#焦点与裁切边界)选择 `focus-gutter` 或 `focus-inset`，验收边缘控件的键盘焦点和输入外圈。不能用全局取消 overflow 或隐藏 focus 解决裁切；文本省略、滚动与动画继续由各自容器负责。

路由、权限、身份隔离、导航保护、草稿恢复与会话行为遵循对应业务契约；接口与后端授权由业务设计维护。资源分页、按需读取和查询失效遵循[前端读取模型](../reference/runtime.md#前端与读取模型)。

自动请求服务器的关键词输入通过共享 SearchInput 显式启用防抖，本地筛选与手动提交字段保持即时编辑；输入法、清空、回车及生命周期规则见[输入、选择与反馈](../../frontend/src/design-system/components.md#输入选择与反馈)。

## 工程选型

| 方向       | 统一方案                                       | 约束                                                   |
| ---------- | ---------------------------------------------- | ------------------------------------------------------ |
| 页面与构建 | React、TypeScript、Vite、React Router          | 全部路由页面采用同一构建方式；布局和访问边界由路由装配 |
| 基础交互   | Base UI，依赖包 `@base-ui/react`               | 基础控件通过 `components/ui/` 使用，统一交互基础       |
| 静态样式   | Tailwind CSS v4、官方 `@tailwindcss/vite` 插件 | 组件和页面通过工具类及语义令牌表达样式                 |
| 日夜主题   | CSS 语义令牌、统一主题控制器、`useTheme`       | 三种偏好、两种实际主题；令牌数值只有一个来源           |
| 共享状态   | React Context、`useSyncExternalStore`          | 按状态来源与作用域选择机制，不为目录引入额外状态库     |
| 目录组织   | 按职责和业务能力划分                           | 私有实现就近存放，公共能力按实际复用提取               |

Base UI 提供无预设视觉的交互基础，项目适配层负责外观与组合。组件按需导入，焦点、键盘、浮层和指示器等行为复用库能力。[Base UI 官方说明](https://base-ui.com/react/overview/quick-start)

Vite 使用 Tailwind 官方插件作为样式构建入口，依赖版本与项目运行环境兼容并提交锁文件。[Tailwind Vite 接入](https://tailwindcss.com/docs/installation/using-vite)

## 目录与职责

独立的 `docs-site/` 使用 Fumadocs 官方 Next.js 模板，复用平台品牌与设计令牌，并独立管理构建依赖。上述 Vite、页面目录和状态工程约定适用于 `frontend/` 平台应用；文档站的内容来源、路由、主题适配与验证见[文档站说明](../../docs-site/README.md)。

目录树展示职责边界，到达单一功能模块后停止展开。只有需要解释多个独立职责时继续展开，具体组件、Hook 和内部文件随实际功能确定；不预建空目录或固定模块模板。

页面、路由和共享外壳位于 `src/` 同一级，不建立 `app/` 或 `workspace/` 分层。

### 页面与组件

前端构建脚本放在 `scripts/`，依赖由前端包清单声明，并纳入同一 ESLint 和格式检查入口；脚本职责与执行时机见 [scripts README](../../frontend/scripts/README.md)。临时验证产物写入系统临时目录，需保留的证据按[文档规范](../documentation.md)归档。

- `pages/` 同时容纳业务页、登录页、帮助页和展示页。是否使用工作台外壳、是否需要身份和权限，由路由装配决定。
- 同一业务的一级页与子页面归入同一模块。复杂子页面可继续分目录；文件夹不机械复制 URL 层级。创建与编辑共享业务实现时复用同一编辑能力。
- 只服务一个页面或页面模块的组件、Hook、转换函数和类型留在所属模块。登录表单归入 `pages/signin/`。
- `components/ui/` 提供不依赖业务模型、身份或路由流程的基础控件；其他组件按复用能力分组。`common/` 只放真正跨业务通用的展示与布局组件。
- 下拉选择通过完整 `SelectField` 配置入口使用，正式页面、共享业务组件与设计展示均不直接依赖底层 `Select`，不另写原生 select/option；图标、选项和已选文案的规则见[输入、选择与反馈](../../frontend/src/design-system/components.md#输入选择与反馈)。依赖边界与原生标签检查已纳入 ESLint。
- 设计展示页使用真实组件及独立演示数据。展示页可以消费模块明确导出的展示能力；正式业务和共享层不导入展示页、演示数据或原型。
- `design-system/` 管理视觉基础与规范，`pages/design-system/` 管理展示页面，`components/theme/` 管理切换控件，`state/theme/` 管理主题状态。

### 依赖方向

| 调用方           | 可依赖的职责                                         |
| ---------------- | ---------------------------------------------------- |
| 页面、路由和布局 | 共享组件、状态、通用 Hook、基础代码和设计令牌        |
| 共享业务组件     | 基础 UI、相关共享状态、通用 Hook、基础代码和设计令牌 |
| 基础 UI          | Base UI、无业务语义的 Hook 与工具、设计令牌          |
| `state/`         | React、相关基础代码和通用 Hook                       |
| `hooks/`         | React、React Router 等所需框架接口，以及基础代码     |
| `lib/`           | 同层基础模块及必要的非 React 依赖                    |

`lib/` 不反向依赖页面、组件、状态或 Hook。共享模型不从页面私有类型导出；展示模型与接口 DTO 分别归属展示模块和接口层。不同页面模块通过共享契约和能力协作，避免跨模块访问私有实现。

## 命名规范

| 对象               | 规则                                   | 示例                                         |
| ------------------ | -------------------------------------- | -------------------------------------------- |
| 分组目录           | 小写 kebab-case，使用职责或业务名称    | `design-system/`、`organization-rules/`      |
| 组件文件与组件名   | PascalCase，文件名与主要导出组件名一致 | `AgentCard.tsx`、`ThemeSwitcher.tsx`         |
| 路由页面入口       | PascalCase，使用 `Page` 后缀           | `AgentsPage.tsx`、`AgentEditorPage.tsx`      |
| 自定义 Hook 名称   | useCamelCase                           | `useTheme()`、`useDraft()`                   |
| 普通逻辑与数据文件 | camelCase                              | `agentPresentation.ts`、`themeController.ts` |
| 状态提供组件       | PascalCase，使用 `Provider` 后缀       | `IdentityProvider.tsx`                       |
| 测试               | 与被测文件同名并就近存放               | `Tabs.test.tsx`、`useTheme.test.ts`          |
| 文档               | 小写 kebab-case                        | `engineering.md`                             |

组件不强制建立同名文件夹。`index.ts` 仅在需要明确模块公共入口时使用，不为每个目录创建聚合导出。框架入口、工具配置、公共资源及第三方约定沿用其标准名称。生成文件的命名由生成器维护，修改生成规则后重新生成，不手工维护副本。

同一控件组合的附属组件可以在同一文件导出，文件名对应主要组件；普通辅助函数不按 React 组件命名。Hook 可以与相关逻辑合并在同一模块，所在文件不要求以 `use` 开头，也不要求与某个 Hook 同名。

## 规则执行与工具约束

能够通过静态分析稳定判断的规则，配置到 ESLint 或对应工具中执行，不只依赖手册、AGENTS 或人工提醒。手册维护规则意图和适用边界，工具配置维护可执行细节，AGENTS 提供必读导航，README 提供检查命令。

| 检查内容               | 执行方式                                                                    | 适用边界                                                                               |
| ---------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 文件名与文件夹名       | ESLint 的 `eslint-plugin-check-file` 命名规则                               | 按文件角色检查 PascalCase、camelCase、kebab-case；测试文件检查主体名称                 |
| 组件与 JSX 用名        | `react/jsx-pascal-case`、标识符命名规则及配置内同名值导出校验               | JSX 用名使用 PascalCase；组件文件有同名值导出，不推断任意函数是否为组件                |
| 普通标识符与 Hook 名称 | `@typescript-eslint/naming-convention`、文件命名规则及 React Hooks 规则配合 | 根据标识符角色检查，保留接口 DTO、第三方属性等外部契约名称                             |
| Hooks 使用与依赖       | `eslint-plugin-react-hooks`                                                 | 检查 Hook 调用位置和依赖数组，不用命名检查代替 Hooks 正确性检查                        |
| 基础库入口与模块依赖   | `eslint-plugin-boundaries` 的路径解析与依赖策略                             | 统一限制基础库直接导入、共享层反向依赖、跨模块私有依赖、业务引用展示数据及路由页面入口 |
| `lib/` 的 React 边界   | 按目录配置导入和语法限制                                                    | 不导入 React 状态或 UI 能力，不定义 JSX、Context、Provider 或 Hook                     |
| 样式入口与内联样式     | ESLint 导入限制及内置语法选择器                                             | 禁止专用 CSS 导入；只检查直接 `style` 对象中的常量属性，动态计算与库样式按职责使用     |
| 代码格式               | Prettier                                                                    | 缩进、引号、换行和文档格式由格式化工具统一                                             |
| 类型与接口契约         | TypeScript                                                                  | 检查类型、组件属性和接口调用，不用命名正则替代类型检查                                 |
| 令牌引用与主题完整性   | CSS 检查与令牌契约测试                                                      | 检查未定义引用、循环、日夜映射及唯一数值来源                                           |
| 职责、复用与业务语义   | 人工与 AI 按手册、模块文档评审                                              | 判断组件是否应共享、状态作用域是否合理、抽象是否必要及业务契约是否完整                 |

文件和目录命名通过插件配置，并非 ESLint 核心自带的完整能力。[文件与目录命名规则](https://github.com/dukeluo/eslint-plugin-check-file)

`react/jsx-pascal-case` 检查 JSX 用名，不完整识别组件定义。大写开头的组件 `.tsx` 文件由配置内的小型规则核对同名值导出，正确处理公开导出别名并排除类型导出；入口、测试与 Hook 文件分别处理。组件语义及主要导出是否合理仍需评审。[JSX 命名规则](https://github.com/jsx-eslint/eslint-plugin-react/blob/master/docs/rules/jsx-pascal-case.md)

### 工具配置要求

1. ESLint 规则集中在 `eslint.config.mjs`，采用与项目 ESLint、TypeScript 和 React 版本兼容的插件。优先使用维护中的标准规则；仅保留配置内的同名值导出校验，不另设本地插件目录或组件识别框架。配置回归测试就近放在 `eslint.config.test.ts`。
2. 按角色设置文件匹配和覆盖规则。组件、Hook、普通逻辑、页面入口与测试分别处理；`main.tsx`、`router.tsx`、声明文件及生成文件明确列出适用方式。不能只按 `.tsx` 后缀把所有文件和函数都判定为组件。
3. 命名和依赖边界等确定性规则作为错误处理。豁免限定到具体文件、规则或外部契约，并说明原因，不通过忽略整个业务模块规避问题。生成目录按明确来源排除，生成器本身接受检查。
4. 路径边界覆盖别名、相对路径、重新导出及动态导入。库和模块边界统一由依赖插件覆盖这些形式，路由只依赖解析后以 `Page.tsx` 结尾的页面入口；核心 `no-restricted-imports` 用于样式入口限制，并配合动态 CSS 的语法检查。[导入限制](https://eslint.org/docs/latest/rules/no-restricted-imports)
5. 每条规则通过正反例验证实际覆盖范围，包括入口文件、测试、组合组件、Hook 和生成文件，避免漏检和误报。安装插件不等于启用规则，规则启用不等于覆盖全部命名场景。
6. 本地和 CI 使用相同检查入口。完成任务时运行与改动范围匹配的 lint、类型、测试及构建检查，不能只依据 AI 自检或编辑器提示交付。

## state、hooks 与 lib

### 共享状态

`state/` 管理具有明确共享范围和生命周期的状态能力。跨一层组件传递数据本身不构成提升到共享状态的理由；页面局部状态仍由页面持有。

| 状态能力       | 共享范围                 | 生命周期要求                                                   |
| -------------- | ------------------------ | -------------------------------------------------------------- |
| 主题           | 整个应用                 | 浏览器偏好持久化，与登录身份无关                               |
| 身份与权限     | 需要会话信息的路由分支   | 会话失效、身份或权限变化时重新确认并隔离旧状态                 |
| 工作台共享数据 | 当前身份的工作台分支     | Context 传固定实例；按记录和查询订阅，身份改变销毁旧读取与缓存 |
| 编辑保护       | 当前已挂载的编辑器及导航 | 显式登记 dirty、saving 与 discard；离开时执行实际清理          |

Provider 建立作用域并管理初始化、更新和清理；Hook 提供读取与更新入口；Controller 或 Store 在需要时管理外部状态及订阅。三者可以按同一职责放在一个模块中，不要求每个模块同时具备三者。

Provider 在需要它的路由或布局层挂载，不统一包到应用根部。主题通过同一控制器和 `useSyncExternalStore` 管理，避免重复初始化和监听。Context 按职责拆分，减少无关状态更新引起的消费者渲染。

服务端记录以接口为事实来源。跨组件、跨页面的数据统一接入 WorkspaceDataProvider：Context 提供固定实例，普通 TypeScript 数据模块维护读取与写入，useSyncExternalStore 订阅需要的记录或查询。共同请求能力复用 Resource；数据模块拥有写操作、提交锁和同步规则，WorkspaceData 集中声明跨业务的更新关系。组件不复制共享结果，不在写入后额外广播全局版本；刷新保留已确认内容，摘要类型不能冒充完整详情。接入方法、生命周期与测试入口统一见[共享数据模块](../../frontend/src/state/README.md)。

编辑器通过 useEditingRegistration 登记真实 dirty、saving、同步忙状态和 discard 回调；Layout 处理离页确认和 beforeunload，不从 URL 猜测是否有草稿。身份改变卸载相关局部状态。

### Hook 归属

| 使用范围                 | 存放位置                  |
| ------------------------ | ------------------------- |
| 页面或业务模块私有       | 对应 `pages/<功能>/`      |
| 组件内部交互             | 对应 `components/<功能>/` |
| 共享状态的访问接口       | 对应 `state/<功能>/`      |
| 跨业务、没有特定业务语义 | 顶层 `hooks/`             |

Hook 优先就近存放；形成明确的跨业务通用能力后再进入 `hooks/`。小模块直接存放文件，职责或规模确有需要时再建立内部子目录，不强制每个模块建立 `hooks/`、`components/` 和 `utils/`。

筛选、分页和需要链接恢复的选项以 URL 为来源，不额外维护一份全局副本。表单字段、弹窗开关和当前对话流保持局部作用域。草稿使用当前标签页存储，按身份、资源和原数据快照隔离；模型凭证不进入草稿。

### 基础代码

`lib/` 包含接口访问、共享模型、注册数据及存储、导航、转换等普通工具，不放 Hook、Context、Provider 或 JSX 组件。HTTP 和浏览器存储允许有副作用，边界是独立于 React 组件生命周期。

通用 Hook 调用 `lib/` 中的普通方法。例如草稿 Hook 管理 React 状态与持久化时机，草稿读写和校验方法属于基础代码；URL Hook 组合路由接口，安全返回地址校验属于基础代码。仅服务一个页面的普通方法和类型仍留在页面模块。

## 基础组件与复用

基础交互统一由 Base UI 提供，业务页面使用本地 `components/ui/` 适配层。对话滚动使用 `@shadcn/react/message-scroller`，同样仅从该适配层导出；它负责滚动和前插位置保持，页面负责数据请求与分页。适配层维护项目视觉、尺寸、状态、可访问名称及必要组合；不复制库已提供的键盘导航、焦点管理、浮层定位或尺寸测量机制。

- Tabs 指示线使用 `Tabs.Indicator` 及其活动标签位置、尺寸变量。项目样式消费库输出的变量，不另写一套活动项测量与监听。[Tabs 官方接口](https://base-ui.com/react/components/tabs)
- 菜单、选择器、对话框、提示和表单使用对应标准能力；有标签、说明与校验需求的表单优先使用配套 Field、Form 组合。[表单组合](https://base-ui.com/react/handbook/forms)
- 组件组合遵循 Base UI 的 `render` 等公开接口，不为保留其他库的 API 建设通用兼容框架。[组件组合](https://base-ui.com/react/handbook/composition)
- 只有标准能力无法覆盖具体业务要求时增加实现，并记录缺口、职责与验证范围。品牌图形和业务展示不强行抽象为基础控件。
- 共享业务组件以展示数据和操作回调为主要接口，不绑定展示页数据或某个页面的内部结构。页面 CSS 不覆盖共享组件内部选择器。
- 同一业务能力保留统一的正式实现，展示、预览和配置场景通过受控接口复用；不因演示调用将所有页面私有组件提升为公共组件。

## 样式规范

页面和组件静态样式统一使用 Tailwind 工具类。可复用变体使用 `class-variance-authority`，类名合并使用 `clsx` 与 `tailwind-merge`；变体以有限、完整的类名表达，不拼接编译器无法识别的动态类名。

`globals.css` 作为样式入口，引入 Tailwind 和设计系统 CSS。CSS 中集中维护令牌、必要的基础规则、共享动画、富文本或第三方内容适配；不建立页面或组件专用的普通 CSS、CSS Modules、CSS-in-JS 样式体系。第三方内部样式、SVG 固有属性和素材颜色按其用途处理。

动态样式按以下顺序处理：

1. 优先使用组件库的属性、状态标记、位置与尺寸变量，通过 Tailwind 消费。
2. 有限状态使用明确的变体映射；间距、颜色和动效引用设计令牌。
3. 只有来自运行时且无法枚举的业务数值，才通过 CSS 自定义属性或库要求的 `style` 接口传递。动态值的注入不承载静态样式，且不重复实现库已有能力。

运行时值使用内联样式或 CSS 自定义属性符合 Tailwind 的使用方式；静态样式统一不等于禁止必要的动态值。[Tailwind 动态样式说明](https://tailwindcss.com/docs/styling-with-utility-classes#when-to-use-inline-styles)

## 日夜主题与设计令牌

### 令牌来源与映射

`design-system/theme.css` 是主题及设计令牌数值的权威来源，包含基础值、语义映射和 Tailwind 映射。`spec.ts` 只维护角色名称、用途、状态和展示规则，不重复维护颜色值。展示页读取实际应用的变量；程序确需读取视觉值时读取计算后的 CSS 变量。

令牌采用“基础值 → 语义用途 → 必要的组件映射”单向引用。具体色值只在基础层登记一次；语义按用途合并，不能仅因某一主题同色而合并另一主题用途不同的变量。组件映射只保留确需独立控制的差异，通过变量引用已有值，避免重复色值、循环和未定义引用。

语义变量使用 `--os-` 命名空间和明确的短名称；前景使用 `text`，背景后缀使用 `bg`，文字角色使用 `size`、`weight`、`leading`、`tracking`。完整变量名、角色用途及组件映射由[设计系统](../../frontend/src/design-system/README.md)和[颜色规范](../../frontend/src/design-system/colors.md)维护，本手册不维护第二份令牌表。

主题使用相同语义键表达不同配色。背景、表面、正文、次要文字、边框、焦点、主操作、品牌、危险、成功、遮罩和阴影按用途命名；字号、字重、间距、圆角、层级和动效纳入同一令牌体系。布局与文字尺度在两种主题下共用。

项目 `--os-*` 语义变量通过 Tailwind 的 `@theme inline` 映射为语义工具类，减少组件反复书写变量表达式。映射引用其他 CSS 变量时采用官方 `inline` 机制。[Tailwind 主题变量](https://tailwindcss.com/docs/theme#referencing-other-variables)

应用和基础控件直接消费语义变量或同名工具类，body 浮层继承根元素主题。同一用途维护一个语义接口。第三方配色优先使用官方主题变量映射，必要时通过公开的属性选择器补充；库的颜色名称仅用于接入，应用仍使用项目语义类。Markdown 接入见[颜色规范](../../frontend/src/design-system/colors.md#markdown-渲染器主题)。自定义字号类需在 `lib/utils.ts` 注册合并分组，避免与文字颜色相互覆盖。

Tailwind 映射直接引用设计系统的语义变量，变量名称与用途以[颜色规范](../../frontend/src/design-system/colors.md)为准：

```css
/* globals.css */
@import "tailwindcss";
@import "./design-system/theme.css";
```

```css
/* design-system/theme.css 中的 Tailwind 映射 */
@theme inline {
  --color-surface: var(--os-surface);
  --color-text: var(--os-text);
  --color-border: var(--os-border);
}

@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));
```

```tsx
<section className="rounded-lg border border-border bg-surface p-4 text-text">
  内容
</section>
```

根元素切换主题后，语义变量改变，组件沿用同一套类名。普通主题颜色不依赖组件内的主题条件分支，也不为每个组件维护一套 `dark:` 色值；确有主题专属结构或资源时，使用同一根属性驱动的主题变体。[Tailwind 主题选择器](https://tailwindcss.com/docs/dark-mode#using-a-data-attribute)

### 主题状态与切换

| 项目       | 约定                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------- |
| 用户偏好   | `light`、`dark`、`system`                                                                |
| 实际主题   | `light` 或 `dark`                                                                        |
| 默认行为   | 无偏好或偏好无效时跟随系统；系统检测不可用时回退日间                                     |
| 持久化     | 使用浏览器 `localStorage` 的 `niuma:theme`；与登录身份无关                               |
| 切换入口   | `useTheme()` 返回 `preference`、`resolved` 和 `setPreference`                            |
| 根元素契约 | `data-theme` 表示实际主题，`data-theme-preference` 表示偏好，`color-scheme` 同步原生控件 |

`state/theme/` 统一完成偏好解析、系统监听、持久化、跨标签同步和根元素更新。显式选择优先于系统；仅在系统模式下响应平台主题变化。存储不可用时本页仍可切换，监听与订阅在重复调用时保持幂等，历史缓存恢复后重新同步偏好。

首屏在页面绘制前应用主题，与运行期控制器共用解析逻辑和状态来源，不等待业务请求。主题令牌定义在根元素，登录、帮助及挂载到 body 的浮层都能继承。

`components/theme/` 负责切换控件，调用统一状态接口；菜单、焦点和关闭行为使用基础组件。普通业务组件通过语义令牌适配配色，只有主题入口或确需区分资源的组件读取实际主题。动效遵循减少动态效果设置，不默认给全站颜色添加过渡。

### 组件生成契约

访问异常使用[统一接入标准](../reference/failures.md)：中央保留事实和上下文，页面沿原状态拥有者恢复，`FailureState`/`FailureNotice`统一展示；正常空列表继续使用空态。

人工编写与生成组件遵循同一套约束：

1. 优先复用本地基础控件；引入组件模板时选择 Base UI 实现并接入项目令牌。
2. UI 颜色使用已登记的语义类，不直接写十六进制、RGB 或固定色板类；头像和品牌素材的固有颜色保留。
3. 新语义先登记用途，并完整提供日夜映射；已有语义能够覆盖时直接复用。
4. 组件的 hover、focus、selected、disabled、invalid、loading 和错误状态在适用时完整实现，状态含义同时通过文字或可访问属性表达。
5. 组件示例进入设计展示页，验证日夜、窄屏、长文本、键盘和浮层。展示页与正式页面消费同一实现及令牌。

## 开发者与 AI 工作约定

1. 开始前阅读前端 README、本手册及相关模块说明；涉及视觉、主题或基础控件时，同时阅读设计系统对应规范。
2. 先确认改动所属能力、状态作用域和公共接口，再决定文件位置。使用项目正式组件、语义令牌及框架接口，公共抽象以实际需求为依据。
3. 按用户授权的任务范围实施，不扩展至无关模块。
4. 并行工作先核对共享文件和公共契约的修改范围。共享能力的生产者维护详细契约，消费者依赖该契约，避免同时维护互不一致的令牌或组件实现。
5. 工程规则变化更新本手册；运行方式变化更新 README；视觉或令牌变化更新设计系统及真实组件示例；业务流程变化更新对应设计与索引。同一规则只维护一份详细定义。
6. 完成与改动范围匹配的检查，记录实际结果和未覆盖范围，不把文档结论或示例效果作为功能已完成的证明。
