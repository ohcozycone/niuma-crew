# 执行对象、事务与生命周期

> 本文保留阶段 A 的设计依据；后续命名、宿主与 Agent 运行协议及实施顺序以[平台重构总计划](../platform-refactor/README.md)为准。旧 Run/Conversation 术语不代表新增一层 Turn+Run。

设计状态：基础执行与聊天发布边界已采纳并实现；Task、Plan、Goal、等待和补充仍为草案。更新日期：2026-10-26。本文细化[后端重设计](README.md)，描述拟议执行与业务发布契约；当前行为仍以[运行契约](../../reference/runtime.md)和[对话契约](../../reference/conversations.md)为准。

## 1. 用一次问答解释对象

用户问“为什么这次构建失败”，产品保存一条用户 Message，随后接受一个 Run。这个 Run 可以先加载技能，再请求模型、调用多个取证工具、再次请求模型并校验报告，最后发布一条助手消息。

这里是一条输入消息、一次执行尝试、多次模型请求、多个实际动作与一份正式输出。失败后重试产生新 Run；原输入、旧动作和失败原因保留。正式任务使用同样的执行过程，结果发布为 Deliverable，无需创建 Conversation。

| 对象      | 负责的问题                               | 不应据此推断                     |
| --------- | ---------------------------------------- | -------------------------------- |
| Message   | 用户提交了什么、助手正式发布了什么       | 一条助手消息等于一次模型调用     |
| Run       | 这次尝试是否被接受、消耗多少、如何结束   | 技术成功等于业务验收通过         |
| RunAction | 哪个模型、工具或检查实际被尝试，结果如何 | 清单勾选等于动作已经执行         |
| RunResult | 这次尝试形成了什么稳定输出               | SDK 所有内部消息都应成为正式结果 |
| PlanStep  | 准备按什么方法推进                       | 与 RunAction 一一对应            |

一个模型响应可以包含多个工具请求。宿主为每个实际尝试创建独立工具动作，关联产生该请求的模型动作；工具请求的生成与工具的实际执行分别记录。没有执行的请求不能显示为成功工具调用。

## 2. 最小数据关系

基础结构已落入正式迁移 0004；以下说明所有权，Task 相关行为仍为后续方案。完整字段见现行模型。

| 对象及所有者                          | 最小内容                                                                                 | 关键约束                                                                       |
| ------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Conversation，conversations           | owner、agent、排序与上下文策略、当前活动尝试关联                                         | 主体归属在所有入口验证；初版同一对话至多一个活动 Run                           |
| Message，conversations                | conversation、角色、顺序、输入正文或输出引用、发布时间                                   | 对话内顺序唯一；助手消息引用稳定结果，正文不能同时有两份可编辑真相             |
| ConversationRun，conversations        | conversation、run、触发输入消息及采用的上下文引用                                        | run 唯一且有真实外键；重试可绑定同一输入消息，不重新制造用户消息               |
| Run，execution                        | agent、发起身份、工作归属类别、触发原因、模式、状态、幂等摘要、retry_of、时间与 revision | 幂等键在明确操作范围内唯一；retry_of 有真实外键且归属一致；终态不可回到运行中  |
| RunSpec，execution                    | 冻结输入与上下文、非秘密配置、能力内容依据、操作上限、输出契约及适配版本                 | 接受后不可改写；所有可回查制品有实际内容或不可变引用，不能只留可变配置 ID      |
| RunAction，execution                  | run、动作序号、种类、状态、调用关联、输入摘要、输出/错误、用量与时间                     | 动作序号与重放键唯一；未知执行结果与已确认失败分别表达；敏感字段不进入公开投影 |
| RunResult，execution                  | run、稳定输出键、内容类型、契约版本、正文或结构化内容、来源证据                          | `(run_id, output_key)` 唯一；发布后不可原地改正文；没有 checkpoint 仍可读取    |
| TaskSubmission / TaskRun，tasks，后续 | task、固定输入版本、run 关联                                                             | 任务输入可独立于对话；关联与冻结输入一起提交                                   |
| Deliverable / Review，tasks，后续     | 采用结果、成果版本、检查摘要、验收决定与人                                               | 验收绑定具体成果，不回写 Run 的技术成功状态                                    |

`RunSpec` 可以先与 Run 同表以受约束 JSON 存储，不要求为每个概念建表。Message 的输入内容和 RunSpec 的上下文可以通过不可变引用复用；若采用内容副本，必须明确它是只读执行依据，而非另一份可编辑消息。

### 工作归属不用无约束多态 ID

各业务模块拥有自己的 Run 关联表，以真实外键连接主体与 Run。Run 的归属类别用于选择受信的结果发布适配器，不直接作为访问授权，也不开放客户端任意指定。

一个 Run 只有一个负责正式发布的业务归属：对话、任务或后续评测入口。其他页面可以在授权范围内引用同一结果，但不因此获得第二个发布所有权。来源对话、采用的任务成果也只是输入证据。跨关联表的互斥不能假称由单表 UNIQUE 自动保证；受信应用入口在同一事务中验证类别、唯一绑定、员工与 owner 一致性，拒绝直接散落写表，并以跨来源竞争测试约束。若后来需要数据库级统一外键，再为真实需求引入公共工作主体。

## 3. 提交、执行和发布

### 接受消息：一个业务短事务

1. HTTP 将身份与已校验请求交给 `SendMessage` 应用用例；后台入口也必须调用相同授权后的用例，不能绕开业务规则。
2. 开启业务事务，取得必要的写入串行保护；校验主体归属，按操作范围查幂等键。相同键和相同请求返回原尝试；同键不同内容返回冲突。
3. conversations 校验对话和消息输入、选择可访问上下文；execution 检查容量、当前权限、员工、能力和模型连接，生成 RunSpec。
4. 同一事务写入用户 Message、Run、RunSpec 与 ConversationRun，并占用主体活动位置。新对话也在该事务创建。
5. 提交后返回已接受身份。驱动从已持久化队列领取工作；进程内唤醒只是加速机制，丢失唤醒不能丢失已接受工作。

幂等重放不重新捕获最新配置、不重复计入容量，也不重新发出模型请求。失败重试是一个新的显式操作，使用新的请求键。

客户端请求键建议按 `(actor_user_id, operation, client_request_id)` 唯一；请求摘要包含规范化的主体或新建意图、输入、方法选择和模式，不包含服务端重新读取的可变配置。这样相同请求不会因为配置已更新而变成摘要冲突，另一主体的请求也不能冒充同键重放。内部触发使用受信的独立操作名与幂等键。

初版不支持执行中追加输入时，对话已忙就明确拒绝本次提交，不能先保存一条没有处理归属的消息，再让用户误以为已采用。

### 执行：事务外进行有界动作

1. driver 使用条件更新领取 queued Run，原子记录运行身份与开始状态；一个 Run 不得被两个本机执行句柄同时驱动。
2. coordinator 读取冻结依据，复核当前身份、授权和配置撤销条件，准备受控能力与 SDK 适配器。
3. 每次外部动作前检查取消、许可和预算，持久记录动作尝试及必要预留；事务提交后再调用模型或工具。
4. SDK 事件映射成动作结果与可公开进度，短事务更新持久事实。循环可以多次请求模型，直到形成候选输出或遇到停止条件。
5. 受信校验器检查结构与来源，返回候选 RunResult，交给结果发布用例。SDK、模型和专业校验器都不能直接把 Run 标为成功。

`RunSpec` 冻结“采用的依据”；实时 guard 决定“现在还准不准执行”。停用员工、撤销工具范围、会话失效或模型连接修订不应因为存在快照就失效。普通内容编辑不静默替换已接受的方法正文。

### 正式发布：一个业务短事务

1. `PublishRun` 用例开启事务，检查 Run 仍可完成、当前授权与业务归属仍允许接收，以及取消是否已经被接受。
2. execution 保存不可变 RunResult，结果发布适配器在同一事务创建助手 Message 或 Deliverable，并更新主体活动位置和相关业务状态。
3. execution 将 Run 和未收束动作写入确定终态，保存用量与 revision，一并提交。
4. 查询和 SSE 读取提交后的安全投影。事务失败则全部回滚，不能广播已成功；协调器进入可重试发布或明确故障收束。

结果发布适配器由 bootstrap 组合，接收共享事务、Run 身份和有类型的候选结果；execution 不导入 Conversation/Task ORM。适配器不得内部 commit，也不得执行网络动作。输出键与 Run 的条件终态更新共同保证重复发布不重复创建消息或成果。

失败、取消和中断也通过应用用例同步清理主体活动位置并保存终态，不能只修改 Run 而让对话永久显示忙碌。

初版可只在成功收尾时发布一份正式回答。内容模型允许零到多份输出，后续确有分段交付需求再增加发布策略。运行中的文本作为持久进度展示；失败时不能把它伪装成已校验的正式成果。

## 4. 状态、取消、重试与恢复

### 生命周期的所有者

| 状态对象      | 状态与含义（后续项仍为建议）                                                                 | 推进者                         |
| ------------- | -------------------------------------------------------------------------------------------- | ------------------------------ |
| Run，首个增量 | queued → running → succeeded / failed / cancelled / interrupted；running 可先进入 cancelling | 受信提交、驱动、协调与发布用例 |
| RunAction     | running、succeeded、failed、cancelled、unknown；按具体动作保留错误与完成证据                 | 宿主动作适配和故障对账         |
| Task，后续    | 工作进行、待验收、需修订、已接受等业务阶段                                                   | 任务模块；不由模型直接任意更新 |
| Plan，后续    | 草拟、确认、被替代等版本状态                                                                 | 规划发布与显式确认用例         |
| Goal，后续    | active、paused、blocked、budget_limited、complete 等控制状态                                 | 持续控制器及有权限的用户操作   |

这些不是同一条状态链。一个 Task 可以在 Run 成功后仍待验收；一个 Goal 可以在一次 Run 成功后继续 active。动作成功也不表示整次 Run 已完成。

### 取消与完成竞争

取消请求必须持久化，并与发布使用同一业务状态检查。取消先被接受，则发布不能再写 succeeded；成功先提交，则随后取消返回已经结束。浏览器断连不改变 Run 状态。

宿主尽力取消正在进行的外部请求并阻止后续动作，但不能声称已撤回远端写入或供应商计费。已完成动作保留事实；对未能确认结果的动作记录 unknown，不能统一改写成“从未执行”。

### 三种“再来一次”

| 操作             | Run 身份              | 输入与配置                                                       | 预算与事实                                 |
| ---------------- | --------------------- | ---------------------------------------------------------------- | ------------------------------------------ |
| 同键重放提交     | 原 Run                | 原冻结依据                                                       | 不重复占用或调用                           |
| 失败后的显式重试 | 新 Run，链接 retry_of | 采用原业务输入版本，按当前授权重新捕获配置；界面明确使用当前配置 | 新尝试单独记账，原失败与动作不改写         |
| 故障后的执行恢复 | 原 Run                | 原 RunSpec 加已接受的有序补充                                    | 使用剩余额度，不能重置计数或抹去已发出动作 |

重试不承诺逐字重现旧模型输出。若以后需要固定旧配置的复现实验，应单独提供明确操作，而不是隐藏在“重试”按钮中。

### 恢复检查与故障窗口

checkpoint 是恢复优化与内部状态，不是业务结果库。按 Run 身份、适配版本和可核对的执行标记隔离；对话上下文可以复用已发布内容，不以 SDK 的某个最新 thread 状态直接决定产品历史。

为覆盖执行完成到正式发布之间的故障窗口，候选输出必须能通过持久标记与原 RunSpec、输出键和内容摘要对应。恢复时重新做必要校验；证据不足就明确中断，不能猜测某段 checkpoint 文本是最终回答。

| 故障位置                        | 处理原则                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------- |
| 接受事务未提交                  | 不存在已接受工作；同键可重新提交                                                      |
| 已接受但尚未领取                | 队列扫描可发现，不依赖原 HTTP 或内存通知                                              |
| checkpoint 已写、业务终态未提交 | 按 run 与输出标记对账、重建候选结果，再走幂等发布；不能把 checkpoint 最新内容直接公开 |
| 业务发布已提交、进程随后退出    | 已发布历史继续可读；重启不能重复发消息或再次运行成功尝试                              |
| SDK 状态不可读或版本不兼容      | 保留已发布历史；停止自动恢复，记录明确原因；由显式重试创建新尝试                      |
| 模型请求已发出但未确认结束      | 记录可能发生的调用与未知用量；只按明确恢复策略继续，不虚报零消耗                      |
| 工具请求可能已经在远端完成      | 有可靠幂等键或查询机制才自动重放；否则收束为需处理的中断，避免重复副作用              |

业务 SQLite 与 SDK checkpoint 若仍为两个存储，无法仅靠一次 Session commit 获得跨库原子性。需要持久标记、幂等发布和恢复对账，不承诺外部动作 exactly-once。

持久等待后续增加 `waiting` 与恢复命令；等待释放模型执行资源，但保留尝试身份、已用预算和有效期。等待机制必须由宿主与可恢复状态共同确认，模型说“等你回复”并不产生等待记录。

## 5. Plan 与 Goal 怎样组合

### 计划模式与计划内容

规划 Run 的预期结果是 Plan，而不是直接实施。模式同时约束提示与受控动作：只允许符合规划目的且已获准的探索操作，不能依赖“请不要写文件”一句提示作为权限边界。

Plan 发布后形成不可变版本；确认的是该版本、输入假设与采用范围。实施创建新 Run，引用确定的 Plan 版本，重新验证当前操作许可。确认计划不是凭证，也不自动授予写入、付款或扩大资源范围的能力。

PlanStep 与 RunAction 可以有可选关联，用于解释哪个动作服务哪个计划项；没有计划也能执行，一个计划项也可以需要多次模型与工具动作。不要给实际动作添加“未计划就不能存在”的强制约束。

### 持续目标作为外层控制

Goal 在一次 Run 收尾后判断是否需要继续：停止条件已满足则 complete，预算耗尽则 budget_limited，外部信息缺失则 blocked，满足继续条件才创建新的有界 Run。用户暂停与预算限制由不同原因驱动，不互相冒充。

Goal 引用已有工作范围；正式工作目标仍在 Task，交流上下文仍在 Conversation。它拥有的是持续控制状态、累计预算与继续策略，不再制造另一套“目标—成果—验收”业务对象。

自动续跑与目标更新需要同一串行控制或条件更新：暂停、撤权或预算变化先被接受后，不得依据旧读取继续创建 Run。每次续跑有幂等触发键，累计预算与动作预留也要原子检查，避免并发续跑各自拿到完整余额。

目标达成判断可以使用确定性检查、人工决定，或有明确证据输入的模型评价；必须说明依据与限制。模型自报完成不等于测试通过或用户验收。初版没有可靠完成标准时，不启用无限自动续跑。

### 执行中补充单独设计

若实现补充输入，将其保存为有顺序、可追踪的输入记录，在下一可控模型边界采用，并记录已消费位置。原始 RunSpec 不改写；恢复使用“初始依据 + 已接受补充”。

已经发出的工具调用参数不因新消息而改变。补充如果改变目标、许可或工作范围，需要明确的新提交，不能借由 steer 绕过授权。首个执行增量可以暂不支持，不能把该能力与基础消息存储捆绑成必做项。

## 6. 安全、预算与读取

### 身份和能力

发起者身份、当前执行许可与配置快照分别维护。首个增量继续要求有效登录身份；以后真正支持后台定时或持续目标时，再引入有 owner、范围、有效期和撤销机制的后台授权。不能通过永久引用旧登录会话实现自动执行。

Skill 内容与模型输出均不能选择任意结果发布器、替换执行身份或授予工具许可。tools 负责实际调用范围，knowledge 负责可检索资料范围，execution 统一做动作前控制，专业校验器只判断输出契约。

### 可核算的有界执行

RunSpec 限制时长、模型尝试数、工具次数及上下文规模。动作前持久预留并发与预算，恢复使用剩余额度。SDK 内部重试必须关闭或纳入尝试记录，避免一个“模型动作”暗中产生多次未计数请求。

供应商没有返回用量时标为未知，不填零；可在调用前估算并限制请求规模，但在没有可靠上游计量时不承诺货币费用精确硬封顶。Goal 的累计限制在单次 Run 上限之外再约束可用额度。

### 读取契约

历史从 Message、RunResult 和业务关联读取；过程从 Run 与 RunAction 的安全投影读取。SSE 初版继续采用持久快照与 revision，断线后读取最新快照，不依赖某个浏览器持有模型流。

不持久化每一个 token 作为业务消息，也不直接返回 SDK 原始状态。公开投影明确区分运行中内容、动作证据、正式结果与错误；凭据、隐藏推理和未经裁剪的工具返回不得因日志或 SSE 意外公开。

## 7. 验收场景

基础执行场景已由当前测试覆盖，实际结果见[第一阶段验收](../../records/execution-refactor.md)；表中“后续增量”尚未执行。

| 场景                         | 可观察的验收结果                                                    |
| ---------------------------- | ------------------------------------------------------------------- |
| 同键并发提交、同键不同内容   | 同内容只产生一条输入和一个 Run；不同内容冲突，容量不重复占用        |
| 新对话接受失败               | 对话、消息、Run 和关联一起回滚，没有空壳或孤立尝试                  |
| 一个输入多次失败重试         | 原输入保持，多个 Run 可追踪；当前配置变化明确体现在新快照           |
| 一个模型响应请求多个工具     | 每个实际工具动作有独立状态与调用关联，未执行请求不显示为成功        |
| 取消与结果提交竞争           | 取消先接受不再成功；成功先提交返回已结束，无重复消息                |
| 发布适配器写入失败           | RunResult、消息/成果、业务状态与 Run 终态全部回滚，不发布成功事件   |
| 重复回调、重启后重复发布     | 相同输出键只产生一次正式发布，原终态保持                            |
| checkpoint 文件丢失          | 已发布消息与成果仍可读；恢复明确失败，不替换为最新 SDK 内容         |
| 撤权、连接修订、预算耗尽     | 后续动作被拒绝，已发生事实保留；补充、恢复和目标续跑不能绕过        |
| SDK 内部重试、未知用量       | 实际请求尝试可核算，未知保持未知，恢复不获得全新预算                |
| 无对话的任务，后续增量       | 直接形成成果与待验收状态，没有伪造 Conversation 或 Message          |
| 计划转实施，后续增量         | 新 Run 绑定固定 Plan 版本，许可重新检查，计划项与实际动作可分别读取 |
| 目标暂停与续跑竞争，后续增量 | 暂停后不创建新尝试，触发幂等，累计预算不被并发重复使用              |

后端状态与约束测试之外，还需验证前端消息、过程、重试和成果投影。真实模型与 MCP 的网络行为单独验收；离线适配器只能证明宿主规则，不能证明上游可用。
