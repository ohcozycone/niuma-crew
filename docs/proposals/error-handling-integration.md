## 问题与目标

目前同一错误常在请求层保存status/code，却在Resource、身份和页面Hook中变成message字符串；页面各自决定提示和按钮，无法稳定区分详情404、刷新失败、配置不足与提交结果未知。目标是集中维护**错误事实、展示策略、视觉组件**，页面只提供操作上下文与真实恢复动作。统一不是把所有失败跳到同一个错误页。

## 统一接入结构

```text
HTTP / 浏览器连接 / 路由模块 / Run.error
              ↓ 保留来源、状态、code和可公开元数据
        lib/failures（纯数据与纯映射）
              ↓ resolveFailure(failure, context)
    FailureState（页面/区域）或FailureNotice（局部）
              ↓ 仅显示拥有者实际提供的动作
     原Resource刷新 / 原保存核对 / 原会话恢复
```

不增加全局错误Provider、全局错误路由或第二套请求缓存；不让展示组件导入页面Hook。结构化事实跨共享状态传递，UI才决定展示层级。业务模块新增错误时，优先复用现有分类；只有恢复方式或公开解释不同才新增中央精确规则。

### 事实与上下文契约

```ts
type Failure = {
  source: "http" | "network" | "client" | "run";
  status: number | null; // 客户端/Run不伪造HTTP状态；兼容旧ApiError.status=0
  code: string;
  message: string; // 公开API消息或已知客户端文案；未知异常不直接公开message
  requestId?: string;
  retryAt?: number; // 绝对截止时间，单位ms；来自有效Retry-After
  issues?: readonly { path: readonly (string | number)[]; message: string }[];
};
type FailureContext = {
  operation:
    "initial-read" | "refresh" | "mutation" | "subscription" | "render";
  resource?:
    | "agent"
    | "skill"
    | "knowledge"
    | "document"
    | "conversation"
    | "connection"
    | "page";
  hasUsableData?: boolean;
  outcome?: "rejected" | "unknown"; // mutation的拥有者判断，不能单凭status断言写入失败
};
```

实际回调按语义传入（retry、reconcile、configure、return），只呈现存在的动作。拥有者给出具体返回地址/配置入口及权限；resolve不读React状态，不生成可越权的链接。已有onReload仍可由适配层映射到retry。先保留ApiError三参数兼容和Resource.error读取兼容；failure是唯一分类事实，兼容message不能独立更新。字段层沿用FormField，不强制为本地必填提示构造整页Failure。需要进入统一catch的预期客户端校验使用小型`clientFailure(code,message)`构造函数；原本地字段字符串可继续在字段旁展示。未知Error不公开原message，也不靠message识别类型。

## 分类与展示标准

规则顺序：预期取消不提示 → 显式source/operation特殊协议 → 已知code精确规则 → 真实status兜底 → 安全未知失败。code优先不意味着忽略操作：保存员工时skill_not_found仍是装配反馈，读取技能详情时才是详情404。HTTP与Run始终分开。

| 上下文                           | 展示层级                             | 恢复原则                                                              |
| -------------------------------- | ------------------------------------ | --------------------------------------------------------------------- |
| 无可用数据的页面首读失败         | FailureState区域或页面               | 404回所属列表；连接/服务可手动重读；配置问题按权限配置                |
| 有data的后台刷新失败             | FailureNotice横幅并保留data          | 原读取refresh；标明旧数据，不清筛选，不卸载编辑器                     |
| 权限明确撤回/详情明确404         | 移除不可继续展示的数据，显示对应状态 | 不借“保留旧数据”继续展示已不可访问内容                                |
| 保存/上传/删除被明确拒绝         | 字段或操作附近FailureNotice          | 保留输入；422定位字段；409按实际冲突处理                              |
| 发送后连接断开/超时/无法确认提交 | 当前表单或消息的未知结果反馈         | 原幂等键/修订只读核对；没有核对能力就提供已有查看入口，不制造重试回调 |
| SSE断线/事件异常                 | 对话连接横幅                         | 复用原GET snapshot和订阅恢复；不POST新任务，不变更Provider key        |
| Run终态失败                      | 对应助手消息                         | 复用现有canRetry与显式重试；上游认证失败不触发本站退出                |
| 正常空列表/取消/已停止           | 现有EmptyState或正常状态             | 不进入错误页                                                          |

普通401只有明确本站会话过期（authentication_required，或auth/me身份确认的401）走既有身份生命周期；invalid_credentials留登录表单。invalid_origin、一般403、503、模型/工具凭据错误都不广播session-ended。权限变动沿用原身份域清理，不能让一个展示组件创建第二个认证流程。

当前无原因的SSE `access.revoked`同时涵盖认证失效和权限拒绝，不能直接视为会话过期。停止当前订阅，并用已有`auth:permissions-changed`触发auth/me重核；只有auth/me明确401才退出。保持事件现有空body协议，补有效会话撤权不被强制退出的回归。findRequest的404仍是“未接受→null”，不进入展示映射。

对身份读取失败，本轮保持安全的“身份未确认就不继续展示受保护内容”原则；沿用已存在的草稿存储和身份key，不新增长期信任过期权限的宽限期，也不显示没有依据的“草稿已保存”。非认证目录刷新失败则保留已成功数据。

## 文案、图片与交互

404继续使用已认可的“缺席拼图块”，保留独立方图、完整HTML错误码与可选文案/恢复组。桌面240px图＋48px间距＋最多384px文字；宿主不足728px采用192px方图上图下文。整组在宿主真正可用区域居中，上下对称留白；长内容自然滚动。正式几何令牌统一进入theme.css和C21规范，页面不复制原型CSS。

剩余五个图的内容先按下表评审，使用内置image_gen生成独立透明PNG；同一细线暖灰、浅灰面、少量柔橙、近方形主体、无字/无数字。每幅只表达一个明确情节，不能复用头像，也不能将代码画进图里；生成后在主站日夜和240/192px下检查结构、含义与重量。

| 家族       | 配图内容与趣味来源（本轮设计选择）         | 主要解释                           | 默认动作                             |
| ---------- | ------------------------------------------ | ---------------------------------- | ------------------------------------ |
| 内容缺失   | 已认可的中心缺块拼图，缺席块戴墨镜休息     | 找不到当前可访问内容               | 回资源列表；有可靠本站来源才提供返回 |
| 身份与权限 | 闭合挂锁戴着眼罩，钥匙等在旁边             | 入口暂时不能打开；不是服务器损坏   | 根据真实身份去登录、返回或切换账号   |
| 连接       | 插头与插座差一点接上，电线自己打结限制长度 | 连接未建立，问题可能在多段链路     | 重连/重读；不擅自断言用户断网        |
| 服务异常   | 小烤面包机弹出一片烤焦吐司                 | 处理出了意外，用小失误减轻挫败     | 安全的手动重读；无维护信号不称维护   |
| 等待与限流 | 蜗牛背着闹钟形的壳缓慢前进                 | 等待/暂缓，真实时长由协议决定      | 有等待头时等到允许时间再手动重试     |
| 配置与冲突 | 小玩具车装着一只方形轮胎                   | 零件或配置不匹配，等待不能自动修复 | 按权限检查配置或查看最新修订         |

上述是共享语义家族，不是HTTP状态一一配图。配置问题也可返回503；Run失败用局部小图标而非每条消息放大图。描述、补充信息、主/次动作、倒计时均可缺席，缺席时不留占位；错误编号只在存在真实HTTP或明确业务code时显示，不生成假500。

429/503的Retry-After支持非负秒数和有效HTTP日期，转换为绝对deadline；缺失/非法值不显示倒计时，不编造恢复ETA。重挂载不重新开始等待，后台标签时间继续经过，结束仅解锁手动动作。404的8秒自动返回属于可选用户控制，业务默认关闭；若启用可取消、隐藏标签暂停，不与服务端等待计时混用。

## 传输、静态与启动边界

1. **请求层**保留真实status、code、安全message、422定位、Retry-After和request ID。网络失败不归因用户网络；取消由调用者signal判断；确实由超时signal造成时才标timeout。成功204保持；成功响应无法解析JSON标invalid_response，不显示原始HTML/异常内容。没有契约证据不称“版本不兼容”。不新增通用写入重试。
2. **已知后端错误**继续现有detail对象/数组，不要求所有后端业务代码导入前端枚举。新增小型纯ASGI边界，只处理HTTP scope，其他scope透传；只捕获Exception，取消不转500。X-Request-ID接受ASCII `[A-Za-z0-9._-]{1,64}`，缺失/非法/超长值重新生成；只是诊断标识，不参与认证、幂等或Run身份。成功、已知错误、字段422、security拒绝及安全500都有此响应头。响应未开始时安全记录类型、帧和ID：API返回500 internal_error JSON，非API使用安全通用500文本，明确不把所有资源故障变成JSON。500显式带no-store/nosniff/ID。响应开始后（包括SSE、普通流和BackgroundTask）不发送第二响应，记录安全诊断，再传播不含原异常值/cause/context的安全异常，以免Uvicorn记录原始SQL或上游秘密；不宣称已交付响应能改状态。脱离HTTP的Runner与维护任务不由此接管。不得记录异常值、SQL/params、请求输入或凭据。无法兜底浏览器DNS/TLS或进程整体消失。
3. **路由边界**静态导入最小Failure组件，根故障无需Layout和身份成功；Layout内的子错误保留工作台。独立signin/help/受保护预览均有出口。懒加载模块失败由路由加载适配识别，普通渲染异常安全兜底，不靠英文message判断版本。不保证ErrorBoundary捕获事件回调/异步请求。
4. **无JS/入口失败**由构建生成最小静态文字、正常链接和noscript；启动观察到明确script失败时提示资源失败，只有等待过长则提示加载较慢。React真实挂载后清理观察器。兜底不依赖API、主bundle或远端字体。
5. **生产404交付**先修复并匹配已知页面白名单（含avatars/svg等页面），再排除api、assets、brand、failures与其余avatars资源前缀、任意点路径段/越界、末段含资源扩展名的路径。剩余GET/HEAD需明确文档导航：Sec-Fetch-Dest=document；若明确为其他dest则拒绝；仅在Fetch导航头缺席时，以安全的无扩展名路径加Accept text/html兼容旧客户端。符合者返回品牌HTML和真实404；其余保持原资源404。错误HTML未构建/缺失、API-only未挂载时保持原404，不新增启动失败。404不因静态文件ETag变成200/304，HEAD空体和长度正确。保留405 Allow、br/gzip协商、406、Vary及原正常资源缓存。新静态HTML先生成，再压缩。生成器使用明确纯JSON公开文案入口，由catalog.ts同源消费，不执行带React或请求依赖的模块。
6. **代理停机兜底**提供可选本地配置与操作手册，静态502/503/504来自独立代理本地文件，API保持JSON且SSE不缓冲。不自动安装或替换当前运行服务。本机未发现nginx/caddy，当前交付配置和说明，真实停应用验收为有条件未覆盖项；不得记为通过，本机make start仍无独立停机首访页。

## 分工与实施顺序

1. 两名独立审查者先复核本方案：前端关注结构化事实、上下文、草稿与生命周期；后端关注公开协议、响应开始后的边界、静态交付和测试。实质问题修正后再改业务代码，保留评审问题与处理记录。
2. 落地纯模型、HTTP事实和公共展示组件/C21标准；生成并检查五张新配图，复制已认可404。先接路由、身份和ResourceStatus，避免出现两套新展示入口。
3. 沿原状态拥有者接入员工/技能、大脑/能力/工具、知识库、规则和会话。保持FormField、ConfigurationConflict的领域逻辑；局部消息改为统一Notice，不重写控制器。
4. 后端安全500/request ID、静态404/启动兜底和可选代理文档可独立实现，构建脚本与前端公共文案接口先对齐。
