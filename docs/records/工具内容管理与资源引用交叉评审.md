# 工具内容管理与资源引用交叉评审

日期：2026-11-10。状态：基于当前工作区的审查报告，协调建议待确认，未实施业务改造。

## 结论与范围

两条线在目标和基本边界上兼容：工具内容管理解决“给模型什么、怎样读取”，资源引用解决“回答指向什么、用户怎样核对”。共同依赖同一份可靠内容及其最终交付事实。当前不能直接并行建设两套公共机制；应先修已确认的数据完整性问题，再验证框架复用范围，最后补实际缺失的引用能力。

本线需要收缩的部分是：不能把五个逻辑对象直接变成五套持久机制，不能让引用层再次决定结果裁剪，也不应将框架已经支持的 Citation annotation 一律推迟。ToolSearch 线需要澄清的是：诊断 wire_request 能辅助排错，但它可缺失、会脱敏，不能单独作为强制引用资格的业务事实。

## 一、共识与边界

| 主题       | 两条线可共同采用的认识                                                 | 直接含义                                               |
| ---------- | ---------------------------------------------------------------------- | ------------------------------------------------------ |
| 先判断价值 | 平台逻辑是否保留，要看功能收益，再看官方能否替换                       | 不因已有代码而保留，也不因框架提供了功能就全部启用     |
| 官方复用   | 循环、消息、checkpoint、摘要、artifact、Citation及文件能力优先使用框架 | 平台只补组织权限、持久业务事实及明确的产品缺口         |
| 存储归属   | 知识、文件和MCP原结果各有所有者                                        | 统一标识和读取描述，不复制进一个新的万能存储           |
| 内容交付   | 共同受最终模型请求容量约束，原生工具保留自己的有界读取语义             | 已确定交付范围后，规范化和引用层不得再静默切片         |
| 事实层次   | 远端返回、平台保存、提供模型、最终引用分别记录或表达                   | 本地文本读完不等于远端无下一页；页面不自动等于文章     |
| 引用用途   | 证据支持、实现导航、成果下载、相关入口不同                             | 共用标签不意味着都要进入Evidence或Sources              |
| 权限与恢复 | 句柄不授予权限，快照不冻结授权，补读不重跑远端操作                     | 官方移存替换须保留Run归属、来源核验和恢复限制          |
| 验收       | 正确性先于性能，整体用量不等于实际费用                                 | 实测质量、耗时和缓存折算成本，不用单次最好结果证明收益 |

“统一交付”不要求所有工具经过相同的新包装。已安装 FilesystemMiddleware 明确将 read_file、grep、ls 等排除在通用长结果移存之外；这是原生读取/过滤语义的差异，不是需要由平台消除的不一致。

“保留原始结果”与“向模型完整发送”也不是同一决策。SDK把大文本写入文件，并不自动证明保存了供应商完整结构、多模态信息、当前访问规则和对外可读证据。两者是否能共用底层字节，应通过集成验证决定。

## 二、实质分歧与本线应修订的部分

### 1. 先建统一机制，还是先验证框架差额

本线原稿预先建议 `app.references` 及 Evidence、RunResource、EvidenceExposure 的独立持久管理；ToolSearch 最新结论反对先建第二套通用结果框架，要求先证明原生能力缺口。这是实施规模与先后顺序的分歧，不是对来源可追溯性的分歧。

建议采纳框架优先的顺序。ResourceRef、Evidence、RunResource、Exposure、AnswerReference 可以继续作为逻辑区分，但首次实现先映射到既有知识证据、ToolMessage、结果文件、动作和Run成果。只有真实跨来源复用和缺失字段得到证明，才新增必要结构；不为五个名词分别建立表、服务或状态机。

### 2. 谁决定交付，谁记录交付

ToolSearch 负责容量决策、完整/预览/文件引用及读取策略；本线原稿也提出上下文选取、交付范围和交付状态。如果两边各自实现，就会再次出现分配不同、记录不同和多层裁剪。

建议同一次最终请求准备只产生一份“交付清单”：关联模型动作、原内容或证据标识、表示版本、实际提供的有界单元/范围，以及采用完整内容还是读取引用。引用侧只消费这个事实，不重新做内容分配。

交付清单先复用最终消息和已有动作事实，是否需要独立持久字段由适配测试决定。需要强制校验引用范围时，最小业务记录应可靠保存；不追踪每个自然语言token，也不将尚未取得的多模态源坐标伪装成精确范围。

### 3. 首期仅Markdown，还是保留原生Citation

本线原稿将供应商annotation接入放到以后；本线后续框架核对已发现标准 Citation。这一结论尚未完整写回原稿，形成文档滞后。

建议首期至少完整保留已有标准内容块与annotations。对已支持来源，annotation与Markdown链接都归一到同一回答引用清单；模型不支持原生引用时继续使用既有Markdown。并非要求首期支持所有供应商，也不直接信任annotation中的URL获得平台资源权限。

Citation的起止位置针对相应回答文本块，不是源文档坐标。适配器应保留供应商原格式、内容块位置及偏移单位，正确映射最终正文；不能默认所有供应商都与平台Unicode字符索引一致。

### 4. 诊断证据是否足够承担引用资格

ToolSearch 方案把交付大小、方式和真实发送内容主要放入现有诊断记录；本线要求引用资格具有可靠业务依据。两者只有在诊断仅用于观察时兼容。

当前 [RunContext.capture_evidence](../../backend/app/execution/context.py) 明确允许采集失败而继续执行，且诊断会脱敏、受独立配额限制。因此，不能只在wire_request中保存交付事实，再把缺少日志当成引用不存在，或从脱敏文本反推原文范围。

建议分开可靠的最小业务关联和可选诊断全文：前者在真正需要强制引用资格时随动作/成果保存，后者继续辅助排错。没有强制范围需求的普通工具结果，不为此增加失败点或单独持久化系统。

## 三、已确认问题与影响

### 高：静默裁剪破坏内容，引用追踪无法补救

[feedback_outcome](../../backend/app/builtin_tools/results.py) 直接将反馈截到24576字节。本次使用真实函数处理有效的30045字节合成JSON，得到24575字节文本，JSON解析失败，附加元数据为空。独立复现与ToolSearch的审查一致。

问题发生在通用反馈规范化阶段：即使上游有完整返回，进入模型的内容也可能被破坏。如果在裁剪前记录“完整交付”，证据记录会与实际输入不符；只新增Citation或引用表不能解决这一错误。

处置建议：先移除无标记、不可补读的二次裁剪，由原生读取/移存与一次请求容量决策提供有界内容。最终检查只验证，不再悄悄修改。

### 中：输入容量统计包含不会发给模型的artifact

[ModelExecutionMiddleware](../../backend/app/agent/model_calls.py) 对消息使用 `model_dump_json` 计量；这个序列化包含artifact。框架的工具消息模型投影不包含artifact。

本次合成ToolMessage正文只有 `ok`，artifact包含140000个ASCII字符：平台消息序列化为140188字节，框架OpenAI消息投影仅75字节。这不是实际模型调用或计费测量，但足以证明当前计量包含仅应用侧的数据，可能提前触发128KiB限制。

这是一处跨线依赖：本线推荐用artifact承载来源元数据，若不先纠正容量统计，元数据越完整越容易误报超限。应基于模型侧消息投影估算完整请求，并与实际provider序列化做隔离对照；平台元数据有自己的存储限额，不能算作模型输入。模型窗口、序列化字节和费用仍是不同口径。

### 中：标准引用保留在SDK消息，却没有进入正式成果

[engine._completed_response](../../backend/app/agent/engine.py) 只返回 `str(final.text)` 与用量，流式 [RunProgress.record](../../backend/app/agent/streaming.py) 也只输出文字及推理摘要。合成AIMessage带一个citation，经过真实最终成果提取后只剩 `Answer` 与用量；原消息中的annotation仍存在。

这确认的是“发布投影未携带annotations”，不是checkpoint已丢数据，也不是当前某次用户回答已经丢引用。当前各模型实际是否返回原生引用仍需分别验证。

处置建议：在成果适配处保留标准内容块与引用，再归一为平台清单；校验和展示不依赖模型把annotation重写成Markdown。

### 中：官方长结果移存尚未完成平台适配

[filesystem_middleware](../../backend/app/builtin_tools/workspace.py) 显式将工具长结果移存设为None，而MCP另用[ToolResults](../../backend/app/execution/tool_results.py)保存结果和固定预览。已安装SDK确实提供移存，但默认目录不在当前工作区允许的写入根中；直接启用不能满足现有Run、来源授权和持久读取规则。

处置建议：先验证受控Backend映射、稳定读取、多模态与结构化原结果、撤权、取消、失败和旧游标。通过后替换重叠实现；不通过则只保留已证明必要的差额。官方默认阈值是单结果移存机制，不等于包含工具定义及全部消息的模型上下文容量分配。

### 中：超时配置覆盖是独立问题，不应被引用改造掩盖

[model_session](../../backend/app/llm/factory.py) 固定HTTP超时。独立离线工厂探针中，配置timeout=7，实际读超时仍为60秒、连接超时10秒，与ToolSearch结论一致。

建议在运行控制线统一配置来源，保留网络超时与Run总时限各自职责。它不需要等待统一资源引用，也不应作为增加新引用控制层的理由。

## 四、尚未证明的事项

1. 官方移存已能替换平台保存、来源权限和对外下载：未证明。
2. 五个逻辑对象都需要独立持久结构或精确范围校验：未证明；需要首批实际引用场景支撑。
3. 原生Citation能在当前所有兼容接口模型上稳定返回：未证明。
4. 三次合成对照证明生产成本下降47.9%：不成立。该数字是该探索的总token差异；共享实测前缀计入每条逻辑轨迹，不是唯一实际收费请求之和，缓存冷热也未严格控制。
5. 交付优化已解决业务事实错误：不成立。现有探索仍记录页面/文章混用、满页推断总量及本地游标与上游分页混淆；质量未过关，不能以更快抵消。
6. 所有任务都应该尽量完整交付：未证明。小结果可能少一轮，大结果或无关明细仍需读取/过滤；并行结果共享一次请求容量。

## 五、统一后的职责和交接内容

| 责任范围         | 主维护位置                             | 向另一侧交付什么                               | 不做什么                                       |
| ---------------- | -------------------------------------- | ---------------------------------------------- | ---------------------------------------------- |
| 工具发现与授权   | 当前builtin_tools/执行链路             | 获准工具和真实调用动作                         | 本次不改发现数量、排序或名称目录策略           |
| 原内容与原生读取 | knowledge、files、MCP结果保存、Backend | 稳定内容引用、来源定位、权限核验、原生读取方式 | 不把全部数据迁入公共引用库                     |
| 给模型的交付     | 官方消息/移存/摘要及必要的模型入口适配 | 最终模型侧内容、交付清单、模型动作关联         | 不产生第二套来源索引或再裁剪一次               |
| 回答资源与引用   | 本线逻辑契约及最小成果适配             | 资源目标、用途、引用位置、可核对内容和读取投影 | 不决定结果分页，不替代工具发现或模型容量规则   |
| 正式结果与展示   | execution完成、业务接纳、前端          | 不可变正文、规范引用清单、正式成果关系         | 不从动作标题、任意外链或供应商annotation猜授权 |

交接内容使用已有框架对象与平台稳定ID：检索侧可以用Document，工具应用侧用artifact或有界引用，输出侧保留标准内容块及Citation。长正文仍在原存储，artifact不重复塞全文；平台只补模型不理解的Run、来源范围和文件生命周期信息。

同一份交付清单既服务性能观察，又为需要证据核验的引用提供事实。诊断可以记录全文以排错，但不再成为另一份必须一致的业务权威。暂不决定新增表、公共模块目录或第二套checkpoint字段。

## 六、协调与推进顺序

| 步骤                  | 责任与产出                                                                                                | 进入下一步的条件                                                                                 |
| --------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 1. 冻结共同边界       | 两线共用一份框架复用映射、内容身份/表示/交付/引用的最小样例；本线修订过早持久化及延期保留annotation的假设 | 明确原数据所有者、唯一交付决定点及引用层消费范围；不预建大框架                                   |
| 2. 修完整性与配置问题 | 工具内容线处理静默截断、artifact误计输入和超时覆盖；重复限次/无效配置沿对方已有审查分别处置               | 有效JSON不被破坏，应用元数据不计模型容量，配置生效；授权和持久计账不回退                         |
| 3. 做官方差额验证     | 使用受控Backend、实际中间件顺序及隔离存储，验证官方移存、原读取及交付记录位置                             | 两种结果结构、并行与大结果、非文本、撤权、取消、保存失败、旧引用均有结果；记录可删和必须补的差额 |
| 4. 做最小引用贯通     | 本线接现有知识证据与一种明确外部来源，保留Markdown和已有标准annotations；成果区继续使用既有文件关系       | 同一最终交付事实可解释行内引用；无额外模型修复、无重复正文存储、无临时路径长期导航               |
| 5. 联合验收并决定扩展 | 沿ToolSearch既定对照方法，增加引用正确性与归属场景；完整报告含不利轨迹和未知项                            | 先过事实质量与权限，再看完整Run耗时、缓存折算成本及维护复杂度                                    |

验收样本共用：最近查看50页、明确完整的小列表、需要末尾证据的长结果、只看摘要不足的网页、并行多结果、知识历史复用和正式成果文件。分别检查平台读完、上游分页结束和业务集合完整，不将其中任何一个替代另外两个。

缓存成本继续按确认的供应商价格或额度规则计算普通输入、缓存读写和输出；当前没有确认的Kimi Code额度权重不补猜。性能对照保持发现方式不变，单独区分交付变化与提示词变化；不因本次新增引用适配就复活已撤回的工具发现方案。

上述责任分工和顺序属于协调建议，不代表两线已经完成实施承诺。代码修改、正式迁移和真实模型/上游验收仍须在后续明确实施范围内进行。

## 本次验证与限制

本次重新执行四个离线探针：JSON完整性、artifact容量差异、标准引用成果投影、超时配置覆盖。没有加载业务数据库、读取真实工具返回或调用模型；探针结果与源码哈希已保存。所有问题均明确区分当前源码事实、合成复现、设计建议和未验证范围。

文档检查与格式结果由本次交付说明报告；不把文档检查、源码阅读或对方历史测试数量表述成生产功能验收通过。
