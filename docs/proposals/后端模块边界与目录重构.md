# 后端模块边界与目录重构方案

设计状态：待评审。实施状态：未实施，仅完成代码核对与方案整理。更新日期：2026-11-11。

本方案以当前工作区为依据。现行实现仍见[后端架构](../architecture/backend.md)与[后端手册](../engineering/backend.md)；本文中的目标目录、接口和依赖约束不表示已经生效。当前核对范围包括 `backend/app` 的 195 个 Python 文件、模块装配与关键业务调用，以及相关测试定义；静态引用统计包含类型检查分支，不能等同于运行调用图或故障路径验收。

## 1. 目标与实施边界

本次整理的目的，是让数据、业务规则、流程、技术适配和资源生命周期各有明确所有者。目录承担发现和导航职责，接口、事务与检查共同约束模块协作。

有效需求：

1. 同一业务概念及其规则就近维护，能按职责定位修改入口。
2. 一项业务流程有明确协调者；其他模块提供有边界的能力，不反过来推进调用方的流程。
3. 分开拥有不同变化原因的代码，例如模型协议适配、Run 调度、对话发布、知识来源有效性。
4. 允许有目的的跨模块协作，但明确输入、输出、事务、失败和生命周期责任。
5. 减少模块通过完整服务对象、内部 ORM、运行快照字典和回调任意穿透彼此实现的情况。
6. 形成模块归属、允许依赖、现有交叉处理、迁移顺序与验收标准。

本轮只写方案。未来迁移保持当前模块化单体、同进程后台执行、SQLite 短事务和 SDK 执行存档部署方式；HTTP 契约、权限语义、模型与工具预算、Run 状态、数据保留和检查点兼容均须按现行契约验证。本方案没有引入多实例领取、消息总线、通用工作流引擎或新增产品能力。

这些交叉的性质不同。元数据注册、只读联合投影、同库原子约束、普通类型共享与业务流程倒置需要分别治理，不能仅凭包级引用环统一判断。

## 3. 总体组织：分区与模块内部职责配合

采用分区式模块化单体：顶层表达架构职责；业务应用和资源分区内部按能力组织；运行分区按可靠执行、SDK 驱动与工具适配组织。各模块就近拥有自己的规则、模型和存取实现，按真实复杂度拆文件。

| 分区                 | 拥有的职责                                                              | 不承担的职责                                   |
| -------------------- | ----------------------------------------------------------------------- | ---------------------------------------------- |
| `api`、`cli`         | HTTP/SSE、命令行输入输出、协议错误和进程入口                            | 业务写入决策、调度、数据库业务查询             |
| `applications`       | 对话、考核及配置摘要等业务用例，以及成果接纳和面向业务的读取投影        | Agent 循环、供应商协议、资源底层清理           |
| `runtime`            | Run、动作、预算、执行授权组合、取消恢复、执行证据、Agent 驱动和工具入口 | 正式消息发布、考核评分、资源配置管理           |
| `resources`          | 员工装配、组织规则、技能、连接、知识、文件、环境等配置与资源生命周期    | Run 调度、对话和考核流程、模型工具反馈协议     |
| `auth`               | 账号、会话、身份值、操作权限和持续工作身份有效性                        | 员工配置资格、资料版本、动作预算等所属模块规则 |
| `infrastructure`     | 共用数据库机制、凭据加密、并发、日志以及共享模型客户端适配              | 业务归属、删除策略、员工装配、Run 状态机       |
| `common`             | 少量确有跨区消费者的普通值、错误与通用输入输出类型                      | 业务流程、权限、提示词、SDK 适配、数据库访问   |
| `bootstrap` 与根配置 | 具体实现选择、元数据注册、进程服务装配与启停                            | 将各模块业务规则集中实现                       |

这里的分区不是所有请求必须逐层经过的调用栈。资源管理 API 可以直接调用所属资源服务；对话和考核经业务应用提交运行；后台知识处理仍属于知识资源的生命周期。

`resources` 中的技术适配器优先留在所属模块，例如 Chroma 在知识模块、OpenSandbox 在环境模块、MCP 传输在 MCP 模块。跨能力共享、且没有所属资源业务规则的技术机制才放入 `infrastructure`。聊天和向量模型客户端已经有多个真实消费者，因此归入公共技术支撑。

命名与边界进一步明确：

- `cli` 是部署者在终端使用的命令入口，负责参数和输出；它调用现有业务能力，不是另一个运行调度层。
- 配置摘要只有一个跨资源读取用例，使用 `applications/configuration_summary.py`；不建立含义过宽的 Workbench 模块。
- `resources` 是具有业务含义的配置、资产与运行资源：拥有资格、修订、发布或回收规则，既可包含规则也可包含专用技术适配。联合目录是这一组资源的只读查询模块。
- `auth` 保留现有名称，回答操作者与会话是否有效、具有什么操作权限；员工装配、资料版本和运行动作预算仍归各自所有者。
- `infrastructure` 实现数据库、加密、通信与共享客户端等机制；`common` 定义少量共享值、数据结构和通用错误。资源业务决策不能通过这两个目录传播到其他模块。

架构验收同时检查源码依赖、运行协作、状态写入和生命周期。目录和接口只能表达边界，实际实现还必须满足第 6 节的依赖规则、第 8 节的协调顺序及第 9 节的验证要求。

| `environments`                                                | `resources/environments`、`cli`、运行工具桥接                   | 供应商实现与 SDK 文件后端分别拥有，历史映射单独处理                 |
| `llm`                                                         | `infrastructure/llm`、`common/usage.py`、运行用量与诊断文件     | 分离公共类型、SDK 解析、累计规则和诊断展示                          |
| `infrastructure`                                              | 原分区，元数据注册移到 `bootstrap`                              | 只保留机制；不在数据库包聚合业务模型                                |

所有模块的 `config.py`、普通内部 schema、说明和图随所有者迁移。CLI 和 subprocess 入口另行更新调用位置；不因迁移顺手统一数据 ID、类名或产品术语。

### 5.2 业务应用内部

**对话。** `commands.py` 接收输入、组织事务并调用 Run 公共操作；`writes.py` 只维护本模块消息和关联；`acceptance.py` 负责发布资格、接纳重试及通知循环；`context.py` 选择已经成功接纳的连续对话基点。当前 `queries.py` 兼有复杂 SQL 与响应构造，拆为可见范围/读取入口和 `projections.py` 的联合只读投影。`files.py` 继续拥有对话附件资格，文件字节归文件模块。

跨模块的受理操作返回普通 `RunReceipt` 数据，包含调用方真正需要的 Run ID、输入文件引用、受理状态和幂等结果，不返回可修改的 Run ORM。停止、读取终态和复核成果通过运行模块的公开接口进行。消息与 Run 仍使用同一 Session，不拆提交。

**考核。** `commands.py` 维护创建和取消；`progression.py` 每次推进一道题，提交 Run 与题目绑定共用事务；`acceptance.py` 接纳 Run 结果、校验评分器版本并推进批次终态；`queries.py` 提供批次及答卷读取。`benchmark.py`、`bfcl_checker.py`、`data/` 保留题库与评分所有权。`worker.py` 只唤醒推进，不重新实现状态转换。

**配置摘要。** 将当前配置摘要查询迁入 `applications/configuration_summary.py` 的一个读取函数，保留管理员/公开读取入口的权限与计数含义；不新增只转发的 service 或 repository。这是对当前后端手册允许该 SQL 位于路由中的规则的拟议调整，实施时须同步手册。

### 6.1 分区规则

下表描述源码依赖。接口调用的运行时实现由装配注入，不能因注入绕过资格检查、事务或生命周期责任。

| 调用方              | 允许依赖                                                                         | 禁止或限制                                                                                        |
| ------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |

| `runtime/execution` | `runtime/contracts`、纯 `runtime/usage`、资源公共操作、身份、基础设施、common    | 不导入业务应用；不直接导入 Agent/工具 SDK 实现，具体实现经装配交接                                |
| `runtime/agent`     | 运行契约、纯 `runtime/usage`、SDK、工具适配、模型客户端、checkpoint 所需技术机制 | 不读取 execution/资源/应用 ORM，不认识 HTTP 请求或身份会话实现                                    |
| `runtime/tools`     | 运行工具协议、资源普通输入输出契约、SDK；具体供应商桥接限于适配文件              | 不启动 Run、不持有 RunStore，不用工具参数自行推导资源授权                                         |
| `resources`         | auth、common、infrastructure；下表列明的其他资源公共能力                         | 不导入 applications、runtime、bootstrap；不因资源被运行使用就读取 Run 表                          |
| `auth`              | common、数据库等基础机制、所属登录适配                                           | 不导入员工、知识、Run 或业务应用                                                                  |
| `infrastructure`    | common、标准库和相应第三方技术库                                                 | 不导入资源/身份/运行/应用实现；模型注册从本包移出                                                 |
| `common`            | 标准库和明确使用的普通数据校验库                                                 | 不导入其他 app 分区、ORM、SDK、FastAPI；不能成为业务规则收容处                                    |

`runtime/contracts` 只保留有实际跨组件消费者的契约；模块私有数据继续在模块内。`TYPE_CHECKING` 中的依赖也属于架构依赖，需要区别于实际运行导入但仍受检查。`__init__.py` 不做整包聚合；仅在确有稳定公共入口时导出，避免普通契约导入连带载入 ORM 或 SDK。

### 6.2 资源之间的明确依赖

| 消费方                     | 允许消费                                                                                  | 依据与边界                                                 |
| -------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 员工                       | 技能定义与发布事实、模型连接资格、MCP 已批准目录/连接事实、知识库可装配事实、环境配置概要 | 员工拥有装配关系；同 Session 校验，不能擅自修改来源资源    |
| 知识                       | 文件资格与字节、模型连接的向量配置和资格                                                  | 不读取员工装配或 Run；调用方提供受限范围并在正确时点复核   |
| MCP                        | 身份会话公共操作、凭据与网络机制                                                          | 员工引用检查经具名能力注入，不反向导入员工                 |
| 联合目录                   | 技能、MCP 的目录读取事实或声明过的只读表投影                                              | 只聚合读，不维护第二套定义                                 |
| 技能、模型连接、文件、环境 | 由消费者提供的具名引用/保留/活跃状态查询                                                  | 不反向认识具体应用或执行宿主，不接受可任意调度的服务定位器 |

资源之间只允许这里有目的的调用；新增边需要说明消费者、规则所有者、输入输出和一致性要求。关系型外键本身可以跨模块，模型注册由装配统一完成，不因此开放业务代码任意跨表修改。

### 6.3 三类协作接口

1. **普通读取或外部调用。** 输入输出使用明确 DTO/普通值，调用方不获取另一模块的 ORM。外部网络与文件重处理在写事务之外；提交前再次复核资格和版本。
2. **同库原子协作。** 明确标注的 `submit_in_transaction`、`assert_current`、引用检查等接口接收调用方 `Session`，不自行开启或提交事务，只访问其拥有的事实。这里是当前单体的受控技术依赖，不引入整套抽象工作单元。
3. **联合只读投影。** `projections.py` 或具名目录查询可在显式白名单内读取多个模块模型，先核对业务可见范围，SQL 继续带完整归属过滤。文件只返回视图，不修改外部 ORM、不调用外部服务、不作为运行授权的替代。

跨模块查询有自己的目录和 import 白名单，但不会为每张表建立 repository。只有持久化复杂度或替换边界确有需要时才引入存储端口。

### 6.4 公共入口与内部实现的判定

模块以明确的服务方法、查询函数和契约公开能力；文件名是定位入口，不表示该文件内所有符号都可跨模块调用。

| 模块      | 可公开的入口                                                  | 保持内部的实现                                                      |
| --------- | ------------------------------------------------------------- | ------------------------------------------------------------------- |
| 对话/考核 | commands、queries、附件用例；仅供装配调用的 references        | writes、状态推进辅助函数、本模块模型和投影 SQL                      |
| 执行      | Run 受理/取消/成果读取、诊断查询、references、普通运行契约    | Store、Task、Context、调度内部表、证据 ORM、具体资源准备            |
| 员工      | 管理服务、assembly 快照、access 的装配事实检查、references    | 关系替换和存取细节；运行方不得写员工关系                            |
| 技能      | 发布与读取服务、发布定义、参数校验、内容读取                  | 内容存储路径、源目录替换和 ORM                                      |
| 模型连接  | 管理服务、resolution、普通配置与使用事实接口                  | 密文、ORM、具体探测请求                                             |
| 知识      | 库/文档管理、处理操作、限定范围的检索和来源读取、普通数据契约 | Chroma collection、向量 lease、发布 SQL、资料 ORM                   |
| MCP       | 服务/连接/目录/调用/OAuth 的用例及普通数据契约                | token 存储、stdio 进程、传输 SDK、连接 ORM                          |
| 文件/环境 | 文件资格与字节、输出核验、沙箱使用和回收操作、窄能力契约      | 磁盘键、申请记录、远端 SDK 句柄与 CAS；必要句柄仅交给具名桥接适配器 |
| auth      | Actor、权限函数、请求认证、持续工作身份检查                   | 会话 ORM、登录中间状态、密钥处理                                    |

只读 SQL 的初始例外白名单限于：对话 `projections.py` 读取 Run/RunAction、员工概要和文件；考核 `queries.py` 读取 Run 状态与用量；`applications/configuration_summary.py` 读取员工/技能数量；联合目录 `queries.py` 读取技能/MCP 服务概要。它们不获得外部对象写权限；各模块自己的 ORM 查询不受这一跨模块白名单限制。

`references.py` 由被引用事实的所有者读取自己的数据，消费者通过注入使用，不能借该文件名直接查询所有模块。实现阶段把允许的符号、跨表对象和 import 写入逐文件测试；临时例外注明真实用途和退出阶段。

### 6.5 依赖图应有方向，运行协作应有受控出口

以业务模块和执行组件为节点，目标的正常源码依赖图应当无环。分区间的消费者与提供者已经在上表限定；资源内部再按具体模块细分，不能因为同在 `resources` 就任意互调。

第 6.1、6.2 节是允许依赖的唯一清单。对话和考核使用执行公共入口，执行宿主使用资源公开能力；资源内部由员工装配和联合目录读取所需来源事实，知识再使用文件和模型连接。被使用的资源不能反向创建消息、推进考题、重新编辑调用方配置或启动 Run。

普通契约和客户端纯配置模块作为独立的共享依赖叶节点，不能反向载入消费者实现。`bootstrap` 与 `runtime/assembly.py` 是装配入口，可以同时认识消费者和提供者；业务代码不得在处理请求时回到装配入口重新取得服务。

运行时调用方向不完全等于 import 方向。当前系统需要以下明确协作，它们保留有限能力与调用时机，不开放任意回调：

| 协作                           | 允许的范围                                    | 约束                                                                              |
| ------------------------------ | --------------------------------------------- | --------------------------------------------------------------------------------- |
| Agent 调用宿主 `AgentContext`  | 同一 Run 的动作许可、进度、结果和受控资源访问 | 宿主实现由 Task 创建并绑定；Agent 不取得 Store、服务容器或其他 Run 的操作权限     |
| 耗时资源操作中的资格复核       | 调用方提供的当前身份/Run/范围断言             | 只检查所需事实，不推进流程、开启独立提交、调用外部网络或递归重入当前检索/受理入口 |
| 删除、更新或清理时查询外部引用 | 注入的引用事实、兼容事实或保留集合            | 只读提供者自己的事实，复用原事务；不能借查询同步修改另一个业务模块                |
| 执行完成通知业务接纳           | 成果提交后发送唤醒提示                        | 不在执行事务中调用发布/评分；持久扫描仍负责漏通知和重试                           |

以上协作通过签名明确的能力接口或普通函数装配，不能使用万能 callback、全能力 context 或通用事件总线替代接口设计。新增注入点需明确消费者、提供者、读写类别、事务和关闭责任；仅修改 import、把原来的双向流程藏入回调不算完成解耦。

遗留多态模型只在具名兼容映射文件中保留元数据依赖；联合投影只有声明过的只读边。这些例外与正常业务依赖分别检查，不能豁免整个资源或应用目录。

### 6.6 状态写入归所有者，跨模块修改归用例协调

| 状态                                             | 唯一写入所有者                       | 其他模块如何使用                                  |
| ------------------------------------------------ | ------------------------------------ | ------------------------------------------------- |
| 消息、对话绑定与接纳状态                         | 对话应用                             | 执行只提交成果或通知，不修改正式消息              |
| 考核批次、题目与评分                             | 考核应用                             | 执行提供 Run 终态与结果，不解释考题完成规则       |
| Run、动作、预算与本 Run 证据                     | 执行模块的公开事务操作及账本         | 应用提交/取消/读取；Agent 经受限能力申请动作      |
| 员工、装配关系与修订                             | 员工资源；组织规则由独立规则资源维护 | 执行读取当前事实，不能修改装配来让一次调用通过    |
| 资料发布、索引代际、文件归属、连接凭据、沙箱记录 | 各自资源模块                         | 协调者调用公开操作，不直接修改外部 ORM            |
| 账号、会话与身份有效性                           | auth                                 | 消费方检查资格，不自行刷新/修改会话状态来延长工作 |

一个用例可以同时调用多个状态所有者，但只有一个协调入口决定业务顺序、事务和失败处理。需要同库原子提交时，多个所有者的方法使用同一 Session；这不会把外部表的写权限交给协调者。纯规则函数与只读投影不拥有调度能力。

## 7. 现有交叉依赖逐项处理

### 7.1 知识与执行双向依赖

现状见 [KnowledgeAccess](../../backend/app/knowledge/access.py)、[KnowledgeSearch](../../backend/app/knowledge/search.py)、[KnowledgeEvidence](../../backend/app/knowledge/evidence.py)。执行授权调用知识服务，而知识服务反过来读取 Run、会话、员工装配和运行时限。

目标分工：

| 事实或操作                                        | 所有者                                     |
| ------------------------------------------------- | ------------------------------------------ |
| 库、文档、片段、索引、来源版本与读取有效性        | `resources/knowledge`                      |
| 员工挂载的库、模式、top_k 和关系修订              | `resources/employees`                      |
| Run 当前状态、发起身份、总时限、冻结范围          | `runtime/execution`，身份有效性委托 `auth` |
| 本 Run 检索结果登记、来源继承、最终回答的引用归属 | `runtime/execution/knowledge_evidence.py`  |
| JSON 工具反馈、模型工具名称和 SDK 返回对象        | `runtime/tools/knowledge.py`               |

将 `run_scope`、受管多库检索协调、Run 证据登记和历史 Run 归属检查移到运行侧；资源模块接收明确的库范围、资料版本和检索输入，返回自己的检索/来源结果。员工模块提供当前挂载事实，知识模块不再自行读取员工关系。管理侧的 `search_library` 仍由知识资源按当前用户权限执行。

受管调用顺序必须保持：短事务复核 Run 与当前资格，关键词 SQL 和来源读取使用各自短事务，embedding、向量存储等耗时 I/O 在写事务外执行，再在登记证据的写事务中复核 Run、装配与来源版本后保存。每库和耗时阶段所需的中途复核，经运行侧传入窄能力或分阶段调用实现；不能把准备时快照当作永久授权。

继续复核全部挂载库的文档版本摘要与冻结的 `memory_scope`，不能只检查已经登记的证据。知识模块提供当前来源版本事实，运行模块组合员工范围并判断冻结上下文是否仍有效。

`RunKnowledgeEvidence` 跟随 Run 生命周期，且现表没有实时资料外键，目标 ORM 定义迁到 `execution/evidence_models.py`，表名、字段、级联和历史保存语义先保持。知识模块只验证来源数据，不负责修改 Run 证据记录。最终来源核验仍与 Run 成果提交同事务完成。

已有按 Run 查询来源的 HTTP URL 保留，处理入口改调运行侧来源查询；资源模块继续提供当前来源读取。保留当前私有配置、历史来源和普通运行查看各自的读取资格，不因移动所有权扩大可见范围。

当前运行与历史读取的兼容校验分别保留：当前知识装配拒绝带旧 `user_id` 的快照；历史证据可接受旧值，但要求 `legacy_user == owner_user_id == initiated_by_user_id`，来源为成功的对话 Run，且员工、所有者、线程、精确原链接和资料版本均符合当前历史引用规则。不能将两类校验合并后放宽当前装配或拒绝合法历史。

### 7.2 知识与工具协议的引用环

`knowledge` 当前使用 `ToolInvocation/ToolOutcome`，工具适配又读取知识 schema。目标是知识入口返回 `SearchResult`、来源片段和状态等知识 DTO；运行侧补充本 Run 证据信息；工具适配负责输出 `ToolOutcome`。工具名称、绑定 ID 和参数映射留在运行工具层。这样知识资源不再依赖工具协议，也无需把工具 DTO 放入全局公共包。

### 7.3 员工访问检查与运行动作混合

`employees/access.py` 的员工启用、模型绑定和技能/工具关系修订复核保留。技能只读文件范围、结果补读的特殊动作、模型可见工具与父动作关联、动作默认限次由执行授权和工具策略协调；工作区路径语义委托文件/环境策略，MCP 参数和批准目录语义委托 MCP。

检查组合依然进入同一个动作开始事务，返回完整许可后才预占预算并登记动作。策略拆开不增加隐式重试或额外调用次数，也不为模型和工具建立第二套授权账本。

保持不同工具的现有策略范围：MCP 默认 `max_calls=32` 由其许可策略补入，工作区不自动附加同一限次；技能文件和结果补读各有独立只读许可分支，不提取成全工具公共默认值。

### 7.4 资源删除、技能变更与反向引用

当前检查承担真实约束，保留其行为：

| 写入方            | 现有反向事实                     | 提供者与处理方式                                                     |
| ----------------- | -------------------------------- | -------------------------------------------------------------------- |
| 员工删除          | 对话和考核历史是否引用员工       | 两个业务应用的 `references.py` 提供事实，装配注入员工删除服务        |
| 技能修改          | 启用装配的参数是否兼容新规范     | 员工 `references.py` 返回相关装配事实；技能模块用自身参数规则判断    |
| 技能删除          | 所有装配关系，包括停用关系       | 员工提供全部引用事实，技能决定是否拒绝                               |
| 模型连接删除      | 员工、活动 Run、知识向量索引引用 | 三个所有者分别提供查询，经具名引用能力组合；模型连接模块保持拒绝策略 |
| MCP 定义/连接删除 | 员工固定工具引用                 | 沿用已有 `check_references` 注入方向，将签名和责任明确化             |
| 文件清理          | 消息、Run、知识资料保留集合      | 沿用已有 `retained(session, candidates)` 组合，提供者各管自己的引用  |
| 环境回收          | 活跃 Run 是否仍拥有资源          | 沿用已有活跃 Run 查询注入，环境模块不导入 Run 实现                   |

引用接口按消费者分别命名和定义，不创建能调用任意模块的统一引用注册中心。回调接受同一个 Session，返回计数、关系或布尔事实；写入方拥有错误码和拒绝决策。

当前文件保留回调仍接收 `StoredFile` ORM 候选对象；目标接口改传只读的文件候选值，当前所需字段是 `id` 和 `origin_run_id`，保留相同的批量检查与返回 ID 集合。ORM 由文件模块持有，提供者只根据候选值读取自己的引用事实。这样既保留已有同事务清理机制，也落实跨模块不传可变 ORM 的边界。

MCP 普通更新仍按当前修订、批准目录失效和后续授权复核处理，不因已有员工装配就统一拒绝更新。删除引用保护与更新兼容策略分别维护。

写入方必须在读取引用事实之前获取当前所需写锁，查询与删除/更新处于同一事务。将这些检查移到提交前预检、网络 API 或另开事务都会破坏约束，不能作为解耦方案。资源管理页面的反向用量展示可以使用同一事实查询或独立只读投影，不能与删除约束共用过期缓存。

### 7.5 冻结快照与 SDK 定义

保留 `RunConfiguration` 作为受理快照协调者。员工提供装配快照，组织规则和模型连接提供当前配置事实，知识提供来源版本事实；执行层组合预算、版本及连续上下文依据。

当前 [workspace_tools](../../backend/app/builtin_tools/workspace.py) 通过官方 SDK 获取工具定义。目标通过装配注入 `ToolDescriptorProvider` 一类窄接口，向快照协调者返回普通名称/schema/描述、哈希及对应 `recovery/scope_policy` 策略字段；SDK 工具构造留在工具适配。指令组合也以明确能力交接，固定指令归 Agent，组织/员工/技能正文归资源。

这里消除的是源码对具体 SDK 实现的穿透。受理阶段仍可以调用描述提供者读取官方定义，但不申请远程沙箱或执行模型。必须核对受理冻结描述与实际运行工具定义一致，不能在两侧分别手写工具 schema。

### 7.6 普通运行契约与模型用量

`RunSpec`、`Completion`、`InputMessage`、`ContentUpdate` 等普通运行数据按实际所有权迁到 `runtime/contracts`，Agent 和宿主共享它们；资源模块仍使用自己的 DTO。`ToolBinding` 留在 SDK 工具绑定文件，`ToolInvocation/ToolPermit/ToolOutcome` 等留在普通运行契约。

`TokenUsage` 迁到 `common/usage.py`，业务响应只依赖这个普通值类型。供应商/SDK 字段解析和消息片段合并留在 `infrastructure/llm`；跨动作累计“缺失即未知”的纯规则迁到 `runtime/usage.py`，只处理已经规范化的数字，不导入 SDK。诊断字段投影迁到执行 `metrics.py`。

保留当前普通请求与摘要共用一份 `RunUsage` 状态的机制，调用同一个纯累计函数；累计结果继续通过 `context.finish` 保存，也供 SDK 的 `model_usage` 状态更新和最终成果读取。执行账本保存已经累计的结果并处理在途未知模型消耗，不再对累计值二次相加。恢复继续以持久控制恢复出的 `recovered_usage` 初始化，存档中较晚的状态和未结束动作按当前恢复规则核对，不另建一个权威计数器。不改变缺失、未知、中断和缓存 token 的含义。

### 7.7 知识内部完整门面传递

不再把完整 `KnowledgeService` 作为所有子组件的依赖。资料管理只取得库/文档存取、文件资格与发布能力；处理组件取得领取/发布操作、解析器与索引能力；检索组件取得读取范围、关键词/向量检索和来源读取；向量组件取得连接解析、向量存储与代际发布能力。

这些依赖可以是已有具体服务的窄公开操作或有替身需求的协议，不要求先建一整套接口类。统一构造移到装配入口，公开用例直接绑定相应组件；不保留只为兼容旧调用而存在的层层转发门面。入库任务与向量发布仍属于知识模块，不迁入通用 Run 调度器。

### 7.8 沙箱供应商与 SDK 文件后端

环境模块提供沙箱申请/释放和运行所需文件、命令、结果收集能力；供应商创建、查询、销毁及网络配置留在 `open_sandbox.py`。`runtime/tools/workspace.py` 管官方虚拟文件后端和路径路由；`sandbox_backend.py` 管官方 SDK 与具体远端操作之间的适配。

普通能力契约避免把 SDK/供应商实例扩散到 RunStore 或业务应用。当前第三方 `OpenSandboxBackend` 确实需要供应商句柄时，允许这个依赖仅出现在具名桥接文件，由装配绑定；不为了形式上的完全隔离重写官方后端。当前每 Run 申请、未知创建占容量、等待在途准备完成及可靠关闭等语义保持。

`environments/models.py` 的 `WorkspaceProfile(ToolConnection)` 是历史多态读取映射，与网络策略无关。先核对旧数据和读取测试，将映射隔离到 `legacy_models.py` 并仅由模型注册装载；未证明可移除前保留兼容。删除该映射或清理旧数据属于单独的数据迁移增量。

### 7.9 模型连接探测与 MCP OAuth 存储

模型连接服务拥有测试操作的权限、配置选择、凭据解析与公开结果；供应商 `/models` 网络探测和协议解释归模型客户端适配，不在资源 CRUD 内继续堆网络分支。

保留当前两类探测的含义：向量探测真实调用 embedding，并在成功返回前复核配置/凭据修订；聊天探测读取 `/models`，只证明目录和模型可见性，不能表述为生成能力已验证。当前聊天探测没有同样的返回前修订复核；若统一这项行为，须另列明确增量及测试，不能作为移动文件的隐含变化。

MCP 的 `tokens.py` 拥有 token 持久更新、配置/凭据/存储修订 CAS 与当前资格；`adapters/oauth_storage.py` 负责 SDK 存储接口和 token 对象转换。SQLite 写入开始后取消仍须等待其结束，不能因移动适配文件在取消时提前释放连接或上报未写入。

### 7.10 元数据、配置与装配

`infrastructure/database/models.py` 的业务注册搬到 `bootstrap/model_registry.py`，Alembic 从该入口加载完整元数据，数据库 Base/Session 保持通用。普通业务不能通过注册聚合文件取得模型。

各模块配置定义留在所属模块，根 `config.py` 只组合、加载和交叉校验。运维 CLI 是允许读取根配置的入口；业务服务不能通过根配置间接载入其他模块。现有 `auth.cli` 等操作入口移到 `cli`，MCP stdio 的内部 subprocess 桥接仍由所属传输适配维护。

启停仍有统一所有者：数据库与资源先准备，工作生产者和执行宿主按现有安全次序启动；停止时先结束生产/接纳与所有在途执行，再关闭沙箱/文件服务，最后关闭连接和数据库。迁移须覆盖部分启动失败，不能只按正常路径关闭。

### 7.11 联合投影与业务接纳

对话查询可以将本模块消息与执行动作/文件做联合投影，但跨表 SQL 限于声明文件；命令和接纳不再直接修改外部 Run ORM。考核通过公开 Run 终态读取与事务操作推进答卷；引用历史检查由所属应用的 `references.py` 提供。

对话/考核到执行诊断的关联核验仍由所属应用完成，执行诊断另查运行事实和证据资格；HTTP 适配可以按明确读取契约连接这两步，但不能自行编写关联 SQL。当前公开知识来源 URL 改由运行来源查询接入，不改变 URL 和读取权限。

## 8. 保持主流程、一致性与失败语义

### 8.1 对话受理与发布

1. API 转换请求并取得当前 Actor。
2. 对话命令开启短事务、获取所需写锁，检查幂等、对话占用和输入资格。
3. Run 公共受理操作在同一 Session 捕获当前装配、来源和模型配置，创建 Run；对话保存消息和关联，一起提交。
4. Worker 领取持久工作，Task 准备资源并运行注入的 Agent；Context 将能力请求送往受控操作。
5. 动作开始事务复核许可与版本，预占预算并登记动作；外部调用结束后可靠保存结果，再反馈模型。
6. Task 等待执行、看护与收尾；Run 服务在完成事务中核验当前资格、引用和附件，保存成果及终态。
7. 完成通知唤醒对话接纳；扫描机制补漏。接纳单独提交正式回复，失败按现有分类重试，不重跑模型。

### 8.2 其他生命周期

| 场景           | 协调者                          | 保持的边界                                                                                         |
| -------------- | ------------------------------- | -------------------------------------------------------------------------------------------------- |
| 考核逐题执行   | 考核推进与接纳                  | 批次/题目绑定与 Run 受理同事务；结果已完成时的取消仍按现有规则处理；评分器版本不被新代码静默重解释 |
| 知识入库       | 知识处理组件                    | 短事务领取，事务外解析，正文/片段/FTS/向量可见关系一起发布；失败保留已发布内容                     |
| 向量构建与查询 | 知识向量组件                    | I/O 不占写事务，发布前复核源/模型/generation，查询持有 lease 并在返回前复核                        |
| 文件清理       | 文件清理组件                    | 保留查询与元数据删除同 writer 事务，提交后删除字节                                                 |
| 沙箱申请与回收 | 环境组件，Task 持有本轮使用责任 | 先登记申请，未知创建占容量；核对 metadata 归属再销毁，不盲目重建                                   |
| 会话授权       | auth 与运行授权组合             | 请求会话的空闲超时和持续工作的硬过期/撤销语义分别保留                                              |

### 8.3 必须保留的运行不变量

- 当前授权、预算预占、动作开始共同提交或回滚；模型发起的工具调用按父模型动作核验真实可见工具集，发现集合不授予调用权；宿主前置检索 `host_presearch` 保留当前无父模型动作的受管分支。
- 工具结果先持久化再反馈；结果补读、缓存重读仍核验当前资格。
- RunTask 等待已启动的准备线程、数据库操作、watcher 和资源释放；取消不提前结束资源责任，Worker 最后释放宿主锁。
- 业务发布失败不改写已保存的 Run 成果；持久化故障不伪装为普通业务拒绝或上游错误。
- 成功接纳的明确基点才可用于下一轮；同 Run 恢复不重置预算/总时限，不重放沙箱或 MCP 副作用；首次虚拟工作区修改开始前，在动作事务中标记本 Run 不可自动恢复。
- SDK 存档和业务引用分别提交，恢复继续按 Run/Thread 归属查可信存档；完整成果以存档完成标记和最终消息为依据。
- 未完成模型/工具动作保持 unknown，技能激活等其他动作沿用所属终态分类；未知 token 保持未知，不靠默认零或最后一个流事件补齐事实。

### 8.4 每项流程明确一个协调入口

流程协调按范围分工。业务应用协调用户用例，Task 协调一次可靠执行，官方 SDK 协调模型工具循环，资源组件协调自己的发布与回收；每个范围有单一协调者，不把所有工作收进一个总调度器。

| 流程              | 协调入口                                 | 顺序与交接                                                                     | 明确禁止                                                          |
| ----------------- | ---------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 编辑员工装配      | 员工命令服务                             | 检查操作资格和预期修订，获取写锁，读取来源事实，替换本模块关系并一起提交       | 技能/连接服务反调员工编辑，读取组件自行提交部分关系               |
| 对话提交/重试     | 对话 commands                            | 检查对话与幂等，调用 Run 受理并保存消息/绑定，同事务提交                       | 路由启动模型、资源服务隐式创建 Run                                |
| 考核推进          | 考核 progression                         | 选择当前题，读取已有 Run 终态或受理新 Run；通过考核 acceptance 接纳和评分      | Worker 重复实现题目规则，RunWorker 直接评分                       |
| 一次 Run          | RunWorker 调度，RunTask 拥有本轮生命周期 | 领取、逐项登记准备资源、运行 Agent/看护、等待在途操作与收尾、提交终态          | 子组件递归启动 Task，资源服务结束 Run，迟到成功覆盖已生效取消     |
| 一次模型/工具动作 | Agent 循环发出意图，宿主能力协调受控操作 | 校验意图及来源，在动作事务中授权/预占/登记，执行调用，可靠保存后反馈模型       | 工具适配绕过能力接口自行记账，资源返回前自行驱动下一次模型请求    |
| Run 知识调用      | execution/knowledge                      | 核对运行范围，调用知识读取/检索，阶段间复核，登记本 Run 证据，交给工具适配反馈 | 知识资源持有 RunStore，工具反馈层重写资料可见范围                 |
| 对话成果接纳      | 对话 acceptance                          | 扫描或被唤醒，读取已提交成果，复核接纳资格，保存正式消息；失败只重试此阶段     | 完成通知同步执行整段发布、接纳失败重新请求模型                    |
| 知识处理/向量发布 | 知识 processing/vectors 各自所属用例     | 短事务领取，事务外耗时处理，提交前复核并原子发布                               | 不经所有者直接改索引可见关系，套用 RunWorker 托管所有资源后台流程 |
| 文件清理/环境回收 | 文件 cleanup、环境 service               | 查询保留/活跃事实，完成所属状态转换，按当前要求删除字节或确认远端终止          | 引用查询主动清理业务历史，回收组件反调业务取消入口形成递归        |

模型与工具循环、队列轮询、恢复扫描属于各自协调者内部的合法循环；它们不是模块之间任意互相驱动。重复唤醒应回到同一入口，读取持久状态并按幂等规则推进，不建立额外的内存权威状态。

### 8.5 启停与失败顺序按依赖约束

启动时先创建数据库与技术客户端，再构造资源、身份和用例服务并完成能力绑定；服务具备被调用条件后，才开放相应运行入口。RunWorker、考核推进、知识处理、接纳扫描和资源维护各有就绪依赖，不要求所有后台组件共享一套启动状态。资源管理与配置读取也不因某个外部模型暂不可用而统一停用。

关闭时先停止接收新工作，并阻止生产者继续受理；等待在途业务/执行/资源工作完成或按当前取消语义退出，随后关闭它们使用的客户端、存储与数据库。实际退出顺序必须满足“使用者先退出、提供者后关闭”，部分启动失败也要释放已创建资源。

停止期间新完成的 Run 仍以持久成果为准；是否在本次关闭前完成业务接纳遵循已验证的退出策略，漏通知可在下次启动扫描补齐。不要为了等待一次通知，把资源或数据库提前关闭，也不要将本节的依赖约束直接替换成未经测试的新启停顺序。

每个失败只由所属范围决定重试：供应商故障解释归适配，动作/运行终态归执行，发布和评分失败归应用，资料发布/远端回收失败归资源；调用方保留失败含义，不在多层重复重试同一副作用。

## 9. 迁移顺序与验收

每阶段形成可独立审查的改动，先恢复职责和依赖，再进行大范围路径迁移。当前测试名称只是验证入口，历史通过不能替代各阶段重新执行。

| 阶段              | 可交付增量                                                                       | 验收重点                                                                                                |
| ----------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 0. 建立基线       | 更新实际依赖清单，记录当前 API/OpenAPI、元数据、快照、线程与恢复样本；确认本方案 | 相关离线场景实际执行；将现存失败与重构引入的失败区分                                                    |
| 1. 普通契约与注册 | 分开用量 DTO、运行普通契约、SDK 绑定；元数据注册迁至装配                         | 导入普通契约不载入 SDK/ORM；完整模型注册无遗漏，迁移 head 与模型无非预期差异                            |
| 2. 引用事实接口   | 逐项替换员工/技能/模型连接反向查询，保留文件/环境既有注入方向                    | 同 Session、先锁后查、回滚与并发修改；启用/停用关系差异不丢失                                           |

| 4. 模块内部职责   | 考核命令/查询/推进/接纳，知识窄依赖，运行准备，OAuth/沙箱桥接及快照提供者        | 业务状态和资源生命周期保持，删除无意义转发，组件可用窄替身验证                                          |
| 5. 目录迁移与接线 | 按完整映射表搬迁、更新 import、CLI/subprocess、配置路径、Alembic、测试及文档     | 无旧路径遗漏；元数据、静态资源、样本位置、启动/关闭/部分失败、框架构造一致                              |
| 6. 收口           | 删除阶段兼容层和已替换实现，扩展依赖检查、回写现行正文                           | 完成匹配风险的测试与 `make check`，无重复规则或两套活动入口                                             |

### 9.1 结构检查

在现有 [运行依赖测试](../../backend/tests/test_runtime_boundaries.py)与[执行边界测试](../../backend/tests/test_execution_boundaries.py)基础上扩展：

1. 同时解析绝对、相对、包聚合和类型检查导入，检查本方案的分区及资源间允许边；动态导入和属性穿透仍需代码审查。
2. 普通契约、common、纯 `runtime/usage.py` 的传递导入不得载入 ORM、FastAPI 或模型/Agent SDK；测试在隔离进程中检查导入副作用和模块加载集合。
3. `execution` 的实现依赖不得通过工具描述、包导出或 helper 传递引入 Agent/工具具体实现；装配到提供者的运行时调用是显式许可边界，另测返回描述与实际工具一致。
4. `resources/knowledge` 不再导入员工、执行或工具实现；跨模块 ORM 读取只开放给逐文件声明的 projection/目录查询和必要 legacy 映射，不使用目录级大豁免。
5. 检查引用事实接口不自行开/提交事务，服务不接收 FastAPI Request、完整容器或全能力门面。
6. 模型注册入口只供 Alembic、启动装配和测试使用；保留外键元数据，不产生通用基础设施对业务的反向依赖。
7. 以具体业务模块与执行组件建立正常源码依赖图，检查直接与传递依赖及强连通分量；除具名元数据兼容映射外，模块边界之间不得成环。新增边和白名单必须对应第 6 节的能力关系。
8. 对注入的引用查询、资格断言和完成通知检查读写类别：前两者不得推进业务或隐式提交，通知必须发生在成果提交后；禁止服务定位器和运行期重新装配。

结构检查通过只证明检查范围内的约束，不能代替事务与运行行为验证。

### 9.4 用修改影响范围验收内聚度

在公开契约和产品行为不变的前提下，用以下变更问题检验边界是否真正建立；不能仅以目录已搬迁或导入测试已通过判定完成。

| 变更问题                           | 主要修改位置                             | 应避免被牵动的实现                        |
| ---------------------------------- | ---------------------------------------- | ----------------------------------------- |
| 某供应商新增响应字段或改变请求参数 | 模型客户端或对应供应商适配及其验证       | 对话发布、员工装配、账号权限              |
| 调整知识排序和召回算法             | 知识检索算法及其输入输出验证             | Run 调度、工具门、对话接纳                |
| 调整对话正式回复的接纳重试         | 对话接纳与发布规则                       | 模型循环、向量索引、资源配置              |
| 调整一次动作的预算或恢复判定       | 执行授权组合、原子账本及配置契约         | 员工 CRUD、知识检索算法、供应商 JSON 适配 |
| 调整远端沙箱创建或 token 存储 SDK  | 所属资源适配、既有能力接口实现及故障验证 | 业务应用、Run 持久模型、其他资源内部实现  |

评审时还要检查：同一规则是否只有一个维护位置；一项流程能否从协调入口连续读懂；组件是否仅持有所需能力；是否出现新建文件仅转发旧大服务、兄弟组件继续通过完整门面互访、或只是用 callback 隐藏原有反向流程的情况。这些都是职责验收内容，不由目录名称自动保证。

### 9.5 验证调用顺序与状态所有权

对受理、动作、发布、删除保护和关闭这些重要路径，使用窄替身与真实隔离事务验证必要的先后关系和故障结果，不把内部每次函数调用都固定成脆弱测试。

| 路径           | 必须验证的顺序或结果                                                                          |
| -------------- | --------------------------------------------------------------------------------------------- |
| Run 受理       | 资源资格复核及消息/Run/绑定一起提交；失败不留下部分业务记录，重复提交不再次执行               |
| 模型/工具动作  | 授权、预算和动作登记成功后才发起外部调用；结果可靠保存前不反馈模型；拒绝路径不触发上游        |
| 资源引用检查   | 先取得写锁，在同 Session 读取引用，再决定更新/删除；查询不写外部状态、不自行提交              |
| 运行完成与接纳 | 成果提交先于通知；丢通知仍可扫描接纳，重复通知不重复发布，接纳失败不再次调用模型              |
| 检索与证据     | 当前范围和上下文检查、耗时 I/O、返回前复核、证据登记边界完整；取消/撤权在中间发生时不继续交付 |
| 准备与关闭     | 资源创建即登记关闭责任，部分准备失败和取消仍等待在途操作；使用者退出前不关闭其依赖            |

迁移完成必须同时满足：模块边界图方向明确，状态只有所属模块写入，各流程的协调入口可定位，关键顺序和失败语义有测试证据。目录已调整或静态检查通过只能完成其中一部分，不能据此宣称运行协作已经正确。

## 10. 评审要确认的取舍与本次验证范围

本方案推荐采用受控的同库事务协作，保留模块内部 ORM；以普通契约、具名引用能力、窄只读投影和关键处的端口隔离依赖，不进行全仓纯领域模型与每表 repository 改造。代价是少量接口显式接受 Session，需要在签名、事务说明和检查中持续约束。

建议评审重点是：知识 Run 证据的所有权迁到执行侧、组织规则从员工模块提取、资源反向引用改成同事务事实查询、普通运行契约独立，以及依赖无环、状态写入所有权和分级流程协调。具体辅助函数和类型名可在实现阶段随实际代码收敛，不预建无调用者的组件。

本次完成现行文档、静态导入关系、服务装配和关键生命周期代码核对，发现和区分了业务交叉、只读投影、原子约束与历史映射。未修改后端代码。

首次代码核对阶段执行了两项现行导入边界、独立内存控制下的 SDK 执行、模型预算登记失败回滚、执行成果保留与业务接纳重试，共 5 项测试通过，作为限定范围的现行基线。

本轮命名与协作边界优化只修改方案和索引，实际运行文档链接/索引及 Markdown 格式检查，不重复运行后端行为测试。检查复用现有虚拟环境，以 `UV_NO_SYNC=1` 运行对应 Makefile 目标，没有安装依赖，也未验证依赖重建。

这些结果只覆盖现行实现和本文档，不表示目标架构已经实施或验证。未执行完整业务回归、迁移演练、旧存档跨版本演练或真实外部服务验收，后续实施结果以逐阶段实际验证为准。
