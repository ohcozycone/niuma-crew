# 员工设计

设计员工，从一类具体工作开始：它要替人完成什么，怎样才算做好，再为它准备必要的方法、资料和操作能力。

## 先说明要交付什么

以材料整理员为例，输入是一段会议记录，成果是负责人、事项、期限和待确认问题。检查时看行动项是否遗漏、日期是否有依据、含糊内容是否明确标出。

明确成果后，再决定员工需要哪些能力。只整理给定文字时，重点是整理方法；需要查制度时，增加对应资料；需要写入外部系统时，再选择相应操作。

## 挑选完成工作所需的能力

| 工作需要           | 相应准备                             |
| ------------------ | ------------------------------------ |
| 理解材料、生成结果 | 选择适合任务的模型                   |
| 沿用固定做法       | 整理技能、步骤、模板与示例           |
| 查阅业务资料       | 选择相关知识库及检索方式             |
| 访问外部系统       | 选择工作连接和具体工具操作           |
| 处理附件或交付文件 | 准备必要的文件能力，按需增加代码环境 |

装配以够用为起点。例如员工只需读取 Notion 材料，就选择必要的搜索和读取操作，把修改、删除等无关操作留在装配范围之外。具体方法见[工具装配](../architecture/工具装配.md)。

这样做的目标是减少无关信息和可选操作，让方法、上下文与工作要求保持一致，也减少为过大的执行范围补充控制的负担。

## 把做法写清楚

岗位指令说明职责和成果要求，技能保存可以反复使用的步骤与模板，知识库提供需要查询的资料。本次工作的特殊条件直接写在交办要求里。

步骤围绕工作展开，例如“提取行动项—核对负责人和期限—列出待确认问题”。必要时给出合格示例，让使用者和维护者都知道期待什么结果。资料与工具按需要提供，避免每次交办都重复堆入全部内容。

## 用实际工作检查和改进

先拿有代表性的任务检查最小组合，发现明确缺口后再增加能力。更新模型、方法或资料时，用同类任务对比结果、用量、耗时和人工修正，判断调整是否值得保留。

[配置员工](workflows.md#配置一名可以工作的员工)提供操作步骤，[能力评估](../architecture/能力评估.md)展开验证方法与后续建设方向。
