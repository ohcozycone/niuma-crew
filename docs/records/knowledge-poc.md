## 边界与剩余验证

- 测试向量只能证明持久化和混合链路；评测入口拒绝用它报告向量/混合语义效果。用户确认目前没有 Embedding API，先完成离线验证并保留真实模型接入；真实三路对照留待有连接后执行，不作为当前离线交付的阻塞项。
- 此前真实问答因具体数据流未授权而被自动审批审查拒绝；用户随后明确允许仅向已配置 Kimi Code 服务发送虚构教学片段与测试问题，最多 2 次。本轮按此范围完成 2 次调用，没有发送评分参考答案。
- PDF/DOCX 为程序生成夹具，未获得真实复杂文件；不将格式测试称为真实资料验收。
- POC 发布使用独立目录及 collection，不写正式知识表；没有业务层权限、持久作业或 active_release_id，也未开放上传接口。
- Chroma 引入约 50 项传递依赖，已记录为选型成本；未据此替换选型，也未测试生产容量或启动资源。

## 真实聊天验证

使用现有 Kimi Code 连接（模型 `kimi-for-coding`，服务 `https://api.kimi.com/coding/v1`），在下述固定发布上执行 **BM25 → 6 个实际证据片段 → 单次回答**。每题只调用一次，无修复或自动重试。模型未接收参考答案；向量检索没有参与这两例。

| 问题                                                 | 模型结果与人工核对                                                                                                                                                                                                          | 服务返回 token 用量（输入 / 输出 / 合计） |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 出差已经获得主管批准，我能直接买高铁一等座并报销吗？ | `answered`：普通出差批准不足；须在购票前取得直属主管及财务负责人的特别批准，并明确覆盖该次一等座费用。E1/E3 对应 KB-101「高铁席位 / 出差申请」，补充材料要求的 E4/E5 对应 KB-104「提交顺序 / 必备材料」；逐段核对支持结论。 | 768 / 277 / 1045                          |
| 仅凭这些差旅制度，能确定我的报销款今天已经到账了吗？ | `insufficient`：无法据制度确认个人到账，建议查费用系统或联系财务。E1 对应 KB-105「个人业务状态」，E2/E3 对应 KB-101「适用范围」及 KB-104「提交顺序」；未编造个人状态。                                                      | 749 / 264 / 1013                          |

两例输出结构和引用编号校验均通过；人工比对了实际送模文字与结论，并按固定正文区间核对来源。第一例引用区间为 KB-101 `[415,580)`、`[315,415)` 与 KB-104 `[332,411)`、`[202,332)`；第二例为 KB-105 `[288,401)`、KB-101 `[206,315)`、KB-104 `[332,411)`。区间以 Unicode 码点计数，左闭右开。

这是两个人工审阅样例，不是答案正确率或向量效果验收。报告行的 `status=answered` 表示生成与校验完成；第二例业务判断保存在 `answer.status=insufficient`。token 为服务实报，当前本地预算使用 cl100k_base，尚未证明与 Kimi tokenizer 完全一致；本轮未测稳定延迟或费用。

## 复现与证据

执行 `make verify-knowledge` 可重新生成本地报告，路径由 KNOWLEDGE_POC_DIR 指定；临时目录可能被系统清理。报告保存候选、融合、最终上下文、来源范围、状态和评分分母，避免只留下一个成功率。

最新烟测发布为 `93692b7034ec4a3db30f9c28f8c258b5`，报告在 `/tmp/niuma-crew-knowledge-poc/smoke-93692b7034ec4a3db30f9c28f8c258b5.json`。原始路径不是工程运行依赖。

两次真实回答及实际证据分别保存在同目录的 `answer-b4250c350a864191860e5ce8bb39adae.json` 与 `answer-38e249e520014bc48f185da8d9b7534c.json`。可用模块入口的 `ask` 命令复现数据链路，但再次调用需要相应数据流授权，不能沿用本轮已用完的两次额度；模型输出也不保证逐字相同。

实际检查：`make verify-knowledge` 的 19 项定向测试和组件烟测通过，含跨进程重开与分词器/词典摘要不匹配拒读；`make lint-backend` 通过（247 个 Python 文件格式检查、22 个入口类型检查），文档链接检查通过。完整后端回归收集 684 项，沙箱内 667 项通过；17 项因本机端口绑定被禁止而失败，在允许本机端口的环境补跑均通过。之后新增的两项 POC 测试均纳入最终 19 项定向通过，不将分批结果写成一次全量通过。
