# 组织资产

一份好用的整理模板、一套排查问题的步骤、一组可靠的参考资料，都可能替团队省下重复准备的时间。平台希望让这些积累有地方保存，有人维护，也方便其他人用起来。

## 把经验整理成可用的方法

先从反复遇到的工作入手，留下完成它所需的条件。

| 积累       | 整理时需要说清楚                             |
| ---------- | -------------------------------------------- |
| 工作经验   | 适合处理什么，输入和成果有什么要求           |
| 方法与模板 | 按什么步骤做，容易遗漏什么，有哪些示例       |
| 业务资料   | 内容来自哪里，适用于什么范围，怎样更新       |
| 工具用法   | 需要哪些操作，使用什么工作连接，访问哪些对象 |

例如，整理会议纪要的经验可以包含行动项模板、遗漏检查方法和示例。后来的使用者交付本次材料，就能沿用这套准备。

## 用员工把资源组织起来

共享员工承担一类工作，把岗位要求、技能、知识和工具组合起来。多位成员使用同一位员工，维护者统一调整方法与资源，减少每位使用者分别配置的负担。

方法和资料分别维护，又能按不同岗位组合：同一份报告模板可以供多个员工使用，一份业务资料也可以服务不同任务。这样既能复用共同内容，也能保留各岗位的分工。

维护时需要知道谁负责、改动影响哪些员工，以及后续怎样检查效果。具体保存和版本规则见[配置说明](../reference/configuration.md)。

## 工具和工作连接按组织资源使用

接入平台的工具和工作连接，按组织共享资源管理。即使使用你个人申请的 API Key，只要将连接装配给员工，其他成员使用这位员工时，也会通过该连接调用工具，使用对应账号的权限和额度。

管理员决定哪些员工可以使用这份连接、允许执行哪些操作。成员无需各自配置账号，密钥本身也不会向其他成员展示。

## 让使用反馈回到方法中

资产沉淀的目标，是把“使用—发现问题—修正—验证—复用”连起来。某次统计漏了一页数据，就应追问是否缺少分页检查；某类回答反复需要人工补充，就应考虑把必要要求写进方法。

经过核对的改进可以进入岗位指令、技能或知识资料，具体案例则保留发生条件和验证依据，方便后来的人理解。目标是让同类问题少出现，让下一位使用者少走弯路。
