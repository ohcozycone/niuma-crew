# Agent 与执行宿主：怎样协作而不互相接管

本文解释[后端模块](modules.md)中最重要的一条运行边界。目标是让 SDK 变化局限在适配器，同时保留取消、授权、预算、过程保存和恢复。这里的执行宿主，是负责启动、看护并结束处理的应用代码。下文保留设计讨论的协议示意；实际签名以[agent_runtime/contracts.py](../../../backend/app/agent_runtime/contracts.py)为准，包含 guard/start_model/start/finish/report_content/checkpoint_saved，当前边界已实施。

## 1. 先用一个实际例子划线

Agent 想读取一种工作方法，再请求模型继续回答：

1. Agent 判断需要读取方法。
2. 调用运行控制的动作开始方法。
3. 宿主确认仍允许运行、方法在范围内、预算足够，并保存开始记录。
4. 保存成功后，适配器执行实际读取。
5. 适配器报告普通结果，再继续请求模型。
6. 得到完整候选答复后返回给协调器；应用共享发布流程决定能否交付。

Agent 决定下一步工作，宿主管理这次处理的执行资格与记录，请求与共享流程管理业务提交。模型提出“读取”只是请求，不是已经读到资料的证明。

## 2. 最少需要哪些边界类型

集中放在 agent_runtime/contracts.py，不为每个类型建文件，也不在 execution/contracts 复制这些类型。当前实现文件直接放 agent_runtime，不再嵌套 langchain_adapter 目录：

| 类型                                    | 包含什么                                                         | 为什么需要                                        |
| --------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------- |
| AgentRequest                            | 已选输入、岗位与公司指令、允许的方法内容、当次模型配置及恢复引用 | 不把 Run ORM、员工服务或 HTTP 请求交给 Agent      |
| RuntimeControl                          | 检查、动作开始结束、普通内容报告、存档引用通知                   | Agent 需要受控协作，但不能取得全部宿主能力        |
| ContentUpdate / ActionStart / ActionEnd | 普通字符串、类型、ID、用量和安全详情                             | SDK 对象必须在适配器内转成普通数据                |
| AgentOutput                             | 候选正文、已知用量，以及当前专业执行器需要的可选 JSON 数据       | 宿主不解析 SDK 最后消息，专业数据由对应发布器校验 |
| 明确边界异常                            | 用户停止、宿主保存失败、引擎不能恢复等原因                       | 及时停止后续动作，不把内部异常原样公开            |

AgentOutput 的专业 JSON 只服务现有 CI，接收方必须用 CI 契约验证，不在 execution 随意解释或落成通用结果仓库。普通 Agent 不填该字段，不因此建设插件系统、多产物协议或任意对象透传机制。

执行协调器实际只需要一个已准备的异步执行函数。conversations/preparation 把普通 AgentRequest 或 CI 专业输入绑定进去，协调器无需知道二者请求字段的区别。

## 3. 受限运行控制的形状

```python
class RuntimeControl(Protocol):
    async def check_allowed(self, resources=()) -> None: ...
    async def begin_action(self, action: ActionStart) -> str: ...
    async def report_content(self, update: ContentUpdate) -> None: ...
    async def finish_action(self, action_id: str, result: ActionEnd) -> None: ...
    async def checkpoint_saved(self, reference: str) -> None: ...
```

这是一份边界草图，最终参数在 P1 根据实际调用方收敛。具体实现为 execution/control.py 的 RunControl；不公开 store、database、auth、request 或 checkpoints 对象。

begin_action 在短事务内完成仍可运行检查、已冻结预算扣减和动作开始记录。原有 reserve_model 与 start_action 的必要操作可以合并，避免授权、记账和发出调用之间出现多段不清楚的约定。

预算确认和开始记录失败，不能发出模型或工具调用。外部调用完成但结果保存失败，也必须停止后续动作，不能静默继续。

这是 Python 代码之间的维护边界，不是进程隔离或任意代码安全沙箱。当前适配器仍是受信应用代码；不承诺一个许可对象就能限制其所有网络行为。

## 4. 进度如何跨过边界

| 步骤                                               | 谁负责                                                   |
| -------------------------------------------------- | -------------------------------------------------------- |
| 识别 AIMessageChunk、SDK 节点、模型轮与工具请求    | agent_runtime/streaming.py                               |
| 拼接片段，处理完整响应覆盖和迟到片段               | 适配器                                                   |
| 标记哪些普通文字可作为当前回复草稿                 | 适配器报告规范化内容；业务部分输出政策由共享发布流程确定 |
| 限制大小、缓冲、保存频率、动作归属和终止后拒绝更新 | execution/control.py                                     |
| 按状态选出页面应显示的正文、步骤和完整性           | conversations/queries.py                                 |
| 展示 Markdown、步骤、状态与操作错误                | 前端回复组件                                             |

适配器得知一轮模型结果实际是工具请求后，要把对应文字归为过程，而不是让前端判断 has_tool_calls。最终答复还要通过 SDK 完成判断和业务发布，不因流结束或出现一段文字就宣告成功。

运行中可见内容来自已保存进度；SSE 不直接转发未提交 SDK token。保持当前快照观察方式，不引入第二套实时事件事实。

SDK 解析迁走后，剩余普通缓冲、限制和恢复是 RunControl 的内部状态，合入 control.py，不保留独立 progress.py。协调器决定刷新时机，store 持久保存；Store 返回普通恢复数据，由控制对象自己的方法恢复，不修改其内部字典。

## 5. 授权为什么要检查多次

conversations/authorization 组合现有模块规则，不取代它们：

| 时点       | 检查目的                               |
| ---------- | -------------------------------------- |
| 接受输入   | 当前用户、归属、员工及所选能力是否允许 |
| 启动或恢复 | 排队期间身份、装配、连接是否已经变化   |
| 外部动作前 | 此次资源、当前能力和预算是否仍允许     |
| 长等待期间 | 用户撤销、停用或停止后及时收束         |
| 发布之前   | 防止权限变化后仍交付不再允许公开的结果 |

动作开始/结束结构包含明确资源 ID。RunControl 从成功激活动作恢复已经使用的资源集合，后续检查合并“已激活资源＋此次申请资源”；发布前从持久动作重新核对，不能只检查当次参数或相信内存集合。

共享规则并不意味着只检查一次。最终本地授权检查使用发布事务当前 Session；涉及远端 CI 来源的复查留在执行器返回前、业务事务外，不在数据库写锁内等待网络。

运行控制通过注入函数询问权限，不把 Actor 或完整授权服务交给 Agent。员工装配规则仍由 agents 提供，CI 仓库与来源规则仍由 CI 提供。

## 6. 恢复能力如何注入

bootstrap 构造 LangChain 适配器时注入其专用 checkpoint 读写资源。Agent 不通过 RunControl 取得它，也不沿 Store 访问其他数据。

- 适配器保存、解释 SDK 状态，形成新存档后报告不透明引用。
- Run 保存当前引用、冻结协议版本及是否允许恢复。
- 协调器始终调用同一个已准备执行函数；适配器内部决定继续执行、返回已完成候选或拒绝恢复，不增加第二套恢复探测协议。
- 已知旧格式按明确兼容代码读取；未知格式报告不能恢复，不能白纸重跑。
- 当前只有一个 SDK，不增加引擎注册中心；未来多引擎成为实际需求时再加标识与路由。

逻辑边界不要求拆数据库文件或拆进程。具体存档仍沿用既有配置位置；本次没有改变数据目录的产品要求。

## 7. 三种恢复情形

| 情形                                        | 如何处理                                                         |
| ------------------------------------------- | ---------------------------------------------------------------- |
| 普通 Agent 尚未完成，存档可信且有待处理节点 | 继续原 Run，保留开始时间、预算、动作身份与冻结输入               |
| SDK 已完成，业务尚未提交，Run 仍活动        | 验证完成标记、归属、最终答复和授权，只补业务发布，不再次调用模型 |
| 存档丢失、不可信或专业流程不支持恢复        | 明确 interrupted，保留历史，用户可新建重试                       |

当前已有真实测试覆盖第二种情形；删除 RunResult 不改变这个恢复依据，因为现有 RunResult 原本也在业务发布事务中才产生。

Run 已提交成功或失败时，只读取既有终态，不因存档里有完整文字而改写它。CI 当前不支持自动恢复；专业 report 字段出现也不等于成功交付。

## 8. 完成与保存失败

AgentOutput 是候选产出，不是业务成功。协调器通过注入回调把它交给 conversations/publication 中的 PublishRun；共享发布流程在一个事务中重新检查状态和授权，写 Message、CI 数据、Run 终态和活动占用。

当前实现的发布失败策略是：事务回滚、停止后续调用、宿主降级，待存储可写后把相关 Run 收束为 failed/persistence_unavailable。**本次先保持该策略，不暗中承诺同进程自动重试候选发布。**

如果进程恰在业务提交前被终止，重启后仍活动的普通 Run 可按可信完成存档补交。它与已经被失败收束的 Run 是不同情况。

未来若增加自动补发布，要单独规定候选保存依据、次数与退避，保证只重做业务事务而不重发模型。本次不建立 outbox 或通用重放框架。

## 9. CI 执行器如何共用控制

CI 保留自己的受控取证流程，使用同一 RuntimeControl 记录模型、方法、MCP 和验证动作。专业过程通过用例提供的 save_diagnosis 函数保存到 CiDiagnosis，该函数和通用动作保存一样需要等待成功；在同一短事务中先核对 Run 仍为 running，只写允许的有界过程字段，推进专业及观察版本。它不得写 report、feedback 或 delivered，终态后拒绝迟到进度。

CI 执行器负责证据和报告含义，execution 只知道动作与运行是否允许继续。候选报告经过专业校验后返回，发布前阶段仍为 validating/ready_to_publish；PublishRun 才能同时写 report、delivered、正文和终态。现有 CI 结束前提前保存 report/delivered 的代码必须一起改掉。

普通失败或用户取消的终态正文必须来自执行器或控制对象明确提供、符合部分输出政策的回复片段，不能兜底挑最后模型动作的文字；撤权不新增可见正文。过程仍可按授权查看。共享发布流程再次执行本地授权和原子交付。

不要求 CI 先迁成普通自由 Agent，才算运行边界清晰。两个算法共用队列、时限、控制与发布保证已经足够。

## 10. 如何证明隔离真的成立

1. 用内存 RuntimeControl 运行真实 SDK 适配器，验证它不需要业务数据库和身份服务。
2. 用假执行函数测试队列、停止、超时、撤权与发布失败，验证宿主不需要 SDK。
3. 检查进度、控制、协调器不导入 SDK；Agent 不导入业务 ORM 或访问 control.store。
4. 保留真实 SDK 的方法加载和流关闭测试，以及子进程崩溃补发布测试。
5. 将检查放入现有测试与静态入口，不只在文档中写禁止依赖。

具体阶段与验收见[实施计划](migration.md)。

共享准备、授权和发布不依赖 API；协调器取得的是 bootstrap 注入的函数或实际协作者，不从 api/routes/conversations/service 导入实现。请求与后台分工见[服务归属](service-boundaries.md)。
