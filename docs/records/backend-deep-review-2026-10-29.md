# NiumaCrew 后端全面审查报告

评审开始于 2026-10-29，完成于 2026-10-30，均为北京时间。本文检查当前工作区源码，未修改业务代码，也未操作开发数据库。建议尚未实施，不能将本文当作修复验收记录。

## 1. 先说结论

当前后端适合继续保持按业务能力组织的模块化单体。员工、技能、模型连接、对话内容、运行调度和 Agent 循环已经有实际的所有权边界；模型与工具调用也没有散落在 HTTP 路由中。没有足够证据支持为了套用某个架构模式，全面重建目录、拆微服务或给每个数据库表增加 Repository。

本轮确认了九项问题。最应先处理的是：普通聊天在撤权与输出超限同时发生时，失败分支仍可能交付新的部分正文。文件配额拒绝后的磁盘残留、普通成员读取全局沙箱状态，以及个人连接页刷新 404，也有可重复的隔离实验。它们说明当前更需要补齐跨边界的失败场景，而非先移动大量文件。

结构上的后续重点是两处小范围职责环、跨模块字典的类型契约、逐项读取造成的重复查询，以及已经落后于代码的现行文档。文件长短只能帮助定位阅读重点，不能独立证明职责过多。

## 3. 全局架构实际怎样工作

### 一条回复经过哪些地方

这里的 Run 是一次处理尝试；Message 是用户输入或助手回复；checkpoint 是 SDK 继续执行所需的内部存档。三者承担不同责任，不能混用。

| 顺序 | 谁负责                        | 实际行为和原因                                                                                                   | 源码入口                                                                                                                          |
| ---- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 1    | HTTP 路由与对话请求服务       | 解析输入和身份，核对重放键、目标、权限与容量，在同一事务保存输入、空助手消息、Run 和对话绑定；不在请求里执行模型 | [请求服务](../../backend/app/conversations/service.py) L65 至 L224                                                                |
| 2    | conversations                 | 固定本轮员工指令、全员规则、技能/工具、模型修订和预算，给后台准备执行函数                                        | [准备流程](../../backend/app/conversations/preparation.py) L59 至 L153                                                            |
| 3    | execution                     | 持有单机进程锁，领取排队记录，看护取消、总时限和当前许可，记录动作与预算                                         | [调度器](../../backend/app/execution/scheduler.py)、[协调器](../../backend/app/execution/coordinator.py)                          |
| 4    | agent_runtime 或 ci_diagnosis | 普通聊天运行 SDK 模型/工具循环；CI 运行固定 GitHub 取证流程；两者返回候选结果                                    | [普通执行](../../backend/app/agent_runtime/langchain.py) L109 至 L232、[原CI 执行（已退役）](../reference/ci-diagnosis/README.md) |
| 5    | conversations                 | 同事务写入终态、正式正文、专业报告或输出文件关联，并释放活动占用                                                 | [发布器](../../backend/app/conversations/publication.py) L33 至 L86                                                               |
| 6    | 查询与 SSE                    | 从已提交数据库状态生成相同的回复视图；刷新、重连和离开页面不重新启动模型                                         | [查询](../../backend/app/conversations/queries.py)、[SSE](../../backend/app/api/conversation_streaming.py)                        |

这种划分有现实依据。对话模块决定内容怎样成为一条正式回复；执行模块决定一次尝试怎样被可靠运行；Agent 模块解释 SDK 的消息和工具往返。将三者合成一个“大 AgentService”会把消息、授权、异步任务和供应商协议混在一起。

接受时固定内容，动作前检查当前许可，也是合理的区分。员工停用、会话撤销或连接修订变化后，旧快照不能继续授予权限。当前成功发布路径会再查许可；F01 是失败部分正文路径没有遵守同一规则。

### 模块引用如何判断

完整导入位置见[依赖清单](backend-deep-review-2026-10-29/evidence/dependency-summary.json)。它来自 Python AST，包含函数内导入，表达静态引用，不是运行时调用次数，也不能覆盖任意动态加载。

| 引用关系                                                        | 当前判断                                                                                                 |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| bootstrap 同时认识 HTTP、业务服务、数据库和运行器               | 合理。它就是组装具体实现和管理生命周期的入口                                                             |
| api 调用业务服务；conversations 组合员工、模型、文件、CI 与执行 | 合理。跨能力接受和交付需要集中协调；依赖多不能直接等同于职责混乱                                         |
| execution 引用 agent_runtime.contracts 和 tools.contracts       | 是普通数据及受限操作契约，未把 SDK、HTTP 或对话 ORM 带入执行核心；应区分契约引用与实现引用               |
| skills 查询 AgentSkill、model_connections 查询 Agent/活跃 Run   | 当前用于兼容校验和删除保护，属于同库数据完整性协作；没有因此调用多个各自提交的保存服务                   |
| infrastructure/database/models.py 反向导入业务模型              | 仅为元数据注册，迁移从此加载全表；不是数据库机制运行时拥有业务。这个窄例外应继续保持可见                 |
| agents.schemas、tool_grants、service 形成文件职责环             | 值得整理。输入结构放在工具许可实现里，工具许可又回调员工服务；局部导入避免初始化出错，但没有消除知识往返 |
| tools.definitions 与 tools.service 双向引用                     | 值得整理。HTTP 头校验、stdio 定义和服务身份等规则放在两种管理服务之间，导致相互借函数                    |

最后两项见[精确文件引用环](backend-deep-review-2026-10-29/evidence/file-import-cycles.json)。它们包含函数内导入，本轮启动与测试并未因此失败，不能写成“当前存在循环导入崩溃”。更合适的改法是提取小范围输入契约与纯校验，保留现有业务所有者。

### 数据和事务边界

正式历史来自 Message；Run/RunAction 保存处理状态与实际动作；CI 报告和反馈由 CiDiagnosis 保存；SDK 恢复单独读 checkpoint。文件字节及技能不可变资源在磁盘，数据库持有关联和摘要。实际表和约束分别在所属模块 models.py 与 0001 至 0011 迁移中，未集中成一个业务模型总文件。

SQLite 写路径用短事务，并在有竞争的先查后写操作前取得写入资格。模型、MCP、密码计算和沙箱远端创建不放在业务写事务内。这里的 `reserve_writer` 解决的是 SQLite 快照升级顺序，不应在重构时当作多余 UPDATE 删除。[事务机制](../../backend/app/infrastructure/database/transactions.py)、[会话机制](../../backend/app/infrastructure/database/session.py) L55 至 L66。

同库的消息、状态和发布可以原子提交，数据库与磁盘目录替换却不能据此宣称具有断电原子性。技能目录目前对 Python 异常做回滚，blob 为旧 Run 保留字节；文件服务则先落盘再登记。F02 正是后者在“已知拒绝”情况下未清理残留的问题，与不可预知的进程崩溃应区别处理。

## 4. 逐模块内部分析

以下逐项覆盖全部 15 个应用模块，顶层文件和辅助工程另列。每项既说明实际责任，也说明哪些地方值得保留、哪些地方适合调整。

### 4.1 api：把浏览器请求翻译成业务操作

`dependencies.py` 解析当前身份和服务依赖；`security.py` 处理浏览器来源、媒体类型、体积和响应安全头；`errors.py` 转换应用错误；`rate_limit.py` 做进程内限速；`frontend_delivery.py` 交付静态应用。routes 按能力分文件，对话复杂请求另用 router/service/streaming 三个文件，组织与变化原因相符。[模块入口](../../backend/app/api/README.md)

路由整体没有承担模型循环。同步数据库操作放同步路由，异步上传和 SSE 对同步操作显式转线程。对话请求服务虽然位于 API 目录，却接收 Actor 和普通参数而非 FastAPI Request，后台也不导入它。这是围绕请求命令的协作，不应只因用了数据库就机械搬走。[对话请求服务](../../backend/app/conversations/service.py) L42 至 L65、[文件入口](../../backend/app/api/routes/files.py) L18 至 L35。

需要先修 F03 的状态入口权限和 F04 的页面路由遗漏。静态交付的页面白名单与前端路由分两处维护，新增页面容易只改一端；应加已支持页面路径的契约检查，同时继续让不存在的 API/资源返回真实 404。现有测试在接口错误脱敏、来源拒绝和响应协议方面有价值，不等于每个新增页面都已覆盖。

### 4.2 auth：确认“是谁”，再判断“能做什么”

`actor.py` 是身份数据；`permissions.py` 是纯能力和资源归属规则；`models.py` 保存账号、会话和外部身份；`service.py` 管登录、撤销和会话时效；`github.py` 处理 OAuth；`config.py` 管来源与会话配置；`cli.py` 维护本机管理员。文件划分清楚，没有把 Cookie 读取塞进纯权限判断。[身份模块](../../backend/app/auth/README.md)

密码验证在写事务外，写入时再检查原账号条件；数据库存 token 摘要而非原 token。后台会话验证不会自己续长用户闲置期限。GitHub 身份通过提供方用户 ID 关联，不能因用户名相同就合并。[登录与会话](../../backend/app/auth/service.py) L88 至 L177、L179 至 L256。

当前 member 已能建立自己的对话和个人工具连接，guest 才只有公开阅读能力。auth README 的旧描述应修正，不能据它把当前 member 的正常操作误判为漏洞。F03 的问题在于“全局资源状态”借用了 member 已有的普通工具能力。会话、Origin 和 OAuth 测试覆盖了关键拒绝路径；本轮没有登录真实 GitHub。

### 4.3 agents：员工定义与能力装配

`models.py` 保存员工及其技能、工具和个人账号绑定关系；`access.py` 判断创建者编辑范围；`personal_tools.py` 维护使用者自己的工具绑定；`service.py` 处理员工与技能装配；`tool_grants.py` 处理工具装配和运行许可。该模块没有运行模型，也不解密模型 Key。[员工模块](../../backend/app/agents/README.md)

保存员工及关系使用同一 Session；关系重建的 created_at/revision 用于识别旧许可。配置管理与历史运行没有混成一张员工总表。全局目录已批量取摘要，和详情读取的需求有所区分。[装配保存与捕获](../../backend/app/agents/service.py) L124 至 L176、L311 至 L456。

F05 和 F08 均在这里。结构改善应先处理 `schemas → tool_grants → service → schemas`：把 GrantInput/GrantsInput 放到明确的输入契约位置，把真正的员工访问规则放在清晰的公共入口，减少靠局部导入借函数。`tool_grants.py` 的管理写入、快照捕获和动作许可有不同变化原因，可先补类型，再决定是否拆运行许可文件；不必把每个函数拆一个文件。

### 4.4 skills：当前方法、可编辑来源和旧版本字节

`parameters.py` 校验非秘密参数；`packages.py` 验证标准包并保存不可变 blob；`library.py` 管可编辑目录的锁、替换和异常回滚；`service.py` 协调导入、同步、更新与发布；`schemas.py` 定义输入输出，`models.py` 保存当前版本与来源关联。[技能模块](../../backend/app/skills/README.md)

三种状态分开有必要：可编辑目录给人和安装器维护，数据库保存平台已接受的版本，不可变字节保证旧 Run 还能用当时的方法。包内声明工具需求不会直接获得工具权限。路径穿越、符号链接、展开大小、压缩比和 YAML 重复键已有处理，F07 则说明损坏压缩流的异常分类仍不完整。[包读取](../../backend/app/skills/packages.py) L168 至 L245。

服务文件较长，原因包括真实的数据库与目录协作。优先可将 `sync_library` 的目录同步编排提取为独立职责，保留 create/update 的事务顺序；不能简单拆成几个会各自提交的服务。列表查询虽然延迟了部分正文，却仍加载 skill_md 和 manifest，摘要路径可以进一步只取需要字段。blob 长期保留是恢复取舍，尚未做总容量回收与生产备份恢复演练。

### 4.5 model_connections：模型配置和凭证保管

`presets.py` 定义已支持端点，`credentials.py` 管 Fernet 主密钥和加解密，`service.py` 维护配置、测试与运行解析，`schemas.py` 用独立白名单返回状态。配置修订与凭证修订分开；Key 不进入公开 DTO。[模型连接模块](../../backend/app/model_connections/README.md)

它读取 Agent 和活跃 Run 是为了删除保护，并未承担回答生成。`resolve` 在事务退出后解密，主动模型检查也在事务外。[连接服务](../../backend/app/model_connections/service.py) L147 至 L265。主动检查只证明模型目录认可凭证并包含目标模型，不能写成“Agent 已可正常完成工作”。

当前规模不需要进一步拆管理层、Repository 和实体映射。resolve 已有明确参数和返回类型；后续值得补的是 assert_current/_current 等校验入口的类型及修订可选语义，以及主密钥轮换和恢复操作的真实演练；本轮没有使用真实 Key 或调用模型供应商。

### 4.6 organization_rules：一份全员规则

只有 models、schemas、service 和包入口，共 99 行。id=1、正文长度和修订有数据库约束，更新通过预期修订控制竞争，相同正文不增加修订。[规则服务](../../backend/app/organization_rules/service.py) L28 至 L47。

规则的组合与冻结在 conversations/preparation，而非本模块或 agents；README 应改正归属。现在的目录规模与职责一致，没有实际理由增加 repository、规则引擎或独立 application 层。它是模型输入，不能替代后端权限；修改规则也不会自动改写已接受的 Run。

### 4.7 conversations：内容、上下文和交付

`models.py` 定义对话、消息、Run 关联和文件关联；`writes.py` 参与调用方事务；`queries.py` 生成历史、首屏、目录和回复；`preparation.py` 捕获本轮依据；`authorization.py` 组合持续许可；`publication.py` 交付；`files.py` 处理对话中的文件可见性和保留；`schemas.py` 描述对外视图。[对话模块](../../backend/app/conversations/README.md)

这是跨模块协调最多的业务位置，但每项协作都围绕接受或交付一条回复。正式上下文只选成功问答，失败片段与工具中间消息不会自动成为下轮正式历史。[上下文选择](../../backend/app/conversations/queries.py) L182 至 L211。正式历史也不依赖 SDK 存档继续存在。

先修 F01。再处理对话列表重复取员工、最后回复和活动回复：本轮实测 5 个对话产生 17 条 SELECT。`queries.py` 543 行并不自动构成坏设计；若问题目录继续增长，可以把问题检索与预览按完整职责拆出，同时保持同一读事务。`files.py` 应进入模块维护说明，避免新维护者遗漏来源资料与正式输出的区别。

### 4.8 execution：一次尝试的可靠运行

`admission.py` 登记、去重和准入；`models.py` 保存 Run/动作；`store.py` 做状态存取；`control.py` 提供受限操作和内容缓冲；`coordinator.py` 看护一次运行；`scheduler.py` 管队列、进程锁与关闭；`config.py` 管预算；`contracts.py` 管跨边界数据；`queries.py` 查内部记录；`errors.py` 定义失败语义。[执行模块](../../backend/app/execution/README.md)

普通 Agent 的模型/工具真正开始前，通过 start_model/begin_tool 在同一事务检查许可、扣预算并建动作，保存失败就不调用外部服务。取消、结果、步骤未知状态和恢复预算也有明确处理。进程锁保证的是单主机、单宿主，不具备跨主机租约；这是当前已声明的部署边界。

值得改善的是注入回调与快照的类型。比如 RunControl 的授权标注与实际 db/invocation 调用形态不完全一致，新增字段主要靠消费端发现。应给 prepare/authorize/publish 和工具快照补契约，保留注入协作，避免将其他业务模块 ORM 或 SDK 类型重新带入执行核心。[控制接口](../../backend/app/execution/control.py) L38 至 L117。

### 4.9 agent_runtime：解释 SDK，约束实际动作

`langchain.py` 创建与消费图；`middleware.py` 检查模型输入、动作和用量；`streaming.py` 合并片段；`skill_loading.py` 验证实际方法激活；`tool_calls.py` 执行工具门禁；`tool_results.py` 管结果游标和网页来源；`workspace.py` 路由虚拟路径；`sandbox_backend.py` 适配工作区；`resources.py` 注入资源操作；`checkpoints.py` 管 SDK 存档；`contracts.py` 定义普通输入输出。[Agent 模块](../../backend/app/agent_runtime/README.md)

模型说“已读取”不会直接生成成功动作；实际读取和持久化完成后才更新记录。SDK 流结束也不足以成功，还检查本 Run 的完成标记、待执行节点、最终 AI 消息、当前许可和必要来源。[完成检查](../../backend/app/agent_runtime/langchain.py) L169 至 L225。

这套细分与 SDK、资源和协议的独立变化对应，宜保留。后续优先补跨文件数据类型和维护入口，修正旧 `hooks.progress` 描述。网页读取门禁只能证明代码识别到目标、结构化提取和送模范围，不能证明页面内容真实完整或模型理解正确。运行层边界也只是受信 Python 代码的职责边界，不是进程沙箱。

### 4.10 ci_diagnosis：有范围限制的专业调查

`contracts.py` 定义目标和报告；`mcp.py` 限定固定 GitHub 只读方法；`executor.py` 串起有界调查；`service.py` 保存专业进度与反馈；`report.py` 检查来源并确定性排版；`models.py` 持有专业结果。它不只是普通 Agent 换一个提示词，保留专用流程有实际理由。[原CI 模块（已退役）](../reference/ci-diagnosis/README.md)

程序核对运行 attempt、失败 job、目标仓库和报告引用；最终再次确认目标版本。模型只能从已列出的失败 job 选择日志，报告行号必须落在真实来源里。专业的四轮模型、五次 MCP 业务调用预算属于既有契约，不能因没有复用普通 Run 计数就断言漏计。[原取证执行（已退役）](../reference/ci-diagnosis/README.md)、[原报告校验（已退役）](../reference/ci-diagnosis/README.md)。

`execute` 较长，后续修改调查策略时可按收集目标、读取日志、生成草稿和最终核验提取协作函数，保持整个顺序可读。不要把专业报告塞回通用 Run，也不要为了复用而开放任意 MCP 方法。引用格式合法不等于根因解释正确，真实模型质量仍需独立评测。

### 4.11 llm：小而明确的供应商适配

`config.py` 维护显式模型参数，`factory.py` 创建和关闭客户端，`usage.py` 解析用量，`errors.py` 分类已知上游错误。它不读业务数据库、不取员工、不自行发现 Key。[模型工厂](../../backend/app/llm/factory.py)

SecretStr 只隐藏常规输出，不能当作加密存储。默认重试为零，未知用量不按文字长度猜算。当前走 OpenAI 兼容 Chat Completions，不能从参数名推断支持任意供应商原生协议。128 行的规模与职责相称，本轮没有找到需要进一步拆分的依据。

### 4.12 tools：服务定义、账号目录和外部协议

`definitions.py` 管 MCP 服务定义与配置导入；`service.py` 管连接、凭证、发现、批准和调用；`models.py` 保存定义/账号；`catalogs.py` 维护展示别名修订及显式丢弃候选；`policy.py` 检查范围；`access.py` 检查账号可见性；`network.py` 管目标地址与传输限制；`contracts.py` 定义摘要和工具结果；adapters 适配 MCP HTTP/stdio，`stdio_runner.py` 补齐进程组后代回收，子进程环境限制由定义校验和 stdio 适配器承担。[工具模块](../../backend/app/tools/README.md)

服务说明、账号目录与员工许可的身份摘要在运行中继续复核，发现候选不会自动成为可调用目录。stdio 由 Run 持有，和 OpenSandbox 的脚本容器不是同一种资源。该模块不反向导入 Agent 或对话实现，员工关系仍由 agents 维护。

最有价值的整理是 definitions/service 之间共享的纯规则。例如 valid_header 放在连接管理服务，定义创建/导入再局部导入它；另一方向又借用服务身份和 stdio 校验。可下沉为明确的配置校验/身份规则文件，减少双方知识。`ToolService` 的目录批准与运行调用也有不同变化原因，先补明确契约，再按维护需要分离运行调用，避免建立泛化“工具引擎”。真实远端 MCP 认证和提供方格式兼容性未在本次验证。

### 4.13 files：字节与元数据的持久化

`models.py` 保存文件身份、归属、摘要和来源，`config.py` 管配额与保留时间，`service.py` 管存取和清理。HTTP 权限在 API 与 conversations/files 组合，底层 read 不是可直接公开的下载接口。[文件服务](../../backend/app/files/service.py)

写入使用临时文件、fsync、原子改名，再登记元数据；读取拒绝符号链接，检查大小和摘要。后台清理按引用保留数据。这些机制说明它不是简单的“上传目录”，重构时必须保留字节先于引用的顺序。

F02 应区分已确认回滚和提交结果未知：前者应及时删除本次 最终 UUID 文件，后者保留待核对，不能盲删可能已提交的字节。当前 service 只有约两百行，无需仅为形式拆分；可在修复时把一次保存的状态和清理责任表达清楚。

### 4.14 sandboxes：远端资源的申请与回收

`service.py` 保存申请意图与生命周期；`provider.py` 适配 OpenSandbox；`verify.py` 和 `cli.py` 提供环境验证与人工核对入口；`config.py` 管部署参数；`models.py` 保存资源债务。RunSandbox 管一次工作的句柄和关闭，SandboxService 管持久资源记录。[沙箱模块](../../backend/app/sandboxes/README.md)

远端创建前先记录申请，未知结果继续保留回收责任，不能把创建失败等同于远端肯定不存在。调用发生在事务外，部署身份用于避免错误回收其他服务资源。F03 暴露的是全局运维状态的读取权限，不意味着沙箱系统隔离本身已被突破。

本轮检查了申请、释放、未知资源核对和调用方顺序，没有连接真实 Linux/OpenSandbox。创建与清理的极端并发、远端取消、镜像限制和系统隔离还需部署级故障注入；这里保留为未覆盖项，不能把假提供方测试写成容器验收通过。

### 4.15 infrastructure：共用数据库机制

database 下的 `base.py` 定义 ORM 基础，`fields.py` 提供 UUID/UTC/JSON 机制，`session.py` 管连接和短事务，`transactions.py` 管写入顺序，`errors.py` 识别可确认的 SQLite 错误，`models.py` 仅注册元数据。它没有统一接管员工、技能或对话查询。[数据库模块](../../backend/app/infrastructure/database/README.md)

连接启用外键、WAL 和 FULL 同步；事务上下文负责提交、回滚和 Session 释放。数据库技术错误与业务冲突分别处理，未知完整性错误保留原语义。这些共用机制值得保留。不要把模型注册的反向引用误写成数据库机制依赖全部业务，也不要为了“依赖纯净”把各模块查询集中到此处。

## 5. 问题详情

### F01：失败部分正文没有执行发布前授权

模型调用开始后，员工被停用；周期看护尚未察觉，模型以 `finish_reason=length` 返回。中间件将正文作为 partial_text 带入失败，协调器生成 failed 候选。发布器只在 succeeded 分支授权，因此该失败正文仍写入 Message。

代码链为 [middleware.py](../../backend/app/agent_runtime/middleware.py) L81 至 L87 → [coordinator.py](../../backend/app/execution/coordinator.py) L122 至 L134 → [publication.py](../../backend/app/conversations/publication.py) L38 至 L54、L77 → [writes.py](../../backend/app/conversations/writes.py) L92 至 L105。本轮分别直接调用真实发布器，以及通过真实 SDK/协调器运行假模型复现。会话/工具许可撤销属于同一发布检查缺口的需补回归情形，本次完整 SDK 探针直接验证的是员工停用。

建议任意新增业务可见正文都在同一写事务内复核许可；撤权时不交付本次新增候选，保留已合法提交历史的既有语义。补员工停用、会话撤销及工具许可变化与部分失败组合的回归。[探针和输出](backend-deep-review-2026-10-29/evidence/runtime-review-probes.log)

### F02：配额拒绝后仍留下 最终 UUID 文件

[FileService.save](../../backend/app/files/service.py) L65 至 L75 先写临时文件并改为最终 UUID 文件；L77 至 L93 才检查账号和 Run 配额。拒绝后 finally 只删除旧临时路径，最终文件保留到孤立清理。已有会话的 member 可以上传，因此影响不限于管理员。

隔离实验设账号配额为 1 B，先成功保存 1 B，再三次提交 2 B；三次均被拒绝，数据库仍 1 条/1 B，磁盘却是 4 文件/7 B。默认配置中的同一顺序允许拒绝请求持续消耗磁盘，但仍受单文件、请求频率、剩余空间下限和保留期限制，不应描述为无限制写入。

建议显式记录 最终文件路径和提交结果，对确定未登记成功的本次文件做即时清理；提交结果未知则交给核对流程。保留崩溃孤立清理作为后备。[实验输出](backend-deep-review-2026-10-29/evidence/boundary-reproduction.txt)

### F03：全局沙箱状态使用了普通工具读取权限

`/api/sandbox-status` 只检查 tools:read，而 member 已有此能力。随后 SandboxService.resources 不按用户过滤，返回所有未销毁记录中的前 100 条，包含其他用户 Run ID、资源状态、回收次数、过期与错误信息。[工具路由](../../backend/app/api/routes/tools.py)、[角色能力](../../backend/app/auth/permissions.py) L36 至 L45、[全局状态](../../backend/app/sandboxes/service.py) L76 至 L93。

本轮用普通成员请求，实际看到管理员运行资源。按现行管理员运维契约，应使用单独的运维能力或管理员检查；若产品需要成员查看本人状态，则另外按 Run owner 过滤并缩小字段，不能直接复用全局列表。

### F04：前后端对页面路径的定义不一致

[前端路由](../../frontend/src/router.tsx) L139 已有 `/agents/:id/connections`；[后端 PAGE 白名单](../../backend/app/api/frontend_delivery.py) L14 至 L18 只接纳一层员工路径，子路由不能映射到 index.html。使用隔离静态目录验证，员工详情 200、个人连接页 404。

它影响 FastAPI 同源交付场景，不能推断所有反向代理部署都失败。建议补支持路径，并用实际页面路由清单核对刷新行为；保留 API、未知资源和错误路径的 404，不能无条件把一切路径都回退成首页。

### F05：反向筛选没有显式包含空绑定

[员工列表](../../backend/app/agents/service.py) L216 至 L222 用 `NOT IN` 取“没有可用模型”的员工。SQL 中 NULL 与非空集合比较得到未知，不能通过 WHERE。实验同时建立未绑定、可用绑定和后来停用三种员工，false 只返回后来停用，遗漏未绑定。

建议使用包含 `model_connection_id IS NULL` 的完整条件，或用对应的 NOT EXISTS，并测试非空和空连接库两个情形。公开列表没有声明该筛选参数，传参会被忽略，不能拿公开列表的实验当作同一个缺陷。[原始结果](backend-deep-review-2026-10-29/evidence/configuration-reproduction.log)

### F06：生命周期清理覆盖不完整

[bootstrap.py](../../backend/app/bootstrap.py) L52 至 L124 创建资源，L125 才进入 try/finally；构造中途抛错，已创建资源没有进入统一退出路径。L132 至 L137 顺序关闭 Runner、沙箱、文件、工具和数据库，前一步抛错又会跳过后面几步。

隔离探针注入 ToolService 构造失败，确认 Database 已创建却没有调用 close；注入 Runner.stop 失败，确认其他 stop/close 没有执行。它证明清理责任缺失，不等于证明每次启动失败都会泄漏远端容器或数据库连接。[探针输出](backend-deep-review-2026-10-29/evidence/bootstrap-repro.log)

建议按成功取得的资源立即登记清理，逐项独立尝试释放并汇总错误；可以采用 ExitStack/AsyncExitStack 或等价机制，明确停止顺序。测试分别覆盖构造中途失败、start 失败和每个 stop 失败。

### F07：损坏压缩流越过无效输入分类

[archive_files](../../backend/app/skills/packages.py) L227 至 L228 读取压缩内容时可能抛 zlib.error，L244 至 L245 的转换集合未包含它。保留正常 ZIP 目录、只破坏 DEFLATE 内容，即可得到原始异常。服务预览/导入直接调用此解析，API 没有额外转换。

真实预览接口在隔离 TestClient 中返回 500 / Internal Server Error。应补捕获已知解压异常并返回 package_error，保留未知编程错误的可诊断性；不应用一个宽泛 except 将所有服务错误都伪装成用户输入问题。[最小复现](backend-deep-review-2026-10-29/evidence/configuration-corrupt-zip.py)

### F08：工具集合没有变化也增加修订

[AgentService.update](../../backend/app/agents/service.py) L329 至 L343 以字段是否出现判断工具变更；[ToolGrantService.replace](../../backend/app/agents/tool_grants.py) L103 至 L107 无条件增加修订。实测空工具集合原样 PATCH 后修订 1→2，再 PUT 空集合后变为 3，与“不变不递增”的当前契约不符。

影响是无意义的编辑冲突和版本变动，本轮没有据此证明旧 Run 被撤权。建议对规范化后的工具身份、范围、账号模式和启停值比较后再递增，并保留真实变更的并发保护。

## 6. 文件归类、命名与拆分的具体建议

### 先保留什么

保留当前业务模块名及 `main → bootstrap` 入口。`agents` 表示员工配置，`agent_runtime` 表示模型/工具执行，两者虽都含 Agent，但生命周期不同，分开有帮助。`model_connections` 和 `llm` 分清凭证配置与供应商调用，`execution` 和 `conversations` 分清运行可靠性与消息业务，也应保留。

`models.py`、`schemas.py`、`service.py` 在各模块内复用同名是可接受的，包名已提供上下文。没有出现需要全局强制改成 `agent_model.py` 或“一类一个文件”的依据。纯内部 `__init__.py` 保持薄入口符合项目约定，不需要为了遵从外部 skill 全面建立再导出层。

### 哪些调整有明确收益

| 位置                                          | 建议                                                                                                                                 | 具体收益和边界                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| agents/tool_grants.py 的输入类与员工访问函数  | 把输入结构放到不依赖管理服务的契约位置，再按依赖方向整理员工查找与运行许可入口，保留调用方 Session；仅移动输入类不足以消除全部职责环 | 改动输入结构不再加载整套连接管理实现；保持员工装配所有权和同库事务             |
| tools/definitions.py 与 service.py 的共享校验 | 提取 HTTP 头、服务身份和 stdio 定义的纯规则                                                                                          | 消除相互借管理服务函数；不用泛化 utils 或全局“大公共模块”                      |
| skills/service.py 的目录同步                  | 下一次实质修改同步流程时，可独立为明确的同步编排                                                                                     | 将外部目录扫描与管理 CRUD 的变化分开；仍共享原保存/回滚边界                    |
| conversations/queries.py                      | 先批量读取列表摘要；问题检索增长时再独立拆出完整查询职责                                                                             | 优先减少实际查询，避免只是把 543 行分成几个文件                                |
| ci_diagnosis/executor.py                      | 按实际调查阶段提取协作函数                                                                                                           | 降低局部协议修改的阅读成本，保留调查顺序与专业预算                             |
| 跨模块 snapshot、binding、grant、资源回调     | 为高频边界补 TypedDict、dataclass 或 Protocol                                                                                        | 让字段和回调形态由工具检查，而不是靠阅读所有消费端；不要求所有内部变量都类型化 |

当前 Ruff 检查的是基础错误、未使用项和导入排序；mypy 的显式入口只有 9 个文件，未开启全仓严格类型检查。`lint-backend` 通过不能写成“140 个文件均通过严格类型审查”。建议先扩展工具许可、资源回调和快照边界，和修复真实问题同时推进。[工具配置](../../backend/pyproject.toml) L42 至 L59。

### 查询与容量改进

对话列表实测 5 条产生 17 次 SELECT，来自列表 count/取页及逐条员工、最后回复和活动回复查询。建议批量取摘要并用查询数回归守住，不先引入缓存。[查询位置](../../backend/app/conversations/queries.py) L214 至 L273。

skills 列表仍会载入 skill_md 和 package_manifest，summary/public DTO 最后丢弃。单主文上限为 128 KiB，100 条页的主文理论搬运量可达约 12.5 MiB；这是上限推算，没有生产压测。可为列表补明确列投影或延迟字段，详情与运行捕获仍正常读取完整内容。[技能列表](../../backend/app/skills/service.py) L343 至 L382。

## 10. 建议的实施顺序
