# 实施、数据迁移与验收

本文把[推荐方案](README.md)拆成可连续实施、独立检查的步骤。P1—P4 当前范围已完成，下面保留实施顺序与验收要求；实际检查、开发库升级、启动结果和未覆盖范围见[实施记录](../../records/platform-refactor-implementation.md)。

## 1. 实施原则与顺序

先隔开运行边界，再改存储，最后切换公开读取与前端。不要把目录移动、表结构、接口和页面状态同时压进一个无法定位问题的改动。

保留已有行为测试，修改与旧结构绑定的断言；不为纯文件移动编写镜像测试。对取消、幂等、数据与恢复等风险场景必须运行真实行为检查。

| 阶段 | 主要产物                           | 可以停下来的完整状态                |
| ---- | ---------------------------------- | ----------------------------------- |
| P0   | 语义、协议草图、映射和验证矩阵     | 用户可评审，业务尚未改变            |
| P1   | Agent/宿主隔离、状态与配置基础整理 | 旧外部 API 和旧存储仍工作           |
| P2   | 消息与 CI 数据迁移、发布与查询适配 | 新存储可通过旧 API 完成全部当前功能 |
| P3   | 新对话 API、统一助手视图、前端切换 | 正常客户端只使用新协议              |
| P4   | 删除限期旧入口、收尾文档与工程检查 | 没有无调用者的过渡实现              |

## 2. P0：先固定容易混淆的含义

1. Conversation 是交流容器，Message 是内容，Run 是处理尝试。
2. response_id 等于助手 Message ID，不创建新回复实体。
3. Message 可以在排队时存在；完整性与运行状态清楚区分。
4. 显式重试新建 Run/回复，输入复用；提交未知用原键确认。
5. 同事务接受与发布、取消优先与恢复条件形成验收场景。
6. 核对现有调用方与[逐文件去向](file-map.md)，不把旧方案的 Thread/Turn 改名当作实施前提。

## 3. P1：隔开 Agent 与应用管理

按依赖顺序：

1. 从真实调用提取 agent_runtime/contracts，建立普通内容与受限控制协议。
2. SDK 实现直接移至 agent_runtime，agent_loop 改 langchain；streaming 接管 SDK 片段与模型轮判断，不再嵌套适配器目录。
3. hooks 改为 control，普通 progress 缓冲并入；Agent 不再访问 control.store，专用存档在 bootstrap 注入。
4. Store 返回恢复数据，控制对象与适配器各自恢复，不直接修改内部字典。
5. 停止操作与既有领取、完成和恢复集中到 store 的调用方 Session 入口；不新增 lifecycle。撤销 Store.complete 发布薄包装，由协调器调用注入的发布能力。
6. 撤销 agents/execution.py：员工读取与装配规则并入 agents/service.py，快照/提示词/完整准备移至 preparation，跨模块授权组合移至 authorization。传调用方 Session，保留未就绪员工可编辑和装配重建识别。
7. driver 改为 scheduler，保留队列、并发、进程锁与故障收束。
8. 撤销 use_cases 目标目录：请求命令迁 api/routes/conversations/service，三项共享流程迁 conversations/preparation、authorization、publication；拆出 router 和 streaming，注册器显式导入 router。先完成共享归位，再移动请求编排，避免后台导入 API。
9. CI service 拆出 executor/report，服务类改 CiDiagnosisService；安装业务从路由归位，当前专业算法及限制不改变。

同步调整 bootstrap 的回调注入、请求与授权调用，以及员工身份/提示词测试的导入。函数归位不改变原提示词、快照内容、装配检查与事务语义；配置页读取未就绪员工仍应成功。

验收：用假执行器验证宿主，用内存控制验证真实适配器；SDK 加载、取消关闭、撤权和崩溃恢复仍成立。此阶段不修改表名、Message 规则或对外协议，不顺手放开自动重试。

### 3.1 可单独验收的配置与技术整理

这些整理使用现有 API 和存储，可以与运行边界分别提交，不与 P2 数据迁移捆绑：

1. 员工就绪与数量计算归 service，明确摘要/详情/公开读取；CI 工具数量取自统一声明，不重复写 3。
2. auth 会话判断复用，后台保持只读；连接版本复核支持调用方 Session，发布前授权读取同一事务。
3. select_context 改显式读取限制和返回值，由准备决定 CI 上下文和 RunSpec，不增加查询文件。
4. DatabaseConfig 回到数据库 session，usage 去 SDK 类型依赖；静态目录由配置解析并显式传入 frontend_delivery。configuration_summary 仅改文件名，URL 不变。
5. 配置大 Provider 拆回四个页面 Hook；外壳只读取导航摘要并提供轻量更新通知。
6. 编辑器显式注册 dirty/saving/discard，外壳统一离开保护，移除重复 beforeunload 和草稿猜测。
7. 员工/方法客户端与公开 DTO 归位，摘要和完整编辑类型分开，URL 参数联动由页面声明。
8. 搜索、收藏归导航，规则编辑归知识页面，CI 展示改 Setup；品牌原稿归 brand，更新构建引用。

保留页面、权限、原请求路径、草稿、配置修订、视觉和静态交付。验收覆盖未就绪员工编辑、公开白名单、资源计数、身份与查询切换、写入后摘要刷新、完整配置保存、编辑注册/清理和品牌构建。现有 ESLint 边界、mypy 检查范围和构建输入随路径调整；不能以当前静态配置推断新目录已经被检查。

## 4. P2：正式数据迁移

### 4.1 迁移前提

- 使用备份副本演练，记录当前 Alembic 版本、文件位置、表计数与外键检查。
- 停止接收写操作并退出执行宿主后备份；按现有 SQLite 操作规范处理 WAL，不能只复制一个仍在写入的主文件。
- 默认保留全部已有身份、配置、对话、输入、回复、动作、反馈和 SDK 存档，不因 demo 阶段自动删除开发数据。
- 历史 0001—0004 不改写，新增下一条迁移，已实施为 0005_message_delivery.py；保留 0001—0004 原有迁移链。
- P1 保持恢复格式。P2 仅修改业务保存关系，不批量替换 SDK 中的 app_run_id、完成标记或内部消息 ID。

### 4.2 迁移前校验

逐条确认：

1. 每个 ConversationRun 的输入属于同一对话且角色为 user。
2. 现有成功 Run 有对应 answer、有效正文和正确助手关联。
3. response_id、已发布消息 ID 与顺序没有冲突；失败占位也有唯一身份。
4. Run 与关联的用户、员工、来源及重试链一致。
5. CI 的 RunResult.structured、Run.progress_payload 和反馈按已知格式可解释；最终 report 若有多份必须一致。
6. 当前产品入口均可识别。若发现无业务承接者的未知来源或结果，停止迁移并报告 ID/原因，不静默丢弃。

### 4.3 迁移步骤

| 步骤 | 修改                                                                       | 保留或检查                                                     |
| ---- | -------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 1    | 重建 Message 内容约束，允许助手待完成正文为空                              | 用户原文、消息 ID、sequence 和时间不变                         |
| 2    | 已成功助手消息从 answer 填入 body                                          | 逐条核对正文，不读不到就填空                                   |
| 3    | 为失败、取消、中断或活跃的回复位置补建助手 Message                         | 使用原 response_id 与 response_sequence；有获准 partial 则保留 |
| 4    | ConversationRun 改为 reply_message_id                                      | 所有回复均存在；复合外键、唯一回复和活动部分索引保留           |
| 5    | 创建 CiDiagnosis，搬迁专业过程、报告与反馈；为 Conversation 增加 revision  | 专业 JSON 上限、来源、引用与反馈决定不丢                       |
| 6    | 删除 Message.result_id、旧占位/发布字段、通用 RunResult 与原 CiFeedback 表 | 所有外键、调用方与迁移断言已切换后才删                         |
| 7    | 移除 Run.progress_payload 的 CI 专业用途                                   | 通用普通内容仍从动作/进度读取                                  |
| 8    | 核对外键、计数、正文、状态、重试与历史顺序                                 | 输出可复核报告，失败不继续启动应用                             |

CI 执行器只报告过程和返回候选，移除发布前设置 report/delivered 的保存；反馈请求服务同事务推进专业与公开观察版本，迟到专业进度拒绝。

CI report 的结构化事实与聊天 Markdown 不做不明格式的相互猜测。已知 schema 明确转换；未知 schema 必须报告。正式 report 只从已成功交付的可信数据回填；旧活跃或失败 CI 的过程 payload 若提前带 report/delivered，不提升为正式报告，按真实 Run 状态和来源记录转换。无法无损解释时停止并输出审计项，原始候选留在迁移备份中，不能静默丢弃。旧活跃 CI 若不可恢复，按当前中断策略处理，不仅因 payload 有 report 就标成功。

SQLite 的表重建与外键启停要沿已验证迁移方法实施，并在真实旧库副本测试。仅用 ORM create_all 不能证明迁移正确。

### 4.4 发布和查询一起切换

PublishRun 直接写 Message.body 和专业结果，与 Run 终态和 active 释放一起提交。历史与上下文改读 Message 正文，移除 result join。

普通终态不可覆盖；Message 不另存运行状态；Conversation 新增 revision，接受、释放占用和元信息变化同事务推进，前端以此防止摘要回退。活跃草稿仍读已保存过程，不把空 body 误解释成内容丢失。

为 P3 保留的旧 API 可将新记录转换成旧响应，但不能继续维护旧表或双写正文。该适配有明确删除阶段。

## 5. P3：API 与前端切换

1. 实现 snapshot 同事务读取，并用并发注入证明其一致性。
2. 实现统一助手视图，历史、GET、确认与 SSE 共用；单回复、停止与观察外壳同时返回带版本当前摘要，验证终态后迟到摘要不能回退活动目标。
3. 发送改为 messages，控制与观察改为 response_id；旧路由暂调同一用例。
4. CI 读取和反馈同步迁到对话回复路径，带专业版本；不能遗漏 Run ID 消费者。
5. 保留 useConversation/useMessage，控制器与状态改读公开视图，删除前端模型轮选择逻辑。
6. 内部订阅改为 useResponseSubscription，待确认存储和控制器文件按实际职责改名。
7. 保持单订阅、身份隔离、连续历史窗口、稳定逐行快照和操作错误反馈。

前端页面继续 /conversations，无须制造深链重定向或批量替换 OAuth 返回路径。开发代理、静态回退、帮助文案与接口测试核对新增路径。

## 6. 待确认命令与短期兼容

浏览器可能还保存旧 pending 命令。仅改文件名不能丢弃它：

- 保留原请求键、原目标与规范化输入，识别旧存储版本。
- 新客户端先用兼容查询核对旧操作；找到后转换为新助手视图。
- 未找到但需重发时，沿可识别的旧操作语义使用原键；不能换键创造第二次工作。
- 旧键摘要按已知版本计算，不因 URL 改名发生幂等冲突。
- 不兼容且无法自动确认时，明确显示待核对状态，保留原文，不自动发送。
- 旧身份的 pending 数据不能交给新身份使用。

兼容入口只维持一个可验证切换窗口，P4 删除条件包括旧客户端退出、pending 处理策略和存储版本验证完成。没有客户端部署与保留范围信息时，不承诺具体日期。

## 7. P4：删除过渡并维护现行文档

- 删除无调用者的旧 /api/runs 和旧发送入口、execution/schemas.py 中旧 DTO、结果查询与测试专用正式接口；公开步骤归对话结构，不另复制一套内部 RunRead。
- 全文复核后删除没有消费者的 Popover；可选样式合并、登录动画内部改名和额外导出层不纳入本轮必需任务。
- checkpoint 测试图构造移至测试 helper；正式恢复读取不能误删。
- 更新各模块 README、architecture、reference、工程手册、学习入口和文档索引，使其描述实际生效结构。
- 方案保留取舍与未实施增量，records 记录本次真实验证，历史记录不改写当时名称和数量。
- 更新现有依赖检查，防止 SDK 再流入执行核心或前端公开结构。

## 8. 验证矩阵

| 方向     | 必须验证的行为                                                     |
| -------- | ------------------------------------------------------------------ |
| 接受     | 首条一起保存、同键重放、冲突拒绝、容量、并发活动唯一、完整回滚     |
| 消息     | 用户与助手 ID/顺序不变，失败回复存在，终态正文不覆盖               |
| 上下文   | 成功配对、预算裁剪、失败片段不进入后续输入                         |
| 生命周期 | 排队停止、运行停止、取消/成功竞争、迟到片段、总时限、队列超时      |
| 权限     | 接受/启动/动作/等待/发布各时点；游客公开字段与秘密隔离             |
| 进度     | SDK 工具内容不当作正文；持久化失败停止外部动作；未知用量不补零     |
| 恢复     | 原预算与时间；可信完成仅补发布；不兼容 interrupted；CI 不伪成功    |
| CI       | 真实来源、引用/覆盖、报告同事务、专业版本、一次反馈与迁移一致性    |
| API      | 同读取结构、准确回复目标、错误分类、SSE 撤权与只读重连             |
| 前端     | 单订阅、StrictMode、未知提交、旧闭包、身份切换、历史锚点和局部渲染 |
| 配置外壳 | 目录/详情隔离、摘要完整性、写入刷新、编辑注册与放弃、同步保存保护  |
| 迁移     | 新库/每种旧状态升级、外键、正文及反馈保留、失败回滚与旧存档可读    |
| 交付     | 文档链接、静态检查、受影响测试、构建、开发脚本与静态深链           |

工具沿现有入口：make check-docs、make lint-backend、make lint-frontend、受影响测试及 make build。类型检查是否覆盖新文件必须在配置中确认。真实上游与隔离替身结果分开记录，不将旧455项通过当成本次结果。

## 9. 回退与运行数据

P1 纯内部边界可按代码回退。P2 是数据结构变化，不能声称旧二进制可以直接读取新库：

- 演练中优先恢复已核验备份。
- 若需要 downgrade，必须明确迁移后新增记录如何还原为旧结果/正式消息语义，经过测试才提供。
- 生产切换失败时停止写入，按既定备份与恢复步骤处理；不静默重建数据库。
- 本次计划编制不会运行迁移、修改开发数据库、调用真实模型或部署。

每阶段验收通过后再扩展检查；没有新增变化或未解风险时，不机械重复全量测试。

服务位置修订的逐项去向和事务矩阵见[服务归属](service-boundaries.md)。API 请求服务提供当前 Session 的反馈组合；P1 保留现有记录和提交语义，P2 引入专业 revision 后验证专业/公开版本共同提交；其余简单配置路由不强制建子目录或 ApiService。
