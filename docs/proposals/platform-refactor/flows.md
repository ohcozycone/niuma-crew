# 完整流程：从用户输入到结果保存

本文将[目标模块](modules.md)、[API](api.md)和[前端](frontend.md)串起来。每个流程说明谁做决定、修改什么以及何时提交，避免只用名词连线。

## 1. 打开应用与保存配置

1. bootstrap 创建数据库、身份、配置、对话、CI、运行控制与具体 Agent，并启动唯一调度宿主。资源关闭仍由应用生命周期管理。
2. 浏览器启动主题与路由，读取身份；管理员、游客、登录分支沿现有规则展示。
3. Layout 保留共享外壳。进入员工、方法、模型连接或规则页时，页面按需要加载配置。
4. API 检查当前操作权限，配置服务在短事务中检查参数、资源关系和修订，保存成功一起提交，冲突或校验失败一起回滚。
5. 前端表单草稿与服务器修订分开；秘密不进入草稿。保存模型连接与显式测试可调用性仍是不同操作。

配置修改影响之后接受的 Run。已经接受的输入和方法内容不被新配置覆盖，但停用、撤销及连接变化仍可按现有规则阻止后续动作。

## 2. 打开已有对话

1. 路由选择 conversation_id，Provider 创建身份与对话作用域，控制器读取 snapshot。
2. 后端核对归属，在同一真实读取事务中取得摘要、最新窗口与当前回复，返回安全员工摘要。
3. store 分别按对话 scope_version 和回复 version 保存信息；页面无需等待所有配置目录。
4. 有活动回复时建立一条观察连接，无活动回复时只读历史。
5. 刷新、返回、悬停、历史跳转与自动重连都不发送新的工作。

尚未发送的新对话只是本地草稿，第一次 POST 才创建持久记录。

## 3. 用户发送消息：接受事务

| 顺序 | 负责者                     | 做什么                                                               |
| ---- | -------------------------- | -------------------------------------------------------------------- |
| 1    | 输入组件与 useConversation | 规范化内容，固定请求键、对话和员工目标，保存待确认命令               |
| 2    | HTTP 路由                  | 校验来源、格式、大小和身份，调用对话请求服务                         |
| 3    | ConversationRequestService | 先取得写入资格，再检查对话归属和请求重放                             |
| 4    | execution.admission        | 相同键同内容返回原结果；新请求检查容量                               |
| 5    | 对话与共享准备流程         | 检查空闲；读取有效员工、方法、规则、模型连接和专业输入，构造冻结依据 |
| 6    | conversations              | 创建用户 Message、空助手 Message，分配唯一顺序                       |
| 7    | execution 与关联写入       | 创建 queued Run 和 ConversationRun，固定输入与配置                   |
| 8    | 同一事务                   | 一起提交；任一步拒绝不留空对话、孤立消息或运行                       |
| 9    | HTTP / 前端                | 返回202及同一种助手视图；重放返回200；开始观察准确回复               |

新请求的执行输入包含按预算选出的成功历史和本次用户原文。使用相同请求键恢复提交时不得重新选择输入或更换员工。

调用模型和工具都在这个事务之外。返回202表示系统已经接受，不表示已经完成。

## 4. 排队、准备与启动

1. scheduler 持进程锁，扫描 queued Run，在全局和用户并发范围内安排任务；排队超时不启动 Agent。
2. coordinator 为一个 Run 计算剩余总时间，调用注入的 conversations 共享准备与授权回调。
3. conversations/preparation 从已冻结依据构造普通 Agent 或 CI 输入，解析当前允许使用的连接；不能把当前新配置偷偷替换成旧 Run 的依据。
4. execution/store 领取运行，保存 running 与首次 started_at。
5. coordinator 创建受限 RunControl，同时启动执行函数与停止/授权/刷新看护。
6. 观察端与请求端是否仍在线，不影响已接受运行。

调度器拥有“哪些 Run 可以开始”，Agent 拥有“本次运行下一步调用什么模型或工具”，二者不是同一种调度。

## 5. 普通 Agent 的内部循环

1. LangChain 适配器装配本次模型和受限方法资源。
2. 每次模型调用前，运行控制确认授权、预算与动作开始记录。
3. 适配器请求模型，消费 SDK 流，转换成普通内容与用量更新。
4. 模型要求读取方法时，先核对其在冻结且当前有效的范围内，保存真实动作，再读取资源。
5. 读取结果交回模型，继续原 Run；调用次数不代表对话问题数量。
6. 适配器只在可信完成标记、最终消息和待执行状态都满足要求时返回候选答复。
7. SDK 内部工具消息和系统指令不自动保存为聊天 Message。

内容报告经运行控制缓冲与持久化，再由观察接口读取。取消上游时应关闭流和网络会话，不仅停止页面更新。

## 6. CI 专用诊断

1. 共享准备流程捕获明确仓库和构建输入，核对员工装配与专业范围。
2. CI executor 验证构建身份，枚举失败任务，按既有上限读取实际日志。
3. 每个 MCP、模型和验证动作通过通用运行控制记录；专业阶段、调用摘要和脱敏来源在 Run 仍 running 时保存到 CiDiagnosis，不提前写正式 report 或 delivered。
4. CI 只允许模型引用实际读到并提供给它的资料，校验来源、任务、行号和覆盖。
5. 返回前复查构建 attempt 与 SHA 等来源依据，网络操作在业务事务外。
6. 形成经过验证的候选 report 和确定性正文，交给共享发布流程。
7. 当前仍不自动恢复 CI，也不把部分模型草稿当成功报告。

保留专业流程是为了真实证据约束，不创建第二套队列、时限或身份系统。

## 7. 完成发布：一次业务提交

PublishRun 取得同一业务写入资格，在一个事务中完成：

1. 重新读取 Run，已终止则直接返回，不覆盖旧结果。
2. 看到已接受停止时，以取消政策收束，拒绝迟到成功。
3. 使用当前事务复核本地身份、归属、装配、连接与业务发布条件。
4. 调用对话写入填写回复正文；专业成功则同时写 CiDiagnosis.report。
5. 结束未结束动作，保存用量、错误、Run 终态和时间；只采用明确获准的 partial，不从任意最后动作推断失败答复。
6. 释放 ConversationRun.active，推进回复观察版本和对话 scope_version；CI 成功在此时才保存 report/delivered。
7. 全部提交成功后，GET/SSE 才能观察到终态。

具体 flush 顺序可以满足外键要求，但提交边界不能拆开。任何故障均回滚；不能先标记成功再另发消息事件。

专业 report 与聊天正文在这次提交确定，之后普通重复完成回调不能改写它们。

## 8. 前端收到进度或终态

1. 历史、GET 和 SSE 都通过同一读取函数得到助手视图。
2. 控制器校验作用域，store 按 ID/version 合并，拒绝乱序旧状态。
3. useMessage 更新相应行，正文与步骤始终来自同一已保存快照。
4. 终态通知与停止响应同时携带提交后的带版本对话摘要；先合并新 scope_version，再清理匹配的活动观察，不能被迟到旧摘要重新挂回活动回复，也不能误清除新回复。
5. 正在看历史时只更新重合消息，保留阅读锚点；回到最新按需读取。

CI 只在专业版本变化或需要展开时读取专业数据，不随每次文字片段重新请求来源。

## 9. 停止与完成竞争

| 场景                         | 处理方式                                                   |
| ---------------------------- | ---------------------------------------------------------- |
| queued 回复被停止            | 停止用例原子结束 Run、保留回复记录并释放占用，不启动执行器 |
| running 回复被停止           | 保存 cancelling；看护中断外部调用，共享发布流程统一收束    |
| 停止先提交，候选答复稍后返回 | 发布看到 cancelling，不能提交成功                          |
| 成功已提交，停止稍后到达     | 返回原 succeeded，不改写为 cancelled                       |
| 停止请求网络失败             | 页面显示操作错误或继续核对，不擅自显示已停止               |
| 页面已切换回复               | 旧操作仍指原 response_id，不对新回复执行停止               |

停止是尽力中断已经发出的调用，不是撤回远端已发生行为。当前受控读取的未知结果仍需准确记录。

## 10. 提交未知、显式重试与内部重试

| 情形                          | 保持什么                                | 新建什么                             |
| ----------------------------- | --------------------------------------- | ------------------------------------ |
| POST 结果未知，原键重发或核对 | 原输入、原请求键；若已接受则原 Run/回复 | 不重复新建                           |
| 用户对失败末次回复点击重试    | 原用户 Message 和旧失败记录             | 新键、新 Run、新助手 Message、新关联 |
| 同一运行内模型调用的网络重试  | 原 Run 与总预算                         | 仅按显式策略记录实际调用尝试         |
| 服务重启继续可信未完成运行    | 原 Run、时间、冻结依据、已用额度        | 不作为用户新提问                     |

当前 SDK 自动重试策略不因重构默认放开；未来开启必须定义计费、次数与未知结果含义。重新输入相同文字是新提问，与按钮重试不同。

## 11. 撤权、超时与保存失败

| 情况                             | 结果与责任                                                   |
| -------------------------------- | ------------------------------------------------------------ |
| 用户登录失效或权限撤销           | 应用授权组合器拒绝；运行控制停止后续动作，发布前仍检查       |
| 员工停用、方法装配或模型连接变化 | 按现有变更规则终止，不改写旧冻结记录                         |
| 排队超时                         | scheduler 结束，未发生外部调用                               |
| 运行总超时                       | coordinator 中断；恢复使用原开始时间，不能重置额度           |
| 动作或进度保存失败               | 控制对象报告明确故障，不继续调用；宿主进入降级收束           |
| 业务发布事务失败                 | 所有业务写入回滚，不发成功终态；沿现有降级及失败收束策略处理 |
| 第二个执行驱动启动               | 进程锁明确拒绝；本次不宣称多 worker 能力                     |

数据库不可用期间不能假称已经成功保存 failed；待可写后才提交故障终态并释放占用。当前同进程故障收束不等于自动重试候选发布。

## 12. 重启与恢复

启动恢复先取得唯一进程锁，核对未终止 Run：

- 排队记录按剩余排队时限处理。
- 支持恢复的普通运行交给适配器判断存档是否可信。
- 可信未完成则继续原运行；可信已完成且 Run 仍活动则只补发布。
- 取消意图、授权变化、总时限和累计预算仍有效。
- CI 或未知格式无法恢复时明确 interrupted，不根据半份专业数据补成功。
- 已经终止的记录不被 SDK 状态改写。

已保存历史和专业报告不访问 checkpoint。删除存档后的历史读取测试仍应通过。

## 13. 专业反馈与外围流程

CI 反馈由对话与回复找到 Run，再调用 CI 服务检查成功报告和一次反馈约束；它只修改专业反馈，并在同事务递增专业和回复观察版本，不重新运行模型或改写答复。

身份切换销毁旧前端作用域；服务器仍执行真实权限。静态资源、压缩缓存、前端深链、开发代理、端口与资源关闭沿既有规则保持，不因新增 API 路径回退成错误 HTML。

调用路径的具体文件、请求服务与后台共享流程，以及各场景事务持有者，统一见[服务归属](service-boundaries.md)。SSE 的 HTTP 连接管理归 api/routes/conversations/streaming；后台准备和完成不调用 API 服务。
