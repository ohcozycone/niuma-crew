## 1. 基线与设计依据

当前以 0001 的十一张业务表为基线，保留 admin/member 与外部登录身份。目标仅扩展尚未实施的能力，不假定当前已有工具连接目录、真实知识库或技能制品仓库。

| 现有事实或既有要求                                                     | 对模型的约束                                                      |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 员工、技能、模型连接由不同操作维护，资源可以共享                       | 保留独立主体和明确引用，不复制共享内容到每个员工                  |
| 当前员工选择技能是集合，没有同技能多实例的明确需求                     | 保留 `(agent_id, skill_id)`，增加该关系自己的配置，不先改变身份键 |
| CI 已使用参数、范围与凭证，但配置分散在员工列和服务端                  | 让能力参数与授权有明确归属，同时保留既有证据校验                  |
| 普通聊天需要按需使用已装配技能                                         | 建立发现、加载和工具协调；不以发布中心为前置                      |
| 运行已经保存岗位、规则、模型与 CI 方法快照                             | 沿用本轮快照固定依据，避免为了历史留存重做所有配置表              |
| 知识助手已有多库管理、单员工单库、资料编辑、发布、引用、反馈和评测要求 | 为文档和发布保留不可变内容，为非聊天作业和回答依据建立独立记录    |
| 当前 Run 依赖真实对话与输入输出，执行资源应共用                        | 保留聊天 Run，知识后台作业有独立记录，共享准入与生命周期驱动      |

这些依据来自[现有 ORM](../../../backend/app/infrastructure/database/models.py)、[员工保存](../../../backend/app/agents/service.py)、[对话提交](../../../backend/app/conversations/service.py)、[CI 契约](../../reference/ci-diagnosis/data.md)、[后端架构](../../architecture/backend.md#当前架构)及[知识助手](../knowledge-assistant/README.md#结论与目标)。例子用于检验模型，不参与替代这些依据。

## 2. 先分清对象及其归属

| 对象           | 它保存什么                               | 谁使用它，怎样变化                                             |
| -------------- | ---------------------------------------- | -------------------------------------------------------------- |
| 数字员工       | 岗位、行为要求、展示与能力选择           | 管理员维护当前配置；对话保留自己的历史依据                     |
| 技能           | 标准方法与资源、参数规范和可选工具需求   | 多员工共享；修改影响后续新运行                                 |
| 员工技能配置   | 某员工是否启用某技能、参数和工具依赖映射 | 属于员工配置；解除不删除共享技能                               |
| 大脑           | 模型服务、能力类别与加密凭证             | 多员工或知识处理复用；不保存岗位或聊天记忆                     |
| 工具契约与连接 | 前者规定操作及参数，后者保存服务身份     | 内置契约来自代码，MCP 目录来自批准连接；连接可管理、撤销与轮换 |
| 知识资料与发布 | 原文版本、来源、处理依据和确定的可用集合 | 编辑不覆盖旧发布；员工只引用库和策略                           |
| 运行与步骤     | 本轮获准依据，以及实际加载、调用和结果   | 不随员工最新配置重写，不等同于模型自报的工作过程               |

“共享”描述资产复用，不意味着每个用户都能读取私有资料。员工、技能、大脑和工具连接仍是平台管理资源；知识库首版按创建者归属，运行内容遵守对话与资料范围。当前的 member 沿用现有公开展示权限，不因 GitHub 登录获得模型运行、工具账号或资料访问权。

## 3. 全局关系与基数

原目标关系图的技能/工具部分已过时，不再作为新方案实施依据；当前关系以下表与[标准 Skill/MCP 设计](../skills-and-mcp/README.md)为准。

[原 SVG（历史目标）](diagrams/agent-capability-model.svg) · [原 PNG](diagrams/agent-capability-model@2x.png)。当前外键、头指针和删除规则以[数据字典](data.md)为准；本次没有将旧图改画为已实施架构。

| 关系                                 | 本版采用的表达                           | 为什么                                               |
| ------------------------------------ | ---------------------------------------- | ---------------------------------------------------- |
| 员工 → 大脑                          | 可空单外键，多个员工可引用同一聊天连接   | 当前基数不变，额外绑定表没有独立职责                 |
| 员工 → 技能                          | 多对多；每对一份参数化配置，保留联合主键 | 配置确实属于关系，但不需要独立多实例身份             |
| 技能 → 内容制品/工具需求             | 当前制品指针与可选平台附加需求           | 原包不改写，需求只用于就绪检查，不授予权限           |
| 员工 → 工具许可 → 连接/获准工具      | 独立许可，技能配置可映射到已有许可       | 不配 Skill 也可使用获准工具，多技能复用同一许可      |
| 员工 → 知识库                        | 首版可空单库外键与使用策略               | 已有知识助手范围；系统多库、同库可供多员工引用       |
| 知识库 → 文档/规则/发布              | 各自一对多；发布通过选材关系固定文档版本 | 编辑、处理与上线各有变化时点，旧引用需保留           |
| 对话 → 运行 → 步骤                   | 一对多、一对多，沿用已有输入输出消息关系 | 一条消息可触发多次操作，重试是新的运行               |
| 运行 → 获准知识上下文 → 实际回答依据 | 每轮最多一份上下文和一份正式知识回答     | 允许访问不代表实际使用；实际证据和引用有独立复核价值 |

员工工具许可独立管理，不要求为每个 MCP 工具建立空技能。知识读取仍由员工资料绑定提供；这些许可与方法内容分别维护。

## 4. 保留与调整现有十一张表

### 4.1 保留的主体与边界

| 现有表                                          | 结论                             | 依据                                                                       |
| ----------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------- |
| `users`、`auth_sessions`、`external_identities` | 保留                             | 操作者、会话与登录身份不等于数字员工；沿用当前 admin/member 及 GitHub 绑定 |
| `organization_rules`                            | 保留全局单例                     | 当前全员继承同一份规则；不需要员工关联，也不放知识索引                     |
| `messages`                                      | 保留                             | 保存可见交流正文；不能与调度、错误和重试状态混合                           |
| `agents`、`skills`、`model_connections`         | 保留主体，做下述增量             | 独立归属与共享关系已成立                                                   |
| `agent_skills`                                  | 保留表名及联合主键，升级关系属性 | 参数与授权属于员工怎样使用技能，无须另起一套多实例模型                     |
| `conversations`、`runs`                         | 保留聊天与执行主体，增加必要依据 | 幂等、取消、历史及真实消息外键已工作，应复用                               |

岗位指令、示例任务和交付说明仍在员工表；展示数组不具备独立身份，不拆表。平台共享收藏仍在员工表。本版不引入个人收藏、租户、复杂分类或头像数据库。

### 4.2 现状与目标结构对照

| 位置          | 现状                                | 目标变化                                         | 调整依据与代价                                                         |
| ------------- | ----------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------- |
| 员工模型来源  | 连接外键与遗留 `model_id` 同时返回  | 运行和展示统一读取连接，P1 删除遗留列            | 避免双重表达；同批切换前后端，不保留旧协议                             |
| 员工知识配置  | 无                                  | 增加单库引用和策略；保持可空                     | 引用共享资料，不复制正文；须配合私有内容权限                           |
| 员工技能关系  | 仅选择与装配时间                    | 加启停、非秘密参数、修订号，授权仍用独立关联     | 关系开始拥有配置；写入需原子校验                                       |
| CI 仓库       | `agents.ci_repository`              | 移入对应技能参数；授权范围由工具授权明确保存     | 业务能力配置退出员工通用属性；迁移时双份角色分别校验，参数不能替代权限 |
| 员工/技能编辑 | 当前值覆盖，无预期修订              | 对员工、技能和关系增加条件更新修订               | 防旧编辑覆盖；这是并发控制，不是历史版本仓库                           |
| 模型连接      | 聊天连接，`updated_at` 拒绝配置变化 | 增加 chat/embedding、启停及配置/凭证修订         | 支持知识处理与每次调用前复查，额外版本号不保存旧密钥                   |
| 对话可见性    | 管理员可读平台记录                  | 增加 platform/owner 范围，私有知识准入前收紧     | 资料不会因绑定共享员工而公开；所有读取必须同步修改                     |
| 运行方法依据  | 普通聊天无通用技能；CI 已保存正文   | 新快照保存获准技能当前正文、修订、参数和工具依据 | 无需技能发布表，代价是重复存储与体积预算                               |
| 运行实际动作  | CI 专用 JSON；普通聊天无统一步骤    | 新增 `run_steps`；保留 CI 领域报告和一次反馈列   | 多步骤需要增量保存、排序与分页；不为统一而强拆当前受限结果             |

员工、技能和关系的修订在真实变更时递增。员工配置与其关联、授权一起保存；改授权也更新关系修订和员工修订。共享技能方法编辑不改写正在执行的快照；禁用技能、移除关联或撤权仍影响后续调用。

### 4.3 明确后置的内容

本版不建立技能发布审核中心、独立装配 ID 或不可变装配修订表。标准目录资源需要不可变内容制品及当前指针，以便旧运行回查原文件；它不是发布治理。每员工每技能一份配置继续保留。

这不是永久限制。出现上述管理需求或快照规模实测不可接受时，再增加相应对象。届时从本版稳定技能 ID 和关系迁移，不能直接改写历史快照。

## 5. 工具模型：标准内容、动态目录与实际许可分开

### 5.1 两类工具来源

内置函数、业务范围解释器和专业交付检查仍由受信代码登记。MCP 服务由管理员配置连接，通过标准工具发现取得名称、描述和 schema，审核后成为获准目录；不为每个服务手写 provider 或业务路由。

内容声明与授权分离。Skill 可选的工具需求帮助完成配置，但实际许可属于员工，既支持纯 Skill，也支持独立工具或组合使用。MCP 上游新增操作不自动扩权，已获准工具发生相关契约变化时停止该工具并要求复核。

### 5.2 最小新增实体

| 实体              | 保存什么                                 | 依据                                            |
| ----------------- | ---------------------------------------- | ----------------------------------------------- |
| skill_artifacts   | 不可变标准目录、来源、文件清单和内容摘要 | 只有正文/哈希不能取回旧资源；不建设完整发布中心 |
| tool_connections  | 连接身份、秘密、获准 MCP 目录与修订      | 动态发现和账号生命周期独立于工作方法            |
| agent_tool_grants | 员工对明确连接、工具和资源范围的许可     | 无需虚拟 Skill，多个方法可复用同一许可          |

旧目标 skill_tools/agent_skill_tools 尚未实施，由技能附加配置、依赖映射和独立员工许可取代。明确字段、外键与清理规则在[字段字典](data.md#工具定义连接与装配授权)维护，技能内容制品见同文技能章节。

### 5.3 实际权限与运行一致性

工具调用受用户身份、员工许可、上游身份、宿主固定的本轮范围和预算共同限制。MCP schema 不自动解释业务范围，优先用受限上游身份，必要时用受信范围解释器；不能用提示词伪装仓库级隔离。

运行固定内容制品和获准工具摘要，调用前复查许可、连接、配置/凭证及目录修订。秘密只在调用前解析；新连接和新权限不能透明进入旧运行。固定内容不使已撤销授权继续有效。

## 6. 知识模型：资产、发布、作业和回答各有归属

### 6.1 为什么知识需要版本，而技能暂不建设发布仓库

知识助手已有“编辑资料后构建发布、失败保留旧版、历史回答查原文”的要求。原文与派生产物会同时存在，必须知道哪些版本构成线上可用集合。因此文档版本、处理规则版本和发布是本版实体。技能方法和资源用不可变内容制品及运行快照固定，不需要复制知识发布审核流程；两者不能因为都叫“版本”就机械采用同一套治理。

### 6.2 新增知识实体及各自理由

| 表                            | 职责与新增依据                                                                   |
| ----------------------------- | -------------------------------------------------------------------------------- |
| `knowledge_bases`             | 资料范围、创建者、默认规则及当前发布；多员工可引用                               |
| `knowledge_groups`            | 库内一级分组，支持共享改名、排序和移动；分组不是权限或来源                       |
| `knowledge_sources`           | 稳定接入出处，与来源条目标识共同识别重复导入；首版仅手工和内置样例               |
| `knowledge_documents`         | 文档稳定身份与当前管理状态；同名不自动合并                                       |
| `knowledge_document_versions` | 不可变原文、标题和来源说明；修改不覆盖旧依据                                     |
| `knowledge_processing_rules`  | 不可变解析、切片和索引规则；重建与比较需要确切依据                               |
| `knowledge_source_blocks`     | 某原文版本与解析版本中的可引用区间；检索片段最终映射回这些原文块                 |
| `knowledge_releases`          | 固定选材、处理与产物的发布；成功后才能成为当前可用版本                           |
| `knowledge_release_documents` | 发布采用的文档版本及顺序；关系用外键保证，不在 manifest 重复维护选材数组         |
| `knowledge_jobs`              | 一次导入、构建或检索诊断尝试；共用状态、幂等、取消、额度与恢复，仍独立于聊天 Run |
| `knowledge_import_items`      | 导入作业内每个文件的操作与结果；支持部分失败及仅重试失败项                       |
| `knowledge_answers`           | 实际送模证据、引用和回答依据；与本轮获准资料分开，后续评测复用同一问答用例       |
| `answer_feedback`             | 用户对某份回答的判断与说明；不修改知识、运行成功状态或评测评分                   |

原先分别提出的导入批次、构建、试检索作业，收敛为有明确 `kind` 的 `knowledge_jobs`。三个类型都代表一次有界后台尝试；其目标只允许明确的知识库、来源、规则和发布外键，不使用任意资源类型/资源 ID。导入明细保留子表，构建产物归发布，试检索诊断是受限结果。这样共享准入和恢复不用在三张近似作业表间复制规则。

来源仍独立，因为它有稳定身份和条目去重职责；不提前增加 Wiki 凭证、游标或同步调度。索引是发布的可重建产物，不先建设检索切片业务表或构建资产中心。嵌入式向量存储和 BM25 后端在[Notion 选型清单](https://app.notion.com/p/409eab92f60081cfa7e1ca0e3b640f02)中作为待 Review 建议维护；不把旧草案的无向量库方案视为已采纳要求。

### 6.3 资料如何生效

1. 创建库、默认处理规则及来源；知识默认不对其他用户开放。
2. 原文件安全落盘后提交导入作业，逐项保存文档及内容版本；创建与替换明确区分，不凭文件名覆盖。
3. 创建固定选材与规则的发布候选，构建在事务外执行；构建成功只使候选 ready；用户显式发布时再以短事务切换当前发布，未发布前旧版继续生效。构建失败不污染旧版。
4. 员工保存单库与策略引用。接受私有上下文前检查发起人同时拥有库和对话，并把对话收紧为 owner 可见。
5. 运行固定库、发布及策略。实际读取记录步骤，正式回答保存真实送模区间和校验过的引用，之后仍能查原文。

`full_context` 在预算内加载固定发布全文；`hybrid` 结合关键词和向量检索，必须有匹配规则、模型和维度的索引。本轮按[知识库详细方案](../knowledge-assistant/implementation.md#实施与验收)完成混合闭环，全文可作为学习子增量，不是完整交付的替代或前置门槛；不在缺索引时静默降级。移组、改标签不改变已发布选材，换默认规则也不会自动上线。

### 6.4 问答与评测的衔接

本版核心结构先支持对话问答：`knowledge_answers.run_id` 唯一且必填，正文仍由对应消息保存，回答表管理证据与引用。评测随后使用独立的题集、批次和结果表，不伪造聊天消息。

评测阶段再显式扩展回答归属：增加 `evaluation_result_id`，将 run 引用改为可空，要求二者恰好一个非空；评测正文归评测结果，证据仍归知识回答。这样当前迁移不会提前引用尚未建立的评测表，也保留了既有[评测设计](../knowledge-assistant/README.md#核心数据与接口方案)的复用边界。

## 7. 普通聊天怎样消费这些配置

一轮运行接受时，后端从员工、当前技能关系、内容制品和独立工具许可读取本轮依据，固定用途摘要、资源摘要、修订、参数和获准目录。先把摘要给模型，需要时才加载正文；后端保存了全文快照，不等于将全部正文送进模型。

候选数量和快照体积必须有限，超限明确拒绝。标准资源保存在受控不可变制品，不能只记哈希而无法回查原文件；资源可读不表示脚本可执行，兼容范围见新设计。

模型选择技能后，宿主复查权限并激活；工具也可不依附技能使用，往返均由统一循环执行。显式选择必须生效或明确失败，不相关任务可以直接回答。`run_steps` 记录真实激活、模型调用、工具、知识读取和校验；允许目录仍在快照，不单建 `run_skill_bindings`。

知识许可进入独立的 `run_knowledge_contexts`，因为它有明确的库/发布外键与私有可见范围。上下文存在不表示已读取；实际使用与回答证据另记。实际检索无命中或资料不足也可正常回答，保留边界诊断且不编造引用；仅获准但未读取时不创建知识回答。CI 继续保留领域证据校验、报告及原一次反馈，旧 schema 1/2/3 不改写。

完整流程、幂等、预算、错误、权限与接口见[运行契约](runtime.md)。P1 SDK 组合已经实测；通用 MCP 和 CI 迁移仍需实测，SDK 默认内存结构不决定业务表。

## 8. 实施范围、文档责任与验证

P1 已实现十二张业务表。后续按真实实体和验收分期，不再以旧目标图的十五/二十九表总数约束方案；标准内容和 MCP 使用上文新目标，知识和评测沿用专项设计。

| 阶段                          | 结构范围                                                | 为什么可独立推进                                   |
| ----------------------------- | ------------------------------------------------------- | -------------------------------------------------- |

每阶段正式迁移号在实施时按实际 head 分配，不在文档中预占。迁移映射、同批切换、回退和逐条验收见[迁移清单](migration.md)。字段、约束、索引和删除规则只在[数据字典](data.md)维护；知识处理参数和评测算法只在专项设计维护。
