# MCP 接入与 Agent 工具使用深度审查

日期：2026-10-30，时间统一按 Asia/Shanghai。范围为当前工作树、已安装 SDK、正式业务库的只读投影，以及隔离数据库、假模型和进程内 MCP 探针。未修改业务代码、员工配置、真实连接或数据库，未新增付费模型请求或真实 Context7 调用。

## 分级发现

### P1：查新任务缺少外部证据完成条件，零调用和失败查询都能交付“已核实”

真实 Run `2b532d98-af7a-4605-a486-fa38ec673a00` 的输入为“最新版本 LangChain 版本提供了什么有意思的能力 ？”。当时已冻结 Tavily 五项工具和 Context7 的 `resolve-library-id`、`query-docs`；两项 Context7 的 `auth_required=false`，快照包含要求在库/框架问题上查询当前文档的服务说明。员工工作指令明确要求涉及版本、API 等易变信息时核对官方资料；历史已有用户要求基于真实检索证据回答的纠正。

该轮实际为 **1 次模型调用、0 次工具调用、succeeded**。模型步骤记录无工具调用、`finish_reason=stop`，正文却声称依据官方文档“逐条核实”。随后用户要求查看最新源码和文档的 Run `4d9b5aa4-006b-4703-884c-a94ffa4911e0` 仍是 1 次模型、0 次工具并成功交付。两次请求分别发生在北京时间 10 月 30 日 01:15、01:16。见[历史轨迹](mcp-agent-integration-review-2026-10-30/evidence/historical-runs.json)。

当前实现的隔离对照也能复现：

| 场景                                                      | 模型请求 / MCP 调用 | 结果      |
| --------------------------------------------------------- | ------------------- | --------- |
| 查最新文档，假模型直接给虚构回答                          | 1 / 0               | succeeded |
| 明确“必须使用 Context7，禁止凭记忆回答”，假模型仍直接回答 | 1 / 0               | succeeded |
| resolve → query-docs → 基于结果回答                       | 3 / 2               | succeeded |
| 同轮两项工具调用，参数按 SSE 分片                         | 2 / 2               | succeeded |
| resolve 成功、query-docs 返回 error，模型仍声称查询成功   | 3 / 2，含 1 次失败  | succeeded |

名称、描述与参数 schema 完整进入真实 ChatOpenAI/OpenAI SDK 生成的 HTTP 请求；标准工具调用也能完整回到 MCP 执行路径。因此不是“仅在界面装配，没有把函数送给模型”。最后一组还证明，工具调用数大于零不足以证明取得了文档证据。

机制位于 [Agent 结束检查](../../backend/app/agent_runtime/langchain.py) L210–225：非空、无待处理工具调用的 AIMessage 可以成为最终候选；唯一外部读取核验来自 [verify_web_reads](../../backend/app/agent_runtime/tool_results.py) L124–181，只识别带明确 URL 和指定读取措辞的输入。无 URL 查新、显式“使用 Context7”和自然语言追问均不建立此类证据要求。普通 Agent 请求没有 `tool_choice`；[模型中间件](../../backend/app/agent_runtime/middleware.py) L46–94 也不将任务取证要求转成完成条件。

影响：模型可绕过检索或忽略失败结果，把记忆回答包装为已核实资料。成功正文又可进入后续问答历史，未随正文送入“前轮零调用”的状态。原始动作仍由平台保存，不能称为审计数据丢失；也不能仅据此证明历史必然导致下一次幻觉。

建议：为必须外部核实的任务明确本轮证据要求，结束前检查相关的成功检索结果。允许如实说明未核实或服务失败；不能仅凭模型自称判定完成。适用时可在只读取证工具集合内使用 `required`，但仍要检查成功结果；无关调用、仅 resolve 或失败的 query-docs 均不充分。

置信度：高。真实历史证明症状；假模型探针证明当前后端接受路径，不衡量真实模型主动选工具的概率。

### P2：服务版本混入工具摘要，普通部署更新会使未变工具失效

[descriptor](../../backend/app/tools/adapters/mcp.py) L33–43 将整个 SDK metadata 纳入摘要；当前 LangChain 把握手 serverInfo 放进 `metadata.mcp.server`，其中含服务版本。

两个同名 FastMCP 服务注册同一函数，原始工具定义、描述、输入 schema 完全相同，仅版本从 1.0.0 变为 1.0.1；真实进程内协议下，旧摘要调用新服务会在业务执行前报 `tool_catalog_changed`。确认新目录后，员工仍持有旧摘要，[capture_tools](../../backend/app/agents/tool_grants.py) L222–225 会跳过该工具，快照不保存过滤原因。

影响：服务部署版本变化成为所有工具定义变化，要求重新确认和装配；用户可能只看到员工不再调用工具。本次两项 Context7 已在快照，此项不是该次原因。

建议：区分工具契约、服务说明与部署身份的修订。排除 SDK 额外注入的服务版本，保留原始 schema、描述、annotations 等契约变更检查；若需要部署版本审批，显式建模和提示。具体协议复现见[补充审阅](mcp-agent-integration-review-2026-10-30/context/discovery-and-call.md)。

### P2：网页提取规则被套用到所有 MCP 的 url/urls 参数

[authorize_arguments](../../backend/app/tools/policy.py) L94–120 按参数名推断“公开网页提取”，对所有非 native 工具统一要求公开 HTTP(S) 且最多三个 URL，没有检查该工具是否确为网页提取能力。

离线探针中，schema 允许字符串数组的通用批处理工具收到四个公开 HTTPS URL 时被拒绝；允许资源 URI 的工具收到 `url=resource://catalog/library` 时也被拒绝。最多三个网页属于当前网页契约；问题是该语义被扩展到所有同名参数，且没有体现在送模定义中。

影响：通用 MCP 可接入成功却无法执行合法参数，模型无法从 schema 提前得知原因。Context7 基本工具没有此类参数，故不解释本次零调用。

建议：把网页规则绑定到显式声明或受信登记的能力语义；通用 MCP 依据批准 schema 和明确装配范围验证。对确实需要的额外限制，同时向模型提供有效约束，保留网络与账号控制。

## 架构诊断与已排除方向

当前链路为：接入发现 → 账号目录/说明确认 → 员工逐工具授权 → 发起者身份解析/Run 快照 → StructuredTool → 模型请求 → 模型自行选择 → 工具执行/结果保存 → 候选检查 → 发布。

| 检查层         | 结论                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| 接入与错误状态 | 进程内 MCP discover/invoke 可工作；`isError=True` 正确保留为失败。                                    |
| 员工装配与账号 | 真实失败轮含两项 Context7，账号不缺失。                                                               |
| 送模定义与说明 | 名称、描述、schema 构成真实函数；服务 instructions 进入系统指导。                                     |
| 模型工具协议   | 标准串行、并行和参数分片均走通；未发现统一剥掉 tool_calls 的证据。                                    |
| 选择与完成     | 已有多处提示要求查询，但普通 Agent 可直接 stop，通用查新没有证据门槛。                                |
| 草稿与前端     | 核验前显示“生成中”草稿；显式 URL 核验失败后正式正文为空并显示失败，断言只留在折叠过程，符合现行契约。 |
| 历史与隐藏修复 | 成功正文进入后轮历史；未发现通用结束路径暗中再跑模型重写成功回答。                                    |

平台实现了“允许调用什么”，没有通用表达“本轮必须取得什么证据”。此次故障主要落在工具选择与完成判定之间；现有证据不支持把责任归给用户没有重复写工具流程，也不支持认定 MCP 传输整体断链。

补充因素与未知项：

- 普通模型请求没有自动注入当前日期/时区。可补时间锚点，但日期不能替代检索，也不能证明加日期就会调用。
- 工具调用名为连接 ID 加摘要，系统提示另有原名映射。可读名称可能影响选择，但没有真实模型对照，不能判定为此次原因。
- 模型连接检查仅读取 `/models`，界面已说明不验证生成或 Agent 任务，不能当作工具兼容性验收。
- 通用 ChatOpenAI 不保留第三方 `reasoning_content` 往返字段已复现；Kimi 当日模型是否要求回传、强制工具选择和其他参数的兼容性未新增真实请求验证，不能认定为此次根因。
- Context7 文档命中不自动证明最新发布版本、日期和所有新功能。需要核对库、语言、版本和来源；未取得的信息继续保留未知。

## 修复顺序与验收（建议，尚未实施）

1. 明确查新/外部核实的本轮证据要求及完成状态，定义平台规则、员工配置、用户显式要求和模型规划各自的职责。普通讨论保持可直接回答，模型自称“已核实”不是唯一依据。
2. 在工具选择和结束检查中落实要求：优先取得相关文档，失败时有界重试/换源或如实说明。至少区分零调用、仅 resolve、查询失败、无关结果与有效文档，不能只检查调用次数，也不靠正文正则猜真假。
3. 补日期/时区、库文档检索指引及失败后的行为；复用 MCP 描述和服务说明，避免为每个厂商维护重复 prompt。
4. 修正服务版本与工具摘要耦合，分开通用 MCP 与网页提取参数语义；为已装配但被过滤的工具保留可观察原因。
5. 在隔离协议测试外做少量真实模型行为对照，覆盖自然请求、显式 Context7、新对话、旧历史、查询失败和概念问答；分别统计正确取证、错误成功和失败如实报告。

核心验收：本次请求应观察到合适的库解析与成功文档查询，并按结果回答；或者明确说明未取得可确认资料。零调用、只查到库 ID、失败查询、无关调用均不能作为“最新文档已核实”的依据。普通概念问题不应被迫无意义调用工具，失败草稿不进入后续成功历史。
