# 配置与备份

面向部署者。安装、构建和账号维护命令在仓库根目录执行；配置使用后端服务实际读取的环境，不以开发机器上的默认路径代替。

## 运行与配置

生产启动前安装依赖、初始化数据库和管理员，构建前端后执行：

```bash
make build
make start
```

默认在 `127.0.0.1:3000` 同源提供页面与 `/api`。使用 `START_PORT` 改端口时，同时调整浏览器允许来源及已启用的回调。`make preview` 只预览前端，不能替代完整服务。

同一数据库只运行一个后端进程，不能增加 Uvicorn worker。数据库、存档和运行锁须来自同一套配置；独立环境使用各自的数据目录与锁。

后端先读取 `backend/.env`，再用进程环境覆盖，包括显式空值。配置修改后重启生效。内置网页能力需要 `WEB_BOCHA_API_KEY`，`WEB_JINA_API_KEY` 可选；员工权限仍须单独开启。`WEB_TIMEOUT_SECONDS`、`WEB_MAX_RESPONSE_BYTES`、`WEB_MAX_CONTENT_CHARS` 分别限制调用时长、响应字节及正文字符数。密钥只能配置在服务器环境，不放入员工指令、网页 URL 或 MCP 配置。可填写项及单位见[环境变量示例](../../backend/.env.example)；新建生产配置可参考[生产示例](../../backend/production.env.example)，不要整体覆盖已有配置。

| 配置                            | 本地开发                                                      | 生产部署                                                                 |
| ------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `AUTH_ALLOWED_ORIGINS`          | 实际访问的 `http://127.0.0.1:3000` 或 `http://localhost:3000` | 实际 HTTPS 来源，不含路径                                                |
| `AUTH_COOKIE_SECURE`            | `false`                                                       | `true`                                                                   |
| `TOOL_OAUTH_CALLBACK_URL`       | 通常不设置，使用发起授权的受信任来源                          | 需要固定回调时，填写本站 `/api/tool-connections/oauth/callback` 完整地址 |
| `GITHUB_OAUTH_CALLBACK_URL`     | 启用 GitHub 登录时显式配置                                    | 填写本站 `/api/auth/github/callback` 完整地址，并在 OAuth App 中登记     |
| 文档 `NEXT_PUBLIC_PLATFORM_URL` | 默认本机 3000                                                 | 同域默认 `/`；独立文档域名在构建时指定平台 URL                           |

工具回调、GitHub 登录回调分别配置。域名变化后，更新允许来源及服务方登记；工具旧来源的授权需要重新连接。反向代理只调整内部转发地址，不能代替应用的公开来源配置。

检查服务时，`/health` 表示进程存活，`/ready` 表示执行服务可接受工作。开发环境提供 `/docs`、`/openapi.json`；开启 Secure Cookie 后关闭接口文档入口。

## 登录与账号维护

| 身份   | 可以做什么                                                     |
| ------ | -------------------------------------------------------------- |
| 管理员 | 维护共享员工、模型、技能、组织工具连接和知识，使用员工完成工作 |
| 成员   | 使用共享员工，查看本人对话和考核；不单独维护工具账号           |
| 游客   | 只读浏览配置与历史记录，不能发起或修改工作                     |

首次创建管理员时，密码按终端提示隐藏输入并确认，长度为 8 至 20 个字符。已有管理员时跳过创建；重复创建不会覆盖账号。

```bash
make admin-create ADMIN_USER=admin
```

账号维护使用以下命令。重置密码、启停账号或撤销会话都会使该账号已有会话失效：

```bash
make admin-reset-password ADMIN_USER=admin
make admin-disable ADMIN_USER=admin
make admin-enable ADMIN_USER=admin
make admin-revoke-sessions ADMIN_USER=admin
make admin-cleanup-sessions
```

GitHub 登录由部署者注册本站专用 OAuth App，在后端同时配置 `GITHUB_OAUTH_CLIENT_ID`、`GITHUB_OAUTH_CLIENT_SECRET`、`GITHUB_OAUTH_CALLBACK_URL`。全部缺省时关闭入口，部分配置会启动失败。回调来源须与浏览器一致，本机也不要混用 `localhost` 和 `127.0.0.1`。重启后检查 `/api/auth/providers`，再验证首次登录、重复登录与退出。

会话时限、可信来源和 Cookie 的完整规则见[身份与会话](../reference/auth.md)。公网入口需配置 HTTPS 与入口限速，不能靠增加后端 worker 扩容。

## 数据库与本地文件配置

`APP_DATA_DIR` 相对路径以 `backend/` 为基准；其他相对文件路径以 `APP_DATA_DIR` 为基准，`~` 展开为服务用户的主目录。

| 配置或内容                   | 未配置时的位置                       | 维护要求                                                  |
| ---------------------------- | ------------------------------------ | --------------------------------------------------------- |
| `APP_DATA_DIR`               | `backend/.data/`                     | 本地示例改为 `~/.niuma-crew/data`，生产按实际持久目录设置 |
| `DATABASE_URL`               | 数据目录下的 `app.db`                | 仅支持本机磁盘上的 `sqlite+pysqlite` 文件库               |
| 执行存档                     | 业务库旁的 `app.checkpoints.db`      | 与业务库同批备份，不能代替正式对话和成果                  |
| `MODEL_CONNECTIONS_KEY_FILE` | 数据目录下的 `model-connections.key` | 保留原密钥，单独保护备份                                  |
| 工具主密钥                   | 模型主密钥文件名追加 `.tools`        | 与组织连接密文配套保存                                    |
| `FILES_DIRECTORY`            | 数据目录下的 `files/`                | 包含原件与成果的实际字节                                  |
| `SKILL_STORAGE_DIR`          | 业务库旁的 `skill-assets/`           | 不可变技能包存储，与标准技能源目录分别保存                |
| `SKILL_LIBRARY_DIR`          | 服务用户的 `~/.agents/skills/`       | 页面创建、导入和目录同步使用的标准技能源                  |
| `KNOWLEDGE_VECTOR_DIR`       | 业务库旁的 `knowledge-vectors/`      | 本地 Chroma 索引，与业务库指针匹配                        |
| `RUNNER_LOCK_FILE`           | 数据目录下的 `runner.lock`           | 同一业务库共用，不能用另一个锁绕过单进程限制              |

`MODEL_CONNECTIONS_ENCRYPTION_KEY` 显式设置时优先于密钥文件，同时供模型和工具凭据使用。未设置时，各自首次保存凭据才创建相应密钥文件。已有密文但密钥丢失时须恢复原密钥，不能生成替代密钥或直接改配置冒充轮换。

修改数据路径不会搬迁已有文件。先停写和备份，再移动数据、更新配置，并核对绝对路径后重启。数据库 URL 使用绝对路径的例子是 `sqlite+pysqlite:////srv/niuma-crew/data/app.db`。容器部署也必须为上述持久内容提供对应挂载；当前仓库没有平台 Docker Compose 发行文件。

SQLite 使用 WAL，数据库与 `-wal`、`-shm` 文件不得提交到 Git。使用包含 WAL-reset 修复的 SQLite 版本，例如 3.51.3 或更新版本；修复与回补版本见 [SQLite 官方说明](https://www.sqlite.org/wal.html#the_wal_reset_bug)。

## 数据库迁移

应用启动不自动升级业务库。按以下顺序备份、升级和恢复：

1. 停止后端及其他数据库、技能目录写入，记录代码版本和上表各项实际路径。不要只备份 `app.db`。
2. 在同一停写窗口，分别使用 SQLite backup API 备份业务库与执行存档库，复制相应主密钥、文件、两处技能存储和 Chroma。写入时单独复制主数据库可能遗漏 WAL 中的数据。为备份保存路径清单，验证数据库可打开、完整性与外键检查通过。
3. 在备份副本上先验证目标版本的迁移与数据保留，再对服务使用的配置执行以下命令。空库可直接升级；已有资源先核对下方特殊条件。

   ```bash
   make db-current
   make db-upgrade
   make db-current
   make db-check
   ```

4. 启动后检查 `/health`、`/ready`、登录、历史对话、来源和成果读取，再提交小型测试任务。重建向量索引、真实模型或工具调用由部署者按需要安排，会产生相应外部用量。
5. 升级失败时保留现场，停服后恢复同批数据、密钥、技能与匹配代码。部分迁移无法无损降级，`downgrade` 不能替代备份恢复。

| 涉及的升级            | 升级前必须核对                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------- |
| 0003 至 0005 旧历史   | 历史名称、内容、归属和报告通过迁移预检；损坏时先修复来源                                      |
| 0011 及更旧的固定试验 | 0012 前使用 `migrations.retire_ci_source` 盘点并处置固定技能源；缺失或内容不符时停止          |
| 0020、0021 执行格式   | 0021 要求相关执行表为空，不转换旧运行数据；有旧数据时先制定保留、导出或重建方案，不能直接清库 |
| 0022 考核             | 部署固定题库资源，不在开始考核时临时下载                                                      |
| 0023 向量索引         | 旧 SQLite 派生向量和指针会移除，原文与关键词保留；需显式重建向量并承担编码用量                |
| 0027 检索策略         | 移除旧强制算法选项，保留选库、时机、片段上限及历史；回退需恢复备份                            |
| 0028 组织资源         | 已有工具和知识资源须提供明确接纳清单；空库无需清单                                            |

0028 升级前先排空活动工作并停写，明确全部活动工作连接、知识库、每项员工工具许可的固定连接，以及每名员工采用的原知识设置。清单格式如下：

```json
{
  "schema_version": 1,
  "connections": ["连接ID"],
  "knowledge_bases": ["库ID"],
  "employee_tools": { "许可ID": "连接ID" },
  "employee_knowledge": { "员工ID": "原知识设置ID" }
}
```

在 `backend/` 执行：

```bash
uv run alembic -x org_assets=/绝对路径/组织资源接纳清单.json upgrade head
```

缺项或配置冲突会中止，不自动取并集。含旧资源的迁移须在线读取并审核；离线 SQL 只支持空库初始化。迁移保留资源 ID、密文、文件、索引和历史快照，删除个人工具绑定与个人知识设置；无法无损降级。清单字段与保护检查见[0028 迁移](../../backend/migrations/versions/0028_organization_employee_resources.py)。

恢复完整 Chroma 时，必须与同次备份的业务库指针匹配。索引缺失时需要手动重建，平台不会自动调用向量服务。

## 模型、知识与执行维护

聊天连接由管理员在“大脑配置”维护；向量连接在知识库“检索设置”中维护。模型密钥不填写到对话或公开配置中。聊天检查验证模型目录，向量检查会发送固定短文本调用向量服务。

知识分片和向量索引均由后台处理，可离开页面。向量任务在“检索设置”提交后返回排队记录，重新打开页面可查看进度、取消或重试；成功编码批次持久保存，同模型空间与文本内容复用，只请求缺失向量。重启保留排队任务，执行中任务标记中断并等待手动重试；未知上游结果不会自动重发。旧可用索引在新一代完整发布前保留。迁移0029只增加任务与编码缓存表，不删除已有文档、关键词或Chroma索引。

执行服务采用队列、用户活动工作数和单次预算控制容量。配置项与单位以[环境变量示例](../../backend/.env.example)为准；图步数上限不等于模型或工具调用次数。超出预算时检查具体错误，避免只增加一个无关额度。

断线只影响观察；显式停止、会话失效和授权撤销会影响执行。重启只恢复符合存档、快照版本和资源条件的普通聊天，预算与总时限不重置；未完成的模型请求可能重发并重复计费。核对恢复结果后再决定是否重新提交，详细条件见[执行规则](../reference/runtime.md#checkpoint历史与恢复)。

## 前端交付与可选代理

`make build` 生成 `frontend/dist`，FastAPI 通过同一来源提供页面与 API。进程环境 `FRONTEND_DIST` 可指定其他构建目录；未构建时仍可单独运行 API。网关需要保留状态码、Cookie、Origin、压缩、缓存、GET/HEAD 和持续响应，关闭 SSE 缓冲。

需要应用停机时仍能展示代理错误页，可使用[Nginx 模板](../../deploy/nginx/nginx.conf.example)：

1. 构建前端，确认 `frontend/dist/failures/` 中有错误页和图片。复制代理模板并替换所有 `/ABSOLUTE/PATH`。
2. 模板监听本机 3000、转发到后端 8000。后端使用单个 `app.main:app` Uvicorn 进程，不带 `--reload`，保留 `--no-proxy-headers`；避免另起占用 3000 的 `make start`。
3. 对复制的配置执行 `nginx -t -c /绝对路径/nginx.conf`，通过后再按部署环境启动。公网另配 TLS、可信来源与 Secure Cookie；模板不安装服务或管理证书。
4. 在独立端口验证正常页面深链、API、缓存与 SSE，再停止测试后端，确认页面返回真实 502 错误页、API 返回 JSON；恢复后重新核对。仅停止本次测试进程。

模板不把后端业务错误、OAuth 跳转或 SSE 改写成 HTML。静态错误页只能覆盖代理仍可访问的情况，不能处理 DNS、TLS 或整机不可达。模板不提供维护状态开关。

工具 OAuth 回调查询串可能含授权码。Nginx 模板默认关闭访问日志并丢弃错误日志；如需保存日志，先过滤请求行、查询参数和凭据。部署者也应检查上游代理的日志设置，具体回调配置见[工具授权配置](agent-tools.md#oauth-与-notion-接入)。

## 配置内置网页服务

只编辑实际部署环境的配置副本，不把密钥写回版本库中的示例。网页访问同时需要服务器配置和员工开关；填写博查密钥后重启后端，再在员工能力装配中开启网页访问即可。未配置时普通聊天仍可用。

| 配置 | 必填/默认 | 用途与限制 |
| --- | --- | --- |
| `WEB_BOCHA_API_KEY` | 启用网页能力时必填，默认空 | 博查搜索密钥；空值不装配搜索和读取两项能力。 |
| `WEB_JINA_API_KEY` | 可选，默认空 | Jina Reader 密钥；空值尝试公开额度，不保证可用性。 |
| `WEB_BOCHA_ENDPOINT` | 可选，默认 `https://api.bocha.cn/v1/web-search` | 仅接受该地址或 `https://api.bochaai.com/v1/web-search`。 |
| `WEB_TIMEOUT_SECONDS` | 可选，默认 20 | 单次调用总时限，单位秒，范围 1–60；没有自动重试。 |
| `WEB_MAX_RESPONSE_BYTES` | 可选，默认 1048576 | 上游正文最大字节数，范围 4096–4194304，超限返回失败。 |
| `WEB_MAX_CONTENT_CHARS` | 可选，默认 24000 | 单次网页正文最大字符数，范围 1000–100000；截断明确标记。 |

本次持久向量任务没有新增必填环境变量，沿用 SQLite 数据库与已有 `KNOWLEDGE_VECTOR_DIR` 可选目录。该目录默认在业务数据库旁；显式相对路径基于 `APP_DATA_DIR`。任务状态与可复用向量保存在 SQLite，索引文件与数据库仍需按已有备份要求管理。
