# 设计取舍：每个抽象解决什么问题

本文说明[总方案](README.md)的判断依据。以下为已采纳并用于本次实施的取舍；提问用于检验方案，不把能够从源码确认的问题重新交给用户回答。

## 1. 从必须成立的事实开始

当前产品必须做到：保存用户原话；识别一次提问的多次处理；保留成功、失败与取消过程；刷新后继续观察；按问题定位历史；从成功交流构造后续输入；核对 CI 专业报告；限制权限、预算和并发。

“采用哪个知名项目的名字”“少几个文件”“统一所有数据格式”都不是这些要求本身。判断一个结构是否值得保留，要看删除后这些事实是否更难表达、约束是否变弱、维护者是否需要知道更多内部细节。

## 2. Message 能不能删

**追问：如果一个问题失败两次，第三次成功，问题目录应该有几项？**

仍然是一项。三次处理有不同时间、预算、状态与过程，但它们使用同一次提问。交流内容与处理尝试有不同身份。

| 选择                             | 得到什么                          | 付出什么                                                       |
| -------------------------------- | --------------------------------- | -------------------------------------------------------------- |
| 输入和答复都塞进 Run             | 少一个内容记录的名字              | 问题去重、回复定位、历史顺序重新依赖处理分组；执行混入交流职责 |
| 新建 Question 和 Answer 两种记录 | 分别表达输入和输出                | 当前共同字段与历史查询相同，拆表后还要合并读取                 |
| 保留轻量 Message                 | 稳定内容 ID、顺序、用户与助手内容 | 需要 role，以及与执行的明确关联                                |

推荐轻量 Message，归 conversations 管理，不建立独立 Message 领域模块或 MessageService。

## 3. 为什么不继续使用“占位—正式消息—结果”三段关系

**追问：用户看到排队、失败或停止时，页面上是否已经有一个回复区域？**

有。当前代码其实已经为它分配 response_id 和顺序，只是成功后才把它建成助手 Message。

**追问：这个区域失败了，是否意味着它是假记录？**

不意味着。它记录“系统曾接受并处理这次请求”，只要状态和正文完整性明确，就没有冒充成功。

因此推荐在接受时建立助手内容记录，结束时填写应保留的正文。处理状态从 Run 取得，不再给 Message 复制一套状态。这个决定允许删掉成功后才出现的第二种消息身份和通用 RunResult 引用。

当前[历史查询](../../../backend/app/conversations/queries.py)已经按用户消息和回复位置组合列表，助手 Message 并不是读取的唯一入口。这说明现有复杂关系未带来统一读取的收益。

## 4. 为什么不把关联表一起删掉

**追问：删一张表后，同一对话只能运行一个处理的规则由谁保证？**

若只在 Conversation 保存 active_run_id，就增加了一个需要同步的活动指针；若只查询 Run 状态再插入，竞争时需要额外保护。当前 ConversationRun 已有部分唯一索引和复合归属外键。

推荐保留精简关联表：一次处理、一个对话、一个输入、一个回复、活动占用。顺序只在 Message，执行状态只在 Run。active 是对话占用标记，与终态在同一事务释放。

这里保留一个有约束价值的表，比为了“四张表”放弃数据库保护更简单。

## 5. 为什么保留 Run，不改为 Turn

**追问：我们想记录的是“一组问答”，还是“一次可能失败的处理尝试”？**

当前需要后者。显式重试新建处理，恢复继续原处理，模型内部网络重试也不等于新处理。

Run 可以直接解释成“一次处理尝试”。Turn 也能人为定义成这个意思，但已在讨论中引发“一个问题为何多个 Turn”的持续误解，改名没有提供额外能力。

Conversation 继续表示交流容器。正式任务、文件工作区和持续目标有各自的规则；不因为可能增加这些功能，就现在把交流容器改成包罗所有工作的 Thread。

关联研究中 Codex 的名字可用于理解生命周期，不能代替本项目的命名论证。

## 6. execution 为什么仍然存在

**追问：取消、超时、预算、排队和恢复能否全部放进消息服务？**

可以写进去，但这些逻辑管理的是运行过程，并不管理交流内容。这样只会把对话模块变成作业执行器。

**追问：接受输入和发布答复是否也全部归 execution？**

不归。它们同时触及身份、配置、内容与运行状态，由请求与共享流程组织。execution 管理自己的处理记录和运行控制，既不是整个应用的组织层，也不负责所有业务规则。

**追问：员工目录下是否还需要一个 execution.py？**

不需要。当前文件不执行模型或工具，跨模块准备迁走后，员工读取与装配检查可以与 service.py 已有规则共同维护。保留函数复用不等于必须保留一个独立文件。快照、提示词和本次预算归共享准备流程，员工服务只提供配置事实与本模块检查。

## 7. Agent 与执行管理是否值得拆开

**追问：换一种 SDK，哪些代码应该必须跟着改？**

模型消息类型、片段拼接、工具循环、SDK 存档格式应改变；对话分页、取消请求、执行预算、用户权限和发布事务不应因此重写。

目前 SDK 已通过 hooks.store 取得存储，并且 RunProgress 直接解析 SDK 消息。这是实际变化原因，值得建立 agent_runtime 边界。

只建立普通输入、受限运行控制和候选输出协议，不引入事件总线、万能上下文、工具许可对象、引擎注册中心或第二套调度框架。

## 8. 为什么 API 与 Hook 不跟随后端命名

**追问：停止按钮需要管理一条 Run，还是停止这份回复背后的处理？**

用户需要后者。API 可以按对话中的 response_id 操作，后端通过关联找到准确 Run。response_id 就是助手 Message ID，不新建 Reply 表。

**追问：回复组件同时显示内容和状态，是否必须调用 useMessage 和 useRun 两个 Hook？**

不必。现有 useMessage 已按一行回复的交互组合，保留即可。订阅由对话作用域统一维护，消息行不独立建立连接。

API 围绕稳定用户操作设计，Hook 围绕组件状态和生命周期设计；二者也不需要一一对应。

## 9. CI 是否应该立刻改成通用自由 Agent

**追问：普通 Agent 决定读什么工具，是否能替代诊断所要求的完整证据范围和报告检查？**

不能直接替代。当前 CI 流程限制目标、日志来源与引用行号，还会核对构建 attempt、SHA 和调查覆盖。它有真实专业约束。

推荐先保留专业执行器，整理代码与数据归属。只有通用工具能力和等价验收成熟后，再单独评估迁移；本次不承诺统一一条自由循环。

## 10. 没有现在解决的问题

未来是否需要正式任务、执行中追加输入、计划版本、人工等待、持续目标、定时触发，取决于实际产品要求。本方案给出[接入条件](extensions.md)，不提前建空表、空页面或完整未来文件树。

失败回复默认继续逐次保留，沿用当前展示行为；将来是否折叠到同一问题下，只改变显示方式，不改变历史记录身份。

方案采用最少但足够的结构。“最少”按需要理解和维护的规则衡量，不按目录数、字段数或数据库表数单独衡量。

## 11. 为什么不是每种职责都单独建文件

**追问：SDK 解析迁走后，progress 还有独立消费者和规则吗？**

剩下的是每个 RunControl 的缓冲、限制和恢复状态，可以作为 control 的私有实现。刷新时机仍由协调器决定，持久保存仍由 store 承担，不需要单独文件表示每个环节。

**追问：Run 状态规则应该抽 lifecycle 吗？**

当前 store 已拥有领取、结束和恢复操作；只需收回API 请求服务中的取消赋值。额外 lifecycle 反而分散同一规则。本轮不新增。当前唯一 SDK 实现也直接放 agent_runtime，不再嵌套适配目录。

**追问：前端配置多个页面使用，是否就应有一个资源大 Context？**

页面共享的是数据来源，读取目标、生命周期和编辑资格各不相同。员工列表和详情不能替代彼此；导航只需要摘要。页面各持有实际读取，全局只通知写入变化，比同时理解路由解析、混合资源缓存和两套保存门闩更直接。

边界必要不代表每个边界都必须对应文件。合并和拆分均要有调用、规则或变化原因；完整证据与保留项见[全工程职责复核](responsibility-review.md)。

## 12. service 是否必须集中或全部靠近 API

**追问：统一命名是否要求统一放到一个 application 或 use_cases 目录？**

不要求。现有业务服务已经维护各自规则，迁走会把每个功能分散到两处。API 对话请求编排有独立复杂度，可以就近放；真正的后台共享准备、授权和发布仍归 conversations，其他服务留所属模块。

**追问：是否只要出现跨模块调用就必须迁到全局？**

不需要。对话发送可以协调员工和执行登记，员工配置也会检查模型与技能。归属看操作服务的业务与实际调用；共同事务由完整操作持有。也不因为当前只有一个 HTTP 入口就把员工所有规则搬入 API。

**追问：有没有需要两个 Service 同名转发的地方？**

没有。不会建立 ApiAgentService.update 再调用 AgentService.update；也不建 ConversationService 包装三个共享流程。完整选择、开源依据和可执行验收见[服务归属](service-boundaries.md)。
