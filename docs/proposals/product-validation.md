## 1. 推荐结论与证据边界

推荐先为 B2B 软件与技术服务团队的交付/支持负责人，验证一项工作：把已有项目资料转成可核对的答复草稿，负责人确认后复用；后续资料变化时提示哪些已确认答案需要复核。产品价值用接入、交办、复核和维护的总成本衡量。

这是首批客群与工作假设，不是已确定市场定位。用户已明确目前没有试用客户；行业频率、资料质量、采购意愿和分发渠道都未知。选择此方向是因为它贴近已有项目知识助手规划、结果便于抽查，并可先用资料完成试验，减少外部系统改造。不是因为已经证明它比其他场景更赚钱。

标准 Skill 与 MCP 是扩展和迁移的基础，不足以单独成为企业买单理由。CI 继续作为真实执行示例；不因已有 CI 代码，就把平台定位为 CI 产品，也不因本次脑暴扩张为所有岗位的自动化平台。

本轮只查官方产品/规范和仓库，未独立试用竞品、访谈客户或完成付费试点。没有足够证据声称任何候选功能“别人都没做”。模型同质化按分析前提处理，不据此断言各模型能力、成本和可靠性相同。

## 2. 第一性原理：企业到底购买什么

企业通常需要有人把一项工作做到可采用。模型、Harness、Skill、MCP、知识和界面只有在改善这项工作的成本、速度或可靠性时才产生购买理由。

拆开一次真实工作的成本：准备可访问资料与连接 → 说明任务 → 执行与等待 → 复核纠错 → 采用结果 → 后续维护。若执行快了，但准备、复核与维护更贵，企业没有得到净收益。模型成功返回也不等于结果已被采用。

用于试点的账本：

- **人工净投入变化**：同类任务的原有人工投入，减去接入分摊、交办、复核、纠错和维护投入；不同人的分钟数分别记录。
- **总成本变化**：上述人工投入按明确口径折算，加模型、工具、平台、部署与维护费用，再与基线比较。固定费用按真实使用量和明确期限分摊，不按假定高频摊薄。
- **现金收益**：仅记录实际减少的支出或可归因的新增收入/毛利；释放工时而没有减少支出时，称为容量释放，不冒充现金节省。
- **业务效果**：采用率、事实修正次数、交付周期、积压和错误影响；未知损失、收入归因或供应商用量保持未知。

不让模型自行估算“为企业节省了多少时间”。时间可由人工抽样、轻量计时及明确的前后任务记录得到；产品早期用表格即可，不先造复杂 ROI 大屏。

## 4. 苏格拉底式自审：逐层排除没有依据的主张

这里按“购买对象 → 替代方案 → 收益 → 采用 → 扩展”追问。客户事实未知时保留假设；分析建议不替代客户决定，也不因写了答案就视为问题已验证。

| 追问                                               | 暂定回答与依据                                                                 | 能推翻回答的证据                                                   |
| -------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| Q1：如果模型和工具都可以换，客户究竟为什么付费？   | 为一类重复工作更快形成可采用结果，并减少交接与复核。Harness 本身主要吸引开发者 | 客户只想要更便宜的聊天入口，不愿为工作结果或维护付费               |
| Q2：为什么不用现有 Agent + 同一 Skill + 同一 MCP？ | 只有当本平台减少了接入、交办、复核和持续维护成本，独立产品才有必要             | 同样资料和权限下，现有工具同样省事或总成本更低                     |
| Q3：大家都建设，还有必要再做吗？                   | 有条件建设一个具体客群的工作产品；现有底座优先复用，差额价值须独立测量         | 唯一优点是头像、技能数量或模型列表；试点无法找到明确买方和重复任务 |
| Q4：别人会如何发现并注意到它？                     | 用具体任务的前后对比、可核对案例和同行推荐获得注意；搜索和展示围绕工作问题     | 技术演示有流量，却没有愿意提供真实任务的负责人                     |
| Q5：“简单”是谁少做了什么？                         | 使用者不装配技术组件，维护者少配重复参数，复核者只看依据与待确认部分           | 界面看似简单，但每接一客户都要开发定制流程或替其长期维护           |
| Q6：企业收益能直接证明吗？                         | 把准备、复核、纠错与费用计入，与当前最好做法比较；先验证容量释放               | 只有 token 成本或模型自评，省下时间被更长复核抵消                  |
| Q7：什么会越用越好？                               | 经人确认的答案、错误案例与资料变化记录可减少重复复核；效果需回归比较           | 只存聊天历史，不减少下一次成本；错误被自动复制进知识               |
| Q8：如果大厂一个季度增加同类功能怎么办？           | 可争取的是特定客户的交付经验、可信案例、采用渠道和更低部署维护成本             | 价值依赖一个容易复刻的按钮，缺乏可持续客户关系或执行成本优势       |

不把“无人做”作为选题前提。若企业已有方案能够低成本满足需求，优先集成、分发标准工作包或停止该方向；不为证明平台必要而制造复杂功能。

## 5. 首批切口如何选

以下为方案筛选，不是需求规模或市场份额排序。首客可达性目前全部未知，必须先补证。

| 候选工作                    | 可验证结果与潜在收益                                               | 主要反证/成本                                                   | 建议                             |
| --------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------- | -------------------------------- |
| B2B 项目交付/支持的重复答疑 | 答复草稿、原文依据、人工修正及复核时间；减少重复查资料与向专家追问 | 资料可能过期，很多问题实际依赖代码/现场经验；现有知识工具竞争强 | 首选试验，沿用项目知识助手主线   |
| 售前技术问卷/方案答复       | 逐项答复及缺口，便于逐项接受与复用                                 | 频次、保密、措辞承诺和表格导入成本待查                          | 相邻扩展，先验证任务重复度       |
| CI 诊断                     | 日志、判断与下一步可核对，已有技术闭环                             | 现有 coding agent 替代强，真实频次与净收益未证明                | 扩展机制示例，暂不作核心商业卖点 |
| 对账与财务录入              | 差异清单、金额和处理状态可核对                                     | 系统、数据、资金风险和专业规则显著增加接入成本                  | 没有真实客户与样本前后置         |
| 通用会议纪要/文案           | 容易开始使用                                                       | 现有办公工具替代强，单独购买理由弱                              | 不作首发定位                     |

推荐首批用户画像：B2B 软件/技术服务团队中，负责项目交付或客户支持、每周反复回答同类项目问题、有可合法提供资料的负责人。试点不是让企业先上全员数字员工平台，而是拿一组脱敏资料和一批近期真实问题完成比较。

排除条件：资料不可访问；问题主要要求实时操作/源码核查而非资料回答；没有重复量；答案没人负责验收；现有工具已经足够好。满足这些反例时调整切口，不扩大底座解释为问题都能解决。

## 6. 推荐的差异化组合

定位假设：**让交付和支持团队，把公司资料变成可核对、可复用的答复，减少找人、找资料和逐次复核的投入。** 对外先讲工作和结果，技术标准放到管理与开发者说明中。

| 候选能力         | 用户实际少做的工作           | 最小做法与边界                                                                         |
| ---------------- | ---------------------------- | -------------------------------------------------------------------------------------- |
| 有依据的答复草稿 | 少在多份文档间查找、追问专家 | 明示已支撑、缺资料、冲突和待人工确认的条目；原文可定位，不能把引用存在等同语义正确     |
| 已确认答案复用   | 少重复审核已经处理过的问题   | 人工确认后才进入批准答案集合；保留适用范围、责任人和来源版本，不自动收录聊天回答       |
| 资料变更影响复核 | 少靠人记住哪些旧答案可能过时 | 更新来源时按依赖提示候选受影响答案；先标待复核，不自动断言旧答案错误，也不自动外发修订 |
| 针对差异的复核   | 少从头阅读未变化部分         | 展示相对已确认答案的变化、依据和未知项；新问题仍需完整复核                             |
| 一页工作收益记录 | 少猜测是否值得继续           | 记录采用、人工修正、复核分钟与真实费用，和同任务基线比较；缺数据标未知                 |

这是组合打法和默认体验的差异化假设，不声称上述功能独家。壁垒只有在真实复核成本下降、客户愿意持续使用、部署和维护成本可控后才成立。数据归客户，允许导出批准答案、来源关系和标准 Skill，不以锁定格式制造留存。

最小日常流程：交办工作 → 看草稿与依据 → 接受或修改。模型连接、Skill、MCP、知识处理和预算放在维护设置；不要求普通用户面对节点图、schema 或工具代码名。已确认答案与结果先服务一个工作场景，不扩张成综合任务管理系统。

## 7. 为什么会被发现：分发与购买理由

不能从“产品做得好”推断它会被看见。推荐先用人工辅助交付和窄场景案例验证渠道，再投入产品增长。

1. **验证需求用真实旧单**：由建设者联系少量交付/支持负责人，了解最近一次问题怎样解决、耗时在哪、谁承担错误；请求其在明确授权下提供脱敏样本。本设计不授权代理自动发送邮件或私信。
2. **演示围绕一项工作**：同一批资料和问题，展示原有过程、答复依据、人工修改和总投入。使用虚构/获准材料公开演示，不能发布客户私有记录。
3. **采用门槛有限**：固定一个团队、一组资料、一类工作做小范围试点；现有工具能完成的部分先复用，不要求迁移企业全部系统。
4. **发现入口贴近问题**：面向“项目答疑反复找人”“客户技术问卷总要重写”等具体主题发布可核查案例和标准工作包；同时争取实施服务伙伴/同行转介。这是渠道实验建议，不是已验证渠道。
5. **成交理由可比较**：拿真实任务说明复核投入和维护成本；先尝试范围明确的付费试点，价格与长期计费方式待意愿验证，不靠虚构节省额定价。

“开源 Harness”“支持 N 个 MCP”“N 位数字员工”可以作为技术信任材料，不能代替企业结果案例。先不承诺全行业、完全自治、零接入、自动省人头或无法归因的收入增长。

## 8. 两轮有限实验与停止条件

下面是推荐实验门槛，数字是控制投入的设计建议，不是已测效果、行业标准或服务保证。没有客户证据时不启动大规模基础设施建设。

### 第一轮：先证明有人需要

目标是在约一周的主动接触中找到 5 位符合画像的负责人；时间窗是建议预算，不是自动任务。核对近期具体工作、重复频次、现有最好做法、合法资料、验收责任人和预算归属。

只有至少 2 个团队愿意提供真实样本、共同定义可接受结果并实际参与比较，才进入产品试点。若联系不到、拿不到资料或找不到买方，调整客群/渠道；这不等于立刻证明需求不存在，但不继续以新增技术功能代替客户证据。

先用现有工具与相同 Skill 做少量人工辅助交付，观察价值缺口。如果不用专门平台也能同样省事，可优先交付标准工作包或集成服务，而不是建设完整平台。

### 第二轮：再证明平台增加了价值

建议在 2 个团队累计比较至少 20 项近期真实任务，含资料不足、冲突、过期资料和简单问题。先冻结方法与资料，保留未参与调参的任务；在同类独立任务间交叉安排方案顺序，避免同一操作者第二次处理同题的学习收益被误算。

基线使用客户当前最好方法，并额外比较“现有 Agent + 相同 Skill/MCP/资料”。模型、权限和输入尽量一致，确实无法一致时记录差异，不把收益都归因于平台。人工复核可盲化方案标签；不只使用成功演示样本。

| 判据       | 推荐继续条件                                                 | 停止或调整信号                                   |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------ |
| 人工总投入 | 计入接入分摊、复核、纠错和维护后，同类任务中位数下降至少 30% | 净投入不降、只少了生成时间，或靠额外驻场人力维持 |
| 交付采用   | 至少 80% 任务达到事先约定的可接受标准，事实修正次数可核对    | 漂亮文本多，但实际采用低；只接受简单样本         |
| 权限与隐私 | 无越权、秘密外泄或未经授权外发                               | 出现即停止相关能力并修复，不能用平均成绩抵消     |
| 可复制性   | 第二团队主要通过内容、配置和已有连接上线                     | 每位客户都新增专用 Agent 流程或长期人工兜底      |
| 付费信号   | 至少 2 位有预算责任的负责人愿意付费继续有限试点              | 只称赞演示，不愿投入样本、时间或预算             |

样本小，只用于决定是否继续投入，不宣称统计显著、普适 ROI 或行业可靠性。需要时间验证的收益（维护、资料变化、批准答案复用）单独持续观察，不能在两周试点中假称已证明长期效果。

## 9. 对当前建设顺序的影响

1. 完成标准技能/MCP 设计与必要的可复用底座；以新增第二个服务无需业务代码作为技术验收，CI 只作示例。
2. 商业验证继续围绕既有项目知识助手最小闭环，不等完整工具平台完成，也不预先实现全量 29 表目标。
3. 第一批交付只建设真实资料、带依据答复和最小人工接受记录；批准答案复用在重复需求成立后增加，资料变更影响复核再按维护成本验证。
4. 只有确实减少人工复核和维护，才增加收益自动统计、系统内入口及更多连接；先用小样本表格测量即可。
