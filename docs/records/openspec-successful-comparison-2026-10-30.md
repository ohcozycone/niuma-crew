# OpenSpec 放宽预算后的成功对照与结论修订

本记录是[前次对照](codex-openspec-comparison-2026-10-30.md)的后续真实验证。用户指出，原对照未测出平台成功交付的成本，要求放宽轮次上限后比较成功结果。本次实际调用原 Kimi 模型与已装配工具，未修改开发库中的原对话或平台全局配置。

## 修订后的结论

1. **原运行是一个能在第 9 轮收敛的过程，被 8 轮上限提前终止。** 在隔离副本中保留原来的 8 轮消息、工具结果和 checkpoint，放宽上限后，第 9 次模型调用直接给出答案，未追加工具。之前不能确认第 9 轮是否会回答，现在已实际确认。不能再把该轨迹描述为无法收敛或无止境思考。
2. **平台具备完成原题的能力，实际成功样本的速度和 token 开销也没有落后于本次 Codex 样本。** 从头复测得到一个 5 次模型请求、6 次工具调用、58.324 秒、56,020 token 的核心结论正确样本；Codex 自主取证样本为 6 次模型请求、6 次底层工具调用、87.388 秒、284,657 token。双方工具、模型及运行环境不同，只能作为这些实际样本的比较。
3. **交付稳定性和事实准确性需要分开处理。** 另一份从头运行只用 2 次模型请求、1 次搜索便完成，却错误否认 OpenSpec 的 Skill 集成。加大轮数上限解决了原运行不能交付的问题，不会自动修正证据选择和概念判断。

因此应把问题定位为：**原样本的预算截断，以及不同取证路径下的答案质量波动。** 现有证据不支持“平台架构让模型普遍比 Codex 慢、费 token 或没有能力完成”这一判断。之前失败样本可以用于定位预算边界，却不足以单独说明成功回答的成本与质量；本次已补上成功对照。

## 实验范围与控制

执行脚本为[raised_budget_trial.py](agent-openspec-nonconvergence/evidence/raised_budget_trial.py)。它使用 SQLite 只读 backup 创建权限为 0700 的临时目录与隔离数据库，复用真实应用装配、授权、执行协调器、LangChain Agent、MCP、checkpoint、用量汇总和发布流程。后台扫描和清理服务关闭，只手动执行目标 Run。

冻结的模型 `kimi-for-coding`、系统提示、问题、技能目录、工具定义和账号装配保持一致；原始提示 SHA-256 和首轮输入计数已核对，两次从头运行首轮均为 6,873 token。实验只调整三个运行保护参数：

| 保护参数     |   原值 | 实验值 | 原因                                                     |
| ------------ | -----: | -----: | -------------------------------------------------------- |
| 模型调用上限 |      8 |     24 | 避免在正常回答前截断                                     |
| 图步数上限   |     64 |    256 | 图步数包含中间件和工具，不能继续以旧上限截断更长模型流程 |
| 总时限       | 180 秒 | 600 秒 | 避免扩大轮数后被另一保护提前停止                         |

这些预算值没有注入模型提示。两个从头运行实际只有 2 和 5 次模型请求，未用到 24 次；因此不是“强迫模型花更多轮才回答”。

续跑只在副本内重新激活原 Run；原运行装配了不支持自动重放的外部工具，产品本身不支持直接复活这种终态。实验保留原 checkpoint，实际没有重新执行原来的外部工具，也没有改变正式恢复策略。

从头运行清除副本中的目标动作、来源和 checkpoint，保留原始接受快照与唯一用户问题。一次启动被原登录会话刚失效拦下，尚未调用模型；之后使用同一用户当前仍有效的会话绑定，并完整经过权限校验，没有恢复或改写任何会话的有效状态。所有这些变化都只发生在副本中。

## 答案准确性核查

### 续跑：有答案，但不能全部当作正确结果

第 9 轮正确指出本体是 CLI 与规范框架，也提到 Skill 集成。但它把 `openspec propose/apply` 写成 CLI 子命令，而[官方 CLI 文档](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/cli.md)区分 CLI 命令和 AI slash commands；该命令示例不成立。

它还将 `AngDrew/opencode-openspec` 归为第三方 MCP 封装。该项目的[仓库说明](https://github.com/AngDrew/opencode-openspec)给出的集成是 OpenCode plugin 配置，并说明提供 agent skills 和 custom tools；不能因为工具名为 `openspec_list`、`openspec_view` 就认定其实现 MCP 协议。这也验证了原诊断中关于社区插件概念混入的怀疑。

### 从头运行 1：结束很快，但核心集成判断错误

唯一一次搜索主要呈现旧 Cursor 社区介绍及官网摘要，结果预览为 3000／6615 字符；模型没有进一步读取现行集成文档便作答。答案称项目内指令“不以 Skill 形式挂载”，并用“安装在项目里，不是宿主能力”否认 Skill。

这与[官方支持工具表](https://openspec.dev/docs/supported-tools)明确列出的 Skills 路径及调用方式不符。它说明当前取证和语义判断存在问题，不能将 16,154 token 当作本题准确回答的已验证成本。

### 从头运行 2：核心结论正确，附加断言仍有范围问题

本轮依次进行 4 次搜索与 2 次提取，其中两个模型轮次各请求两个工具；证明平台当前能够一轮发出多个工具请求。它最终区分 CLI／规范框架、本体与提供的 Skills，正确回答原题的主要分类问题。

不足之处是将 `.agents/skills/` 写得过于通用，实际目录随选定的助手变化；依据历史 Issue #319 判断 MCP“目前仅提案”的表述也需要收窄。历史提案与当前全部实现状态不是同一事实。本次认可其核心分类，不将全文每条附加说法判为完全准确。

Codex 自主样本直接读取现行官方初始化和支持工具文档，答案较短，引用可追溯，较少引入额外协议推断。它的这项质量优势与工具选择和回答范围有关，不能仅用模型次数或推理 token 解释。

## 对流程的实际判断

| 维度           | 本次能确认的结论                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------- |
| 思考／模型轮次 | 原轨迹第 9 轮会回答；同一冻结配置从头可在 2 或 5 轮结束，取证路径有明显波动，原样本不是无限循环 |
| 工具调用       | 原平台可批量调用；关键是是否拿到现行、相关的官方证据，以及是否把插件、自定义工具和 MCP 分清     |
| 流程合理性     | 8 次硬限在原轨迹中差一个回答轮；放宽实验预算后均能交付，仍需避免读完工具后没有答案机会          |
| 结果质量       | 完成、快、省 token 与准确分别计量；一次极快作答存在核心事实错误，不能只优化结束次数             |

工程优先级应是：为最终回答保留预算机会；对这种分类问题优先核实现行官方集成说明；区分项目本体、文件型 Skill、命令、原生插件和 MCP 协议。当前实验没有依据要求更换运行框架或普遍新增监督 Agent，也不足以直接确定生产默认上限必须是 24。
