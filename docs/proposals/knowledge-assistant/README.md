## 结论与目标

先建设一个项目知识助手，回答项目文档与已导入研究资料中的问题，提供可定位的原文依据，并通过固定问题集判断是否改进。首版闭环是：**建库与分组 → 导入与预览 → 构建发布 → 员工绑定 → 带引用问答 → 反馈与评测 → 调整资料或处理规则**。

保留一套员工、知识管理和回答执行能力，本轮必须交付 B 混合召回；A 全文上下文可作为小资料集对照或学习子迭代，不是混合检索的前置门槛。重排是 B 的后续优化，不作为第三种首版方案、员工配置选项或连接依赖。Agentic RAG 留给已证明需要拆解、补检索的复杂问题。

本阶段不建设独立任务交办、正式报告验收或写入工具。已有对话承接提问，回答反馈承接质量改进。研发研究员是后续扩展方向，其旧草案不再作为当前开发主线。

学习顺序见[智能应用开发学习路线](../../learning/roadmap.md)，具体学习任务见[首个学习迭代](plan.md)。该子迭代覆盖本文开发阶段 1—3及轻量 JSONL 评测，不能代替本轮混合检索交付；本轮实施顺序见[Notion 方案导航](implementation.md#实施与验收)。正式评测作业/页面后置，不将轻量脚本标为完整评测平台。

## 与统一能力设计的关系

知识实体来自本文既有的资料编辑、构建发布、历史引用与评测要求。[目标模型](../agent-capabilities/README.md#6-知识模型资产发布作业和回答各有归属)已经明确库、组、来源、文档/规则版本、来源块、发布选材和回答证据；没有要求先建技能发布或多实例。

## 策略对比

### 两种首版方案

| 配置         | 做法                                                                      | 要验证的问题                                               | 建设顺序                                       |
| ------------ | ------------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------- |
| A 全文上下文 | 把同一资料快照中所有授权正文与来源标识放进回答上下文                      | 在小资料集内，不做候选检索是否已经足够；检索是否反而漏证据 | 可选的小规模对照或学习子迭代                   |
| B 混合召回   | 同一问题分别做 BM25 与向量检索，经 RRF 融合、去重、按预算补充上下文后回答 | 精确术语与语义改写能否兼顾，能否降低上下文开销             | 首版核心实现、拟议默认；须通过评测再选生产默认 |

A 是全文上下文问答，应用没有先检索一组候选文档；模型注意力不能当成可观察、可评分的检索结果。上传文件给某个产品后由产品自动检索，也不等于把全文发送给模型，实验必须记录实际实现。

重排只对已经召回的候选重新排序，不能直接补回未进入候选的证据。首版保留候选与最终上下文记录，后续需要优化排序时再接入，不提前建设 rerank 连接或接口。切片、上下文补读和查询改写也应逐项改变，以便判断收益来自哪里。

Agentic RAG 决定何时、怎样检索，可复用 B 作为底层检索器。首版不按市场热度追加第三类架构；后续只有复杂题出现稳定的漏查原因时，才以同一评测方法验证有界多轮检索。

### 比较约束

1. 固定知识发布版本、问题集版本、回答模型与连接版本、回答指令、输出上限、历史输入和并发设置。A/B 使用相同授权资料；实际送模证据量可以不同，这正是两种方案的差异，需分别记录。
2. 在整个发布资料能装入上下文的规模轨道做 A/B 成对比较；另用更大发布单测 B 的扩展性，不跨资料版本汇总胜负。A 经预检确认超限时记 `not_applicable`，不静默截断、不自动回退成 B，也不把它计为内容错误。预检误判后供应商拒绝请求属于技术失败。
3. A 与 B 的对比看最终答案、引用、耗时和成本；A 不产生候选排序，候选证据覆盖与排序指标记不适用。全文上下文也不是正确答案上界或 ground truth。
4. B 记录 BM25、向量、融合后的候选顺序，以及补读去重后最终送模的原文区间；首版不做额外重排。开发诊断可复用同一用例比较 BM25-only、vector-only 与 hybrid，不增加业务员工或知识库；重排后置。
5. 开发集用于选择切片、top-k 与模型；保留题用于冻结配置后的验收。模型输出有波动，重复次数与汇总口径见评测章节，不凭一次截图定胜负。
6. 单次请求使用同一知识授权范围；资料、问题或系统指令不同的两个员工回答，不能作为检索策略优劣的证据。

## 知识库入口与全局规则

知识库共用左侧一个入口，页内分“知识资料”和“规章制度”两个 Tab，默认资料。资料资产、导入与外部来源在知识资料下组织；规章制度是自动继承的工作指令，仍由独立规则模块管理，不进入知识检索索引或知识库绑定数量。入口整合已授权，当前实施状态与验收见[规章制度设计](../../reference/organization-rules.md#前端交互)。本次只合并已有教学资料展示与真实规则管理，不表示本设计中的上传、发布、检索或外部连接已经实现。

## 模块职责与协作

知识资产、分组与来源、导入处理、检索算法、问答编排、运行调度与评测是不同职责。首版仍是模块化单体，不增加微服务；下表中的 knowledge、evaluations 与相关文件为待新增位置，不预建空代码目录。

| 模块                         | 拥有的职责                                                        | 协作与边界                                                                               |
| ---------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 前端 knowledge               | 多库、分组、导入批次、处理规则、原文、试检索和发布页面            | API 数据为真值；列表筛选与问答检索分开；教学数据不冒充真实库                             |
| 前端 agents                  | 员工的知识绑定与策略选择                                          | 保存引用 ID，不复制正文或索引；复用现有配置保存与未保存提示                              |
| 前端 conversations           | 提问、流式回答、来源展开、反馈与历史恢复                          | 复用现有 run 订阅；浏览器不执行 embedding 或检索                                         |
| 前端 evaluations             | 题集编辑与冻结、批次状态、A/B 并排对比和评分                      | 复用员工与回答能力，不复制业务助手；策略调试参数集中在评测诊断                           |
| knowledge                    | 库与分组、来源、导入批次、文档/规则版本、解析块与索引、检索和发布 | 提供 `capture_release`、`retrieve`、`read_blocks` 等应用接口；不调度回答模型、不管理员工 |
| agents                       | 当前知识绑定与策略引用规则                                        | 保存绑定前检查库归属与可用发布；与员工配置同事务更新                                     |
| conversations                | 接受一次问答，固定员工、资料与策略依据，创建对话 run              | 复用幂等与额度；不实现切片、RRF 或评测评分                                               |
| runtime                      | 装配知识问答：可选问题独立化 → 获取上下文 → 回答 → 引用校验       | 同一 `answer_question` 用例供对话与评测调用；不把流程硬编码到队列扫描循环                |
| runs                         | 对话执行状态、阶段、实际上下文与引用记录的关联和安全查询          | 记录发生了什么，不把技术成功当作答案正确                                                 |
| evaluations                  | 问题集版本、证据标注、评测批次、逐题结果与评分                    | 调用同一问答用例；不复制检索和提示词实现，不反向修改生产绑定                             |
| model_connections / llm      | 首版聊天与 embedding 的加密连接、能力校验及适配                   | 业务侧使用能力接口；供应商 SDK、向量维度与协议在适配端处理；rerank 后置                  |
| bootstrap / runtime 基础设施 | 单进程生命周期、调度、资源准入、取消与重启清理                    | 对话、导入、构建、试检索与评测共享有界执行资源；网络调用不占 SQLite 事务                 |

当前 Run 的对话外键保持不变。知识导入、索引构建、试检索和评测批次有自己的持久化作业记录，由同一生命周期驱动器接入有界执行；共享取消、准入和模型调用接口，不复制整套 Runner，也不为复用表强造聊天消息。首版导入/构建/试检索/评测后台作业合计最多一个活跃，模型并发与总队列额度和对话共同受限，不能各自默认开满。

准入服务需将对话和所有知识/评测作业的排队与活跃数量纳入同一事务检查，不能继续只统计 runs。模型调用使用共享容量门，后台批次按题、导入/构建按批请求容量；批次本身不再持有同一容量等待子调用，避免嵌套占用造成死锁。解析、切片预览、排序和向量计算放工作线程，SQLite Session 不跨线程复用。

## 知识管理与发布

### 多知识库与库内分组

正式知识入口是本人可访问的知识库列表，不再把差旅示例固定成全站唯一知识库。用户可创建多个库，例如“行政制度示例”“项目研发资料”“产品客服手册”；同一库可被多个员工引用。首版每次问答仍使用员工绑定的一个库，跨库联合检索后置。

| 对象         | 首版职责与关系                                                                         | 不承担的职责                                       |
| ------------ | -------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 知识库       | 组织业务资料范围，维护发布和默认处理规则；可选一个库级分类标签，用于列表筛选           | 不是一个上传文件、一个检索算法或一个 Wiki 目录     |
| 文档分组     | 一个库内的一级分组；每篇文档至多归一个组，也可未分组；支持改名、调整顺序、批量移动文档 | 不改变访问授权或员工问答范围，不隐式排除其他组     |
| 文档标签     | 同篇文档可有多个标签，供列表筛选；主题标签与草案/实现状态分别管理                      | 不把标签自动解释为“已审核”或权限                   |
| 知识来源     | 一个库可有多个来源；首版为手工资料和内置示例包，维护来源 ID 与原始条目标识             | 不将分组等同于来源，不为每次上传创建一个新的知识库 |
| 文档与版本   | 文档有稳定 ID；原文、来源说明和内容状态变化形成不可变版本                              | 同名文件不能自动认定是同一文档                     |
| 处理规则版本 | 一个库选择一套默认规则；构建时固定具体版本，后续可重建索引                             | 不将 A/B 回答方案复制为两个资料库                  |

首版只做一级文档分组，不做嵌套目录、目录权限、知识库的多级分组树或源 Wiki 目录的强制一比一映射。库级分类只是一个可选文本标签；与库内文档分组是不同筛选条件。

分组名在同一库内按去首尾空白和统一大小写后的名称唯一，不同库可同名。移组只能在同一库内操作并校验全部文档归属；跨库复制/移动暂不提供。删除组时先在同一事务把文档移到“未分组”，不删除原文、版本或引用；“未分组”是空 group_id 的展示，不是一条可删除分组记录。

分组、排序和主题标签属于当前管理信息，可直接调整，不重建索引。首版它们只筛选管理列表，不作为检索过滤条件，也不拼入模型上下文；文档内容状态、生效日期等证据语义仍属于文档版本。页面明确“当前分组筛选不改变员工使用的已发布资料”，避免用户把目录浏览当成问答范围设置。

### 上传与导入

在库详情中用统一的“添加资料”入口接入以下内容，不建设独立上传门户。

| 入口         | 首版输入                                                     | 后端行为                                                                                    |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 上传文件     | 单个或批量 UTF-8 `.md`、`.txt`，选择目标分组；批次上限待验证 | 接收实际字节，检查类型、编码、文件与库额度；原文件按服务端 ID 保存，不使用用户路径落盘      |
| 粘贴文本     | 标题、正文、可选来源标签、目标分组                           | 与文件导入走同一版本、解析与构建流程，不单独维护一套知识正文                                |
| 导入现有示例 | 明确选择差旅教学包，并显示“虚构、待审核、5 篇文档”           | 只读取服务端登记的样例标识和 manifest 中的 documents 清单，核对文件哈希；不接收任意本机路径 |

已有 5 篇 Markdown 无需重写；普通上传即可复用，样例入口只简化选择。12 道开发题与参考答案通过评测页导入，不随示例知识一起入库。示例不会因应用启动自动进入所有用户的库；用户显式选择目标库与导入后才创建资料。

导入前展示待处理清单、文件大小、目标分组和已有同名/同内容提示。创建新文档与替换已有文档是显式操作；替换必须提供文档 ID 和预期版本，不能根据文件名、目录名或内容相似度猜测。新文档保留独立身份，即使正文相同；原文件存储可按哈希复用，不能因此合并业务文档。内置样例按库内来源条目标识识别已有文档，同一包重复导入无变化时返回已有结果，有变化时展示替换计划。

一次导入创建一个批次，每项有稳定 item_id。整个批次和单项分别记录状态、目标文档、创建/替换方式、源文件哈希、处理规则版本及错误。相同 client_request_id 和请求摘要重发返回原批次；换内容为 409。导入准入在同一短事务中检查并预留已导入及待处理的文档/字节额度，失败或取消后释放未使用额度，不能让多个排队批次各自通过后超出库上限。处理失败重试仅新建失败项的尝试，不重复创建成功文档；替换前重新校验预期版本，过期返回冲突。

批次状态沿用统一 knowledge_jobs：`queued → running → succeeded / partially_succeeded / failed / cancelled / interrupted`，可经 cancelling；单项使用 queued/running/imported/failed/cancelled/interrupted。原文件先写入临时存储，再事务保存批次及引用，确认持久化后交给后台解析；崩溃留下的无引用文件按保留期清理。网络上传进度由浏览器观察，不代表服务端已解析或可问答。

解析成功的文档进入待发布资料区，显示“已导入，待构建/发布”。一项失败不丢弃其他已导入文档，但批次必须显示部分失败；失败项不能伪装空文档。构建时用户可显式排除失败项或补齐后重建，不能自动把部分成功内容发布。取消保留已持久化的暂存资料，不自动发布；应用重启不自动重发外部请求。

### 文档与解析

上传生成不可变文档版本，原文件与规范化文本分别保存；记录内容哈希、解析器版本、标题、可选来源路径、导入时间，以及人工确认的资料类型和状态。来源路径只是标签，服务器不能据此读取任意本机路径。一个文档绑定一个来源；手工上传与粘贴共用该库的手工来源，具体输入方式记录在导入项中。

文档的设计状态、生效时间、导入时间与实现状态分别表达。Markdown 中自动识别到的状态先供确认，缺失记 unknown；不通过较新的上传时间推断内容更权威。问“当前是否实现”时，草案只能支持“计划怎样做”；仅导入文档不等于已核查源代码，答复应明确依据是文档。

解析生成稳定的来源块标识，关联文档版本、解析版本、章节路径、原文位置与正文哈希。来源块是可定位依据，检索切片可以覆盖或组合多个来源块。调整切片不改原文位置与旧块 ID；以后升级解析器若改变规范化正文或来源块边界，要保存新的解析版本与产物，不覆盖旧块，评测引用也需复制题集重新复核。

### 处理规则与检索设置

库内“处理规则”提供可用默认值，并支持保存新版本、预览和重建；首版不做任意脚本、插件式解析器或通用流水线画布。保存规则形成不可变版本，库当前选择指向最新指定版本；构建固定所选版本，不因用户再次保存而改变进行中的作业。

具体算法、存储候选、参数状态与模块边界由[Notion 分层方案](implementation.md#入库主线)维护；下表只说明页面提供的能力及配置变化影响。

| 环节         | 首版规则与页面能力                                                                                         | 改动的影响                                                                |
| ------------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 解析与清洗   | Markdown/文本；保留标题层级、代码、表格、日期与状态；仅规范化编码/换行等明确规则，不删金额、否定或版本限定 | 解析器版本只读展示；以后升级需新解析产物，不改旧引用                      |
| 切片         | 按标题/段落组织、长度兜底；规则和待验证参数见[分块模块导航](implementation.md#入库主线)                    | 改边界或长度生成新片段及 BM25/向量索引，复用原文与未变化的来源块          |
| 中文与标识符 | 使用支持中文并保留英文模块名、路径、配置键的分词规则；展示分词器版本                                       | 更换 BM25 分词规则需重建词法索引，不能把空格分词当中文基线                |
| 向量化       | 选择已校验的 embedding 连接；记录模型、维度、tokenizer 和输入上限，未配置时 A 仍可用                       | 换模型/维度重建向量，禁止跨向量空间混用；只改凭据仍检查连接版本与中断策略 |
| 引用与状态   | 检索输入带标题、章节与内容状态，引用回到原始来源块；首版不额外生成模型摘要                                 | 影响索引文本的版本变化需重建，历史答案仍指向旧发布                        |
| 检索与上下文 | 受控的双路召回、RRF、去重补读与预算；参数见[检索实现](implementation.md#召回主线)                          | 这些是请求时检索参数，单独快照，不改变文档版本；无重排                    |

切片计数使用受控的本地 tokenizer 预设并记录版本，不要求先配置远程 embedding。B 调用前还按 embedding 模型实际限制复查输入；A 按回答模型检查全文预算。两者不能用同一个“字节数近似 token”代替真实限制。

首版可编辑的处理参数限于切片目标、上限、重叠和 embedding 连接；清洗、解析器和中文分词使用受控预设，只展示实际版本。target/max 必须为正整数、overlap 为非负整数，约束为 `0 ≤ overlap < target ≤ max`，并检查具体模型输入上限，不接受仅数值合法但供应商无法处理的配置。A 的 token 预算按回答模型计算，不依赖配置 embedding 后才可运行。

处理规则与检索设置分开：前者影响资料怎样形成片段与索引，后者决定请求怎样选择证据。首次实现使用固定、有版本的检索预设，不开放任意 query 脚本；高级 top-k/RRF 调整留在开发评测配置中，不塞进常用上传表单。选择 A/B 仍由员工/评测配置负责。

规则预览只针对指定的候选文档与已保存规则版本，返回来源块、片段文本、token 数与原文位置。它使用与构建相同的解析/切片实现，但不调用 embedding、不发布，也不计作完整检索测试。预览受批次大小与执行时限约束，结果关联规则版本防止用户看错配置。

试检索必须选择具体 ready 发布，显示线上或候选标识、实际规则版本与查询。A 显示全文范围和输入预算，B 展示两路候选、融合与最终上下文；不生成回答，也不替代端到端评测。修改参数后若索引不匹配，明确要求构建，不能在预览或试检索中悄悄重建。

### 构建与发布

每次构建固定候选文档版本、解析版本与块清单、处理规则版本、BM25 分词与 embedding 模型/维度，形成不可变发布候选。A/B 使用同一资料清单，A 不执行候选检索，B 使用该发布的索引。分组/主题标签不进入首版发布检索范围规则。

先准备原文与来源块即可发布 full_context 版本，不依赖 embedding；后续用同样文档版本构建 hybrid 发布，再运行 A/B。B 缺少匹配索引时明确不可运行，不临时补造索引或降级策略。改默认处理规则不立即切换线上发布，页面显示“配置已保存，线上仍使用旧规则”，由用户完成预览、构建和发布。

构建尝试保存在 kind=build 的 knowledge_jobs，状态为 `queued → running → succeeded / failed / cancelled / interrupted`（可经 cancelling）；候选发布状态单独管理，产物成功且校验通过才能进入 ready。产物准备好并校验哈希后才能发布；短事务检查预期库 revision、候选完整性和归属，再切换 active_release_id，不在事务中生成 embedding。原文、来源块与索引先准备，数据库指针决定可见性；未发布孤立产物可清理，不得用于普通问答。

首次发布前库显示不可问答。更新中旧发布继续可用，构建失败不污染旧索引。标题、来源标签、内容状态变化也形成新文档版本；停用文档通过新发布生效，停用整个库立即禁止新问答并在后续调用前复查。旧版本、旧块和旧引用保留；删除库采用归档，不硬删历史证据。无永久擦除入口，后续删除合规需求需单独定义。

SQLite 保存库、分组、来源、文档/规则版本、规范化正文、来源块、统一知识作业及导入项与发布清单；应用数据目录保存服务端 ID 命名的原文件及不可变索引。BM25 与向量存储通过 LangChain 检索接口接入，后端候选以 Notion 决策 D04/D05 为准，不把原精确矩阵方案视为已采纳。按用户范围、发布与索引配置限制查询和缓存，首版建议不额外部署独立检索服务。处理规则变化产生新派生数据，不改原文件；达到规模上限或实测性能不足再更换存储适配器。

### 企业 Wiki 扩展边界

首版只实现手工与内置示例来源，不实现 Wiki 授权、同步任务、外部检索调用或企业权限映射，也不显示可点击但不可用的连接按钮。来源页面可用文字说明后续接入方式，不创建空连接器代码、凭据表或同步调度器。

| 后续模式         | 与平台的边界                                                             | 不能混淆的事项                                                                  |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 同步原文后索引   | 连接器枚举授权空间/目录的条目与变更，将内容交给现有导入、版本和构建流程  | Wiki 是原文维护方，平台保存只读副本；不做双向回写；不能按每层目录自动创建一个库 |
| 调用外部检索服务 | 查询适配器接收问题、用户授权范围和上限，返回证据片段、来源标识与版本信息 | 不假装已执行本地 BM25/embedding；外部片段不能自动参加全文 A/B 比较              |

逻辑契约应允许来源提供：稳定 source ID 与 source_item_key、原始 URL/路径、上游版本或 ETag、更新时间、内容/哈希、删除标记、授权信息，以及可选增量游标。手工与示例来源也保存自己的稳定条目标识；未来外部身份映射可沿用 `(source_id, source_item_key)`，不根据标题判断更新。不在首版数据库中提前填充虚假的企业同步字段；具体连接器落地时再扩展存储契约。

未来同步按批提交新候选，内容更新经构建/发布生效；删除与授权撤销必须有独立的拒绝路径，不能等管理员发布下一版才停止越权访问。授权同步未确认、连接故障或映射不完整时不能扩大可见范围；索引、缓存、证据阅读与历史来源访问都需纳入策略。企业权限模型、故障后的资料可用性与保留期，在第一个真实连接器前补完整设计。

外部检索结果需记录实际返回时间、查询、来源定位与可用版本。若无法固定全文、稳定版本或重放查询，评测必须标注动态来源与不可比项，不将它冒充当前的固定资料 A/B 实验。只有选定实际企业系统、验证接口和权限语义后才实现连接器。

## 员工绑定与问答

1. 管理员在员工配置中选择自己可访问且已发布的库及策略；保存时后端校验。未绑定保持普通聊天，已有员工默认不变。绑定了库但无可用版本属于配置错误，不静默退化成无资料聊天。
2. 提交消息时，保存用户输入、员工配置、库 ID、具体发布 ID、策略版本、模型连接版本及预算；与现有 run 一起事务提交。相同幂等请求返回原 run；显式重试是新执行，可固定当时最新发布并展示依据变化。需要严格重放旧依据时使用评测，不伪装成普通重试。
3. 简单追问可增加至多一次问题独立化请求，只使用本次固定的成功对话历史；输出独立问题或请求澄清。历史回答不是事实来源，答案事实仍要有本次证据。A/B 使用同一个独立化结果，评测的共享步骤计量见评测章节。
4. A 按固定顺序组织全部授权正文，每个来源块提供标识与状态；B 执行 BM25 与向量两路召回，融合去重，选取证据并补充必要的邻近上下文。候选数、RRF 参数与最终 Top-K 分别验证并保存到策略快照，不沿用旧草案数值；是否增加重排按真实失败原因另作决策。
5. 以实际模型输入上限减去系统指令、问题、历史、保留输出和安全余量得到证据预算。B 对候选按确定规则整块选取，记录排除原因，不静默截断原文；A 放不下时明确超限。字节限制与 token 限制分别检查。embedding 请求也检查供应商输入与批量上限。
6. 回答指令要求区分事实、文档中的计划、推断和未知；对重要结论输出来源编号。资料缺失或冲突可以正常回答“目前资料不足”，不能补写不存在的项目实现。低相似度不等于一定无答案，不凭单个分数自动断言。
7. 保存实际送模证据和来源映射；流式文本是暂存回答。完成后检查来源编号是否存在、是否属于本次上下文、可选引文是否匹配原文；失败标记 `citation_invalid`，保留诊断但不显示“引用检查通过”。ID 有效不代表语义支持已验证，后者由人工评测检查。
8. 终态持久化后显示回答及可展开的原文、版本、状态和来源位置。反馈关联具体回答，支持“有用／有问题”、原因和可选纠正；纠正不会自动覆盖知识或加入评测答案。

知识问答拟沿用现有 180 秒总时限，最多两次聊天请求（可选独立化、一次回答）；B 另有一次 query embedding，A 不调用 embedding，无重排或自动生成修复循环。每阶段有子超时与取消传播，具体限制按供应商实测调整。取消与迟到结果遵循现有终态规则；无命中是正常边界，检索服务故障则是技术失败，不能混记为资料不足。

知识问答扩展当前聊天快照协议，由 run_knowledge_contexts 与实际知识步骤/答案表达资料使用，不另造聊天模式或作业 Run。SSE 仍传安全状态摘要，来源明细按权限另取；刷新从数据库恢复，不重跑检索。来源与上下文准备在模型请求前持久化，数据库不可用时停止后续外部调用。

## 评测题集与结果比较

### 建题与冻结流程

先复用已有资料与题集，核对后固定资料发布版本，再补真实使用中缺失的问题。已有差旅包的 12 道题全部作为公开开发/回归题，不重新编写，也不改名成为保留题。适配时沿用题号、answer_points、must_not 与原文引文，将它们对应到下文要点、禁止结论和证据位置；缺少的问题族、评分字段和区间映射再补。

题集评测的是“给定这份资料，系统应该怎样回答”，不是考模型的外部常识；资料本身是否覆盖工作需求另列缺口。以下 40 题是后续真实项目题集的扩展采样计划，并非先重建 40 题才能开发或联调；本轮未新增真实题目或执行评测。

| 主类别         | 计划题数 | 题目重点与项目示例                                            |
| -------------- | -------- | ------------------------------------------------------------- |
| 精确术语与标识 | 8        | “RUNNER_LOCK_FILE 保护什么”；模块名、路径、配置项是否准确命中 |
| 同义表达       | 6        | “换个大脑会影响正在回答的问题吗”；用自然语言描述已有概念      |
| 多处资料综合   | 8        | “员工知识配置怎样影响问答”；需要多个章节共同支持              |
| 版本与状态判断 | 6        | “装配技能后会进入模型上下文吗”；区分配置、目标设计与已实现    |
| 冲突处理       | 4        | 当前说明与草案表述不一致时，指出差异与适用范围，不任意选边    |
| 无答案         | 4        | 在所选资料确实未提供某项参数或决定时，不编造具体答案          |
| 简单追问       | 4        | 固定前文后问“那它重启后呢”；检查问题独立化及证据重新获取      |

主类别互斥用于计数，题目可另带多个标签。证据标注完成后再确认题目属于可完整回答、部分可回答、资料冲突、无答案或需要澄清，不能因为某个方案没找到就标为无答案。

1. 从真实提问、查找记录和已知易错点收集候选，人工确认业务价值；模型可以辅助起题，不自动确认答案。
2. 在固定发布资料中找出最小必要原文，标注答案要点、禁止结论与边界处理。若现有资料不能支持预期答案，要么改题/预期，要么登记资料缺口；补资料则生成新发布后重新冻结。
3. 按 `family_id` 归组：同一事实的改写、同一追问链及共享答案模板的近似题属于同一族。按族划分约 28 题开发集与 12 题保留集，数量可因族边界略调；两组都覆盖关键类别。禁止把同义改写分到两组后宣称独立验收。
4. 人工复核证据、禁止结论、问题归属和重复题。首版单人可以隔一次工作会话复查；记录复核人和时间，不假装具备独立多人标注的一致性。
5. 题集从 draft 冻结为 frozen：固定资料发布 ID、题目、划分、评分规则版本与默认通过门槛。开发集可看参考依据并调参；保留集参考内容在正式评分前不主动展示，开发者不得用它调参，这不是对管理员的保密权限保证。
6. 正式运行后如按保留题失败进行修正，该题可作为回归题，但需要新补未见题才能再次声称独立验收。改题、改评分规则或更新资料均创建新题集版本，旧批次仍指向旧版。

### 单题结构与证据标注

| 字段                              | 内容与约束                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------------- |
| case_id / family_id               | 版本内稳定题号与问题族；同族不跨开发/保留划分                                      |
| category / tags / split           | 一个主类别、多标签、dev 或 holdout                                                 |
| question / history                | 原始问题；追问题保存固定前文，非追问题为空历史                                     |
| answerability / expected_behavior | full、partial、conflict、none、clarify；说明应该回答、限定回答、提示冲突或澄清什么 |
| required_points                   | 带 ID 的必要要点；各要点标记是否关键，不要求逐字匹配标准答案                       |
| forbidden_claims                  | 明确不允许的结论，例如“当前技能已进入执行上下文”                                   |
| evidence_groups                   | 每个必要依据的组 ID、关联要点、替代证据组合与原文位置；详见下文                    |
| boundary_rubric                   | 无答案/冲突/追问怎样才算合格，是否需要引用证明冲突；没有时为空                     |
| review_metadata                   | 标注人与复核时间、规则版本；资料绑定在题集层，单题不能私自切换发布                 |

证据位置使用不可变文档版本、来源块 ID 与最小原文区间。区间在保存的规范化块内按 Unicode 字符偏移 `[start, end)` 定位，并保存引文与哈希；不是字节偏移，也不是切片 ID。标注界面通过选择原文生成位置，不让用户手工填写偏移。JSON 导入时后端校验引文与实际内容一致。

一个证据组可有多个替代组合，组合内的区间必须全部覆盖，组合之间满足任意一个即可。即“组间逐个计数、组内替代组合为 OR、一个组合内多个区间为 AND”。同一原文被多个重叠切片命中只算一次，最终上下文可由多个片段合并覆盖一个区间。证据完整覆盖才能算命中，不能只因位于同一大章节就判定命中。

例如必要组 G1 可由 a 或 b 支持，必要组 G2 必须同时读到 c、d。候选包含 a、c 时只命中 G1；最终上下文经补读包含 a、c、d 时两个组均命中。这样既允许替代证据，也能识别多处综合时遗漏一半依据。

题目额外记录 `evidence_annotation_complete`。只有确认必要组标注足够完整的题才计算证据覆盖；开发题的不完整标注显示 `annotation_incomplete` 并排除对应指标，保留答案人工评分；正式保留集的 full/partial/conflict 题必须在冻结前补全证据组。对 full/partial/conflict 题通常需要证据组；none/clarify 题可为空，不用“零个必要组”自动计 100%。评测题、预期要点、证据标签和评分意见均不进入被测知识库或回答提示，只有评分页面可读取。

### 批次执行与固定条件

首版每题各执行 A/B 一次，默认依次交替 A→B、B→A，保存顺序与随机种子，降低顺序影响；不把两个方案同时压满服务后把排队差异当成算法延迟。批次固定员工配置、资料发布、题集版本、回答模型与连接版本、指令、输出上限、历史与策略参数。模型不可完全确定时记录可设置的采样参数，不承诺同配置逐字复现。

两种方案调用同一 `answer_question` 用例。评测用固定题目历史，不把前一题生成结果带到后一题；模型答案不写入普通聊天历史，也不回填题集。简单追问先共用一次问题独立化结果；生产执行和评测共用相同步骤，评测只固定其输出，不能把参考答案用于改写。

创建批次时先为每个计划键 `(case_id, strategy, repetition)` 创建 not_run 结果槽，取消后仍保留未执行槽，避免分母缩小。每个结果保存状态、实际问题、原始答案、候选与最终原文区间、引用、阶段耗时、用量、错误及评分 revision。状态区分 succeeded、failed、cancelled、interrupted、not_run、not_applicable。技术成功和质量通过是两项判断；引用编号失效属于运行检查失败，仍保留原始文本供诊断。

额外重复实验先选固定的易波动题做各 3 次，标记为独立重复批次；报告同题通过次数和波动，不将 3 次当成 3 个独立问题合并进首轮通过率。保留题不能挑表现最好的一次进入主报告。

### 指标计算口径

以下比例在页面显示为百分数，后台保存分子、分母、口径版本及排除原因。`N/A` 不计零也不计满分；每项显示有效样本数。涉及人工判断的指标在评分完成后才生成正式值。

**混合召回诊断**：对题 q，Gq 是已标全的必要证据组集合，hit(g, X) 表示集合 X 完整覆盖该组任意一个替代组合。

- `候选证据覆盖@k(q) = Σ hit(g, 融合排序前 k 个候选的原文区间并集) / |Gq|`，首版记录 k=10、20；k 超过候选数时取全部候选，显示实际数量。
- `最终证据覆盖(q) = Σ hit(g, 实际送模原文区间并集) / |Gq|`，包含补读上下文且对重叠区间去重。它不叫 Recall@k，因为最终输入受 token 预算而非固定片段数控制。
- A 没有候选召回与排序，上述候选指标显示“不适用”；可以显示“全文包含必要证据：是/否”校验资料一致性，但不计入检索排名。两种方案都另查最终上下文预算和来源是否正确。
- 这是本项目按必要证据组定义的覆盖指标，不冒充穷举文档相关性后的标准检索 Recall。首版不展示 Precision@k、MRR 或 nDCG：必要证据标注不等于对所有候选完成相关性标注，未标注也不等于不相关。

**A/B 共用答案指标**：人工先勾选必要要点，再标记原子事实陈述及其引用。事实陈述按独立可核查结论拆分，不按句号数量计算；新增的无依据断言也必须纳入，不能只检查题目预期要点。

| 指标           | 单题计算                                                                              | 分母为零或特殊情况                                                                    |
| -------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 必要要点覆盖   | `(正确要点数 + 0.5 × 部分正确数) / 必要要点数`；缺失或错误计 0                        | 无必要要点时 N/A；部分正确需说明缺了什么；错误的关键条件同时触发严重错误标记          |
| 事实正确       | 人工检查所有事实与条件，含额外断言；没有事实错误或禁止结论记 1，否则 0                | 纯拒答/澄清无事实时 N/A，不因“没说事实”获得满分；资料过期但忠实复述也不自动算事实正确 |
| 引用定位合法率 | `合法引用关联数 / 全部引用关联数`；合法要求来源在本次上下文内、位置与引文有效         | 无引用时 N/A；无效编号仍计分母；同一“事实 ID＋来源区间”重复出现去重                   |
| 引用支持率     | `得到所引证据充分支持的已引事实数 / 已引事实数`，由人工判断；多来源共同支持可一起判定 | 无已引事实时 N/A；无效引用无法支持，计 0；部分支持不算充分支持                        |
| 事实引用覆盖率 | `有充分支持引用的需证据事实数 / 全部需证据事实数`                                     | 有事实却没有引用时为 0；无需证据事实时 N/A；不能靠只引用一句正确话掩盖其他无依据结论  |
| 边界处理通过   | 按该题 expected_behavior 与 boundary_rubric 全部满足记 1，否则 0                      | 常规 full 题此项 N/A；partial/conflict/none/clarify 分类别汇总                        |

事实正确性相对于题集人工复核的有效资料和状态判断，而引用支持性只检查“原文是否支持该陈述”。若评分时发现资料本身错误或标注不成立，标记 `needs_annotation_review`，暂停该题质量比较；修正题集后开新批次，不能为一个方案临时修改答案。

逐题通过规则在运行前冻结。首版建议：必要要点全部正确（覆盖=100%）、事实正确且无禁止结论/严重错误、所有需证据事实有充分支持引用、全部引用定位合法、适用的边界规则通过；N/A 项仅在确实无适用事实或要点时豁免，不免除 expected_behavior。无答案题若没有事实陈述且按要求说明缺失，可通过；冲突题仍需引用相互冲突的材料。人工还需确认确实回答了所问问题，不能靠回避问题通过。

必要要点、证据和引用比例先按题计算，再对非 N/A 且已评题取算术平均，避免长答案凭陈述数量主导总分。事实正确与边界通过按适用已评题计通过数/题数。每项显示自身分母，不将不同适用题数的百分数直接作总体优劣结论。

**批次完整性与边界错误**：

- `执行完成率 = succeeded / (计划执行数 - not_applicable)`；取消、中断、尚未执行单列，不伪装内容错误。未结束批次只显示临时进度，不据此选默认策略。
- `已评回答通过率 = 质量通过数 / 已完成且人工评分完整的结果数`；同时显示失败数与待评分数，不能只展示该条件通过率。
- 批次结束、适用结果均为终态或明确未执行，且成功结果完成评分后，`端到端通过率 = 质量通过数 / (计划执行数 - not_applicable)`；技术失败、取消、中断或未执行均未交付合格答案，不进入分子。没有适用题时 N/A。
- `无答案乱答率 = none 题中给出无依据具体答案的数量 / 已完成并已评 none 题数`；`过度拒答率 = full 题中无正当理由只拒答或只要求补资料的数量 / 已完成并已评 full 题数`。partial/conflict 不混入这两个分母，另按边界规则评分；技术失败另见执行完成率。

例如某方案 40 个适用计划结果，38 个成功且完成评分，其中 36 个通过、2 个未通过，另有 2 个技术失败：已评回答通过率为 36/38≈94.7%，端到端通过率为 36/40=90%。这只是口径示例，不是项目实测成绩。

**性能、成本与资料质量**：

- 每个结果记录等待容量、问题独立化、检索/上下文准备、回答生成、校验落库时间；单题计时从该题进入执行准入开始，不从整个批次创建开始。批次总墙钟时间另列，失败耗时不混入成功延迟而单独显示。
- 成功结果的 p50/p95 按排序后的第 `ceil(p × n)` 项取值，p 为 0.50/0.95；同时显示 n，小样本不据此承诺服务指标。原始服务耗时与排队时间均保留。
- 追问共用的问题独立化耗时/费用独立保存。比较单方案完整请求时，用共享预处理加本方案分支；这属于可比请求估算。实际批次总费用只计一次共享步骤，不能双算；两项分别标识。
- 聊天输入/输出、query embedding、建索引用量分开。已知请求费用为各用量乘冻结的对应单价之和；任何必要用量或单价未知则显示“部分已知”，不能当成总费用或计零。索引建设是一次性成本，问答是逐次成本；如展示摊销，必须注明假设问题次数 Q，按 `建库费用/Q + 单次问答费用` 估算。
- 资料覆盖作为题集侧诊断：按 answerability 展示 full/partial/conflict/none/clarify 数量与具体缺口，记录过期/状态不明材料。不把人为多出简单可回答题造成的覆盖上升当作技术进步；比较不同资料集合需固定问题族、模型与检索参数，另建实验批次。

`/evaluations` 提供题集和批次列表；`/evaluations/{id}` 打开批次对比。草稿编辑、评分与批次查询的后端真值及权限遵循后文接口，首版不建设通用标注平台。

逐题成对结果使用确定规则：一方通过另一方未通过则记通过方胜；双方通过则质量平局，成本/延迟另外比较；双方未通过记“双未通过”，不挑较像正确的一方；任一技术失败、N/A 或评分未完成分别归入失败、不适用、待评，不能偷偷剔除。部分得分保留作诊断，不自动折算为胜负。

页面显示“A 胜、B 胜、均通过、均未通过、单方/双方执行失败、执行中/未执行、不适用、待评分/标注待复核”的题数。执行失败包括 failed、cancelled、interrupted。依次优先判断不适用、已知执行失败、执行中/未执行、待评分/标注待复核，剩余题才判断通过关系；每题只进一类，所有互斥题数之和等于选中划分的题数。筛选或展开不会改变底层分母，汇总需注明当前是全批次还是筛选子集。

可比请求的费用和延迟在双方均成功的共同集合另算；错误导致少调用模型的方案不能据此宣称更省。补充的选定重复题页显示每次结果及同题通过次数，不覆盖首轮答案。刷新后恢复筛选与当前题定位，已保存评分在数据库；保存中禁止重复提交，失败保留本地评分草稿，revision 冲突提示重新读取，不覆盖他人修改。SSE/轮询断开只停止观察，不重新执行批次。

### 首版验收与选择默认策略

正式比较前冻结逐题通过规则、保留题范围和严重错误清单。质量门槛在题集审核后、正式运行前明确，旧草案的通过数量不作为默认要求；权限、旧引用、取消和更新一致性专项边界仍需验证。若未达约定门槛，列出失败继续开发，不靠更改分母或降低标准宣布完成。题量小只能证明这批场景可用，不能证明企业客服泛化。

两种方案均达到门槛时，再按常见问题的复核成本、完整请求耗时、实际费用和资料规模选默认；A 超出适用规模时说明容量原因。某方案没达到门槛仍保留其诊断结果，不因预设 B 是默认而隐藏 A 的优势。重排只在 B 的错误集中到候选排序与证据选择时，再以新配置做受控优化实验。

## 普通聊天与私有历史目标（未实现）

提交每轮运行时固定可访问发布及策略，模型按任务激活知识能力：全文按预算读取，混合使用匹配索引，实际检索和引用另记步骤。没有使用资料时不能宣称“根据知识库回答”。显式要求资料回答但资源不可用时明确失败，不换库或静默降级。

知识按创建者归属，绑定共享员工不自动共享资料。接收具有私有上下文的运行时，对话拥有者必须是发起者且收紧为 owner；私有消息、运行、SSE、步骤、引用、导出及缓存不能沿用当前 resources:all 的绕过规则。未授权资料不进入能力目录或快照；全链权限规范只在[统一设计](../agent-capabilities/runtime.md#权限与敏感数据)维护。

## 权限与故障边界

当前首版不开放游客知识问答、来源访问或评测。员工绑定不授予用户知识访问权限；所有资料版本、检索缓存、问答、反馈与评测查询均检查用户归属。不同 owner 的库不混合检索；缓存键包含用户范围、发布版本与索引配置，后端不能只在浏览器隐藏来源。

上传内容是资料，不是运行指令。Markdown 里的命令、链接和提示不触发执行或抓取。上传文件名不作为磁盘路径，原文件使用服务端生成标识存储；不得读取仓库 `.env`、密钥或用户未选择的目录。资料会发送到选定聊天与 embedding 服务，导入与连接配置页面明确这一数据流。

新 embedding 连接沿用加密凭据和安全投影，不在快照、日志或来源里记录 Key；供应商地址由受控预设维护。文档停用、用户授权失效与取消在后续外部调用前复查，已发出的请求费用无法撤回。历史证据读取仍需归属检查，库归档不把私人资料变成公开资料。

单进程重启将活跃构建、评测和问答标记 interrupted，不自动重发外部请求；候选索引不发布，已完成题保留。取消发生在发布前，候选保持未发布；取消与发布并发通过库 revision 和作业终态复查确定一个结果。数据库失败停止新增外部调用；单个来源无法解析时返回明确错误，不把失败正文当空文档发布。

## 开发顺序与阶段验收

本表维护专题完整能力的阶段拆分，包含正式评测作业和页面。本轮四项能力的最小交付按[Notion 分步交付](implementation.md#实施与验收)，其中混合检索、来源与轻量真实评测必须完成，全文基线可选，正式评测平台后置。企业 Wiki 和重排不计入本轮；先用存量资料贯通，不因规划更多题或连接器推迟可用功能。

| 顺序 | 增量与依赖                                                                                                              | 阶段验收                                                                                                                                                   |
| ---- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 核对现有 5 篇差旅文档、12 道开发题及参考状态，固定首批导入清单、分组和开发评分口径；复用现有项目文档                    | 不重编资料或题目；明确 documents 与 evaluation 的接入分离、同名替换规则及样例标识；补齐正式迁移前的最小契约                                                |
| 2    | 知识库、一级分组、来源、原文件与版本、导入批次持久化；多库列表/详情、上传/粘贴/样例导入、移组与重试；默认规则与解析预览 | 至少两个库可独立导入相同样例；分组/来源不串库，删除组不删文档；重复请求不重复导入，部分失败保留成功项；原文和规则在刷新后可恢复，不先要求 embedding        |
| 3    | 构建/发布全文版本；员工绑定单库与 A；来源阅读、历史引用和反馈；全量预算检查                                             | 网站完成建库、导入、预览、发布、绑定、全文问答；移组不改变问答范围；更换默认规则不改变线上发布；超限/无答案/故障分开。形成首个可用增量                     |
| 4    | Embedding 能力连接、中文 BM25、向量索引、RRF 与 B；规则重建、B 试检索与索引诊断；共用问答用例                           | 相同资料发布可跑 A/B；预览、索引、正式问答使用同一规则产物；试检索能解释候选与预算；换模型/规则产生新索引，失败不污染旧版；无需重排                        |
| 5    | 已有 JSONL 适配、题集标注与冻结、批次、公式、人工评分和双栏页面；简单追问及共享计量                                     | 先用已有 12 题回归，逐步补真实问题与未见保留题；固定 A/B 条件，复核各分母、N/A、失败和待评；旧题不冒充独立验收，40 题仍是扩展目标                          |
| 6    | 冻结候选配置后跑保留题与真实自用；多库隔离、导入取消/重启、发布竞争、旧引用和旧聊天兼容验收                             | 按前文门槛报告失败与剩余范围；达到门槛再结合完整请求耗时、费用和复核时间选默认。此时完成专题完整平台验收；本轮轻量范围按详细方案，不把前三阶段等同混合闭环 |

阶段 1 直接使用已有 JSONL 和审核稿；阶段 5 适配导入评测页面。已有路径/引文对应阶段 2/3 生成的不可变文档/解析版本和原文区间，保留原题号及来源关系，不让用户重写参考。资料审核、评测规则冻结与软件发布是不同动作，不能互相替代。

阶段 2/3 先提供受控默认规则和全文能力；B 的模型、索引与试检索在阶段 4 接入，不把“规则页面存在”当作已支持向量检索。企业来源身份结构只用于稳定引用与未来扩展，不预建同步队列、授权按钮或凭据管理页。

阶段 5 的指标验收覆盖：证据 OR/AND、重叠去重、无必要组 N/A、无/非法引用、部分要点 0.5、不同适用分母、失败/取消/未评分，以及重复实验不扩大独立题数。按文中口径手算后再和页面核对，不用指标实现自身生成验收答案。预览与试检索可诊断问题，不能替代完整问答评测。

所有阶段复用现有认证、额度、取消和持久化边界，不把代码目录重构当作前置工程。后续依据实际需求单独建设重排、Agentic 检索、跨库联合检索、更多文档格式或第一个企业 Wiki 连接器；连接器动工前必须补齐权限撤销、删除同步、故障策略及接口能力验证。

## 验证与迁移

| 场景             | 预期验收                                                                                                     | 当前结果 |
| ---------------- | ------------------------------------------------------------------------------------------------------------ | -------- |
| 正常闭环         | 真实文档导入、发布、绑定、问答、原文阅读、反馈、评测可完成并刷新恢复                                         | 未实施   |
| 多库与分组       | 至少两库同名组/文档互不干扰；跨库组/来源引用拒绝；删组只移到未分组，移组/标签不改变当前问答范围              | 未实施   |
| 上传与重试       | 文件/文本/样例共用版本流程；编码/类型/容量限制明确；同请求不重复，部分失败只重试失败项，不覆盖成功或新版文档 | 未实施   |
| 规则与预览       | 同一规则预览与构建片段对应；保存规则不切换线上；换切片/模型产生新产物，旧块/引用/题集不被覆盖                | 未实施   |
| 试检索与扩展边界 | 诊断不生成正式回答，不污染评测；首版无 Wiki 授权、同步或外部检索调用，不伪装已接通连接器                     | 未实施   |
| 当前与目标       | 草案与模块当前说明同时命中时，不把计划说成已实现                                                             | 未实施   |
| 中文与精确标识   | 同义问法、中文术语、路径与错误码分别验证候选和答案                                                           | 未实施   |
| 引用与证据       | 越界编号、跨库块、已替换原文和无依据引文不能通过定位检查；人工另查支持性                                     | 未实施   |
| 版本与索引       | 构建失败、更新、归档、发布竞争、embedding 模型变化不污染旧发布                                               | 未实施   |
| 权限与恶意资料   | 非所属库、来源和评测拒绝；资料中指令不执行，不自动读取路径或 URL                                             | 未实施   |
| 预算与比较       | A 超限不静默截断；A/B 同发布与规则；未知费用不记零；标注不泄漏到回答                                         | 未实施   |
| 故障与兼容       | 取消、重启、网络和持久化错误不产生虚假成功；schema 1 普通聊天与游客样例继续工作                              | 未实施   |

核心阶段新增知识库/分组/来源、规则/文档/解析版本、统一知识作业及导入项、发布选材、回答证据和反馈；E 阶段另建评测三表并扩展回答归属；Agent 新字段默认不绑定，旧模型连接默认 chat，旧 run 无须补造知识证据。SQLite 与本地原文件、索引须一起备份；部署先停止执行并备份，再迁移、升级后端与前端。回退先停止新作业、导出新数据，不能直接删表并声称无损。旧对话查询对新字段兼容，旧教学页保持展示隔离。

本轮仅进行设计与文档检查，未新增迁移、业务代码、模型连接或真实问答/评测数据；算法效果、供应商能力和性能均待实际验证。

本轮更新知识管理设计、领域术语及文档入口。四份 Markdown 的 Prettier 检查通过，89 个本地文件链接可解析；章节唯一性、首版 A/B 与六阶段范围、旧第三方案清除及既有指标示例算式检查通过。未运行知识问答、导入/同步、检索基准或业务测试，未新增或覆盖存量资料、题目、参考答案或实测成绩。

## 外部依据与选择

- [Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)：讨论小资料集的全文上下文、BM25 与 embedding 互补、补充片段上下文及重排。本文据此选择实验维度，不把其数据集上的提升比例或上下文阈值当成本项目结论。
- [Azure 混合检索](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)与[RRF 排序](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)：提供文本与向量结果融合、后续重排的具体实现参照，不代表需要使用 Azure 服务。
- [LangChain 检索架构](https://docs.langchain.com/oss/python/deepagents/retrieval)：区分固定检索后回答与 Agentic 检索。本文先控制变量，再验证多轮策略。
- [Azure Agentic Retrieval](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview)：说明查询规划、子查询与证据合并的组合方式，不能用作全行业采用率依据。
- [RAG 评估](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators)：区分检索过程与回答质量，并区分需要人工标注和可由模型辅助的指标。本文首版采用人工确认题集与证据，不把自动评分当作事实正确性证明。

- [Dify 外部知识接入](https://docs.dify.ai/en/cloud/use-dify/knowledge/connect-external-knowledge-base)：参照独立检索 API 的边界；不代表首版需要接入 Dify 或已经具备外部知识能力。
- [Azure 知识来源](https://learn.microsoft.com/en-us/azure/search/agentic-knowledge-source-overview)：参照 indexed/remote 两类接入方式；具体企业 Wiki 的接口、授权与删除语义仍需逐一验证。
