## 有效需求与交付边界

用户要求先梳理全站功能，再给出统一设计语言及界面打磨计划。目标是让用户在一个页面学会的视觉含义和操作方式，在其他页面仍然成立，减少重新辨认和试错。

本文保留功能盘点、当时差异和迁移依据。后续已完成[具体设计](site-design-language-design.md)并获实施授权；生效规则归入设计系统，知识库绑定仍为独立功能增量。

已明确的要求：

1. 员工创建和编辑沿用三个入口：**基础配置、指令与知识、能力装配**，继续打磨布局与交互。
2. 员工名称与大脑同页完成最小可用配置；头像缩小、弱化背板，保留现有角色与更换入口。
3. 指令和知识库组合；工具和 Skill 保留在同一装配入口，通过列表、筛选、搜索和面板处理数量增长，不靠增加一级 tab 解决展示问题。
4. 全站相同对象、相同动作和相同状态具有稳定表达，覆盖名称、图标、颜色、控件、位置和反馈，不允许每个页面自行解释。
5. 优先采用可核验的通行规范；规范未规定的业务含义，需要制定站内规则，并由正式组件和设计样板共同落实。
6. 用户以闪电举例说明稳定识别，不代表指定 Skill 必须使用闪电，也不代表替所有类型分配不同颜色。

当前需区分的状态：三个 tab、站内图形映射和本次交互已获认可并接入正式前端；知识库挂载与聊天使用尚未实现。原型中的演示操作不构成实际能力或权限。

## 规范依据与采用边界

采用顺序：**可访问性等适用要求 → 稳定的交互惯例 → 项目现有设计语言 → 站内业务语义规则**。发现冲突时明确取舍，不因为某个参考站使用某图标就称为行业标准。

核对时间为 2026-10-31。下表链接为实际读取的官方资料；WCAG Understanding 页面是准则的解释性材料，不能把其所有示例都当作独立强制条款。

| 依据                                                                                              | 采用什么                                                             | 不从中推导什么                                                            |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| [W3C：3.2.4 一致标识](https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification.html) | 重复的同功能组件可被一致识别；视觉标识、文字与可访问名称协调         | 不要求不同任务组件一模一样，也没有为本产品指定 Skill/MCP 图标             |
| [W3C：3.2.3 一致导航](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html)     | 跨页重复导航保持可预测的相对顺序                                     | 不禁止适合任务的子导航或不同内容布局                                      |
| [W3C：1.4.1 颜色使用](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)              | 类型、选择、告警与失败不能只靠颜色区分                               | 不需要给每种业务资源分配一种专属颜色                                      |
| [W3C：3.3.2 标签或说明](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)  | 输入和选择具有清晰可见的标签，必要格式与影响有说明                   | 不用大量常驻说明替代清晰控件，也不只依靠 aria-label 给所有人解释          |
| [Atlassian：图标原则](https://atlassian.design/foundations/iconography/)                          | 优先熟悉隐喻、复用既有图形、保持成套风格，必要时配文字，避免概念冲突 | 不直接照搬其图标库、描边和像素值；也不据此删除项目已认可的角色/知识库形象 |

读取到的资料提供一致性和可识别性原则，没有规定本站业务对象的唯一图标映射。Skill、MCP 等最终图形、中文主名称与组合规则需要成为站内契约，而不是假称外部统一答案。

## 统一方法

具体映射、原型范围、动作/状态对照和逐组件迁移见[语义对照与迁移清单](site-design-language-design.md)。正式前端已按采纳方向接入，实际覆盖与限制以实施记录为准。

### 对象、动作、状态分别表达

建议建立以下业务语义表，具体符号在下一阶段同屏对照后定稿。组件图标库继续优先使用项目已有 Lucide；保留已认可的员工角色、知识库插画和品牌资产。

| 对象/层级        | 需要固定的含义                           | 场景与变体规则                                                                       |
| ---------------- | ---------------------------------------- | ------------------------------------------------------------------------------------ |
| 员工             | 一位可复用的数字员工                     | 始终使用同一角色身份；目录/收藏/对话/选择器允许完整、紧凑变体，不另换角色或标识      |
| 能力库/能力集合  | Skill 与工具能力的集合                   | 集合入口与具体 Skill 类型区分，不让父级标识被误认为“这里只有 Skill”                  |
| Skill            | 可复用工作方法                           | 目录、创建、装配、选择、执行详情保留同一类型标识；加载动作和成功状态另加，不替代身份 |
| MCP 服务         | 提供一组工具操作的服务                   | HTTP/stdio 作为次级属性；账号连接与单个操作不都叫“MCP”                               |
| 内置工具         | 平台提供的实际操作                       | 与 MCP 同属工具能力，保留来源区别；不能因视觉合并而改变许可规则                      |
| 账号连接/绑定    | 用哪个账号访问服务，以及当前使用者的关联 | 与服务身份、岗位许可分开表达；凭据存在、测试通过与可调用不是一个状态                 |
| 大脑/向量连接    | 对话生成与文本向量化的不同用途           | 对话大脑在员工首 tab；向量连接在检索设置；同源服务不等于同一用户概念                 |
| 知识库/文档/来源 | 资料集合、具体文件与证据定位             | 为知识库补紧凑标识与插画的关系规则；各层可识别，绑定和来源引用不混用                 |
| 指令/规章制度    | 员工工作要求、自动继承的全员规则         | 与参考资料分清；同页组合不表示可以随意解除继承                                       |

主对象名称与必要技术名称建立映射，例如 Skill 的中文主称呼及何时保留英文；不在本轮把某一候选名称伪称为用户指定。图标与标签在资源卡片、紧凑行、菜单、选择器及执行详情中成套演示。

状态按三个维度组织：**对象身份 + 当前关系/动作 + 真实结果**。例如一个 Skill 可以“已装配、已停用”，一个 MCP 服务可以“已启用、本人账号未配置”。完成勾选、成功色和对勾只表达它实际证明的结果，不代表整个员工就绪。

### 动作与保存语义

| 动作                                 | 应表达的结果                                                             | 必须保留的区别                                               |
| ------------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------ |
| 创建/新建、编辑、保存                | 新建对象、修改输入、提交当前配置                                         | “添加已有能力”不等于创建能力定义；“完成面板”不等于写入服务端 |
| 选择/装配/绑定                       | 临时选择、岗位关系、个人账号或知识资料关联                               | 共用交互外壳，但清楚指出关系属于谁、何时生效                 |
| 刷新、同步、发现、确认目录、测试连接 | 重读平台数据、扫描技能来源、访问远端读取目录、批准目录、执行特定连通测试 | 不用统一“刷新”掩盖不同副作用，也不把成功提示泛化为全部可用   |
| 移除、解除绑定、停用、删除           | 解除装配、解除关联、保留对象但禁用、删除对象                             | 图标、文案与确认强度对应实际影响；不把轻量移除做成永久删除   |
| 重试、重新核对、重连                 | 重做允许重试的操作、读取确认结果、恢复观察                               | 不能为了统一文案而重复发起后台工作                           |

### 表单、布局与反馈

1. 普通输入、选择、秘密字段和长文本共享标签、边界、焦点、禁用、错误及说明规则。尺寸由内容决定，长指令和文件编辑器保留任务差异。
2. 页头承担主操作，内容工具栏承担搜索/筛选/刷新；配置行承担该对象操作。固定重复操作的相对位置和主次关系，不为整齐移动到不相关的区域。
3. 资源展示、已装配行、候选选择和配置面板采用明确变体，类型标识一致，交互能力按任务不同。不能把展示卡、选择卡、可执行按钮画成无法区分的同一种控件。
4. 全站统一空、加载、刷新中、失败、未知结果、冲突和无权限反馈，复用既有中央错误事实；局部失败不清空可用内容。
5. 草稿选择使用选择控件；立即生效的启停使用开关并反馈提交；员工草稿内的启停仍明确由主保存生效。不要让相似外观暗示错误的生效时间。
6. 复用日夜语义令牌、空间和布局预算，不从参考站复制另一套颜色/圆角/间距。对话、资源目录、文件编辑、登录和阅读页继续按各自任务布局。

## 员工布局打磨范围

| tab        | 保留的布局方向                                                        | 下一轮需打磨的内容                                                                                                                         |
| ---------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 基础配置   | 名称和大脑同一页；小头像编辑、统一字段、实际卡片预览                  | 最小配置优先于装饰；优化首屏顺序和窄屏预览入口；加载/缺凭据/停用大脑明确反馈；不把“可保存”画成“可对话”                                     |
| 指令与知识 | 主指令编辑区 + 知识库辅区；全员规则压缩只读；窄屏知识库摘要与管理入口 | 引导、数量、绑定/解除/查看交互、长库名与长列表、键盘焦点；知识库未接线前保持原型或明确规划态                                               |

原型中的六行分页是布局演示选择，不是已确定的产品规则。长列表采用分页、虚拟化或有界滚动，要依据实际数量、阅读任务及主滚动归属核验；不能通过层层滚动重新制造 Skill 难以到达的问题。

员工知识库绑定另有功能前置：本人知识库与共享岗位的归属/访问权限、绑定关系保存、运行接受和撤权、真实检索与来源引用。先补此增量契约，再接入正式页；设计统一不自动授权跨用户读取。当前库内检索、规则自动继承和员工问答属于不同链路。

## 验收与维护要求

1. **跨页识别**：同一 Skill 从能力库、创建/详情、员工候选/装配、对话选择到执行记录，类型标识和主名称始终可识别。MCP、连接与具体工具操作有明确层级，不能因进入另一页面换一套隐喻。
2. **有意义的差异**：展示/选择/编辑、对象/动作/状态可区分；紧凑与完整变体共享语义，不强求所有页面相同几何或全站每处都放图标。
3. **最小创建路径**：员工名称和可用大脑在同一 tab 完成；指令、技能和工具不是聊天的强制配置。保存草稿与真正可用分别反馈。
4. **数量增长**：建议以 0、少量、30 项装配、长名称及无搜索结果核验；无需滚过全部工具即可筛选/操作技能。测试规模为建议验收数据，不是新增产品容量限制。
5. **操作与状态**：添加/完成/取消/Escape/关闭/主保存、启停、解除关系、永久删除、部分保存、结果未知和版本冲突的实际后果与提示一致。
6. **知识边界**：不得把库内检索成功表达为员工已绑定或已使用；未来绑定有真实权限和保存依据，引用能回到授权原文。
7. **主题与尺寸**：按现行设计预算覆盖日夜、320/390px、常用桌面和短屏；列表、说明、焦点和面板不溢出。键盘、可访问名称、禁用原因和颜色替代信息均可用。
8. **正式与样板一致**：能力卡、SkillCard 等历史/演示变体要么接入同一规则，要么在核对实际使用后归档；不能仅因未被某一路由直接导入就删除。
9. **防止再次分散**：新增资源类型先登记名称、标识和变体，并进入正式样板；对可稳定判定的业务类型映射、可访问名称及必要组件接入建立检查。不要禁止所有页面导入 Lucide，普通动作图标仍按职责使用。
10. **工程验收**：实施时运行受影响静态检查、定向测试和构建，验证深链/历史 tab、主保存事务与草稿保留；视觉检查与业务检查分别报告。本轮仅文档，运行 `make check-docs` 及定向格式检查，不声称业务检查通过。

## 设计选择的后续状态

- Skill、MCP、内置工具、能力集合和知识库紧凑图标及中文主名称已按跨页样例采纳，详见现行设计语言；用户举例未被当作固定图形要求。
- 统一装配列表采用六项分页、类型筛选与搜索；添加候选独立滚动，技能候选按服务端分页；实际窄屏检查见实施记录。
- 本轮不决定知识库绑定的新数据/授权契约，也不承诺所有者不同的资料可用于共享员工；该功能增量进入专项设计。

知识绑定仍待专项设计；其他采纳项已在用户直接实施授权范围内落地。
