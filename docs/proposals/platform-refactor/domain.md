# 内容与处理记录：保存什么，怎样关联

本文保留[总方案](README.md)的数据设计取舍，已通过 0005 落地；实际字段与约束以[数据入口](../../reference/data-model.md)为准。保留 Conversation/Run，助手正文和专业数据分别归位。

## 1. 三个核心概念

| 名称         | 用一句话解释                       | 不混入的职责                     |
| ------------ | ---------------------------------- | -------------------------------- |
| Conversation | 用户与某位员工持续交流的一段对话   | 不管理模型循环、预算或任务验收   |
| Message      | 对话中一段可保存、排序和定位的内容 | 不拥有另一套执行状态             |
| Run          | 系统针对输入进行的一次处理尝试     | 不保存聊天正文，也不解释 CI 报告 |

用户 Message 记录输入；助手 Message 记录一次回复区域，接受请求时已存在，正文可以暂空。空回复、失败片段和完整答复由对应 Run 状态及读取规则区分，不再把 Message 定义成“成功后才存在的正式话语”。

Message 仍是 conversations 内部的轻量记录。无需独立 message 模块、统一 Item 实体或问答轮次实体。

## 2. 推荐存储及归属

| 所属模块与记录                | 关键内容                                                                     | 为什么这样保存                                            |
| ----------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------- |
| conversations.Conversation    | id、agent_id、owner_user_id、title、revision、last_message_sequence、时间    | 对话身份与顺序属于交流内容                                |
| conversations.Message         | id、conversation_id、sequence、role、body、时间                              | 用户原话与回复正文可直接读取，避免正文中转                |
| conversations.ConversationRun | run_id、conversation_id、input_message_id、reply_message_id、active          | 保证准确关联和同对话活动唯一，不让 execution 读取对话 ORM |
| execution.Run                 | 身份、幂等、重试来源、冻结输入与配置、预算、状态、用量、错误、时间、恢复引用 | 完整表达一次运行尝试，独立管理生命周期                    |
| execution.RunAction           | run_id、动作 ID/顺序、类型、状态、关联、受限详情、过程内容和时间             | 保存实际发生的动作及输出，不能把工具请求当执行成功        |
| ci_diagnosis.CiDiagnosis      | run_id、progress_payload、report、revision、feedback                         | 专业阶段、来源、报告与反馈归专业模块                      |
| SDK 自有存档                  | 图状态、内部消息、引擎完成标记、恢复位置                                     | 只用于继续或补交未完成执行，不作为聊天历史数据库          |

删除 execution.RunResult。将原 CiFeedback 的内容合入 CiDiagnosis.feedback，报告与反馈的修改资格仍分开检查。其余用户、会话、员工、技能、连接与规章制度模型按当前业务契约保留。

本方案不是要求把一切数据库字段都集中在此表；具体字段和约束在实施时落入 ORM、迁移与测试。

## 3. Message 的内容规则

1. 用户输入在接受时写入非空正文，此后不覆盖。
2. 助手记录在接受时建立 ID 和 sequence，body 可以为 NULL，表示尚无结束时保存的正文。
3. 运行期间，页面正文来自已保存的普通进度/动作内容，不逐 token 改写最终 body。
4. 发布事务按最终状态决定保留什么：成功保存完整答复；普通失败或用户取消仅保存执行器/控制对象明确标记、符合既有政策的可留存回复片段；撤权不新增可见正文，工具请求不能兜底当答复；CI 失败不生成伪完整报告。
5. Run 终止后，正文只读。重复完成或迟到片段不能覆盖。
6. role、对话、顺序与 ID 在创建后固定；正文只由受控发布入口写入，不继续使用“只要 ORM 已保存就不能更新任何正文”的旧校验。
7. Message 不存 queued/running/succeeded。页面状态从绑定 Run 派生，避免两套状态不同步。

同一文字出现在模型动作过程和最终回复中是允许的：过程用于追踪，回复用于交流。无需为了字节绝对不重复引入通用 Result。

## 4. ConversationRun 为什么保留

它表达“这次处理使用哪条输入，产生哪个回复，是否还占用该对话”。

必须保留的约束：

- run_id 为主键，reply_message_id 唯一。
- 输入与回复都通过 conversation_id + message_id 复合外键确认属于同一对话。
- 输入与回复不能相同；应用检查输入为 user、回复为 assistant。
- active 为真时，同 conversation_id 最多一条；数据库部分唯一索引兜底。
- 结束 Run 和释放 active 在同一事务完成。
- sequence 只存 Message；删除 response_sequence。
- reply_message_id 在接受时就有值；删除 response_id 与可空 output_message_id 双重身份。

不增加 Conversation.active_run_id。活动位置可从唯一的绑定取得，避免再维护一份指针。

## 5. 用失败重试验证关系

| 时刻     | 内容记录                          | 处理与关联                           |
| -------- | --------------------------------- | ------------------------------------ |
| 首次发送 | 用户 M1、空助手 M2                | R1 queued；M1 → R1 → M2，active=true |
| 首次失败 | M2 保存允许的部分文字或保持空正文 | R1 failed，active=false              |
| 用户重试 | M1 不变，新增空助手 M3            | R2 queued，retry_of=R1；M1 → R2 → M3 |
| 重试成功 | M3 保存完整答复                   | R2 succeeded，active=false           |

问题目录只数用户 Message，因此仍是一个问题。历史可展示 M2 和 M3 两次回复。后续上下文采用成功的 M1/M3，不采用 M2 的失败片段。

“不重复创建用户消息”不等于“执行快照不能出现原文”：每次 Run 仍需固定实际使用的输入。相同请求键重发则返回原记录，不创建 M3 或 R2。

当前仅允许重试对话末次失败、取消或中断处理；不借本次重构增加旧问题分叉、成功答复重新生成或执行中追加输入。

## 6. Run 状态和时间

| 状态        | 含义                                 | 允许的后续                     |
| ----------- | ------------------------------------ | ------------------------------ |
| queued      | 已接受，尚未开始                     | 领取、取消、排队超时           |
| running     | 正在处理                             | 继续动作、请求取消、完成或失败 |
| cancelling  | 停止意图已保存                       | 中断上游并收束为 cancelled     |
| succeeded   | 内容、业务结果、终态与占用已一起提交 | 状态、正文与执行事实只读       |
| failed      | 已知失败已经保存                     | 用户可按资格新建重试           |
| cancelled   | 已停止                               | 用户可按资格新建重试           |
| interrupted | 无法可靠继续                         | 用户可按资格新建重试           |

排队即取消可以直接终止，不需要启动执行器。恢复沿用原始 started_at 与累计预算，不重新获得完整时间和调用额度。状态方法归 execution，其他模块通过明确方法请求改变，不自行赋值。

终态后的状态、正文和执行事实不再改变；专业反馈可以在同事务中递增 CI revision 与 Run 的公开观察 revision，不会重新启动执行。Conversation.revision 则在接受新回复、释放占用或元信息变化时递增，用于防止迟到摘要回退当前操作目标。

动作成功只表示该动作结束；模型输出文字、模型提出工具请求、工具实际返回和整次处理完成分别判断。未确认远端结果标 unknown；未知用量保留 NULL，不补零。

## 7. CI 数据如何保存

CiDiagnosis 以 run_id 为唯一关联，保存本次诊断的阶段、目标、调用摘要和来源快照；report 只在成功发布事务中写入经过验证的报告。feedback 在成功且有报告后允许写入一次，相同反馈重放返回原结果，不同反馈冲突。

progress_payload 继续是受控有界 JSON，但属于 CI，而不属于通用 Run；只包含允许的过程字段，不嵌入正式 report 或 feedback。专业进度保存先核对 Run 仍为 running，终态后的迟到进度拒绝。CI revision 只在专业数据改变时递增，普通模型文字变化不会迫使前端重复读取整份报告。发布前保持 validating/ready_to_publish，只有发布事务可以同时写 report 和 delivered；不能照搬当前执行器提前保存 delivered 的代码。反馈由专业服务检查，请求与共享流程在同事务推进专业与公开观察版本。

结构化 report 是诊断事实；Message.body 是交付时由报告确定生成的聊天正文。两者同事务生成，不提供两处独立编辑报告的入口。凭证、未脱敏日志与原始异常不进入这些公开结构。

## 8. 历史、上下文与运行存档

历史直接按 Message.sequence 分页，再按助手关联读取对应 Run 状态与过程。查询层整理用户可见正文，前端不判断 SDK 的 has_tool_calls 或图节点。

上下文继续读取成功问答对，按当前预算选择完整配对，固定到新 Run.input_snapshot。重试和配置编辑不会改写旧 Run 的输入依据。

SDK 存档缺失会影响未完成运行的恢复，不影响已保存 Message 和 CI 报告的读取。SDK 已可信完成但业务尚未提交时，恢复可以重新取得候选答复并调用共享发布流程；不能只看到一些文字就判定成功。

## 9. 哪些名字不再成为核心对象

- Thread、Turn：本次不引入，避免对已有明确身份做全栈改名。
- ThreadItem：不建立核心领域或通用表；API 的消息列表可以直接组合内容与状态。
- TurnResult/RunResult：目标移除通用中转存储，文本归 Message，专业数据归 CI。
- Reply/Response：API 中表示助手回复的易懂路径词，ID 就是助手 Message ID，不新建实体。
- Session：继续限定为登录、数据库或 SDK 的具体技术会话，不增加业务容器。

迁移步骤、ID 保留、约束和回滚见[实施计划](migration.md)。
