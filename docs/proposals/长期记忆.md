# 长期记忆设计调研报告

设计状态：研究建议，待评审。实施状态：未实施。实质更新：2026-11-07。范围：NiumaCrew 数字员工跨对话协作记忆、可验证经验及后续组织资产沉淀；本次只调研和规划，不修改运行行为。

本文以当前工作区为本地依据，并重新阅读外部一手资料。产品公开行为、作者自报效果、实验结果和本平台建议分别标明；不把历史草案、产品宣传或模型生成内容当成已经成立的业务事实。

## 1. 结论与推荐路线

**建议采用“平台治理的记忆资产＋Agent 按任务使用＋受管后台提取”的设计。首期做个人协作记忆，先证明能减少重复沟通、正确接受纠错，再扩展到工作经验和组织共享。**

具体建议如下：

1. **先确定内容和归属。** 用户通用偏好、用户与某员工的协作约定、项目事实、工作经验采用不同的范围和准入条件。共享员工不等于共享所有使用者的记忆。
2. **先解决可见性。** 当前游客可读全平台对话和执行证据。仅给记忆表加 user_id 无法形成端到端隔离；含个人记忆的对话、Run、输入证据和文件必须一起限定可见范围。
3. **首期以明确保存为主。** 用户明确要求记住的信息可立即保存；模型推断先形成候选。自动提取逐步开放给低风险、可溯源的信息，不能把助手自报成功直接记成事实。
4. **保持小规模默认上下文。** 少量稳定偏好按需加载，其他记忆按任务检索；未命中时允许无记忆回答。原始记录、知识原文和业务状态继续由原模块管理。
5. **先复用当前技术栈。** SQLite 保存权威记录、版本和来源，FTS 支持起步检索；复用向量能力时单独建立记忆索引与授权入口。LangMem 可作为提取算法候选，Mem0、Zep 作为对照试验，暂不绑定外部供应商。
6. **经验要经过验证才能发布。** 把一次执行变成带条件、证据和反例的经验候选；通过回放后，才考虑发布为技能、规范或知识资料。
7. **按业务收益验收。** 分别评估写入正确性、召回质量、最终任务效果，以及纠错、删除、撤权、延迟和总成本。

这条路线不是某家产品的完整复制：文件式记忆、结构化记忆和图记忆都已有可用实现，真正影响平台长期效果的是准入、作用域、更新、使用和评测能否闭环。

## 3. 当前平台的实际起点

### 3.1 已有能力与缺口

| 能力         | 当前事实                                                                           | 对长期记忆的含义                                                               |
| ------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 连续对话     | 同一 Conversation 使用稳定 Thread；新 Run 从最近成功且已接纳的明确 checkpoint 续接 | 已解决同一对话连续性，尚未提供跨对话记忆资产                                   |
| 对话摘要     | 使用官方 SummarizationMiddleware，摘要调用计入 Run 预算                            | 能缩短送模上下文，不能承担记忆归属、纠错和删除                                 |
| 恢复存档     | checkpoint 保存 SDK 消息、状态及执行位置                                           | 是恢复依据，不是业务记忆管理界面或事实库                                       |
| 上下文失效   | 员工、用户、知识修订及关键资源变化会影响现有 memory_scope / reset                  | 可参考其失效机制，但现有 memory_scope 是上下文兼容性摘要，不是长期记忆授权空间 |
| 知识资料     | 已有来源、正文、片段、FTS / 向量、员工统一装配和 Run 证据                          | 可复用检索技术与证据模式；不应混用知识与记忆的写入生命周期                     |
| 执行管理     | Run / RunAction 已管理授权、预算、取消、成果与恢复                                 | 记忆查询和生成应纳入既有受管调用，避免隐藏模型调用                             |
| 权限         | 多位用户使用共享员工；普通成员按本人范围操作；游客全平台只读                       | 个人记忆须建立明确的跨出口隔离                                                 |
| 未来业务对象 | 当前没有正式项目成员、任务、SOP、多租户产品模型                                    | 首期不能假设 project_id、tenant_id 或组织审批流已经存在                        |

核查入口：[执行子系统](../../backend/app/execution/README.md)、[运行契约](../reference/runtime.md)、[Agent 组装](../../backend/app/agent/engine.py)、[快照与失效判断](../../backend/app/execution/snapshot.py)、[知识模块](../../backend/app/knowledge/README.md)、[身份契约](../reference/auth.md)。

旧版[长期记忆草案](../records/README.md)中的应用治理、执行使用、外部实现可以分开判断，仍有参考价值；其中关于旧上下文选择和 checkpoint 隔离的描述不作为本次当前实现依据。本报告将其推进为可实施增量建议，未将任何新选择标为用户已确认。

### 3.2 首期必须正面处理的可见性问题

当前 [GUEST_PERMISSIONS](../../backend/app/auth/permissions.py) 包含 resources:read_all、conversations:read、runs:read、agents:read 和 organization_rules:read。[ExecutionQueries.read](../../backend/app/execution/queries.py) 以后二项权限判断是否可检查完整输入，因此游客也满足该判断。对话正文、工具结果或输入证据均可能包含已使用的记忆。

[执行证据文档](../reference/runtime.md)仍写该诊断权限“当前对应管理员”，与代码及当前游客契约不一致。本次将其登记为文档差异，不把它误读成当前已经保护了个人输入。

**建议增加含个人记忆工作的受限可见范围，覆盖整个 Conversation 及其 Run、消息、附件和证据读取。** 游客继续浏览被明确列入展示范围的内容，个人记忆只在受限对话使用。不能仅在 UI 隐藏记忆卡片或日志片段，因为最终回复也可能带出记忆。

这属于拟议的产品边界变化。若继续保持全部历史对游客开放，首期只能在虚构、公开资料上试验，并明确不提供个人私密记忆承诺。平台管理员是否可诊断个人内容也应明确告知；“对其他成员隔离”和“管理员也不可见”是不同承诺。

### 4.2 版本差异带来的实际选型要求

Mem0 的 2025 年论文描述提取、整合和检索，其数据是在当时的实现及 LoCoMo 设置下获得；当前 Platform V3 文档则明确改为追加式管线。这不是从旧论文就能推导的新版本行为，也不能推断 OSS 已完全同步。[2025 论文](https://arxiv.org/abs/2504.19413)、[当前迁移说明](https://docs.mem0.ai/migration/platform-v2-to-v3)

因此，接任何供应商前都应固定所测 SDK、服务版本和策略，并验证以下外部契约：纠正事实是否替换当前视图、旧事实是否保留、删除覆盖哪些派生内容、搜索过滤由谁强制、升级会不会改变写入和排序语义。具体商业数据处理条款、实际 SLA、可用区域和价格本次未完成采购级核验。

### 5.2 暂不采信的常见结论

1. **“某产品准确率超过 90%，因此最适合当前平台”。** 数据集、回答模型、检索预算、裁判和是否给完整历史都会影响分数。不能把不同报告的分数排成统一产品榜。
2. **“节省 90% token 等于平台总费用节省 90%”。** Mem0 旧论文是在特定基线下的实验结果；真实成本还包含提取、整合、向量、重排、重复生成、维护和供应商费用。[原论文](https://arxiv.org/abs/2504.19413)
3. **“框架客户数证明了长期记忆收益”。** Agent 调度、checkpoint 和跨会话记忆是不同能力；未披露记忆机制及评测的客户案例不作记忆收益依据。
4. **“图数据库是长期记忆标配”。** LinkedIn 的层级语义树、Letta 的文件系统、Mem0 的记录管线都给出不同路线；当前没有证据要求本平台首期部署图数据库。
5. **“只记录失败就能持续进化”。** Anthropic 最新实验发现，限定只记失败可能削弱部分模型的记忆收益；成功做法和适用条件也有信息价值，但该实验仍不是企业业务效果保证。[实验原文](https://www.anthropic.com/research/components-of-agent-memory)

## 6. 真实业务实践与可迁移经验

### 6.1 LinkedIn Hiring Assistant：把业务反馈沉淀为有范围的偏好

**公开生产实践。** 团队将招聘活动、聚合偏好和执行方式分别处理，采用异步接入，并将招聘人的记忆限制在相应用户与客户租户范围。其工程文章说明了写入正确性、检索与答案对齐、最终任务效果三层评测。[工程原文](https://www.linkedin.com/blog/engineering/ai/the-linkedin-generative-ai-application-tech-stack-personalization-with-cognitive-memory-agent)

同团队 HLTM 论文称已部署到生产招聘流程，报告回答正确性提升超过 5%、检索 F1 提升超过 10%。摘要没有充分说明这里应如何换算为绝对百分点，本报告保留作者原有百分比口径；这是团队自报，未独立复现。[论文](https://arxiv.org/abs/2604.26197)

**可迁移做法：** 一次“候选人不合适”应先保存为具体招聘活动和理由，不能直接升级成“该公司永远不招这一类人”。对应平台，用户否定一份报告的结构，不等于禁止所有员工以后使用该结构。原事件、局部偏好和广泛约定要分开。

### 6.2 OpenNote：保存学习连续性，减少整段历史反复输入

**厂商发布的具名客户案例。** Mem0 文章描述 OpenNote 用持续变化的学习者资料连接多次学习，按相关摘要组织提示，客户案例自报单次提示 token 使用下降 40%。原文基线是完整历史输入，并未提供可独立复算的样本量和对照配置，不能直接外推到已经使用摘要的 NiumaCrew。[客户案例](https://mem0.ai/blog/how-opennote-scaled-personalized-visual-learning-with-mem0-while-reducing-token-costs-by-40)

**可迁移做法：** 数字员工应记住“该用户已掌握基础概念、上次卡在某一决策”，并支持改正；避免每次从头解释。试点指标应是减少重复说明和完成后续任务的时间，不能只统计保存了多少条记忆。

### 6.3 Claude Code 与 Codex：日常协作需要可检查、可选择的连续性

**已交付产品机制，非独立业务收益实验。** Claude Code 让使用者检查和编辑自动笔记；Codex 分开控制聊天读取记忆和贡献未来记忆。这两种机制直接回应“它到底记住了什么”和“本次工作是否参与以后记忆”的问题。[Claude Code](https://code.claude.com/docs/en/memory)、[OpenAI Docs](https://learn.chatgpt.com/docs/customization/memories)

**可迁移做法：** 提供“本次使用记忆”和“本次允许沉淀”两个清楚的开关；有保存回执、来源入口及纠错操作。用户指定只对本次有效时，后续提取不得把它升级为长期约定。

### 6.4 Anthropic 内部资料实验：整理能增益，也会产生维护负担

**研究实验，未当作客户生产收益。** 2026-11-06 文章披露在内部文档语料上构建 wiki 并保留搜索的实验：在 25 个问题上，wiki 加搜索的评分随整理从 54% 到 61%，只用搜索为 53%；另一些任务没有明显增益，甚至出现 wiki 大于原资料的情况。样本和任务特定，结果不能作本平台预期提升。[原文](https://www.anthropic.com/research/components-of-agent-memory)

**可迁移做法：** 高频、需要跨材料综合的主题可建立摘要或经验导航；低频且能直接搜索定位的资料保留原文检索。后台整理必须记录处理量、成本、纠错和实际使用效果。

### 6.5 未纳入真实业务结果的资料

AWS 官方客服教程、Mem0 现场服务记忆演示可以帮助构造试验，但前者是教程，后者明确使用合成数据，均不能写成已部署客户成果。[AWS 场景](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-customer-scenario.html)、[Mem0 演示声明](https://mem0.ai/blog/memory-for-the-trades-persistent-memory-for-field-service-ai-agents)

因此，本报告的“业务实践”分成公开生产设计、具名厂商案例、已交付产品机制和实验观察；当前平台下文的业务样例均为拟议试点，不冒充已经发生的用户收益。

## 7. 本平台应该记什么

### 7.1 内容类型与权威边界

| 内容                       | 示例                                 | 形成要求                               | 原本的权威位置                                    |
| -------------------------- | ------------------------------------ | -------------------------------------- | ------------------------------------------------- |
| 用户通用偏好               | 默认中文，报告结论前置               | 用户明确设为通用；跨员工使用需单独同意 | 个人记忆                                          |
| 员工协作约定               | 与“研发研究员”协作时附来源和不确定项 | 明确约定，或用户接受候选               | 用户与员工的记忆空间                              |
| 限定事实或决策             | 某项目术语已确定，某方案暂缓         | 来源、适用对象、有效时间和确认依据     | 有正式项目/决策对象后以其为准；记忆保存摘要和指针 |
| 工作经验                   | 某类故障的已验证排查顺序             | 执行证据、条件、结果及反例             | 个人经验候选；成熟后可发布为技能或知识            |
| 当前运行进度               | 本次已读哪些文件、剩余哪些步骤       | 当前执行状态                           | Run / checkpoint，不进入通用长期记忆              |
| 制度、手册、外部资料       | 报销规定、产品文档                   | 来源与版本                             | 知识库；记忆不复制成独立“真相”                    |
| 订单、审批、付款、部署状态 | 已付款、已审批、已部署               | 查询权威业务系统                       | 原系统；记忆只提供查找线索                        |
| 凭据或一次性敏感数据       | 密码、token、临时验证码              | 不进入记忆                             | 已有凭据系统或相应短期存储                        |

偏好、事实和经验不是同一可信等级。模型对“用户重视成本”的推断，应标记为推断，不能自动变成公司采购政策。

### 7.2 作用域建议

首期默认空间为**用户＋员工**，与 Conversation / Run 解耦。用户明确选择后，通用偏好才进入**用户通用**空间；两个空间都由服务端从可信身份生成，不接受模型传入任意 user_id。

项目和组织空间留到存在真实成员、资源归属和发布规则后实施。项目名可以作为首期记忆的主题标签，但标签不赋予项目权限，也不能模拟正式项目空间。

“员工经验”需要拆成个人与员工协作中产生的经验、经过发布的共享能力。前者属于相应用户空间，后者经脱敏和发布进入技能/知识/全员规则的既有生命周期；不建立所有使用者可随意写入的员工公共记忆池。

当前指令与记忆的处理也要区分：用户本轮明确要求优先于其旧偏好；正式规则和权限继续由平台执行。事实冲突则核对证据、时间与适用对象，不能按“谁的提示更靠后”或“哪条更新”决定真伪。

## 8. 推荐架构与数据设计

### 8.1 模块职责

| 所有者               | 拟议职责                                             | 接入当前系统的方式                                                   |
| -------------------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| 记忆业务模块         | 空间、条目、来源、版本、准入、纠错、删除、候选发布   | 新增独立业务边界，权威数据留在平台                                   |
| 执行宿主             | 记忆生成和查询的授权、预算、取消、时限、动作证据     | 复用 Run / RunAction 和已有受管模型调用                              |
| Agent 运行层         | 根据任务使用小量记忆，调用获准查询或提出候选         | 在现有中间件和工具装配处接入，不重写 Agent 循环                      |
| 后台形成流程         | 读取获准来源，提取候选，去重，核对冲突，提交当前版本 | 同进程先实现持久待处理事件和受管执行；不依赖 HTTP 请求尾部的内存任务 |
| 检索与外部适配       | FTS、向量、重排或外部提取服务                        | 返回候选与来源，业务授权和当前状态由记忆模块再核验                   |
| 对话、文件、知识模块 | 管理原始资料及相应可见性和删除                       | 向记忆模块提供来源资格及变化通知，不转让源资源权限                   |

知识与记忆可以复用底层算法，但不应把记忆作为普通知识文档上传，再交由模型任意覆盖。两者的形成权限、时间和纠错规则不同。

### 8.2 最小数据概念

以下是拟议业务概念，供实施时收敛成表和类型，不是已存在表或完整迁移：

| 概念           | 核心信息                                                                | 设计原因                                           |
| -------------- | ----------------------------------------------------------------------- | -------------------------------------------------- |
| 记忆空间       | 所有者、范围类型、员工引用、读写策略、修订与删除代次                    | 授权不依赖聊天 ID；统一失效与并发检查              |
| 记忆条目与版本 | 类型、主题、声明正文、条件、状态、修订、形成方式、有效时间、记录时间    | 区分何时得知与何时适用，保留纠错关系               |
| 来源关联       | Message / Run / 工具动作 / 文档引用及版本、证据位置、获准资格、验证方式 | 可从记忆追到原记录，也能由撤权反查受影响记忆       |
| 使用记录       | Run、记忆 ID 及版本、检索方式、是否注入、字节或 token 数                | 解释本次为何沿用某条记忆，不把“被检索”冒充“有帮助” |
| 待处理事件     | 来源事件、输入修订、策略版本、幂等键、受管 Run 引用、应用完成标志       | 崩溃后补处理；Run 继续作为模型执行状态的唯一依据   |

条目状态建议为“候选、有效、冲突待核对、已替代、已过期、已删除”。修改正文创建新修订；等价重复信息可补充来源，不能靠反复复制同一来源提高可信度。

语义上可识别的事实使用“主体＋属性＋条件”归类，例如“用户 U／研发报告输出形式／研发员工 E”。不要求所有正文强制拆成三元组。复杂经验保留自然语言正文及适用条件，先用简单模型获得可解释性。

不用单个模型置信分数决定是否发布。保存“用户明确指定、用户确认、工具可核验、模型推断”等验证方式；检索分数仅表示排序相关性。

### 8.3 首期存储选型

| 方案                             | 适配当前平台的优点                                     | 代价与限制                                               | 建议                                     |
| -------------------------------- | ------------------------------------------------------ | -------------------------------------------------------- | ---------------------------------------- |
| SQLite＋FTS＋有限结构化提取      | 复用现有部署、事务及备份；便于实现所有权、版本和删除   | 提取质量和长期规模需自测；仍受现有单写者约束             | 首期基线                                 |
| 加独立向量索引，按需使用 LangMem | 对中文改述和语义召回提供候选能力；可保持现有 Agent SDK | 索引与权威记录一致性、模型输出校验仍由平台实现           | 基线出现漏召回后加入                     |
| Mem0 OSS 或 Platform             | 可减少部分提取和检索建设                               | 两种交付不同；需验证版本、权限、纠错、导出、删除及总成本 | 做对照，不直接作为权威业务库             |
| Zep 托管服务或 Graphiti          | 适合关系和时间问题较多的场景                           | 两者部署与治理能力不同；新依赖及运维需要评估             | 多实体、时间推理确成瓶颈后验证           |
| AWS / Google 托管记忆            | 可外置提取、整合和检索                                 | 新增云身份、网络、区域和数据处理依赖                     | 迁移相关云基础设施或有明确托管需求时评估 |

向量库只保存可重建的索引，不承担记忆真相；记录与索引采用版本切换和异步补建，搜索结果必须回查当前条目及权限。管理员重建索引不能恢复已删除或失效的条目。

首期可提供只读 Markdown 导出便于审查，但数据库与导出不能同时充当可写主副本。Agent 文件式访问若后续需要，应映射到同一服务端受控接口。

## 9. 形成、使用与遗忘的完整流程

### 9.1 写入：明确保存与自动提取两条路径

**明确保存：**

1. 用户通过界面或明确指令提出要记住的内容。
2. 服务端确认本人身份、目标空间及本次允许沉淀；存在范围歧义时只澄清范围。
3. 记录用户原文来源，检查禁止内容、重复和同主题冲突，以短事务保存。
4. 提交成功后展示记忆正文与范围，并允许编辑、删除。未落库不得由模型声称“已经记住”。

**自动形成：**

1. 获准的新消息、正式接纳结果或已验证工具结果，产生持久的待处理事件。接纳成果与处理事件的记录应同事务保存，防止成功后漏提取。
2. 后台合并同空间的重复事件，创建有独立预算的受管生成工作。用户消息中的明确偏好可独立处理，不依赖助手本轮是否成功。
3. 提取器区分用户声明、助手输出和工具证据，输出候选及精确来源，不直接控制生效状态。
4. 记忆服务重新核验来源、空间修订、删除代次、幂等键和当前授权；做等价合并、条件拆分或冲突标记。
5. 通过准入的低风险内容可在用户开启自动沉淀后生效；推断、共享、敏感或高影响变化保持候选。
6. 失败可重试提取或应用步骤，不重跑原业务动作；迟到结果遇到删除、撤权、修订变化应丢弃或重新提取。

自动写入不是所有信息都弹窗确认。首期关闭隐式自动生效，在试点达标后按类型开放；用户可批量审查候选，避免打断每次对话。

### 9.2 读取：先授权过滤，再判断相关性

1. 在创建工作时固定读取开关和允许空间；在实际检索及使用前复核当前权限。
2. 按员工、主题、当前任务意图及用户显式对象检索。若用户只说“按上次的标准”，应先利用本次上下文确定对象，不能搜索全平台相似句子。
3. 检索前限制空间、状态和源资格，返回后再次核对条目版本。无关、过期、冲突或无权限条目不进入模型。
4. 少量稳定偏好可直接注入，其他信息通过记忆查询工具按需读取。上下文明确标记它是何时形成、适用哪里的参考，不赋予系统指令权重。
5. 模型需要确认业务状态时查询权威系统。记忆只负责提示“应该核对哪项历史约定”，不能据此认定已付款或已部署。
6. Run 保存使用的条目版本和来源；证据展示继承该工作的可见范围。

建议初始试验预算为：稳定偏好最多约 800 token，召回内容最多约 1,200 token、8 条；总量同时受当前运行字节及模型输入预算约束。这些是待测参数，不是行业通用最优值。没有可用 tokenizer 时使用保守字节限制，不伪造精确 token 数。

可选的个性化记忆检索失败时，可以明确降级成无记忆运行；用户明确要求依赖上次决定的任务，应说明未能取得依据并重试或澄清。授权失败不能降级成扩大搜索范围。

### 9.3 纠错：覆盖当前视图，保留条件差异

例如先前记忆是“研发报告按周输出”，用户后来指定“研发报告改成双周，事故通报仍即时”：

1. 识别同一主题及适用条件，建立新版本，不把事故通报也改成双周。
2. 旧版退出默认当前视图；有明确生效时间时更新有效区间。
3. 不确定是否长期修改时形成候选或按本轮处理，不能擅自扩大成通用偏好。
4. 依赖旧版的默认摘要、检索缓存和后续上下文失效，下一次运行使用新版本。
5. 两个非权威来源互相冲突时保持待核对状态；后台整理不能只按最近时间选择赢家。

### 9.4 遗忘与撤权：覆盖所有可再次使用的副本

删除至少涉及权威条目、来源关系、索引、派生摘要、待处理事件、缓存和执行上下文：

1. 事务内标记条目不可读取并增加空间删除代次；异步清理向量及摘要，即使索引未清也不能返回正文。
2. 待处理和在途生成提交前复核删除代次，禁止旧作业把内容重新写回。
3. 保存最小的来源抑制记录或处理水位，阻止从已知旧来源重新提取；避免墓碑继续保存被删除的正文。
4. 每个模型或工具动作前、恢复时和发布前核对空间代次及依赖版本；已受影响的活跃 Run 取消后续使用。首期让受影响 Thread 的旧基点整体失效，下一轮用本轮允许输入与仍有效记忆建立新分支，不从旧摘要或助手正文重建上下文。正式历史仍可查看，重置造成的连续性损失需提示用户。
5. 原资料撤权、删除或改版时，挂起依赖该版本的自动派生记忆并重验。多个来源共同支持时只能保留当前仍获准且支持该结论的部分。
6. 备份恢复后先应用删除记录和代次，再开放检索；备份到期和外部副本清理有单独策略。

需要明确三种用户动作：“停止以后使用这条记忆”“清除原始对话及相应证据”“清除所有相关数据”。首期的“忘记”默认保证后续召回和自动派生受控，不声称已经抹去所有历史消息、日志、备份或用户已看到的流式文字。完整数据清除需另行覆盖 Run、文件与 checkpoint 的生命周期。

本轮开关关闭写入时不生成候选；关闭读取时不注入已有记忆。两者在恢复时仍须有效。切回读取不能重新激活已删除内容。

## 10. 怎样沉淀有价值的业务经验

### 10.1 从执行记录到经验资产

**执行成功只证明一次运行完成，不能证明总结出的经验正确或可泛化。**

建议使用以下流程：

1. 从真实反馈、可验证结果或重复问题形成经验候选，保留来源事件与输入输出。
2. 记录适用对象、前提、采取的做法、可观察结果、失败反例和有效版本；不收集或发布模型隐藏推理。
3. 由负责人或用户核对“结果确实发生”与“原因是否有证据”。仅有相关性时标成待验证假设。
4. 在同类旧案例及至少一个边界/反例上回放，比较不用经验与使用经验的差别。
5. 个人经验在本人空间使用；跨用户推广前检查来源授权、脱敏、适用性和发布权限。
6. 稳定步骤转为技能；制度性要求由负责人发布为规则；有来源的资料进入知识库；不能由记忆整理器自行修改公共系统指令。
7. 原条件或依赖版本变化后复验，记录撤回原因和替代资产。

这条流程复用当前技能、知识和规则的所有权，并不假设当前已经有完整 SOP 产品。

### 10.2 本平台优先试点

以下均为拟议试点场景，尚无本平台实测收益：

| 场景              | 值得沉淀的内容                               | 不应自动认定的内容                             | 观察指标                             |
| ----------------- | -------------------------------------------- | ---------------------------------------------- | ------------------------------------ |
| 研发研究报告      | 用户接受的报告结构、证据偏好、已掌握的基础   | 一次临时要求变成全局模板；一次讨论变成产品定论 | 重复格式纠正率、审阅修改轮数         |
| 持续行业/竞品研究 | 关注对象、筛选口径、上次已覆盖范围与来源     | 把旧价格、旧功能和旧新闻当当前事实             | 重复检索量、过时结论率、补充信息比例 |
| 研发排障          | 特定版本下被证据支持的原因及排查方法         | 只因重启恢复就认定根因；失败输出写成结论       | 同类问题定位时间、错误复用率         |
| PR 评审           | 已确认的项目约定、可复现的缺陷模式和测试方法 | 所有仓库共用局部限制；模型说测试通过就记录通过 | 有效问题命中率、误报率、边界回归     |
| 项目约定协作      | 有负责人确认的术语和决策、暂缓事项           | 把草案写成生效规则，把决策记忆代替项目状态     | 术语纠正次数、引用当前决定的正确率   |

首期选择“研发研究报告＋连续追问”的原因是：平台已有员工、真实对话、知识证据和执行记录，能构造跨对话重复沟通问题；业务状态依赖较少，容易对照和纠错。排障、PR 经验需要更强验证，放在后续。

## 11. 分阶段实施与失败处理

阶段按依赖排序，不承诺未经排期的工期。每阶段都应具备可撤回开关和独立验收结果。

| 阶段                      | 可交付范围                                                           | 复用及新增接点                                              | 进入下一阶段的条件                                        |
| ------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------- |
| 0：边界与评测基线         | 明确受限工作可见性；准备跨对话样本、无记忆基线和删除语义             | auth、conversations、execution 查询与文件入口；新增评测协议 | 游客/其他用户无法从任何出口读取受限内容；指标及样本可复现 |
| 1：明确保存的个人记忆     | 用户＋员工空间；保存、列表、编辑、删除；有界召回；两个开关及使用证据 | 新记忆业务模块；现有 snapshot、模型中间件、工具及 RunAction | 跨对话有效，纠错与删除立即影响后续读取，故障降级可解释    |
| 2：受管后台提取           | 来源事件、幂等、候选审查、低风险自动沉淀；来源变更和并发保护         | 新生成工作来源类型；复用 Run 预算与恢复；允许替换提取器     | 候选质量、总成本、崩溃恢复和迟到删除用例达标              |
| 3：验证后的工作经验       | 经验结构、对照回放、候选到技能/知识发布                              | 复用员工考核、技能与知识发布能力，补经验用例                | 经验改善真实任务，且误用与泄露样例通过                    |
| 4：跨员工、项目与组织协作 | 显式共享、成员与发布权限、撤回传播                                   | 依赖真实项目/组织对象；再评估图、层级摘要或外部服务         | 共享边界、源权限和组织收益均可验证                        |

首期不批量导入全部历史。先处理用户明确保存和启用后的新增来源，避免旧假设、撤回内容和展示资料被错误当作个人记忆。未来历史回填应单独预览、授权、设预算并遵守删除抑制记录。

### 11.1 关键故障行为

| 故障                      | 推荐行为                                                   |
| ------------------------- | ---------------------------------------------------------- |
| 提取模型超时或额度不足    | 原对话结果保持成功，候选生成工作明确失败或延后；分别记账   |
| 明确保存时数据库失败      | 返回未保存，不展示成功回执                                 |
| 重试和崩溃恢复            | 事件幂等键去重，应用结果独立幂等；不重复执行原业务工具     |
| 同主题并发纠错            | 依据预期修订拒绝旧写入或重算，禁止后完成的旧内容覆盖新确认 |
| 记忆索引落后              | 回查权威版本，缺索引可走允许的 FTS 路径；不返回失效旧版本  |
| 外部记忆服务故障          | 按任务是否依赖记忆决定降级或暂停；身份和权限检查保持强制   |
| 删除/撤权发生在模型生成中 | 停止后续使用与发布，标明受影响执行；已发送内容无法收回     |
| 提取到恶意工具指令        | 不转成行为权限；来源保持低信任并隔离候选，记录拒绝原因     |
| 记忆关闭后恢复旧 Run      | 重新检查当前开关、权限与删除代次，旧快照不授予继续使用权   |

## 12. 验收：证明记忆有用且能纠正

### 12.1 评测设计

保留无记忆、简单记忆、候选方案三个对照：无记忆组仍使用当前同线程摘要；简单记忆组使用明确保存与 FTS；候选组再加入自动提取、向量或外部服务。**不能用“没有当前平台摘要的裸模型”人为夸大收益。**

建议先建设 120 条中文跨会话轨迹，每组 20 条：偏好与范围、事实更新与时间、删除与恢复、来源变化与撤权、经验使用与边界反例、无关信息与不得记忆。每条至少跨两个对话，并包含目标记忆、禁止记忆、预期可见范围及正确行为。划分调参集与保留集，固定模型、提示、检索预算、数据快照与裁判版本。

另设长历史扩容及并发故障集合，不以 120 条功能样本代表所有规模。参考 LongMemEval 的信息提取、跨会话、时间、更新和拒答能力，但补上其并不直接覆盖的平台授权、遗忘和动作验证。[LongMemEval 原文](https://arxiv.org/abs/2410.10813)

### 12.2 分层指标

| 层次       | 指标                                                     | 防止的误判                     |
| ---------- | -------------------------------------------------------- | ------------------------------ |
| 写入       | 声明正确率、应记覆盖、错误自动生效率、来源可追踪率       | 保存数量多不代表价值高         |
| 检索       | 相关证据 Recall@k、无关注入率、过期/撤权命中数           | 检索命中不等于回答使用正确     |
| 回答与行为 | 偏好遵循、更新正确、未知时说明不足、经验适用、任务成功   | 模型裁判高分不等于真实执行完成 |
| 用户收益   | 重复解释次数、纠正轮数、完成时间、接受率                 | token 减少不等于体验改善       |
| 治理       | 跨用户/游客泄露、删除后再出现、源撤权残留、候选越权发布  | 只测正向记住而漏掉遗忘和隔离   |
| 系统       | 在线新增延迟、后台积压、存储增长、模型调用数、全链路成本 | 只统计最终一次回答费用         |

总增量成本应包含：在线记忆上下文与检索＋后台提取和整理＋embedding / 重排＋失败重试＋存储和供应商费用。按获益任务及无关任务分别统计，避免平均数掩盖频繁写入的成本。

### 12.3 初始发布门槛建议

以下均是建议的试点门槛，不是已经测得的结果或对外 SLA：

1. 所有预设越权、游客读取、删除后恢复、来源撤权、候选越权发布用例必须通过；有一项内容泄露即阻止发布。
2. 保留集的明确偏好跨对话遵循率、明确纠错后使用新版的正确率均达到 95%；错误自动生效率不高于 2%。样本量和置信区间同时报告。
3. 有记忆需求的目标任务相对无记忆基线，重复纠正率相对下降至少 20%，或任务通过率提升至少 10 个百分点；不能只依靠主观“更像认识我”。
4. 无关任务不得出现明显退化。显式要求本次例外时，不得被长期偏好覆盖。
5. 初期本地检索新增 P95 延迟以 300 ms 为试验目标；全链路平均增量成本以不超过基线 15% 为试点预算。若收益与成本不匹配，缩小提取范围或停用相应策略。
6. 人工抽查写入与经验样本，针对数字、时效、范围和验证依据逐项复核；模型判分与确定性权限/状态断言分开。

小样本全通过只代表该集合通过，不能宣称隐私泄露概率为零。线上再以受控小范围试点观察，按记忆形成策略和模型版本分别复盘。
