## 1. 当前基础和演进原则

现有 ConversationCommands 在短事务接受聊天，Runner 在事务外驱动，RunStore 保存实际步骤和结果，SSE 只观察。普通 Agent 采用 create_agent 和受限技能加载；CI 共用外层 Runner，但有专用模型往返。当前单进程、SQLite、本机锁；普通聊天按条件恢复，CI 与无法恢复的执行标记 interrupted，具体边界以现行运行契约为准。

普通聊天的 checkpoint 存储与历史读取按[SQLite checkpoint 聊天方案](../sqlite-checkpoint-chat.md)先行验证，不以 W2 任务能力为前置；其[隔离实验记录](../../records/sqlite-checkpoint-chat.md)只证明 SDK 与 SQLite 的执行和读取能力，不表示本文 W3 的业务等待、授权和预算恢复已经实施。

保留提交、执行与观察分离；将 Run 的来源从仅对话扩展为对话/任务，再增加等待和触发。执行器对外统一生命周期，不要求所有工作内部都由模型决定下一步。不同岗位通过能力与方法配置区分，不复制一套 Runner。

## 2. W2：复用 Agent，解除消息耦合

### 2.1 接受与执行的职责

| 协作点                             | 拟议责任                                              | 边界                                                          |
| ---------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------- |
| ConversationCommands / TaskService | 校验各自输入、业务状态、主体范围，组织跨表接受事务    | 各入口保留业务语义，不互调 HTTP 或拥有另一套队列              |
| 共用准入协作                       | 额度、员工可用、模型/方法许可、同键重放规则           | 使用调用方事务，不能内部独立 commit；Task 的 owner 检查先完成 |
| ExecutionAssembler                 | 从已授权输入产生不可变执行说明与能力快照              | 复用当前模型/规则/技能捕获，秘密不入快照                      |
| Runner                             | 领取、并发、时间、取消、授权复核、策略分派与错误收束  | 不解析岗位名称，不把领域流程堆进主循环                        |
| Executor                           | 按冻结说明执行，发出受控动作并返回候选结果            | 可调用相同 Agent；不自行把数据库记为 succeeded                |
| ResultCommitter / RunStore         | 检查取消及归属，原子提交来源主体、Run、步骤与正式结果 | 聊天提交消息；任务提交成果与待验收状态                        |
| 查询与 SSE                         | 授权后返回持久化事实                                  | 不通过重新调用模型恢复展示                                    |

这些是职责名，不要求一项一层或每项一个包。先在真实调用点提取窄协作，保留同库短事务，避免引入通用插件框架。

### 2.2 最小执行协议

| 输入/输出        | 内容                                                                 | 安全和版本要求                                          |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| ExecutionSpec    | run_id、origin、task_type、执行契约版本、输入/配置快照引用、资源限制 | 平台生成，客户端不能指定任意执行器；已接受内容只读      |
| ExecutionContext | 当前授权检查、取消信号、剩余预算、步骤写入、受信工具和知识入口       | 凭证按动作解析；每次模型/工具动作前检查；子执行不能扩权 |
| ExecutorResult   | 候选正文/结构化结果、来源引用、检查所需资料、累计已知用量            | 无“已接受”字段；工具原始 JSON、隐藏推理不进入正式正文   |

聊天和任务都可构造模型需要的 user/system 消息，但任务的这些消息是内存执行输入，不是强行写入 conversations/messages 表。SDK 事件经宿主映射为现有步骤，再由事务分配 sequence 与 revision。

W2 最小策略登记只需要现有聊天、已有 CI、任务答复草稿三类分派。任务与聊天可以共用相同 provider，差别在输入装配和交付检查；不为答复草稿复制另一套模型/工具往返。

### 2.3 成功与故障

任务执行完成后，先在事务外做结构、必需字段与引用定位检查，再原子提交 Deliverable、Run succeeded 和 Task awaiting_review。必要的语义条件仍由人判断，不假称静态检查证明内容正确。

失败、取消或服务中断时统一收尾步骤和 Task；存储失败立即停止后续动作，不先宣告成功。聊天保持原来的消息提交和重试语义。所有来源共用相同的全局/用户准入、队列和真实并发，不因增加任务入口多出不计费或不受限路径。

现有 CI 可继续在相同 Runner 下运行；向通用循环迁移遵循[标准 Skill/MCP](../skills-and-mcp/README.md)，先在同一输入上核对证据与报告，再替换重复循环。W2 不以该迁移完成为前置。

## 3. W3：持久等待与同一尝试继续

### 3.1 先做受控实验，再开放页面能力

基于项目实际锁定 SDK 做一次隔离实验：持久 checkpointer、运行前后重启、interrupt、恢复节点重入、取消和重复 resume。先验证本机 SQLite 兼容组合，不同时更换数据库或引入 Temporal。库的具体构造参数以实施时兼容性验证为准，本设计锁定业务语义，不复制尚未实测的 SDK 示例当成保证。

W3 首个可交付用例是“执行中缺少确定资料 → 等待用户补充 → 继续形成成果”。动作批准属于同一类等待扩展，只有具体写入能力及幂等策略完成才启用；不在 W3 默认开放外部写入。

### 3.2 状态、预算与授权

| 事项       | W3 规则                                                                                                                    |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- |
| Run 状态   | 增加 waiting 非终态；active 唯一索引包含 queued/running/waiting/cancelling；等待仍占该 Task 的一个尝试                     |
| 暂停与恢复 | running → waiting → queued → running；恢复仍为同一 Run，started_at 保留，finished_at 仍为空                                |
| 执行资源   | waiting 释放模型并发和执行句柄；仍计入待完成工作上限，不能无限积累等待                                                     |
| 时间       | 累计实际执行时长与等待有效期分开；每段继续使用剩余预算，不每次 resume 重置模型/工具调用与时限上限                          |
| 输入       | 原快照不改；补充答复保存为绑定 wait ID 的不可变恢复命令，成果依据为初始快照加已采用的补充命令                              |
| 目标变化   | 补充不能改工作目标、扩大工具权限或换执行策略；确需改变则取消旧 Run、修改草稿、提交新 Run                                   |
| 会话       | 聊天及 W2 主动执行语义不变；等待期间无动作，不要求旧 session 常驻；继续时由同一 owner 的当前有效 session 重新授权          |
| 原始身份   | initiated_by_session_id 保留来源，不改写；新执行段的授权来自恢复命令记录，不能伪装原 session 未过期                        |
| 当前授权   | 恢复前重新检查 owner、操作能力、员工/方法/知识/连接及预算；快照不使撤权失效                                                |
| 到期/取消  | 等待到期关闭 Run 为 interrupted 并标 wait_expired；用户取消直接 cancelled；Task 到 needs_attention，已迟到恢复请求返回冲突 |

预算占用由宿主步骤或持久计数在动作前预留，恢复时从已有使用继续核算。供应商用量缺失保持未知，本阶段不承诺货币费用硬封顶。成果依据同时包含初始输入快照和本 Run 已采用的恢复命令，补充材料的引用不得回指可变草稿。

Run waiting 由运行器与持久等待记录确认，不允许模型只说“等你回复”就改变状态。任务需要的动作在首屏明确显示。W3 不因恢复临时换成最新模型/规则；既有许可或连接修订规则拒绝继续时，只能显式创建新尝试。

### 3.3 等待与恢复的最小持久记录

W3 新表沿用 UUID、UTC 时间和创建/更新时间约定，以下是拟议字段，实施前由隔离实验闭合 checkpoint 适配和迁移：

| 对象                | 字段、类型与默认                                                                                                                                                                                                 | 强制约束与用途                                                                                                                                                                                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| execution_waits     | id UUID；run_id UUID；operation_key TEXT；kind TEXT；state TEXT 默认 preparing；payload JSON；revision INTEGER 默认 1；expires_at UTC；checkpoint_ref TEXT 可空                                                  | ID/外键/operation_key/kind/payload/有效期非空；`(run_id, operation_key)` UNIQUE；kind 首先仅 input，未来 approval/external；state 为 preparing/open/resume_requested/resolved/cancelled/expired；open/resume_requested/resolved 必须有 checkpoint_ref；准备失败或取消可为空 |
| run_resume_commands | id UUID；wait_id UUID；actor_user_id UUID；actor_session_id UUID 可空；client_request_id UUID；request_hash TEXT；response JSON；state TEXT 默认 pending；applied_checkpoint_ref TEXT 可空；error_code TEXT 可空 | 除注明者均非空；用户/等待 FK；`(actor_user_id, client_request_id)` UNIQUE；一个 wait 至多一个被接受命令；state 为 pending/applied/rejected；保存的 session 清理后可置空但保留人和操作依据                                                                                   |

每个运行段一次只开放一个 wait。等待 payload 仅含需要用户判断的信息，不含凭证、SDK 原始上下文或隐藏推理。响应按 kind 的 schema 校验，大小限制计入任务上下文预算。

任务执行的 checkpoint 按 run_id 和执行契约版本隔离，不能用 conversation_id 复用跨任务图状态。普通聊天使用稳定的 conversation/thread 延续消息，详见[聊天方案](../sqlite-checkpoint-chat.md)。应用业务状态以 Task/Run 为准，SDK checkpoint 保存消息及内部执行位置；它不能成为第二套任务状态 API。

等待时限由任务类型的受信策略给出且必须有限，恢复命令不能任意延长。checkpoint 及恢复命令按任务 owner 范围保护，凭证由每次动作的受信上下文解析，不写入图状态；不向浏览器开放原始 checkpoint。

### 3.4 不能假设 SDK 与业务表自动原子提交

采用“持久意图 + 可核对 checkpoint + 对账”的边界：

1. 宿主为稳定 operation_key 写 preparing wait，模型/节点获得该 wait ID。
2. 执行器完成持久 checkpoint 后，应用将 wait open、Run waiting 同事务提交，再向页面显示可回答状态。
3. 用户 POST resume 同事务验证身份、wait/task 版本及幂等，保存命令并将 wait resume_requested、Run queued；尚未调用 SDK。
4. 领取时用该命令继续旧 checkpoint；图状态记录已采用 command ID。checkpoint 可证实采用后，应用标 applied/resolved，再写业务进度或终态。

| 崩溃窗口                              | 启动后的核对                                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| preparing 已存、checkpoint 未确认     | 查稳定 wait ID；没有可恢复 checkpoint 则 interrupted/needs_attention，不伪造 waiting |
| checkpoint 已存、应用 waiting 未存    | 确认对应契约与 wait ID 后补齐 waiting；不能将所有 running 直接当作已暂停             |
| resume 命令已接受、尚未继续           | 恢复排队，复核当前执行段授权再应用命令                                               |
| checkpoint 已采用命令、业务记录未更新 | 根据 command ID 补齐应用状态，不再次应用用户输入或重复动作                           |

若所选 SDK/适配器无法提供足以完成上述核对的标识，W3 保持功能关闭并修正适配方案，不能以盲目 replay 代替恢复。已经终态的旧 W2 Run 不自动升级成可恢复运行；缺 checkpoint 的历史只能重试。

### 3.5 恢复 API

新增 `POST /api/runs/{id}/resume`，要求 runs:create、tasks:execute、owner 与有效当前 session，包含 wait_id、expected_wait_revision、client_request_id、response。返回 202，重放 200；过期、已取消、已接受其他答复或契约不匹配返回 409，输入不合法 422，无权读取 404。

GET Task/Run 返回安全 waiting 摘要与允许动作；SSE 继续观察已持久化事实。点击补充资料与点击接受成果是不同动作。外部动作批准启用后，批准绑定服务器保存的动作、目标、参数哈希和版本，禁止恢复请求顺带更改它们。

## 4. W4：定时或事件进入同一任务准入

### 4.1 自动化不等于浏览器 session 常驻

引入独立、可撤销的持续执行委托。首期仍由 admin 创建并属于本人，必须明确员工、任务类型、输入模板、模型/工具/知识允许范围、期限、每次预算、频率/在途上限及通知偏好；不能选择“继承我未来的全部权限”。

实际许可为当前拥有者权限、委托范围、员工获准能力、上游身份及当次输入范围的交集。新增 Skill/MCP 不自动扩大旧委托。凭证从受信连接解析，不存入触发 payload；每次动作继续复核，委托撤销或到期停止后续动作。

自动 Run 等待后的继续仍受原委托范围和期限约束，owner 的补充或批准不自动延长委托。等待有效期不得晚于委托到期时间。

聊天和主动任务仍使用会话授权；自动任务的 Run 则使用 delegation ID。W4 在 Run 新增明确 authorization_kind/session-or-delegation 约束，不通过 initiated_by_session_id 为空就默认放行。owner_user_id 及发起归属仍可追溯；禁用账号不能继续靠旧委托运行。

### 4.2 最小模型与协议增量

| 对象                   | 必需依据                                                                                           | 约束与默认                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| automation_delegations | UUID、owner、员工、任务类型、允许连接/操作/资源、预算、valid_until、revoked_at、revision、UTC 时间 | 期限必须显式确认，无无限期默认；撤销后不靠旧快照继续，秘密不进入对象                                     |
| automation_triggers    | UUID、delegation ID、kind、definition JSON、enabled、revision、UTC 时间                            | kind 先 schedule 或一个明确事件源；默认停用，保存与启用分开；模板和来源映射按版本保留                    |
| automation_occurrences | UUID、trigger ID、definition revision、event_key、状态、payload snapshot、task_id 可空、UTC 时间   | `(trigger_id, event_key)` UNIQUE；task_id UNIQUE FK；记录 skipped/rejected/accepted，未接受时 task_id 空 |

字段细化与迁移在选择首个触发类型时补齐该增量，W4 不以支持任意事件、cron语法和任意模板变量为首发范围。任务类型、输入和执行核心沿用 W2/W3，不能新增自动化专用模型循环。

新增 `/api/automations` 管理入口，包括创建、列表、更新、启用/停用与撤销委托；仅有 automation 管理能力且为 owner 才可访问。PATCH/启停携带预期 revision，写入带幂等键。内部触发在同一短事务核验委托、事件唯一键、容量并调用 Task 接受协作；不能通过公开聊天接口伪造用户发送。

每个触发实例创建独立 Task，Task 创建请求 ID 从稳定 occurrence 身份派生；重复投递沿用原结果。自动入口在一个短事务中创建 Task、queued Run 并标 occurrence accepted，不采用网页“先保存草稿再执行”的两请求流程。准入不通过则没有新 Task/Run，保存 occurrence rejected 及安全原因；重复投递返回同一拒绝结果，不隐式重试。后续主动重试该实例需显式命令并仍使用原 occurrence，不能生成另一份工作绕过唯一键。

### 4.3 首发触发规则

| 事项     | 建议规则                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 定时     | 先每日/每周固定本地时间；存 IANA 时区，UI 初始建议使用用户时区，需明确确认；实际时间存 UTC                                                 |
| 时区边界 | 夏令时缺失时刻跳过并记原因，重复时刻仅取较早的 UTC 时刻；event_key 为计划 UTC 时刻，定义修订单独保存；变更从下个未来计划点生效，不补跑过去 |
| 错过执行 | 只考虑最近一个计划点，超过明确宽限即 skipped；不默认补跑所有历史周期                                                                       |
| 重叠     | 同一触发器上一任务仍 active（含 waiting）时，记录 skipped_overlap；先不排无限积压                                                          |
| 事件     | 先一个已有真实来源；验签、时间窗口、体积限制、域内稳定 event ID；无可靠身份和去重键时拒绝，不按每次接收随机建任务                          |
| 输入信任 | 事件是数据，按允许字段映射到任务；不能覆盖系统规则、员工、授权范围或执行器                                                                 |
| 交付     | 初期只读取证或形成待验收草稿，不自动接受成果，不自动扩大为发布/退款/删除                                                                   |
| 通知     | 站内待处理优先；按用户确认的偏好通知完成、失败或需要行动，监控无相关变化时安静；事务后发出，按业务事件键去重                               |

W4 不调用本机系统 cron 作为规避平台记录的替代，也不使用 Codex 应用的自动化功能来代替产品自身能力。本文仅为设计，当前不创建任何真实定时任务。

## 5. WX：环境、外部动作与规模按需增加

| 触发条件               | 增量                                             | 必须先具备的约束                                                                      |
| ---------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------- |
| 真实工作需要文件/代码  | 隔离 sandbox、持久工作区、受控依赖、成果文件引用 | 宿主/凭证隔离、网络范围、资源预算、制品哈希与 owner；恢复到匹配工作区版本             |
| 需要写外部系统         | action intent/结果核对与按动作批准               | 固定参数、业务幂等键、结果未知状态、可查询远端标识；不能仅依赖框架重试                |
| 一次工作含大量独立项   | item 记录、分片、并发与部分重试                  | 逐项幂等和结果，父级预算/取消传播；不以整批单 loop 替代                               |
| 分工带来可测收益       | 子任务或子执行、上下文和结果合并                 | 权限收敛、共享预算、失败升级；模型互评不能代替真实证据                                |
| 单机不满足负载/可用性  | 多 worker、租约/心跳/fencing、队列及合适数据库   | 先改 recover 语义，不能多进程同时调用现有“中断全部运行”；过期 worker 的迟到写入须拒绝 |
| 客户必须接已有 runtime | 窄执行器适配                                     | 相同授权、事件、取消、制品和终态契约；不只接一个返回文本的函数                        |

外部写入建议以 action intent 保存 run/operation、获准参数哈希、幂等键及远端标识，状态区分 prepared/sending/succeeded/unknown/failed。响应丢失后先查询核对；无法核对或不支持幂等时交人处理。动作批准与成果验收分别记录，取消只阻止后续动作，不声称撤销已完成操作。

在这些条件未成立前，不引入完整工作流画布、多个持久引擎或自研完整 Agent 框架。若未来选择独立 durable orchestrator，应明确由它还是图引擎拥有步骤重试/等待；平台 Task/Run 仍是用户可见业务事实。

## 6. 发布、回退与验收顺序

1. W2 先增加双来源结构和安全查询，再接同一 Runner，最后开放任务页面；完整迁移与兼容见[任务契约](tasks.md#7-迁移兼容与恢复)。
2. W3 先做隔离故障实验并固定兼容组合，添加等待/命令与对账，再开放 input waiting；不把旧 interrupted Run 自动续跑。回退前停止新接受，处理/结束等待项；存在 waiting 数据时不能启动只识别旧状态的后端。
3. W4 先保存停用的委托与触发配置，再用有限一次触发核对归属、预算与交付，最后启用周期/事件；回退先停用触发并撤销委托，保留已创建任务历史。
4. 每阶段验收共用取消优先、持久化失败停止、scope 检查和总预算。新增恢复只对有明确契约及可核对依据的执行生效，不能改变旧历史含义。

必须覆盖每个 checkpoint/业务落库间隙、重复/过期 resume、等待期间重新登录、撤权、预算耗尽、来源变化、重复事件、停机错过周期、取消与迟到响应。真实 SDK、外部连接及业务效果分别验收；本次均未执行。
