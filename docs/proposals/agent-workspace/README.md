## 1. 目标、范围和设计约束

目标是让用户从员工入口完成“了解能力 → 交办或沟通 → 跟进执行 → 查看成果 → 接受或要求修订”，同时保留维护者的配置路径。以一个可用的短任务闭环推进，不先建设通用项目管理、工作流画布或多框架市场。

本次有效要求是先设计，不实施。现有学习路线、知识助手和标准 Skill/MCP 方案继续有效；本文明确它们怎样接入，不因任务设计提前完成或取消这些工作。与现有方案的边界见第 8 节。

首个任务切片建议为“根据明确提供的项目资料，准备一份可复核的答复草稿”。这是工程验收用例，不代表已验证商业客群。首版允许粘贴材料；真实知识能力完成后再复用其发布与引用，不以完整 RAG、通用 MCP、定时或文件生成作为任务功能前置。

设计采用以下约束：

1. 员工工作页是聚合视图，不另建员工工作空间数据主体。
2. 普通问答保持轻量；只有明确交办需要成果与验收的工作才创建 Task。
3. 任务可以没有对话，也不能为了复用 Run 而伪造聊天消息。
4. 成果正文与验收有独立记录，聊天消息、模型自报和 Run 成功都不能代替它们。
5. 现有 Runner、预算、步骤、取消与快照继续复用；不同提交入口共享同一执行准入。
6. 初期仍为单后端、SQLite、本机 Runner。持久等待先解决本机恢复，不同时做分布式改造。

## 2. 核心对象与关系

| 对象                | 负责什么                                   | 不承担什么                       | 关系与权威来源                                     |
| ------------------- | ------------------------------------------ | -------------------------------- | -------------------------------------------------- |
| Agent               | 长期岗位、职责与能力配置                   | 某次工作的进度或成果             | 一名员工可有多个对话、任务；引用现有员工主体       |
| 员工工作页          | 展示可用能力、交办、当前工作与最近成果     | 保存另一份员工或工作状态         | 按当前身份聚合已有主体，读取无副作用               |
| Conversation        | 一段独立交流及消息历史                     | 自动代表正式任务或验收           | 一个对话有多次聊天 Run，可显式作为若干任务的来源   |
| Task                | 一项工作的目标、输入草稿、当前进展与验收   | 整个员工配置或每轮模型输入       | 属于一名拥有者和一名员工，有多次任务 Run           |
| Run                 | 一次执行尝试、冻结输入、实际步骤与技术结果 | 是否被用户接受                   | 来源恰为 Conversation 或 Task 之一                 |
| Deliverable         | 一次任务 Run 形成的不可变成果              | 草稿输入、步骤日志或永久最新答案 | W2 每次成功任务 Run 一份成果；任务可有多个历史版本 |
| Delivery Review     | 针对具体成果的接受或修订要求               | 准许将来执行外部动作             | 绑定 task、deliverable、验收者及请求幂等键         |
| Agent Configuration | 维护员工当前岗位、装配和规则引用           | 当前任务表单与结果编辑           | 保留现有配置保存和修订协议；影响后续新提交         |

关系可以直接读为：员工分别承接对话和任务；两者分别产生 Run；任务 Run 产生版本化成果；验收绑定其中一份成果。任务可记录来源对话，但这条关联只说明从何交办，不使两种历史合并。

### 2.1 对话怎样变成任务

用户在对话中显式点“交办为任务”，选择本次目标及必要消息，预览整理后的任务表单，再保存或提交。读取页面、模型建议或选择消息都不会开始执行。

保存的是选中内容的输入快照及可访问来源引用，不把整段历史、隐藏系统提示词或其他任务成果自动带入。原对话保持原样；后续继续聊天不修改任务。W2 仅允许本人同一员工的对话作为来源，一个对话可交办多个独立任务。

### 2.2 任务中怎样补充与继续

W2 用任务页的“补充资料/修改要求”和“要求修订”完成迭代。保存输入与执行是不同按钮；要求修订只记录验收决定，不立即再调用模型。任务时间线从已提交输入的 Run 快照、Run 和 Review 投影，不新增第二套聊天存储，也不承诺记录每次未提交草稿编辑。

独立问答可以引用明确选择的任务成果来开始新对话，仍须显式确认和权限检查；不会因此启动任务重跑。完整的任务讨论线程、多方协作和任务内随意聊天留待真实需要后另写增量，不在 W2 强制建立 Task 与 Conversation 一对一关系。

### 2.3 成果与普通回答的区别

普通回答仍保存在对话消息中。任务成果由任务页读取 Deliverable，包含正文、采用输入、检查摘要与限制；对话最多显示授权范围内的来源链接或摘要，不复制一份可独立编辑的正式成果。

成果只读。修订以新 Run 生成新版本；首版不支持在网页直接改正式成果。若用户自行编辑采用，记录接受理由即可，不假称平台已保存编辑后的文本。在线编辑与导出文件另行设计。

### 2.4 配置怎样影响工作

| 操作                                            | 对现有工作的影响                                                                   |
| ----------------------------------------------- | ---------------------------------------------------------------------------------- |
| 编辑岗位、规则或共享方法正文                    | 已接受 Run 保留原快照，新提交使用新内容；不回写任务成果                            |
| 停用员工/技能、解除装配、改变参数/模型/凭证修订 | 沿用当前动作前复核机制，可能阻止正在执行的后续调用；不能承诺配置变化只影响下次运行 |
| 保存任务输入                                    | 只改该 Task 草稿，执行后另存新快照；不修改员工 prompt 或共享技能                   |
| 接受成果或要求修订                              | 只记录该成果的业务决定；不自动学习、改配置或扩大授权                               |

维护者从工作页进入配置，再返回工作页或任务时恢复原来源；任务页看到的是本次依据与当前不可继续原因，不把最新员工配置冒充本次执行配置。

## 3. 页面与导航

### 3.1 路由与职责

| 路由                                               | 阶段              | 页面职责                         | 进入后的行为                                             |
| -------------------------------------------------- | ----------------- | -------------------------------- | -------------------------------------------------------- |
| `/agents`                                          | 现有，W1 调整入口 | 发现员工、筛选、收藏             | 姓名/头像进入工作页；设置进入原配置                      |
| `/agents/:id/work`                                 | W1 新增           | 员工工作页                       | 只读加载能力与本人近期活动，不创建 Task/Conversation/Run |
| `/agents/:id`                                      | 保留现有          | 员工配置                         | 原配置标签、未保存保护与旧链接继续有效                   |
| `/conversations/new?agent=…`、`/conversations/:id` | 保留现有          | 即时问答及明确继续某段交流       | 沿用发送时创建和现有重试语义                             |
| `/tasks/new?agent=…`                               | W2 新增           | 交办表单                         | 本地草稿；显式保存才创建 Task                            |
| `/tasks`                                           | W2 新增           | 本人任务列表                     | URL 筛选员工、任务状态及分页                             |
| `/tasks/:id`                                       | W2 新增           | 一次工作的输入、执行、成果与验收 | 从服务端状态恢复，不因刷新重跑                           |

不在 W1 把旧 `/agents/:id` 静默改成工作页，避免破坏配置书签、标签和返回来源。W1 将侧栏收藏、员工姓名/头像及新建员工成功后的“去使用”入口指向 `/work`；设置仍指向原路径。旧兼容链接维持原语义，不靠来源猜测目标。

目录卡片的主按钮在 W1 仍直接开始对话，避免必须绕工作页；W2 对具备就绪任务选项的员工提供直接“交办任务”，否则保留问答入口。姓名/头像负责查看工作总览，设置负责维护，三个动作不再混为同一配置跳转。

W2 成果使用 `/tasks/:id?tab=deliverables&deliverable=<id>` 定位，旧版本可直接打开；不先建全局成果库。任务列表、员工工作页和通知中的成果链接均指向同一权威页面。

W1 保留现有全局导航，只调整员工使用入口；W2 才增加有实际功能的“任务”导航，并保留独立“对话”。根路径及已有旧查询兼容暂不改成任务首页。先让用户能选择工作入口，不用新的空工作台取代现有目录。

### 3.2 员工工作页的分期内容

| 区域       | W1                                                         | W2 及之后                                            |
| ---------- | ---------------------------------------------------------- | ---------------------------------------------------- |
| 身份与就绪 | 姓名、职责、可用/停用/模型未就绪，区分“配置存在”和“可执行” | 增加具体任务选项的就绪原因，不能凭岗位名称放开能力   |
| 主要动作   | 开始对话                                                   | 具备任务选项时主操作为交办任务，问一问为次操作       |
| 最近活动   | 本人的最近 5 条对话，显式继续或新建                        | 本人进行中/待处理任务、最近成果及对话                |
| 能力说明   | 真实可用能力与现有边界                                     | 任务类型、必要输入、结果样例；不展示未接通能力为可用 |
| 管理入口   | 有配置权限才显示“配置员工”                                 | 仍为显式入口，任务状态不放进配置表单                 |

W1 不显示尚不存在的任务、成果和审批空标签。员工停用时仍可查看获准历史，但不能新提交；模型未就绪时维护者可去配置，其他用户只看到原因。不同区域独立加载/重试，近期活动失败不阻塞员工说明。

初期复用现有共享收藏语义，侧栏名称调整为“置顶员工”，管理员维护共享星标，不暗示个人偏好；个人收藏关系不在 W1 新增。需要多人个性化时再迁移，不能把现有共享星标回填给所有人当作个人选择。

### 3.3 任务页的信息顺序

首屏依次显示目标、任务状态及当前需要的动作、当前 Run 摘要、最新成果；输入、历史尝试与完整步骤展开查看。W3 有等待后，首屏优先显示“需要补资料/批准什么/何时失效”。

任务业务状态与 Run 状态分别显示，例如“处理中 · 排队中”“待验收 · 执行成功”“需处理 · 服务中断”。有历史成果但最新尝试失败时，明确“上一版成果”，不显示成最新输入已完成。

“停止本次执行”操作 Run，保留任务待处理；“关闭任务”表示放弃整项工作，要求没有活跃 Run 并填写原因；“接受成果”表示这项工作完成。三个动作的按钮文案和确认内容必须区分，不能共用含糊的“结束”。

### 3.4 身份与状态恢复

W1 管理员有执行及配置入口；游客/member 只读员工公开说明，不返回近期对话、任务、成果或相应计数。是否开放普通用户执行仍由独立授权方案决定。

W2 新任务从一开始采用 owner 范围：访问必须具备操作能力且为拥有者，`resources:all` 不绕过任务私有内容检查。工作页仅聚合本人活动；现有独立对话的历史访问约定不因此追溯改变。所有成果、步骤、SSE、引用与缓存遵守同一任务归属。

URL 保存列表筛选、任务标签与成果版本；草稿按身份及资源隔离，不保存凭证。草稿保存与任务执行有各自反馈；409 保留输入并提供查看最新状态，不能自动用新 revision 重放。离开只停止观察；运行刷新恢复继续观察。页读取、返回与自动重连都不发起执行。

## 4. 分阶段交付与依赖

W 为本方案阶段，避免与既有技能 P1/P2、知识迭代编号混淆。每阶段均可独立发布，后续能力不作为前一阶段验收前置。

| 阶段          | 用户获得什么                                  | 主要改动                                                              | 前置与退出条件                                                    |
| ------------- | --------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------- |
| W1 工作入口   | 从置顶/目录进入员工工作页，快速问答或显式配置 | 新读模型与路由，调整链接；无新表，无执行协议变更                      | 以现有聊天可用为前提；旧配置链接、游客边界、刷新与草稿通过        |
| W2 任务与交付 | 交办答复草稿，查看执行、接受或要求修订        | Task/Deliverable/Review；Run 来源解耦；任务接口及页面；复用受限 Agent | W1 可用；使用粘贴资料即可验收，不等知识/MCP全量完成               |
| W3 持久等待   | 工作可等人，服务重启后从获准位置继续          | 持久 checkpoint、等待/恢复命令、同 Run 续跑、取消及恢复核对           | W2 稳定，存在需等待的真实工作；故障实验先通过；不立即增加外部写入 |
| W4 自动交办   | 该工作接受定时或一个事件源，并有可撤销授权    | 委托、触发记录、去重、错过执行策略、异常入口                          | W3 恢复和授权边界通过；先一种触发，初期只读/形成草稿              |
| WX 环境与规模 | 根据工作需要生成文件、运行代码、批量或分工    | 沙箱、制品、逐项状态或子任务、执行器适配                              | W2 之后按需求选做；不要求先完成 W4，不同时引入所有能力            |

既有知识助手与效果实验可并行；W1 不依赖知识导入，W2 可先用明确粘贴材料。标准 Skill/MCP 作为能力接入支线推进，CI 迁移必须保留领域检查。不能把这些依赖合成一次“大平台重写”。

### 4.1 W1 实施包

1. 增加只读 workspace 查询与公开投影，按身份过滤近期活动。
2. 新增工作页，复用头像、状态、对话入口与现有设计系统。
3. 将目录打开动作与侧栏置顶链接切到工作页，配置按钮和旧链接保留。
4. 验收不同身份、员工不可用、活动加载失败、URL返回及配置草稿保护。

W1 不抽执行框架、不改变数据库。若仅提供前端新页面而仍读取无权限的配置详情，不算完成。

### 4.2 W2 实施包

1. 按 [任务契约](tasks.md)迁移和回归 Run 来源约束，旧对话历史不改造成任务。
2. 复用现有 RunAdmission 与员工执行配置视图，参照 ConversationCommands 的同事务组合方式接入 TaskService；不从新服务调用旧 HTTP 路由，也不在内部多次 commit。
3. 首个任务类型注册为“答复草稿”；复用现有受限 Agent，先输出 Markdown 成果，独立验收。
4. 完成任务列表/详情、来源对话交办、停止/重试/修订、成果历史与 owner 检查。
5. 用正常、资料不足、修订、重复提交、取消及重启场景验证；小样本记录复核耗时。尚未有质量证据时只称“可交办的草稿”。

W2 不实现运行中聊天改变输入、断点续跑、任意工具写入或文件上传。服务中断仍需新 Run 重试，界面如实显示。

### 4.3 W3、W4 与 WX 的启用门槛

W3 先用“缺资料后等待补充”验证持久等待，不以有风险的外部写入作为首个实验。之后才把明确动作批准接到同一机制。W4 每个触发实例创建独立 Task，Run 不依赖浏览器 session。WX 的沙箱或分工必须对应真实工作和单 Agent 基线。

可执行阶段划分和失败处置详见[运行设计](runtime.md)，不能仅增加状态标签或定时器就宣称阶段完成。

## 5. 一个贯穿验收示例

1. 用户从置顶员工进入工作页，先问一个资料问题，产生普通对话 Run。
2. 用户点“交办为任务”，选择必要交流内容，填写“给客户准备部署答复”，显式保存/执行。
3. Task T1 的 Run R1 使用冻结输入和员工配置，交付 D1；T1 待验收，R1 成功。
4. 用户对 D1 要求修订，补充新条件，再点“按修改意见执行”；产生 R2/D2，D1 仍可打开。
5. 用户接受 D2，T1 已接受；原对话仍可继续，其新消息不改写 T1。
6. W3 后，某次执行缺资料可等待补充，恢复仍是原 Run；W4 后，定时实例创建 T2，不把下一周成果覆盖到 T1。

步骤 2—5 是 W2 的独立验收闭环；步骤 6 不作为 W2 前置。

## 6. 模块职责与演进边界

| 模块                     | 拟议职责                                     | 保留的依赖与约束                                               |
| ------------------------ | -------------------------------------------- | -------------------------------------------------------------- |
| agents                   | 当前配置与工作页读投影                       | 读投影按实际对象查询，不拥有任务状态；不新增按岗位名称分派逻辑 |
| conversations            | 原问答消息、来源选择与聊天提交               | 不再是所有 Run 唯一入口；聊天重试语义保持                      |
| tasks（拟新增）          | 任务草稿、提交、交付、验收及跨对象事务       | 控制 Task 与任务 Run 同事务；依赖公共准入，不复制 Runner       |
| runtime                  | 执行装配、策略分派、授权/预算/取消与生命周期 | 模型往返继续用 SDK；业务输入和成果检查走明确接口               |
| runs                     | 来源分派、步骤、尝试状态与安全投影           | 按 Conversation/Task 检查范围；终态写入与业务结果原子协作      |
| automations（W4 拟新增） | 委托、触发实例与创建任务                     | 不是第二执行引擎；重用相同额度与 Task 提交操作                 |

模块按实际阶段创建。W2 的公共协作可以是窄函数或服务，不先建立插件容器、通用 repository 层或微服务。具体输入、状态及迁移分别由配套设计维护，避免在三份正文复制字段。
