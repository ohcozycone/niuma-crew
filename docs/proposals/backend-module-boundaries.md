## 1. 目标与本轮结论

最终目标是：**形成职责明确、边界相对稳定的业务模块，使修改技能格式、工具认证、员工装配或对话表现时，主要修改对应模块和必要的接入代码。** 目录和注释用于准确呈现这些职责，不能代替业务规则、事务和调用关系的设计。

当前建议仍是保留模块化单体，做有范围的边界重构；各模块继续在同一后端进程、同一数据库中协作。

针对“传统业务后端与 Agent/Harness 是否拆分”，建议是：**业务规则、用户接入和 Agent 执行明确分工；共享员工、技能、账号和权限的事实；当前不新增两套后端或独立数据库。** 职责边界现在完善，独立执行进程按部署与隔离需求另行判断；具体依据、例子和演进条件见[第 12 节](#12-传统业务后端与-agentharness-是否拆分)。

本轮需求有一项明确变化：**完全移除之前的 CI 对话诊断试验链路。** 不再设计如何长期保留或扩展这条链路。因此撤销上一版的 CI 配置迁表、CI 工作入口、新专业工作协议、专业错误注册平台等建议。不会为了替代被删除的试验，再建设一套通用工作流。

仍然有独立理由保留的改造包括：

1. 把技能包及旧格式的解释集中到 skills。
2. 统一用户公开操作与内部协作入口的权限责任。
3. 把 tools 内连接维护、工具清单确认、实际调用分清。
4. 把模型和工具共用的凭证加密机制放到基础设施。
5. 澄清员工工具账号绑定，并用更准确的名称表达。
6. 保留方法与工具服务的联合检索，名称收窄为 capability_catalog。

## 2. 实施前问题与本轮处理

| 当前设计或问题                                           | 目标处理                   | 理由                                                                                   |
| -------------------------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------- |
| 员工、技能、工具、模型连接分别维护                       | 保留                       | 员工选择什么、方法内容是什么、工具如何连接、模型凭证是什么，具有不同规则和变化原因     |
| 对话、可靠执行、Agent SDK 循环分开                       | 保留                       | 消息归属与历史、排队和预算、SDK 协议分别变化，不能因换 SDK 重写消息业务                |
| 文件与沙箱分开                                           | 保留                       | 文件需要长期保存，沙箱是临时环境；销毁环境不能删除已交付文件                           |
| 输入/空助手消息/Run 一起接受，正文/输出文件/终态一起交付 | 保留                       | 一次操作要么全部成功，要么全部回滚，不能为了拆模块产生半份结果                         |
| SSE 只观察已保存内容，断线不取消工作                     | 保留                       | 浏览器连接结束与用户要求停止执行是不同事情                                             |
| CI 试验散布在员工、对话、运行错误及界面中                | 删除完整链路               | 用户已决定撤回试验，不再为它保留模块或扩展设计                                         |
| 员工与目录查询自行解释 Skill 原文和旧格式                | 改造                       | 包格式变化不应要求多个业务模块同时理解新旧表示                                         |
| 有些 service 自带用户权限，有些主要靠路由检查            | 改造                       | 新入口应能复用相同操作，不必记忆哪些调用还需补权限；现有 HTTP 保护不能据此被描述为缺失 |
| ToolService 同时管账号、工具清单、实际调用               | 在 tools 内整理            | 改认证、改清单确认规则、改调用资源关闭各有明确落点，无需拆成三个顶层模块               |
| 共用加密机制位于 model_connections，错误写死模型含义     | 迁到 infrastructure        | 工具已经实际复用，技术机制不应带着某一个调用方的业务名称                               |
| personal_tools 名称难以说明实际操作                      | 改为 tool_account_bindings | 它维护的是账号连接的选择关系，不是新建或管理一套“个人工具”                             |

下表的“当前”描述实施前基线，目标已落实到代码。实际验收以本轮执行输出和验收记录为准，历史通过结果不替代当前验证。

## 3. CI 试验链路的完整移除范围

### 3.1 删除什么，保留什么

删除的是固定 GitHub Actions 诊断流程：从输入失败运行链接、专用技能与仓库配置，到取证、报告、反馈的全部功能。普通 GitHub 登录、用户自己登记的 GitHub MCP 服务以及通用技能/工具不是这条试验，不随它删除。

| 范围               | 当前位置与内容                                                                                                                                                                                                                                                                                                                                                       | 目标                                                                                    |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 专用实现           | 原 `ci_diagnosis`（已删除） 下全部 9 个文件                                                                                                                                                                                                                                                                                                                          | 删除整包，不新建 work、bindings、errors 或替代模块                                      |
| 专用路由           | 原 `api/routes/ci_diagnosis.py`（已删除）                                                                                                                                                                                                                                                                                                                            | 删除文件、路由挂载和依赖注入                                                            |
| 员工配置           | [models](../../backend/app/agents/models.py)、[schemas](../../backend/app/agents/schemas.py)、[service](../../backend/app/agents/service.py) 中 ci_repository、固定技能判断、虚拟增加 3 个工具等                                                                                                                                                                     | 删除专用字段与特判；工具数根据真实许可计算                                              |
| 对话全链路         | [service](../../backend/app/conversations/service.py)、[preparation](../../backend/app/conversations/preparation.py)、[authorization](../../backend/app/conversations/authorization.py)、[publication](../../backend/app/conversations/publication.py)、[queries](../../backend/app/conversations/queries.py)、[schemas](../../backend/app/conversations/schemas.py) | 删除 CI 输入、分流、额外授权、报告/反馈和读取结构；保留普通消息、附件、历史、重试和交付 |

| 配置               | [AppConfig 与加载](../../backend/app/config.py)、backend/.env.example、部署说明                                                                                                                                                                                                                                                                                      | 删除 CI_GITHUB_TOKEN、CI_GITHUB_TOKEN_FILE 及对应应用字段；不读取或输出秘密值           |

| 专用数据           | ci_diagnoses、agents.ci_repository、固定内置技能与装配                                                                                                                                                                                                                                                                                                               | 通过新增正式迁移及配套来源目录清理移除，处理方式见下文                                  |
| 测试与文档         | 专用 CI 测试、共享测试助手中的 CI 适配、现行功能入口                                                                                                                                                                                                                                                                                                                 | 删除专用用例，调整共享用例；历史迁移验证及历史记录保留其时点                            |

本轮删除的四个接口：

| 方法 | 路径                                                           | 当前用途           |
| ---- | -------------------------------------------------------------- | ------------------ |
| GET  | `/api/ci-diagnosis/capability`                                 | 查询 CI 接入状态   |
| POST | `/api/ci-diagnosis/skill`                                      | 安装固定试验技能   |
| GET  | `/api/conversations/{id}/responses/{response_id}/ci-diagnosis` | 读取专业过程与报告 |
| POST | `/api/conversations/{id}/responses/{response_id}/ci-feedback`  | 提交专业反馈       |

员工请求/响应不再有 ci_repository；发送请求不再有 CI 的 work；普通回复不再有 ci 摘要和仅用于区分两条试验路径的 work_kind。旧请求应明确被拒绝，不能忽略 work 后悄悄当普通聊天执行。这属于有意删减接口，上一轮“全部响应兼容”的承诺不适用于本次功能删除。

必须保留：

- auth/github.py、GITHUB_OAUTH_* 和 GitHub 登录接口：它们负责用户身份，与 CI 取证凭证不同。
- tools 的服务定义、账号连接、工具许可、HTTP/stdio 适配器：用户可以继续配置通用 MCP 服务。
- Run、RunAction、对话、消息、文件、沙箱和 checkpoint：普通 Agent 仍使用它们。
- 普通输出文件使用的 structured_result/Completion 结果信息，以及普通运行的恢复限制；不能因为 CI 曾使用同一结构而整项删除。
- agent_runtime/tool_results.py 的实际网页读取验证：它属于普通工具结果处理，与 CI 日志证据链不同。
- 项目自身的自动化检查、测试流水线：产品里的 CI 试验与工程 CI/CD 不是同一件事。

没有已确认只供 CI 使用的顶层 Python 依赖。httpx、openai、LangChain、SQLAlchemy 等仍有普通调用方，不能按名称猜测卸载；实施时按实际依赖图清理锁文件。

### 3.2 数据、活跃运行与历史怎样处理

**推荐保留已交付的消息文本及共享 Run/动作作为只读历史，删除专用报告、过程和反馈表。** 已通过正式迁移实现并完成隔离验证；当前本机环境也已备份并升级至 0012，其他部署环境需各自执行操作指南。删除功能不自动等于删除整个混合对话，因为同一对话可能还包含普通消息。

1. 实施前停止旧后端的请求接受、Runner 及来源同步，确认无旧进程继续写入，再成套备份业务库、checkpoint 和相关技能目录；盘点导出专用报告、固定技能及 CI 运行标识，供回退核对。
2. 实施前迁移 head 为 0011，本轮新增 0012 退役迁移。保留既有 0001、0004、0005 等历史迁移，不改写旧升级链或用空库代替升级。
3. 识别已有 CI 快照、work.kind 及专用记录关联。新 Runner 启动前，将待执行/运行中的 CI 收束到中断，正在取消的收束到取消；关闭未完成动作、释放对话占用、更新观察版本。无法确认结果的动作保持 unknown，未报告用量保持未知，不能填成已确定失败或零消耗。不能删执行器后让旧记录被当普通工作恢复。
4. 使用[技能源归档工具](../../backend/migrations/retire_ci_source.py)在迁移前精确归档已同步来源，操作与各状态处理见[部署指南](../guides/backend-operations.md#ci-试验退役与历史处理)。然后删除 ci_diagnoses 和 agents.ci_repository。精确清理固定技能 `6e69bf0e-84ca-44fd-8afb-d299a63d4381` 及装配；不按“CI”名称批量删用户技能，也不删除员工。若该技能已关联可编辑来源目录，使用现有锁与一致性机制归档对应来源，避免下次同步重新导入。
5. 保留历史文本和原运行依据，但对已移除输入结构明确拒绝重试；历史回复通过最小的“是否可重试”状态告知调用方，前端不再展示可用的旧试验重试操作。兼容代码只识别并拒绝旧任务，不包含 CI 执行、报告读取或新工作类型注册。新普通消息仍可正常发送。
6. 检查外键、员工索引和唯一约束、普通消息序号及运行数量；验证备份恢复。删除的专业 JSON 不能通过一个空壳 downgrade 无损恢复，应使用真实备份回退。

历史 ci_* 错误码可以保留在历史 Run 中，读取时返回说明该记录仅可查看的安全提示，不再引导“请重试”；不为保留旧提示恢复整套专业错误系统。已成功的旧正文仍按普通历史规则参与后续上下文，历史只读表示不能再次启动原诊断，不禁止用户继续普通对话。

普通历史和普通可恢复运行的预算、存档不改变。另需保持普通请求的去重编码：[当前请求摘要](../../backend/app/conversations/service.py)包含固定的 `work=None`，不能因删除可提交字段就改变旧摘要。保留其规范编码或提供有界的旧摘要校验，确保升级后原键、同内容仍返回原记录；新输入仍不接受 work，不借兼容恢复专用功能。

历史迁移和对应升级测试中仍可出现 CI 旧结构；最终 head 和运行代码不再提供 CI 功能。这两者不矛盾。

## 4. 稳定模块各自提供什么能力，为什么这样分

| 模块                      | 它具体做什么、提供什么                                                           | 使用它的原因与边界                                                                   |
| ------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| auth                      | 验证用户或游客，签发/撤销会话，判断操作权限和资源归属；已有本机账号运维命令      | 各入口使用同一身份规则；平台登录账号不等于外部工具账号                               |
| agents                    | 保存员工指令、模型和技能选择、工具许可，检查编辑权与修订；取得本次执行的员工配置 | 员工决定“选用哪些资源、能做哪些操作”，不解释技能包或保管工具 Token                   |
| skills                    | 校验和保存方法正文、技能包与参数规范，导入导出、同步来源目录，返回固定版本定义   | 方法可被不同员工复用；格式、旧数据兼容和内容版本集中维护                             |
| tools                     | 登记 MCP 服务，保存用户账号及密文，取得并确认工具清单，执行已许可调用            | 负责“怎么连接、账号是否有效、实际返回什么”；不决定某员工获准哪些操作                 |
| model_connections         | 保存允许使用的模型连接和只写密钥，检查连通性、引用及配置/凭证修订                | 员工引用连接，运行按固定修订解析；模型 SDK 循环归 agent_runtime/llm                  |
| organization_rules        | 读取并带修订更新全员共用的工作规范                                               | 规则自动应用到员工输入，不复制成各员工可独立覆盖的字段                               |
| conversations             | 创建对话、保存输入和正文、读取历史、接受发送/重试/停止，组织回复交付             | 它知道消息归谁、顺序是什么、结果落到哪条回复；不拥有工具认证或 SDK 解析              |
| execution                 | 检查容量和重复请求，登记/领取 Run，记录真实动作与用量，管理取消、期限和恢复      | 提供可靠运行；不保存消息正文，不解析模型协议                                         |
| agent_runtime             | 根据固定输入运行普通 Agent，加载获准技能、解释模型输出、通过受控入口调用工具     | 隔离 SDK 变化；运行层不直接查询身份和业务数据库                                      |
| files                     | 保存并校验文件字节，提供安全引用，执行大小/配额/清理规则                         | 对话决定文件是否对用户可见；文件模块不猜测某条业务关联的意义                         |
| sandboxes                 | 申请并提供本轮隔离环境，控制配额和期限，回收资源                                 | 成果由 files 保存；SDK 命令、路径和执行用户限制由 agent_runtime/sandbox_backend 适配 |
| capability_catalog        | 统一搜索已登记的 Skill 和 MCP 服务，按查看范围计数、排序和分页                   | 负责跨类型检索，不负责新建技能、维护账号或授予员工工具权限                           |
| llm                       | 用显式模型、地址、Key、时限创建客户端，识别供应商失败及用量                      | 不读取业务库、不决定岗位提示词，也不自行选用他人的凭证                               |
| api                       | 把 HTTP 参数转换成业务调用，返回字段、Cookie、下载或 SSE，处理浏览器来源与安全   | 客户端协议变化留在这里，业务操作不依赖 FastAPI Request                               |
| bootstrap、infrastructure | 创建并关闭具体依赖，提供数据库事务、字段和共用加密机制                           | 装配认识业务参与者；普通技术机制不夹带某个业务模块的含义                             |

## 5. personal_tools 到底是什么，为什么归 agents

### 5.1 用一个完整例子说明

有一个“工单助手”，创建者允许它使用某工单服务的“查询工单”操作，并设置为“每个使用者用自己的账号”。

1. 张三在 tools 中创建自己的工单账号连接，填写凭据，读取并确认可用工具。
2. 张三使用“工单助手”时，选择这条已经存在的连接。
3. 李四使用同一个员工时，选择李四自己的连接。
4. 两人共用一份员工指令和工具许可，但实际访问工单服务的账号不同。张三不能通过换账号，给员工额外增加“删除工单”的操作。

`personal_tools.py` 做的是第 2、3 步的选择与校验。它保存的是：**当前用户，在这位员工的这份工具许可下，选用哪条本人账号连接。**

| 事情                                           | 负责人                                 |
| ---------------------------------------------- | -------------------------------------- |
| 创建账号连接、保存 Token、换凭据、读取工具清单 | tools                                  |
| 决定员工允许哪些工具操作、资源范围和调用预算   | agents/tool_grants.py                  |
| 为当前用户选择这份许可使用的账号连接           | 拟议的 agents/tool_account_bindings.py |

绑定入口会检查：连接归当前用户、属于同一个服务、已经启用，且确认过的工具定义与员工许可相容。它不创建工具、不保存 Token、不修改员工指令，也不扩大许可。

如果员工使用的是“共用账号”，账号由员工创建者维护，当前使用者不能在这个入口替换。解除显式个人绑定也不总等于禁用：创建者可能回到使用装配时的本人连接；其他使用者没有绑定时，不会借用创建者的个人账号。这些语义应在说明与测试中保留。

### 5.2 为什么关系在 agents，账号在 tools

账号连接可以被多位员工使用；它存在多久、凭据怎么更换，由 tools 管。绑定必须依附员工的一份工具许可，许可删除时该绑定也结束，所以它是员工装配关系的延伸。

因此仍留在 agents，不新增顶层“个人工具”模块，也不让 tools 为账号选择反向理解员工许可规则。前端页面放在哪里，不决定这项业务归属。

### 5.3 推荐命名与实际接口

| 当前                                       | 推荐                                           | 说明                                         |
| ------------------------------------------ | ---------------------------------------------- | -------------------------------------------- |
| `agents/personal_tools.py`                 | `agents/tool_account_bindings.py`              | 文件直接说明“绑定工具账号连接”               |
| `PersonalToolService`                      | `ToolAccountBindingService`                    | 读取可绑定状态、选择/替换/解除连接并校验     |
| `PersonalToolDependency`                   | `ToolAccountBindingDependency`                 | 请求取得的服务名称与职责一致                 |
| tools/schemas.py 的 `PersonalBindingInput` | agents/schemas.py 的 `ToolAccountBindingInput` | 输入属于员工账号选择关系，不属于创建工具连接 |

已有 `PersonalToolBinding` 模型与 `personal_tool_bindings` 表可以保留，内部命名整理不引发无收益的数据库迁名。`get` 返回状态、`bind` 保存或解除显式绑定；保留现有 GET `/api/agents/{id}/my-tool-bindings` 和 PUT `/api/agents/{id}/my-tool-bindings/{grant_id}`。

当前真实入口是员工详情和对话页的“我的工具连接”，进入 `/agents/:id/connections`。维护账号凭据仍去工具连接管理。对应实现见[当前绑定代码](../../backend/app/agents/tool_account_bindings.py)、[许可与账号解析](../../backend/app/agents/tool_grants.py)、[当前页面](../../frontend/src/pages/tools/PersonalConnectionsPage.tsx)。

## 6. 其余值得做的边界调整

### 6.1 方法定义由 skills 解释，员工只组合装配关系

[skills/service.py](../../backend/app/skills/service.py)的 `_response`、[agents/service.py](../../backend/app/agents/service.py)的 `capture_skills`、[capabilities/queries.py](../../backend/app/capability_catalog/queries.py)目前都理解技能原文和旧格式回退。

增加 skills/definitions.py，统一决定标准包或旧字段如何形成规范名称、正文、文件清单及内容摘要。packages.py 继续负责 ZIP/路径/元数据安全校验和纯格式转换；旧字段转文本的辅助函数可以保留，但“该选哪种来源”的决定只由 definitions.py 维护。

agents/execution_config.py 读取已验证定义，组合员工选了什么、参数和关系修订，并接收现有 authorize_execution 的当前员工启停、模型选择和技能装配复查。关系编辑仍归员工操作，对话 authorization 只组合调用这些检查。

目录继续在数据库合并两类条目、应用查看范围、计数和分页，再只为本页批量取得协议名。协议名目前仍需解析本页 skill_md；禁止的是全表加载正文或为目录读取支持文件，也不能两边各取一页后拼接。

### 6.2 用户公开操作与内部协作分清

员工、对话已有显式 Actor 检查；技能、规则、模型和工具等实际用户操作应逐项补齐相同责任。HTTP 可以继续声明权限，但业务入口的保护不能依赖 HTTP。

内部协作不是用户管理操作。例如普通成员运行已授权员工时，可以间接读取技能、规则和模型配置，不应额外要求管理员的配置管理权限。带 Session 的协作函数使用调用方事务，不自行提交。

auth/cli.py 已经有本机账号运维命令，sandboxes/cli.py 已有环境核对命令；它们不是“尚未存在”。这里尚未交付的是用户业务命令入口，以及无用户会话的机器任务身份。本机管理员初始化也不能被机械改成必须先有一个现有用户 Actor。

### 6.3 工具模块内按三种操作整理

- connections.py：创建/修改/删除账号连接，保存和解析凭据，维护修订；配置变化与旧工具清单失效仍同事务。
- catalogs.py：从远端获取工具清单，保存待确认结果，确认/丢弃变化，维护展示名称与说明。它不执行业务工具。
- invocation.py：执行已经批准且获准的操作，限制结果、处理失败，管理本轮 MCP 会话并关闭。它不决定员工允许做什么。

保留服务定义、网络限制、参数范围和 HTTP/stdio 适配器。旧 ToolService 可短期转发，调用方迁完后删除空转发；不永久堆叠两套同义服务。

### 6.4 凭证机制共用，故障由业务解释

[model_connections/credentials.py](../../backend/app/infrastructure/credentials.py)已经同时服务模型与工具，却固定返回模型密钥故障。工具的一些路径已有转换，stdio 和部分秘密读取路径仍直接使用该机制。

迁入 infrastructure/credentials.py，负责加密、解密和主密钥文件，返回中性内部故障。model_connections 与 tools 各自转换对外错误。保持旧密文、不同密钥文件和路径；本次不轮换密钥。

### 6.5 保留清楚的检索与运行契约，不增空框架

capabilities 推荐迁名 capability_catalog；只承诺“检索已登记的方法与工具服务”，对外 `/api/capabilities` 保留。当前只需维护两类条目的数据库查询，不建设统一 Capability 表或插件提供者平台。

现有准备/授权/发布回调、ExecutionStrategy 仍用于隔离后台调度与对话业务，可以保留。删除 CI 后，不再为两种工作类型增加 Work 基类、专业入口协议或错误注册平台。普通安全失败码继续维护，未知异常仍脱敏。

跨模块实际传递的员工配置、技能定义、普通输出文件结果逐步补类型；JSON 存储可保留。旧快照要验证格式和可恢复条件，不能因补类型或删 CI 就一律允许自动重放。

## 8. 普通员工对话的目标调用流程

### 8.1 保存员工配置

1. 公开操作接收可信 Actor、变更和预期修订，检查权限与创建者编辑权。
2. 在同一短事务中，由 skills 校验方法/参数、tools 校验工具定义与账号连接、model_connections 校验模型引用。
3. 保存员工及装配关系，全部成功再提交。引用或修订无效则整体回滚，不在事务中访问远端服务。

### 8.2 接受、运行与交付

1. 对话操作确认归属、同键请求、容量和空闲；同键重放先返回原接受结果。
2. 捕获固定员工配置，组合本次输入、历史、附件及全员规则。在同一接受事务保存输入、空助手消息、Run 和关联。
3. 后台领取后才解析固定模型修订、载入恢复资料、装配工具与沙箱。接受事务不创建远端环境或执行模型。
4. execution 管预算、状态、取消和恢复；agent_runtime 运行普通 Agent。每次真实动作开始前复查当前许可并记录预算。
5. 交付事务重读运行状态，处理取消优先与当前授权，一起保存正文、输出文件关联、运行终态和占用释放。
6. SSE 推送已提交结果，断线释放订阅；工具与沙箱在成功、失败、取消时都要释放，某一项释放失败也不跳过其他资源关闭。

接受、动作记录和交付分别拥有短事务，只在一次原子操作内共享 Session，不把请求 Session 长期交给后台。快照固定版本，当前授权控制能否继续，二者都保留。

### 10.2 行为与结构验收

- 四个专用端点不再挂载，旧 work/ci_repository 输入明确拒绝，新响应无专用 CI 字段。
- 空库到新 head、旧 head 升级、活跃/终态/混合历史、外键完整性和备份恢复通过；历史升级阶段测试按其范围保留。
- 固定试验技能及装配被精确清理，来源目录不自动重新导入；普通技能、员工、连接不被误删。
- 普通对话发送/同键重放/重试/停止、消息顺序和整体交付保持原语义；旧库普通请求升级后按原键重放仍成功。旧 CI 历史只能读取，不能重新执行，调用方也不显示可用重试操作。
- 权限、归属、修订冲突、删除引用和保存失败都测试拒绝与回滚；公开概要不加载秘密或管理正文。
- 工具调用、文件、沙箱、网页读取验证、SDK 存档与普通可恢复运行回归；恢复不清零已耗预算，不能自动重放不支持的操作。
- 按第 9 节核对实际修改范围，避免把内部格式或规则又复制到别的模块。文件更少和测试总数不是架构质量的替代指标。
- 按第 12 节核对管理操作与运行接口：普通成员能使用获准员工，但不能编辑技能或读取密钥；直接调用业务操作也不能绕过权限。替换 SDK 不改变消息归属、动作记账或发布规则。本轮不包含独立 worker 的实现与部署验收。

| [针对客户端的接入层只处理客户端差异](https://learn.microsoft.com/en-us/azure/architecture/patterns/backends-for-frontends) | HTTP 字段、Cookie、SSE 和页面组合可变化；业务权限与资源规则仍由业务模块负责 |

当前不采用统一 Capability 大表、强制每模块四层目录、远程化同库事务、通用插件/工作流和专业错误注册平台。不是禁止业务抽象，而是把抽象建立在仍然存在、需要长期维护的职责上；CI 试验撤回后，相应设计依据也撤回。

本轮实现已同步当前架构、模块 README 和现行契约。迁移升级与真实部署分开：代码交付不表示开发或部署数据已升级；实际检查与限制由[验收记录](../records/backend-module-boundaries.md)维护。

## 12. 传统业务后端与 Agent/Harness 是否拆分

### 12.1 判断：明确分工，共用业务模块，暂不拆成两个服务

这里有三个不同决定，不能用一个“拆分”概括：

| 决定                           | 当前建议                                          | 解决的问题                                                                           |
| ------------------------------ | ------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 职责和调用接口是否分开         | 需要，补强已有分工                                | 业务模块决定哪些操作合法；执行宿主管排队、预算和恢复；Agent 运行层处理模型与工具循环 |
| 是否按 C 端 / Agent 建两棵目录 | 不建议；沿用第 7 节的完整目标结构                 | 技能、账号和权限各有唯一维护位置，避免修改一条规则要同步两份实现                     |
| 是否独立进程、服务和数据库     | 当前继续同进程同库；有明确收益时先评估单独 worker | 独立进程解决部署和故障隔离；独立服务还要承担通信、数据所有权和失败恢复成本           |

“保留模块化单体”的意思是同一个后端里有清楚的业务模块和执行模块，并非把所有事情写在一个 service。模块边界和部署边界可以分别演进。

当前没有采集 API 延迟、队列等待、执行资源占用或数据库写锁等待，因此不能声称现部署已经满足任意负载，也没有证据要求立刻拆服务。本轮优先修正已经确认的职责问题；下面列出什么变化值得重新判断部署。

### 12.2 为什么 CRUD 和权限不能整体叫“服务于 C 端”

用户在页面上编辑员工，是一种入口。员工的修订规则、可选技能、工具许可和账号归属，是平台的业务规则。将来增加业务 CLI、定时任务或模型工具时，这些规则仍应生效，不应再复制一份“Agent 版本”。

以模型连接为例，同一条连接有两种不同的使用方式：

1. 管理员创建连接、修改模型和 Key、启停连接，得到不含秘密的管理结果。
2. 后台运行根据本轮固定的连接 ID、配置修订和凭证修订，检查当前状态，再为可信模型客户端解析配置。

它们共用同一连接和修订规则，但第二种操作不等于“以管理员身份查看连接详情”。实际代码已有这种区别：[管理响应与运行解析](../../backend/app/model_connections/service.py)、[后台准备](../../backend/app/conversations/preparation.py)。

另一个真实例子是技能：当前普通成员没有技能或模型连接的管理权限，却可以使用员工已经装配的方法和模型，见[角色权限](../../backend/app/auth/permissions.py)。因此既不能让运行调用者获得管理权限，也不能因为收紧管理入口，就误阻断正常执行。

应拆开的是“维护资源”和“按许可使用资源”的操作。二者围绕同一业务对象，由同一模块维护，权限、输入、返回内容和调用时机各自明确。

### 12.3 本项目里的 Harness 具体包括什么

这里把 Harness 理解为：**让模型在限定权限、预算和环境中反复调用工具，并让这次工作能够被观察、停止和恢复的执行机制。** 各框架对这个词覆盖的范围不同，因此设计以明确职责为准，不要求新增一个 harness 目录。

本项目将这些机制分为两部分：

- **execution 负责可靠执行。** 接受容量、领取运行、开始动作前复核授权和扣预算、记录过程、处理取消和期限、判断能否恢复。它不解释 LangChain 消息，也不决定某条正文属于谁。
- **agent_runtime 负责模型与工具循环。** 准备本轮模型输入、加载获准方法、解释 SDK 输出与工具请求、管理 SDK 恢复状态，再通过受控接口请求执行动作。它不直接修改员工权限、工具账号或业务数据库。

其他模块仍提供自己拥有的能力：tools 负责真实连接和调用，files 负责持久字节，sandboxes 负责临时环境，conversations 负责输入、正式正文与回复交付。Harness 使用这些能力，不因此取得这些资源的所有权。

Anthropic 的[运行架构说明](https://www.anthropic.com/research/managed-agents)也区分模型循环、持久记录和执行环境，并说明它们可以分别替换。这里采用这种分工原则，不照搬其云平台部署方案。[Agent 构建建议](https://www.anthropic.com/research/building-effective-agents)强调从简单、可组合的实现开始，也不能被理解成所有项目都需要额外建设一层通用框架。

还有一个容易混淆的名称：**agents 是“员工配置与装配”，agent_runtime 是“实际运行 Agent”。** 前者保存岗位指令、模型选择、技能关系和工具许可；后者执行本轮工作。两者有不同变化原因，应继续分开。中文说明先把含义写清，不因为同时带 agent 就合并或整体迁入一个运行包。

### 12.4 各类操作如何协作，哪些地方需要隔开

| 业务所有者        | 用户维护或业务操作                                  | 运行时消费的能力                           | 必须维持的边界                                         |
| ----------------- | --------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------ |
| auth              | 登录、退出、会话与身份管理                          | 根据已保存的发起身份复核当前会话和权限     | 模型不能自行选择 Actor；不向 worker 发永久管理员身份   |
| agents            | 编辑员工、选择模型/方法、授予工具操作、绑定本人账号 | 捕获员工配置并复核当前装配是否仍有效       | 使用员工不等于能修改员工；换个人账号不扩大员工许可     |
| skills            | 编辑、导入、同步和导出方法                          | 读取本轮获准的固定定义与支持文件           | 包格式只解释一次；不把宿主可编辑来源目录暴露给模型     |
| tools             | 保存账号凭据、发现并确认工具清单                    | 使用当前用户实际获准的账号调用指定操作     | 调用工具不等于能改 Token、批准新工具或扩大范围         |
| model_connections | 创建/编辑、启停和连通检查                           | 按固定修订解析可信模型客户端所需参数       | 管理结果不含秘密；旧运行不能无声改用新凭据             |
| files、sandboxes  | 授权上传/下载、环境就绪与运维核对                   | 读取获准附件、保存成果、申请和释放本轮环境 | 永久成果与临时环境分开；环境管理凭据不进入模型工作负载 |
| conversations     | 发送、重试、停止、读取历史                          | 提供本轮输入，校验并提交最终正文与文件关联 | SDK 完成只产生候选结果，正式交付由业务事务决定         |

这不是要求每个模块再建 management/runtime 两个目录，也不是要求所有模块都有 service.py。小模块可以只有函数；tools 已有账号、清单和调用三种实际变化原因，才按第 6.3 节拆文件。接口需要说清“可以做什么”，无须套统一 CRUD 基类或新增 BackendService 总代理。

一次普通对话的协作顺序是：

1. API 解析用户请求及会话，调用 conversations 接受操作。
2. 对话流程从业务模块取得员工、技能、模型及工具许可，保存输入、待交付消息和 Run；这些记录在同一事务内接受。
3. execution 领取 Run，后台准备可信运行配置和本轮资源。agent_runtime 获得普通输入、RuntimeControl 和受限资源操作，不获得整个 app.state 或管理服务集合。
4. 模型提出工具请求；宿主在开始前复核当前权限、检查预算并记录动作，然后由资源模块执行真实调用。冻结快照决定本轮依据，当前检查决定现在是否还能执行。
5. agent_runtime 返回候选结果，对话发布流程将正文、成果关联和 Run 终态一起提交。API 的 SSE 读取已保存过程，断开浏览器连接不代表取消工作。

现有 [AgentRequest / RuntimeControl](../../backend/app/agent_runtime/contracts.py)、[RuntimeResources](../../backend/app/agent_runtime/resources.py)和[依赖约束测试](../../backend/tests/test_runtime_boundaries.py)已经体现了这种分工。这里是受信后端 Python 代码的职责边界，**不是恶意代码的安全沙箱，也不是已经实现的远程执行协议。**

身份、权限、秘密还需分清：

- 用户身份决定这次工作代表谁；员工是配置，不是登录账号；外部工具使用哪条账号连接，另由员工许可与本人绑定决定。
- 获准使用某个模型工具，是额外的限制，不能替代该业务操作自身的权限和归属检查。若将来开放“修改员工”等模型工具，应以可信的委托身份调用同一业务操作；模型提议的 user_id 或“我已授权”不产生权限。
- 可信模型接入代码确实需要持有模型 Key，当前 LLMConfig 也包含它。应禁止秘密进入模型消息、对外响应、日志和沙箱工作负载，不能不准确地宣称“运行后端完全不接触密钥”。

改造后的模型可调用的是受控工作区/代码执行及员工获准的 MCP 操作，**没有员工、技能、工具账号的产品管理工具**。业务 CLI、定时机器任务、通过模型维护平台配置均是未来场景；现有 auth/sandboxes 本机运维命令不在此列。不能把扩展设想写成已交付能力。

### 12.6 什么情况下值得进一步拆进程或服务

以下情况值得评估独立的执行进程（worker，专门领取和运行后台工作的进程）：

1. 发布或重启 HTTP 服务时，要求正在运行的工作继续执行。
2. SDK、MCP 会话或执行侧资源占用经观测影响了登录、配置、查询等 API 的可用性。
3. 执行并发与 HTTP 请求量有不同扩容需求，或确有不同部署权限和网络访问要求。

第 1 项是可以明确提出的运维目标，不必等到性能压测失败才成立；第 2、3 项应结合延迟、队列、内存和故障记录判断。独立进程也不自动等于独立服务、数据库或多主机。

最小演进可以是**同仓、同库、两个正式启动入口、一个 worker**：web 负责登录、管理、接受操作和读取结果；worker 负责领取、调用现有准备/授权/发布能力、运行 SDK 和清理资源。二者使用同一套业务模块，不在进程间传 SQLAlchemy Session；接受和交付仍各自在同库短事务完成。

但当前不能仅把 execute_agent 放进新进程就宣布拆分完成。至少要补齐：

| 实际问题                                              | 独立 worker 前要完成什么                                                                            |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 服务创建与关闭在 FastAPI lifespan 内                  | 抽出不依赖 HTTP 的装配，定义 web/worker 各自拥有和关闭的资源                                        |
| ExecutionStatus 是当前进程中的对象，/ready 直接读取它 | 定义 web 如何观察 worker 是否可用、失联多久拒绝新任务，以及是否允许有界排队                         |
| Runner 使用本机文件锁，启动恢复会处理全部活动 Run     | 第一阶段仍只启动一个 worker，由它负责恢复；多个 worker 需另设运行所有权及失联恢复，不能只靠原子领取 |
| 运行依赖本地文件、技能、checkpoint 和主密钥路径       | 明确共同配置与可访问路径；跨主机另设计文件和凭证访问，不假定本地路径天然可共享                      |
| 文件清理、沙箱回收、MCP 关闭有各自生命周期            | 指定维护工作唯一负责人，避免两个进程重复回收或遗漏活动资源                                          |

当前 RuntimeConfig.enabled 是测试注入开关，并非已交付的生产 web-only 部署模式。现有实现见[应用装配](../../backend/app/bootstrap.py)、[调度与文件锁](../../backend/app/execution/scheduler.py)、[运行配置](../../backend/app/execution/config.py)。

拆 worker 后必须验证：web 重启不打断执行；worker 重启不重复执行不可重放动作；会话撤销和取消能生效；已耗预算不重置；结果只交付一次；SSE 能看到新提交；worker 不可用时新请求有明确结果；资源能回收。这些是未来拆进程的验收，本轮不声称已实现。

独立服务适用于更进一步的跨主机、独立权限部署或团队发布需求。若再拆数据库，当前 Message、Run 和文件关联的同库原子交付就不再成立，需要单独设计可靠结果传递、去重、失败补偿和历史读取。其收益必须足以承担这些成本，不能以“Agent 技术栈不同”代替论证。

因此本轮实施范围仍是第 10 节：移除 CI，修正业务所有权、权限入口和执行契约；将独立 worker 留作有明确部署目标时的后续增量。最终目标是**业务规则稳定、执行方式可替换、入口可以扩展**，无需为新增一个调用方重排全部模块。
