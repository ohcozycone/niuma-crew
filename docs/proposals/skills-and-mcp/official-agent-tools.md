## 1. 这次要做成什么

让现有员工真正能够使用工具、获取互联网资料、处理工作文件，并在隔离环境里运行代码。继续使用当前对话、Agent 循环和执行宿主，不为每一种能力新增一套业务流程。

可以用下面五句话理解本轮工作：

| 基础能力       | 解决的问题                               | 一个具体例子                                 |
| -------------- | ---------------------------------------- | -------------------------------------------- |
| 通用工具接入   | 让不同来源的工具都能被员工获准使用       | 配置一个 MCP 服务，选择其中的搜索工具给员工  |
| 搜索与网页     | 获取当前资料，读取指定网页正文           | 找到官方说明，再打开页面核实内容             |
| 文件           | 让员工读取输入、保存中间文件、交付结果   | 上传 CSV，最后下载处理后的 CSV               |
| Sandbox / 沙箱 | 给程序提供一个与应用服务器隔离的运行环境 | 创建本次工作专用的环境，放入文件，结束后回收 |
| 代码执行       | 让 Agent 在沙箱里运行命令并取得结果      | 执行 Python 脚本，返回日志、退出码和输出文件 |

这里的关键区别是：Sandbox 管“在哪里运行、能访问什么、怎样停止和清理”；代码执行工具管“运行哪条命令、拿到什么结果”。二者都需要建设，不能只实现一个运行命令的函数。

能力以后怎样组合、提供哪些业务、是否需要工作流编辑器、动态表单或专门报告，留待后续讨论。本轮只做工具连接、授权、文件上传下载和执行观察所必需的管理操作，不把这些后续产品形态作为前置。

## 2. 实施前的基线与缺口

| 部分         | 已确认的当前状态                                        | 本轮怎么处理                                             |
| ------------ | ------------------------------------------------------- | -------------------------------------------------------- |
| 模型与 Agent | 已用 LangChain `create_agent` 运行普通聊天              | 继续复用，加入本轮获准工具                               |
| 工作方法     | 已通过 Deep Agents 读取本轮装配的技能正文               | 保留原有技能激活规则，扩展时不让普通文件读取冒充技能激活 |
| 执行宿主     | 已有队列、Run、动作记录、取消、超时和 SQLite checkpoint | 扩展到一般工具和沙箱，不重写调度系统                     |
| GitHub MCP   | 已有 CI 专用固定客户端和三项受限操作                    | 可用于对照验证；它还不能代表通用 MCP 已接入              |
| 工作文件     | 普通 Agent 只开放技能目录的 `read_file`                 | 增加受控输入、工作区、来源文本和输出文件                 |
| 联网工具     | 普通 Agent 尚无通用搜索或网页读取工具                   | 接一套真实服务，先验证搜索与正文提取                     |
| 沙箱与命令   | 尚无通用沙箱生命周期和隔离执行入口                      | 先接一个沙箱后端，再开放 `execute`                       |

当前依赖为 `langchain==1.4.7`、`deepagents==0.7.30`；OpenSandbox 服务与后端适配仍需显式安装、锁定兼容版本并验证，包或接口存在不表示平台已经提供运行能力。

## 3. 哪些由平台提供，哪些接外部服务

| 能力         | 建议方式     | 优先复用的实现                                | 平台仍需补什么                             |
| ------------ | ------------ | --------------------------------------------- | ------------------------------------------ |
| 通用外部工具 | MCP 接入     | LangChain `MCPAdapter`                        | 连接配置、目录审核、员工许可、调用记录     |
| 搜索         | 接外部工具   | Tavily 官方 MCP 的 `tavily_search`            | 凭证、参数限制、来源记录、失败处理         |
| 网页正文     | 接外部工具   | 同一 MCP 的 `tavily_extract`                  | URL 范围、体积限制、逐页结果与来源保存     |
| 文件操作     | 平台原生工具 | Deep Agents `FilesystemMiddleware`            | 路径与归属控制、输入输出保存、下载         |
| 沙箱管理     | 平台内部能力 | OpenSandbox＋Docker＋gVisor，配套沙箱后端适配 | 创建、配额、文件传输、停止、回收和启动清理 |
| 代码执行     | 平台原生工具 | Deep Agents 的 `execute`                      | 绑定沙箱、授权、时限、结果和取消处理       |

“平台原生”表示由平台预置并维护，并不要求重新编写底层实现。即使沙箱实际由外部服务提供，平台仍应负责它的创建与清理，Agent 主要通过文件工具和 `execute` 使用它。

官方依据：[LangChain MCP 接入](https://docs.langchain.com/oss/python/langchain/mcp)、[Tavily MCP 工具](https://docs.tavily.com/documentation/mcp)、[Deep Agents 沙箱接入](https://docs.langchain.com/oss/python/deepagents/sandboxes)。

## 4. 通用工具接入：先把工具真正接进来

### 4.1 最少需要什么

1. **登记工具来源**：原生工具由受信后端代码提供，外部工具由一个配置好的 MCP 连接提供。
2. **读取工具目录**：取得名称、用途和参数要求；新发现的工具先作为候选，不自动授予员工。
3. **配置员工许可**：明确员工能使用哪几个工具、哪个连接和什么资源范围；使用工具不要求先创建一个空 Skill。
4. **交给模型选择**：每轮只把当前获准工具的说明和参数交给模型，模型提出调用请求。
5. **由平台执行**：先检查许可和预算、保存开始动作，再调用原生实现或 MCP；结果保存后交回模型。
6. **记录真实结果**：页面能够看到实际调用、成功或失败、耗时和必要来源；模型说“已搜索”不算已经执行。

首批只接远程 Streamable HTTP MCP，以及实际选定服务所需的认证方式。OAuth、stdio 子进程和其他认证按需要另加，不能因为客户端支持就默认全部开放。Tavily 文档给出 OAuth 和 API Key 认证路径；应以实际部署验证过的路径启用，秘密经宿主注入，不放进公开地址、目录和日志。

LangChain 当前 MCP 适配需启用 `langchain[mcp]`，且相关命名空间处于 beta。实施时在现有版本上锁定并验证依赖；复用官方客户端处理协议，不复制 CI 专用 JSON-RPC 客户端再声称是通用能力。[官方说明](https://docs.langchain.com/oss/python/langchain/mcp)

### 4.2 共用的配置和调用规则

连接保存地址、认证、配置与凭证修订，以及获准工具目录。员工许可保存明确的操作、范围与预算。继续沿用已有的 `tool_connections`、`agent_tool_grants` 字段草案，不再为每个服务建立一套配置模型。

接受一次工作时，固定工具、连接和许可的非秘密依据；真正调用前再检查当前许可。停用、撤权或凭证修订变化后，旧 Run 不能继续使用新身份调用。MCP 的目录变更检查和审核沿用[既有设计](README.md#7-通用-mcp-与权限的真实边界)。

不同连接的同名工具必须通过稳定标识消歧；`read_file` 等平台文件工具名保留。工具自身的输入输出定义尽量沿用现成格式，平台只补授权、执行和记录，不另造一套函数调用协议。

连接“保存成功”“连通验证成功”“已经授权给员工”分别表达，不能互相代替。

### 4.3 第一项验收

同一个普通 Agent 能调用一个原生工具和一个远程 MCP 工具；禁用其中一个许可后，只阻止相应调用。再增加一个兼容 MCP 连接时，只增加连接和许可，不修改 Agent 主循环。

## 5. 搜索与网页：查得到，也能读原文

### 5.1 搜索怎么接

优先验证 Tavily 官方 MCP 的 `tavily_search`。搜索返回标题、URL 和摘要，平台保存查询依据、取得时间和来源；默认不要求服务生成最终答案，也不把搜索摘要当已读全文。

模型可以按任务选择是否搜索。用户明确要求检索时，需要有实际成功的调用才能声称查过；失败就说明未能取得资料。指定 URL 的任务通常直接读取网页，不强迫先搜索一遍。

调用次数、结果条数、深度和可用域名范围由宿主限制；模型参数不能放宽这些限制。秘密按当前连接实例注入，不能通过修改进程级环境变量给不同员工切换账号。

### 5.2 网页怎么接

同一连接的 `tavily_extract` 负责按 URL 提取正文，搜索与读取分别授权。它不是浏览器，首批验收的是公开网页正文，不把登录、点击和表单提交也称为已经支持。

每个 URL 分别保存取得时间、来源和成功/失败状态。长正文存为只读来源材料，模型先收到摘要及路径，需要时通过 `read_file` 分段读取。返回长度和整轮上下文分别受限，不把所有页面全文一次送给模型。

此路径只用于适合交给第三方处理的公开 URL；平台校验协议、认证信息和范围，但不能声称控制了第三方抓取服务的最终 DNS 与重定向。内部网站和登录资料的读取需要另行接入受控网络路径。

### 5.3 如果 MCP 不满足要求

在验证发现认证、结果限制或部署条件不合适时，可以改用 `langchain-tavily` 已封装的 `TavilySearch`、`TavilyExtract`，仍经过同一工具入口。这里所谓调用第三方库，只是连接实现的备选，不是另一种产品能力。首版选择一条通过验收的路径即可。

搜索与提取的服务能力见 [Tavily MCP 文档](https://docs.tavily.com/documentation/mcp)；直接库集成分别见 [Search](https://docs.langchain.com/oss/python/integrations/tools/tavily_search)、[Extract](https://docs.langchain.com/oss/python/integrations/tools/tavily_extract)。

### 5.4 怎么验收

给定一个小型研究问题，员工实际搜索、读取选定页面，再给出带来源的回答。能够区分未读全文、部分页面失败和全部失败；刷新后来源仍可查阅，失败不能显示为已核实。

## 6. 文件：输入、中间过程和交付结果

### 6.1 工具与目录

复用 Deep Agents 的 `ls`、`read_file`、`glob`、`grep`、`write_file`、`edit_file`，需要删除时再明确开放 `delete`。仅实例化一套文件工具，按路径区分不同文件，不另外创造一个同名技能读取工具。

| 目录          | 放什么                             | 访问规则                                   |
| ------------- | ---------------------------------- | ------------------------------------------ |
| `/skills/`    | 本轮冻结的技能内容                 | 只读；成功读取完整正文后才记录相应技能激活 |
| `/sources/`   | 本轮实际取得的网页、搜索等来源文本 | 只读，保留来源、取得时间和截断情况         |
| `/inputs/`    | 用户明确上传或选择的资料           | 只读，不自动带入其他会话内容               |
| `/workspace/` | 本次工作的脚本与中间文件           | 按员工许可读写                             |
| `/outputs/`   | 计划交付给用户的文件               | 按许可写入，正式保存并发布后才能下载       |

`glob` 找文件名或路径，`grep` 搜文件正文；它们都不是互联网搜索。平台对路径、枚举、检索和写入统一检查，目录名称本身不提供安全保证。

### 6.2 文件放在哪里

只需要小型文本文件时，可以先复用现有 `StateBackend`，文件随本 Run 的 checkpoint 保存。这是虚拟文件，不是服务器任意目录。

需要代码执行时，从本次工作开始就选定沙箱文件后端。文件工具和命令必须访问同一份 `/inputs/`、`/workspace/`、`/outputs/`，避免“文件写在一个地方，程序到另一个地方找”。只读的技能和来源可单独路由；若代码需要处理来源文本，先通过获准文件工具读取，再显式写入沙箱工作区；不假定虚拟来源路径在 Shell 中存在。

当前 checkpoint 的作用域是 Run ID，不会自动跨轮共享工作文件。下次需要旧文件时，显式选择已保存的文件 ID，重新检查归属后装入；不能默认暴露上次沙箱或全部历史附件。[后端说明](https://docs.langchain.com/oss/python/deepagents/backends)

### 6.3 上传、保存和下载

上传后先保存不可变输入及文件 ID；接受工作时固定所选文件、哈希和归属。员工生成的结果先保存字节和元数据，再在现有发布事务中关联回复。下载按用户和会话权限检查，不返回宿主路径或沙箱内部地址。

工作目录是临时过程，下载产物是持久结果，两者分开管理。沙箱回收后，已正式发布的文件仍可下载。取消、失败或尚未完成发布的临时文件不作为成功交付；孤立文件按保留策略清理。

首批用 CSV、JSON 和 UTF-8 文本验证闭环；大文件由沙箱程序处理，只把必要片段和摘要交给模型。复杂文档格式按实际需要增加处理库，不将文件读写等同于已支持所有文档编辑。

### 6.4 怎么验收

上传小型 CSV，读取内容并生成一个新文件；刷新后能下载，文件哈希一致。另一个无权会话不能读取它，目录越界和修改技能文件均被拒绝。

## 7. Sandbox：提供可管理的隔离环境

### 7.1 平台要负责什么

1. **创建**：需要运行代码的 Run 使用独占沙箱；仅搜索或网页读取不因此创建沙箱。
2. **准备**：放入获准输入，选择运行镜像，设置资源、网络和时限。镜像先包含 Python、Node 和选定常用库。
3. **使用**：通过同一文件后端读写，通过 `execute` 执行命令。沙箱管理凭证只在宿主使用，不交给 Agent。
4. **取回**：执行结束前保存允许交付的文件和必要日志，核对大小、类型及内容摘要。
5. **停止与清理**：停止 Run 时终止工作负载；完成后销毁沙箱，记录清理结果。
6. **异常补偿**：创建和清理有持久引用、期限及状态；重启扫描遗留沙箱，配合供应商 TTL 清理，不能只依靠正常退出时的 finally。

沙箱应只接触本次获准文件，不挂载应用数据库、主密钥、宿主目录或 Docker socket。输入只读、可写工作区、资源上限和进程隔离由实际后端保证。工具参数检查约束不了任意 Shell，所以沙箱网络范围和文件挂载需要独立验证。

### 7.2 已选定的自托管方案

采用 **OpenSandbox＋Docker＋gVisor（runsc）**，目标是现有腾讯云 Linux 云服务器或轻量应用服务器，首版单机部署。这里不要求 Kubernetes 或第三方托管沙箱账号；自托管仍消耗自己的计算、磁盘和流量，模型与搜索费用另计。现有机器是否足够需要实测。

| 组成           | 通俗理解             | 负责什么                                                                   |
| -------------- | -------------------- | -------------------------------------------------------------------------- |
| OpenSandbox    | 沙箱管理服务         | 提供创建、查状态、执行、文件传输和销毁等 API                               |
| Docker         | 工作环境的容器载体   | 启动镜像、组织容器和资源                                                   |
| gVisor / runsc | 加强隔离的运行时     | 在 Linux 上增加用户态内核隔离，不把普通 Docker 默认运行当成已经开启 gVisor |
| 平台后端适配   | 员工与沙箱之间的接线 | 把现有文件工具和 execute 接到同一沙箱，并处理授权、预算、结果及回收        |

OpenSandbox 官方示例收录了 `langchain-sandbox-opensandbox` 第三方适配包，可优先验证其与本项目 Deep Agents 版本的兼容性。它不是 LangChain 内置后端；不足之处由平台补薄适配，不要求开源使用者重新编写整套接线。[官方示例](https://open-sandbox.ai/examples/deep-agents)

部署时显式选择 gVisor 并确认实际容器 runtime 是 runsc。缺少运行时或隔离验收失败时，代码能力显示未就绪，不能悄悄换成普通容器或宿主 Shell。服务管理端点与文件/命令端点只向受信后端开放，gVisor 也不能代替凭证、文件和网络访问控制。[运行时配置](https://open-sandbox.ai/guides/secure-container)

默认执行配置用于离线计算；需要联网时由部署者配置并验证明确的出口范围，管理连接和程序出口分别检查。CPU、内存、进程、磁盘、并发与 TTL 也要在实际后端验证；单机先从一个沙箱开始测试，保留应用本身的资源，不能把 Docker 默认行为当成所有限额均已生效。

已采纳的版本、配置片段、异步适配、创建结果未知、清理补偿和隔离验收细节保存在[自托管接入附录](opensandbox-self-hosted.md)。它是本主方案的实施约束，不另外改变当前基础能力范围。

### 7.3 怎么验收

两个 Run 看不到对方文件；沙箱不能访问应用秘密或超出获准范围。主动停止后程序不再运行，结束后能回收。模拟主进程崩溃和删除失败，能够发现并清理遗留资源，已保存产物不受清理影响。

### 7.4 开源后谁负责什么

| 谁负责           | 需要交付或配置什么                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------ |
| 平台开源代码     | 内置工具/MCP 接入、OpenSandbox 适配、授权和预算、文件与产物、停止/清理/重启核对、配置和部署样例  |
| 部署维护者       | 部署 Docker、gVisor 和 OpenSandbox，配置地址/API Key、镜像、网络、主机资源及额度，维护存储和监控 |
| 员工与技能配置者 | 选择已支持工具和执行配置，提供业务方法、参数及工作资料；不能突破部署和授权上限                   |

使用者主要配置环境与业务，不应自行补写基础适配、取消或回收机制。更详细的责任划分见[开源交付附录](opensandbox-self-hosted.md#开源交付平台与使用者的分工)。

## 8. 代码执行：让 Agent 在沙箱里做计算

### 8.1 如何调用

Agent 使用 Deep Agents 的 `execute` 提出命令，平台先检查执行许可、剩余预算、沙箱状态和时限，再发给沙箱。它不是让模型直接在应用服务器执行命令。

例如 Agent 写入一个分析脚本，然后运行 Python 统计 CSV。工具返回退出码、有界标准输出/错误输出，以及必要文件引用；平台据此判断执行动作的实际结果。退出码为零只说明命令成功退出，最终文件是否存在、结构是否符合要求还需要检查。

### 8.2 错误和取消

普通命令错误可以在剩余预算内交回模型，让它修正后再尝试；每次尝试都计数。必要计算一直失败时，最终回答应说明失败，不能宣称已生成产物。

超时和取消必须传播到工作负载。关闭 Python 客户端只表示连接关闭，不代表远端程序已经停止；需要实际的终止/销毁动作。远端已经执行但平台未拿到确定结果时记录 unknown，不能冒充没有发生。

首版采用沙箱工作区的 Run 在进程重启后收束为 interrupted，不恢复旧容器或自动重放命令；保留已经可靠保存的来源和结果，用户可以明确新发起。普通纯指引聊天和已保存只读结果的恢复继续按原契约处理。

### 8.3 怎么验收

脚本读取输入 CSV、生成统计文件，并且文件工具能读到同一内容。错误命令得到真实错误；超时会终止程序；重启不会重复运行不确定命令；“声称已生成、实际没有文件”不能作为成功交付。

## 9. 五类能力怎样一起工作

综合验收可以只使用一项小工作，不增加专用业务流程：

> 上传一份测试结果 CSV，统计失败类型，查询其中一个错误码的官方说明，生成统计文件和带来源的解释。

1. 用户上传 CSV，平台取得输入文件 ID。
2. 接受 Run，固定本轮输入、获准工具、连接修订和预算。
3. Agent 通过搜索找到候选说明，再读取选定网页，平台保存来源。
4. 需要代码处理时，在本轮沙箱准备选定输入；文件工具与命令共用工作文件。
5. Agent 写入分析脚本并调用 execute，取得真实输出和统计文件。
6. 平台确认产物存在、保存文件及来源，完成最终权限和取消检查。
7. 回复正文、文件关联和 Run 终态按现有发布边界提交。
8. 用户读取解释、展开真实工具步骤、下载文件；沙箱回收后文件仍能下载。

这是基础能力的联合验收，不是现在就确定要提供“测试分析工作流”产品。无需新建该场景的路由、表单或报告专用组件。

## 10. 实施顺序

| 阶段             | 本阶段做什么                                             | 用户或开发者能观察到的结果                            |
| ---------------- | -------------------------------------------------------- | ----------------------------------------------------- |
| T0：工具共同入口 | 原生/MCP 接入、明确许可、调用前授权与预算、结果记录      | 同一 Agent 调用两种来源工具；禁用许可立即阻止后续操作 |
| T1：搜索与网页   | 接通一套搜索/提取服务，保存来源并支持分段读取            | 实际搜索、读原文、附来源；失败和截断清楚可见          |
| T2：工作文件     | 受控读写、上传、结果持久保存和下载                       | 能处理小文件，刷新后结果仍可下载，跨会话访问被拒绝    |
| T3：沙箱管理     | 接一个后端，完成创建、输入输出传输、停止、清理及异常补偿 | 能证明隔离、资源和网络范围，能收回遗留环境            |
| T4：代码执行     | 将 execute 与文件、沙箱和 Run 记录接通                   | Agent 实际运行脚本，产物可取回，取消和重启行为明确    |

T0 应和 T1 的一个真实工具接线一起验证，避免只做空注册框架。T1 中读取已取得来源复用 read_file，不等待完整附件功能。T3/T4 技术试验可以连续完成，但验收分别检查“环境可管理”和“Agent 能正确执行”。

现有 CI 保持可用，可作为 GitHub 工具、证据和权限的对照；本轮不要求先删除 CI 专用循环，也不以 CI 迁移、Task/Goal 或工作流编辑器作为前置。

## 11. 初始限制和失败时的表现

以下是建议的首轮实验参数，需用目标服务和模型验证后固定到运行快照，不是已生效配置。

| 项目             | 建议起点                                                     | 达到限制后怎么处理                         |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------ |
| 工具总调用       | 每 Run 32 次，包含实际技能文件工具读取；预加载只用原技能预算 | 拒绝继续调用，说明未完成范围               |
| 搜索 / 网页提取  | 各最多 5 次；提取每次最多 3 个 URL                           | 返回已取得结果和明确的覆盖限制             |
| 搜索 / 提取时限  | 单次 20 / 30 秒，且不超过 Run 剩余时间                       | 记录超时；只有有界只读重试可以重新申请预算 |
| 给模型的工具内容 | 单次最多 24 KiB，仍受整轮上下文约束                          | 保存完整的有界来源或标记截断，按窗口读取   |
| 虚拟文本文件     | 单文件 128 KiB，总量 512 KiB                                 | 大资料改走文件存储/沙箱，不塞满 checkpoint |
| 上传和正式产物   | 首批单文件 10 MiB；全工作总量单独限额                        | 上传或收集前拒绝，不能静默裁剪数据文件     |
| 执行命令         | 单次最多 60 秒，且不超过 Run 剩余时间                        | 终止工作负载；拿不到确定结果则记录 unknown |
| 沙箱资源         | 每 Run 独占；CPU、内存、磁盘、TTL 按目标后端实测配置         | 达到上限终止或拒绝，不能拖垮应用服务       |

当前 Run 总时限为 180 秒、模型上限 8 次；先用这个基线做短任务。需要增加代码任务预算时显式配置并在接受时固定，不在中途无限续时。SDK 隐藏重试要关闭或收紧，避免真实外部尝试绕过账面预算；未确认的费用或用量保持未知。

结果大小上限需要覆盖接收过程，不只是返回模型前截断。官方客户端若只能解析后限制内容，应在客户端/代理层补相应限制，不能声称控制了进程接收峰值。

## 12. 实际工程改动与验证

### 12.1 按现有职责补齐

模块所有权、依赖方向、跨边界契约、调用顺序、数据与资源生命周期统一见[架构边界与实施分工](foundation-boundaries.md)。本轮保留现有对话层、执行宿主和 Agent 循环，新增三个模块：`tools` 管工具连接，`files` 管持久文件，`sandboxes` 管临时环境；不新建一套工作流引擎。

| 位置                           | 本轮改动                                                           |
| ------------------------------ | ------------------------------------------------------------------ |
| 拟新增 tools 模块              | 连接、工具目录、MCP 调用、原生登记和秘密解析；复用既有字段草案     |
| agents、auth 与基础管理接口    | 员工独立工具许可、配置修订和明确权限；不按员工姓名或 Skill ID 授权 |
| conversations 的准备/授权/发布 | 固定工具及输入依据，复核当前许可，关联文件与最终正文               |
| agent_runtime                  | 装配工具，分开技能读取与普通工具处理；SDK 对象不进入业务执行核心   |
| execution 与 RuntimeControl    | 原子申请工具动作、持久预算、结果引用、恢复分类；保留现有队列和终态 |
| 拟新增 files 模块              | 不可变字节与元数据、暂存和受控读取；消息关联仍由对话层保存         |
| 拟新增 sandboxes 模块          | 资源申请、远端身份、配额、期限与清理；不接管 Run 调度              |
| bootstrap 与配置               | 注入客户端和生命周期，关闭连接、启动清理；声明依赖并更新 uv.lock   |
| 前端已有管理/对话区域          | 必需的连接授权、文件上传下载和实际步骤；不建设业务工作流编辑器     |

当前特别要改的地方：技能中间件拒绝所有非技能读取请求；RunStore 只有 read_file 恢复特例；RuntimeControl 尚无完整工具结果引用写入口。先完成这些共同边界，再接具体工具，不能只向 create_agent 添加几个函数。

文件使用 CompositeBackend 时，沙箱必须是支持执行的 default 后端；只挂到某条路径下不能保证 execute 在正确环境运行。还要同步适配路由前缀剥离和现有技能文件键格式。FilesystemMiddleware 的私有权限参数不作为平台契约，沙箱中的符号链接也需要真实路径检查。

新工具快照需版本化；升级时保留旧 v2 普通聊天的明确恢复路径，不能只修改版本常量导致旧活动 Run 意外中断。已保存只读工具结果的复用要匹配调用、参数、连接和来源，并重新授权；涉及 StateBackend 写入或采用沙箱工作区的新 Run 首版在进程重启后中断，不自动重放，详见[恢复分工](foundation-boundaries.md#6-取消失败和重启的分工)。

### 12.2 验证方式

1. 用真实 SQLite 和假上游验证并发预算、撤权、超时、取消、记录失败和重启；开始记录失败时不能发出工具调用。
2. 通过实际选定的官方客户端测试协议和响应边界，不只替换最外层服务；模型实际调用的动作与来源必须匹配。
3. 分别验证文件越界、跨会话归属、同名工具隔离、来源引用、输出缺失、沙箱残留与已发布产物保留。
4. 真实 Tavily 和沙箱各做一组有界冒烟，记录账号环境、依赖版本和真实结果；离线替身不能证明外部服务可用。
5. 涉及表结构使用正式迁移验证；生效规则回写 reference，实际功能验收进入 records。

本方案基于当前代码、已安装 SDK 源码和 2026-10-27 官方文档核对。外部账号、网络、沙箱文件传输/进程终止接口和具体资源限制仍需实测；本次平台接线与离线测试没有代替真实服务验收。
