该运行已经失败，不是仍在后台无限思考。模型在证据已经足够后继续检索，用完 8 次模型调用额度；宿主只有超限失败机制，没有预算耗尽前的回答收束机制，最终没有产生正文。搜索业务失败被记录为成功、提取结果呈现为相关片段等因素加重了过程的不确定性。

不能据此认定 Kimi 的一般能力不足，也不能认定换成 Codex 必然成功。本次没有进行同模型、同工具、同输入的在线 A/B 实验。

## 按优先级排列的发现

### 高：循环有成本上限，缺少预算内交付策略

[中间件装配](../../backend/app/agent_runtime/middleware.py)使用 `ModelCallLimitMiddleware(run_limit=..., exit_behavior="error")`；[宿主计数](../../backend/app/execution/store.py)另行持久校验。达到 8 次后，下一轮在模型调用前被拒绝。[运行适配](../../backend/app/agent_runtime/langchain.py)将 SDK 预算异常转成 `agent_budget_exceeded`。

这些机制正确地限制费用，却不保证交付。模型没有收到剩余调用数，也没有在最后允许的轮次切换到只生成正文的阶段。第 8 次返回了新的工具请求，工具完成后仍需要至少一次模型调用解释结果；这次调用已经没有预算。

模型在第 5～7 轮已有足够信息仍继续检索，是本次可确认的行为问题；缺少收束规则使它最终变成空回复。两者共同构成本案主因。置信度：0.99。

### 高：429 业务错误进入成功轨迹

第 2 次工具返回包含 `error="Search failed"` 和 `status=429`，但动作状态为 `succeeded`，SDK ToolMessage 也为 `success`。

[工具调用服务](../../backend/app/tools/invocation.py)依赖适配器的协议状态；[结果包装](../../backend/app/agent_runtime/tool_calls.py)只在存在来源且来源全部失败等条件下进一步改失败。该结果没有来源，因此正文中的已知 Tavily 错误未被转换。它没有直接导致预算异常，但损害了模型反馈和用户对“成功”的理解。置信度：1.00。

修复应保留 MCP 协议失败，并对已知供应商的结构化错误做窄范围映射；不能把任意网页正文出现的 `error` 字样一律当作调用失败。

### 中：多次提取得到相关片段，信息范围没有清楚呈现

5 次提取都带 `query`。冻结的工具 schema 明确说明，该参数会按相关性选取片段；实际返回存在 `[...]`，并非完整按原顺序排列的文档。模型围绕 Skill/MCP 多次改写问题，重复提取 README。

平台另外只提供前 3000 字符预览，返回的 `truncated` 表达平台预览是否读完，不能证明上游整篇网页完整。本案只有一次结果续读，不是分页死循环；即使这一份提取结果已读完，也不等于读完对应原网页。

最初结果混入社区 OpenCode 插件，而末轮检索又使用该插件的 `openspec_list`、`openspec_view` 名称。可能存在概念混淆或锚定，但这属于行为推断，不能当作已读到的内部思考。事实置信度：1.00；该行为解释置信度：0.75。

### 中：缺少可用于判断进展和慢点的指标

已有动作和 checkpoint 足以还原本次调用顺序，但未记录证据是否新增、剩余回答预算以及模型动作内部延迟细分。页面上的多条模型动作不等于多次有效推进。

原始系统提示词约 5,347 字节，7 个外部工具的描述及 schema 序列化约 16,871 字节，另有框架提示与技能目录。首轮输入为 6,873 token，存在固定开销；但没有达到上下文上限，不能把它升级为本案主因。技能正文虽存于快照，却未加载到本轮模型消息中，不能按快照体积推断模型读过全文。

## 已排除与仍未知的因素

- 没有历史污染证据：冻结上下文历史对话数为 0，输入快照只有当前问题。URL 中的嵌套 `from` 不在本次模型输入中。
- 没有技能反复加载：`skill_reads=0`，本次没有读取 agent-reach 主文。
- 不是网页全文验收卡住：原始问题没有 URL，[verify_web_reads](../../backend/app/agent_runtime/tool_results.py)的目标集合为空，直接返回。
- 不是 180 秒总超时、32 次工具额度或上下文溢出：终态及计数均不支持这些原因。
- 不是已生成答案被前端吞掉：业务库与 SDK 中都没有最终正文。保留工具轮不能替代正式答案，是正确的发布边界。
- 当前工厂默认 `max_retries=0`，本案轨迹未见额外模型修复或重写调用；不能据此证明远端供应商内部完全没有重试。
- 不能从一次运行推断哪个模型普遍更好；也没有证据表明第 9 轮一定会自然结束。

## 与当前 Codex 处理原问题的对照

本次在已定位官方仓库后，通过 GitHub 插件分别读取 [README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md) 与 [Supported Tools](https://github.com/Fission-AI/OpenSpec/blob/main/docs/supported-tools.md)。另一次 Jina 读取因本机 DNS 失败，未取得内容；没有将该失败当成证据。官方两个文件分别确认项目与 CLI 的定位、Skills/命令的交付方式，已足以作答。

合理回答是：OpenSpec 本体是规范驱动开发框架及 CLI；接入编码助手时生成 Skills 和／或命令，Codex 的官方集成是 Skills。官方标准接入不应简单归类为 MCP；第三方可以另做 MCP 封装。无需证明所有社区实现都不存在 MCP。

| 比较维度   | 本案 Agent 的已观察行为                                 | 当前 Codex 的本次对照做法                  |
| ---------- | ------------------------------------------------------- | ------------------------------------------ |
| 目标边界   | 连续追查多个 Skill/MCP 关键词，没有形成可交付的限定结论 | 区分项目本体、官方接入形式、第三方封装     |
| 证据选择   | 搜索混入插件和 fork；多次返回重排片段                   | 在已知官方仓库直接读取两个相关文件         |
| 何时停止   | 第 7 轮已获得支持工具表，仍请求更多资料                 | 官方资料足以回答分类问题即停止扩展         |
| 不确定性   | 没有形成说明剩余未知项的最终文字                        | 限定结论覆盖官方接入，不推断全部生态       |
| 能说明什么 | 一次 Kimi 加当前运行器的真实失败                        | 展示可行的取证与收束策略，不是模型能力跑分 |

Codex 本身也可以研究过度。本次根因诊断需要读取工程、数据库、checkpoint 和做离线验证，不能把这些审计调用混入原问题的两份官方文档核验，再比较总工具数。工具能力和模型不同，不能将直接文件读取的优势全部归功于模型。

OpenAI 的[官方 Agent 运行方式说明](https://developers.openai.com/api/docs/guides/agents)也区分托管 Codex harness、应用内 SDK 和直接模型 API。SDK 提供工具循环不代表已经提供适合每类任务的目标验收和预算内交付策略；本案项目使用 LangChain/Deep Agents，需要自行定义这部分契约。该文档不构成对当前桌面 Codex 隐藏实现的证明。

## 建议修复顺序与验收

1. **在硬预算内预留回答轮。** 按任务复杂度设置研究软预算；接近上限时把剩余次数和已取证摘要交给模型，最后允许的轮次禁用外部工具，要求只根据已有证据回答，并明确未知项。总调用不越过原硬上限。取消、撤权、存储失败仍必须停止，不能为了兜底回答继续执行；不得发布工具 JSON 冒充正文。
2. **修正工具业务状态。** 将本案 429 样本作为协议成功但业务失败的回归输入，分别记录协议状态、业务状态和公开错误类别，便于模型选择替代路径。重试受限，遵守上游等待建议。
3. **改善证据投递。** 已知官方项目优先读取相关官方页面；分别标注全文、检索片段、平台预览，以及来源与范围。不要通过读完包装 JSON 就宣称读过网页全文。长结果支持按相关章节定位，减少为浏览包装字段消耗模型轮次。
4. **加入与任务匹配的收束策略。** 简单概念题允许一份权威定义加一份接入说明完成；新增检索需要说明它会解决哪个影响答案的缺口。重复 URL、相近查询可提示边际收益降低，而非全局禁止再次读取同一 URL。无需为此新增一个无界的“监督模型”。
5. **补端到端评测。** 固定本案工具结果，比较现状、仅预留回答轮、改善工具结果、再换模型；测量最终答案正确性、交付率、模型／工具次数、延迟和 token。另覆盖证据不足、429、长页面、最后一轮仍请求工具、取消、撤权和存储失败。参数取舍由这些结果决定，不只盲目提高 `max_model_calls`。

其中“预留回答轮”是待实施建议，不是已经生效的行为；强制生成正文也不保证答案正确，必须与事实性和不确定性验收一并验证。
