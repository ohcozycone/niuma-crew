## 初案与评审方法

初案选择运维马，通过 GitHub 官方 MCP 读取一条失败运行及日志，交付诊断单并收集验收。候选比较包括项目知识问答、PR 审查、CSV 对账；比较结论是工程与工作边界的判断，不是市场调研或真实使用频率统计。

本次按「需要完成的工作 → 必要输入与操作 → 可验收输出 → 增量收益 → 最小代价」逐层追问。问题由设计者依据代码、官方资料和一个公开样本作答；没有用户访谈，也不把自问自答称为独立用户验证。`grilling` 的追问方法用于自审；依用户要求不执行该技能的中途等待确认流程。事实核查由只读子任务交叉检查。

## 第一轮：这个工作值得交给 Agent 吗

| 追问                                                  | 事实、推断或未知                                                                                     | 评审结论与设计动作                                                                  |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 用户究竟要买到什么结果？                              | 推断：CI 失败后尽快知道下一步查什么、改什么，少在 job、日志与配置间切换                              | 交付为失败定位、依据、建议操作、验证方法及未决问题；报告长度不作为完成标准          |
| 用户真的在用 GitHub Actions 吗？                      | 未知；仓库的产品源码不能证明使用频率                                                                 | 不声称是已验证的最高频需求；设计支持有限试用，不据此替换知识助手既有排期            |
| 为什么不是一段提示词就够了？                          | 事实：提示词无法读取真实运行、区分 attempt、证明引用位置；初案时技能尚未进入模型输入；现CI已快照注入 | 必须接通实际 MCP 调用、配置快照和来源记录；提示词只负责工作方法                     |
| 简单报错自己看不是更快吗？                            | 是。明显语法错误或单行报错可能没有委派收益                                                           | 价值目标是多 job、配置/环境混杂的失败；试用保留简单题测出负收益，不只挑复杂成功样例 |
| 给现有 ChatGPT 或 coding agent 一条链接是否已能完成？ | 有可能；用户现有工具与权限未知                                                                       | 基线采用用户当前最省事的方式，包括已有 AI；不拿纯手工复制作为唯一对手               |
| 如果同样模型和工具，平台还有什么增益？                | 待验证：重复使用已装配的仓库范围、版本化方法、证据与反馈可降低每次准备和复核成本                     | 这些成为试用测量对象；角色头像和「接入 MCP」本身不计价值                            |

## 第二轮：怎样算真正完成

| 追问                           | 判断                                                         | 对完整设计的约束                                                                           |
| ------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 没有自动修复，闭环是不是假的？ | 对「诊断并给出可执行下一步」是完整工作；对「恢复 CI」不是    | 入口写「诊断失败」，状态区分「诊断完成」与用户反馈；不显示「故障已解决」                   |
| Agent 说成功就算成功吗？       | 不算；当前普通聊天以有文本且正常结束判成功，不足以验收诊断   | 必须完成真实取证、结构与引用检查、报告持久化，用户验收另存；技术成功和内容接受分开         |
| 只复述日志错误是不是有用？     | 信息价值有限；更需要区分失败位置、候选原因与能验证它的下一步 | 每个诊断项有事实/假设、来源、建议、验证期望；不能把日志通用修复提示直接当正确建议          |
| 证据不足还能交付吗？           | 可以交付有边界的部分诊断，但不能伪造确定根因                 | 至少有一份实际失败日志才可形成诊断单；部分覆盖要列明漏项；全部日志不可读则失败并给恢复入口 |
| 要求修订后如何避免无限循环？   | 反馈不是模型指令优先级，也不能改变权限                       | 本轮只保存一次最小反馈；再调查须显式交办，不实现自动修订链                                 |
| 接受以后就证明修复建议正确吗？ | 不能                                                         | 接受表示诊断可用；修复是否成功只以实际新 CI 结果或人工验证为准，首版不自动获取修复结论     |

## 第三轮：这个 MCP 真能提供所需证据吗

2026-10-21 核查 GitHub 官方仓库，源码基准为 `b98d115bbb080e9555466a96656ec4df605aea21`。远程 MCP 会随服务更新；此 SHA 是研究依据，不是对远程服务的版本锁定。

| 追问或反例                                       | 查证结果                                                                  | 设计修正                                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 直接调用「所有失败 job 日志」是否已经完整？      | 官方 `handleFailedJobLogs` 内部未显式遍历分页                             | 不采用这个聚合捷径；只取第一页100个job并标记未覆盖，再按已枚举job_id读取日志                  |
| 日志返回的是完整内容吗？                         | `get_job_logs` 支持尾部行数窗口，并报告原始行数；没有任意中间区间检索参数 | 本轮只读尾部500行且最多16KiB；记录窗口，引用快照相对行号；找不到错误就承认不足                |
| run ID 能唯一确定一次执行吗？                    | 同 run 可重跑；当前工具读取最新 job，未暴露按旧 attempt 列 job 的专用方法 | 首版只诊断提交时最新已完成 attempt；前后复查 attempt；执行期间变更则拒绝交付混合报告          |
| 读取 `head_sha` 下的文件就一定是实际执行版本吗？ | PR merge、checkout ref 和可复用 workflow 可能不同                         | 区分 run 关联 SHA、日志证实的 checkout SHA 与工作流来源；未知时只作为上下文，不给确定源码归因 |
| readOnlyHint 能替代权限吗？                      | 不能；注解是元数据，PAT 权限、平台范围和调用参数仍需控制                  | 固定官方端点、只读模式、受限PAT、三项能力适配及每次调用校验共同约束                           |
| 能列出工具就证明能执行吗？                       | 不能；缺权限、模型不支持 tool calling、输出 schema 漂移均可失败           | 分开检查 MCP 协议、目标资源读取及模型工具往返，首个真实 run 才验证整个链路                    |

## 一个真实样本带来的约束

通过本次 Codex 的 GitHub 连接，实际读取了 [CodeQL 失败运行](https://github.com/github/github-mcp-server/actions/runs/39579994242) 的 job `119154957198`。运行元数据列出三个失败 job，均在 Autobuild 步骤失败；本次仅读取其中一个 job 的日志。

在 09:50:19 UTC 附近，日志同时出现通用自动构建失败说明和配置版本 `4.38.3` / 运行版本 `4.38.2` 不一致的具体错误。因此合理交付应先指出实际版本不一致，再建议核对 CodeQL action 各步骤版本与生成配置；不能直接断言仓库缺构建命令，也不能声称已找出不一致如何产生。

这证明了「存在可获取、可定位、值得解释的真实输入」，支持设计一个窄诊断闭环；没有证明平台已运行 Agent，也没有证明建议实施后 CI 会恢复。连接权限来自当前 Codex，不自动成为产品用户凭证。

## 第四轮：成本是否超过收益

初案中需要补齐的不只是 MCP SDK，还包括模型工具调用、装配与即时撤权、日志来源、交付和验收。即使选择只读工作，也不是一个保存 Skill 文本的小改动。

削减后的首版只保留 GitHub.com、一个官方远程 MCP 预设、三项实际工具；配置和文件调查后置、单次最新失败 attempt、现有对话入口及 Markdown 诊断单。不上 OAuth 应用商店、Webhook、定时监控、通用工作流编辑器、独立任务中心、自动改代码或向 GitHub 发评论。工具执行与交付记录作为后续能力可复用，但不先建设一个通用插件平台。

若首轮协议/模型工具往返实验不通过，先解决这一技术门槛；不要用模型编造工具结果、硬编码示例回答或悄悄改成让用户粘贴全部日志来宣称 MCP 已完成。

## 价值试用与停止条件

以下均为拟议试用规则，尚未执行。

1. 冻结方法与模型后，取五个未参与调参的实际失败案例，包含简单失败、多 job、环境/配置问题与至少一个资料不足案例；公开样本只作开发例，不计独立验收。
2. 与用户当前最好用的处理方式比较。两种做法的先后顺序交叉安排；同题二次处理存在学习效应，记录顺序，不将结果包装成严格统计证明。
3. 记录人实际花费的准备、阅读复核、纠错时间；另记总等待时间、模型用量、连接配置与维护时间。不用 AI 自评分代替人工判断，不把未知费用记作零。
4. 试用继续条件拟为：至少四份交付被接受；没有会误导破坏性操作的无依据确定结论；人实际投入的中位数相对基线下降至少 30%。比例是试用门槛，非已测收益。
5. 用实际任务频率摊销成本：`月净节省 = 月使用次数 × 单次净节省 − 当月维护时间 − 首次配置的约定摊销时间`。频率未知时不能声称盈亏平衡；等待影响也需单独审视。
6. 若主要收益仅是「看起来像在工作」，或基线同样省事，就停止扩展；可保留已经有用的工具调用基础，不因沉没成本追加自动修复。

## 评审结论与未被证明的事项

**条件通过，进入完整设计。** 已确认：场景有清晰输入，官方工具提供实际操作能力，诊断单有可核对的工作成果与验收对象，现有对话基础可承载。经过范围削减后，值得做一个有限试用切片。

已确认所选Kimi模型兼容原生工具调用，端到端完成技术验证。尚未确认用户真实频率与净时间收益；它们是后续试用门槛，不是需要现在向用户索取的设计决策。用户已授权收缩并实施；最终仍由用户整体Review，技术验收不能代替价值验证。

## 交叉验证后的收缩

与《对比 StaffDeck 与 NiumaCrew 架构》的价值讨论交叉后，将CI降为真实执行验证样例：能读日志不是平台独有收益，须与同Skill/同工具的现有Agent比较。用户随后明确授权实现最薄闭环。当前实施依据为已收缩的总体设计，不再实施原七类通用表、MCP管理页或复杂修订链。证据、权限与明确失败保留；最小反馈不等于自动进化。

## 实施后的真实核对

2026-10-22，产品Runner通过固定GitHub只读MCP的初始化与工具发现，实际调用运行、job、日志与结束复查；所选Kimi模型通过原生tool call读取两份日志并给出结构化判断。公开样例在核查后重跑过，产品固定并验证的是attempt2，没有沿用初次调研的attempt1。直接API与浏览器各完成一次真实成功运行，后者仅提交一次，刷新没有再次交办。

首轮执行暴露预算控制缺口：读满两份后模型仍申请第三份。修正为无剩余读取预算时强制 `tool_choice=none`，并验证第三个失败job明确未调查；没有放宽预算来换取成功。引用校验、即时撤权、attempt变化、取消优先和反馈幂等均有离线回归。

这证明装配、工具行为、证据、持久交付和最小反馈已连接。反馈来自测试操作者，案例参与了开发；两次成功不是独立价值试验。频率、复核成本、建议正确率及相对已有Agent的净收益继续按上面的试用规则衡量。详见[真实验证记录](../../../niuma-crew-archive/output/reviews/github-ci-diagnosis/validation.json)。
