本文件记录候选模型和取舍，不表示已经决定建设完整工作流产品。此前撤回的流程定义仍不作为有效需求；以下讨论依据本轮新的泛化诉求。当前已具备标准 Skill、多文件资产、通用 MCP、文件与沙箱接线；外部服务及真实沙箱可用性仍依赖相应环境验收。事件触发的后台身份、持久人工等待、流程实例及受控审批提交尚未实现。

## 1. 推荐的复用单位

候选方向是「流程模板 + 员工绑定 + 一次业务流程实例」，不是每个员工一份执行程序。方法、连接和流程分别拥有不同的职责。

| 候选概念                | 回答的问题                                                     | 不能混淆的边界                                          |
| ----------------------- | -------------------------------------------------------------- | ------------------------------------------------------- |
| 数字员工                | 谁承担工作、采用什么岗位与模型                                 | 员工不是一次请求，也不是一个常驻专属进程                |
| Skill / SOP             | 这一类分析工作应怎样做                                         | 提示与包内资源不能授予外部写入权限                      |
| 流程模板                | 哪些步骤必须发生，分支与人工节点怎样连接                       | 平台版本化配置，不宣称为 Agent Skills 或 MCP 的标准格式 |
| 流程绑定                | 哪位员工用哪份模板、哪些资源/账号、什么触发条件和审批人        | 同一模板可绑定多个员工；参数不同不复制模板或员工        |
| 流程实例                | 某个具体目标从触发到结果落实的全过程，例如 PR #42 某一版的审查 | 可经历多个 Run 和长时间等待，不等同于一次 Agent 运行    |
| Run / RunAction（现有） | 某次活跃执行尝试以及实际发生的动作                             | 流程中的计划、等待和人工决定不伪装成已经完成的工具调用  |

示例：PR 审查模板只有一份。员工 A 绑定仓库 X 与确认人甲；员工 B 绑定仓库 Y 与确认人乙。流程修订形成模板的新版本，既有实例固定原版本，新绑定或新实例采用明确发布的版本。普通聊天不必进入正式流程。

## 2. 三种组织方式的取舍

| 候选方式                  | 适用工作                               | 代价与限制                                                       |
| ------------------------- | -------------------------------------- | ---------------------------------------------------------------- |
| 仅 Skill + Agent 自主执行 | 资料调研、解释、建议性报告             | 简单灵活；提示不能保证必须等待人工、必须按顺序提交或安全恢复     |
| 模板驱动的持久流程        | PR 审批、内容发布、对账确认后提交等    | 推荐探索；共享执行与审批机制，允许某个步骤由 Agent 自主调查      |
| 完整可视化编排平台        | 复杂并行、跨服务长流程、大量非技术作者 | 需要图编辑、版本迁移、节点产品化等配套；当前没有足够依据直接采用 |

推荐先验证第二种：有少量固定节点类型，起步可使用受限结构化配置和模板设置页。是否开放任意节点组合、拖拽编辑或采用外部编排引擎，留给真实复杂度和运维需求决定。

## 3. 共用机制与业务扩展

### 四种执行节点，触发在流程之外

| 节点类型 | 共用能力                                                           | 示例                                               |
| -------- | ------------------------------------------------------------------ | -------------------------------------------------- |
| Agent    | 固定输入、Skill、工具范围、预算和结构化输出契约                    | 阅读 PR 变更，形成带文件与行号的发现               |
| 条件     | 对可信字段和已验证结果执行受限规则，选择明确分支                   | 必要检查通过且低风险才进入自动审批分支             |
| 人工确认 | 指定有权限的人、固定待执行动作/正文/目标版本、期限和决定           | 确认批准或要求修改                                 |
| 工具动作 | 经当前授权与业务门禁调用已有工具；持久记录提交意图、实际结果与回执 | 读取目标元数据、提交 GitHub Review、发布已确认内容 |

顺序连接、终止及输出归档属于流程状态转换，无需为所有概念额外增加节点。条件首版采用明确比较规则，不执行用户任意 Python/JavaScript，也不把模型输出直接当成强制许可。平台节点与实际 MCP 工具的副作用边界需要受信实现或审阅，不能只信上游 readonly 等提示。

触发器负责启动实例：手动表单/对话、经过验签的 Webhook、未来的定时触发共用接受入口。先校验来源、归属、输入和去重，再查询有效绑定、生成实例并排队；重复事件不重复发起业务动作。长时间监听不等于一个永久占用的 Run。

### 三类扩展成本

| 新需求                                        | 推荐处理方式                                                  |
| --------------------------------------------- | ------------------------------------------------------------- |
| 同一 PR 审查方法换仓库、员工、确认人          | 新增或修改绑定，不改后端                                      |
| 新增由已有 MCP/Skill 组成的资料分析或发布流程 | 配置模板、输入/输出和权限；仍需验证工具语义与业务条件         |
| 新事件签名、特殊目标版本、专业结果或提交约束  | 增加触发适配器、专业校验器或动作适配；不修改通用 Agent 主循环 |

因此可以减少重复开发，但不能承诺所有新业务零代码。JSON Schema 能检查字段形状，不能证明「这个行号属于本次 diff」「审批对象仍是同一版」「金额符合组织财务规则」。专业校验要有明确实现和测试。初期内置扩展由开发者维护，任意上传代码不能变成后端进程内插件；已有脚本扩展仍走沙箱。

## 4. 用不同业务检验边界

| 业务           | 触发与输入                     | Agent 节点               | 条件与人工节点                   | 最终动作                           |
| -------------- | ------------------------------ | ------------------------ | -------------------------------- | ---------------------------------- |
| PR 风险审查    | 手动 PR 链接，后续可接仓库事件 | 代码分析、风险与证据     | 低风险按规则处理，高风险人工确认 | 提交版本明确的 GitHub Review       |
| 内容审校发布   | 提交文稿，后续可接内容系统事件 | 查证、风格与敏感问题分析 | 硬规则校验、编辑确认             | 通过发布服务提交固定版本正文       |
| 表格核对与通知 | 上传报表                       | 清洗、统计、解释异常     | 核对结果，达到条件时由负责人确认 | 保存成果，按许可发送明确附件与通知 |
| 资料研究报告   | 用户问题，后续可接定时触发     | 搜索、阅读、引用和归纳   | 验证来源覆盖，可不设人工节点     | 保存和交付报告                     |

这是候选复用示例，不表示平台已接入内容服务、通知服务或财务规则。应选两种实际需要的流程做实现验证；至少有一个人工等待和外部写入场景，避免只把 PR 的字段换名字就宣布引擎通用。

## 5. 执行、身份与副作用边界

### 流程状态和 Run 状态分开

流程实例持久保存模板版本、绑定修订、目标版本、当前节点和已完成输出。执行节点时才建立 Run；人工等待只保存等待记录，释放执行名额与临时资源。确认时新建后续 Run，不恢复一个长期挂起、持有旧凭据的协程。节点重试保留旧尝试，不能把 Agent checkpoint 当作整份流程账本。

流程节点的输出通过明确输入映射进入下一节点，附带证据引用和覆盖信息；不把每一步整段聊天历史都拼给后续节点。失败、取消、超时和过期由持久状态转换表达。候选取消语义为阻止未开始节点、请求停止活跃 Run 并关闭尚未使用的确认；已经完成的远端写入不能被伪称撤回，撤销操作需要独立权限与业务实现。

### 后台触发必须补服务身份

当前 Actor 和 ConversationAuthorization 以用户会话为基础，不能直接拿创建者登录会话给 Webhook 长期使用。候选自动化绑定应明确所有者、服务身份、可用工具连接与资源范围；创建者发布时授予有限范围的自动执行权限，管理员可停用和撤销。Webhook 的 GitHub sender 是事件资料，不自动成为平台操作主体。手动触发和人工确认仍检查当前真实用户及其资源权限。

凭据仍由 tools 管理，模板和实例只保存引用及非秘密依据。需要调用者个人连接的流程遇到缺凭据时等待连接，不能回退借用创建者账号；无人值守任务须使用明确允许自动化的连接身份。

### 外部写操作绑定明确意图

待提交意图包含目标资源、目标版本、动作、有效参数/正文摘要、策略与绑定修订、执行身份和期限。低风险自动动作由已发布策略授权；需人工动作绑定有权确认者的决定，确认不扩大原有工具权限。凭据、模板、绑定或资源的相关变更须重新核对，目标变更后使旧确认过期。MCP 工具必须在实际调用前复核这些依据；只在前端隐藏按钮无效。

对外请求在事务外执行，发出前先可靠保存提交意图。超时未知时保留待核对状态，通过服务回执或查询查证，不盲目重试。不承诺通用 exactly-once 或通用补偿：PR Review 可以按版本/标记核对，邮件、付款和发布有不同的重试及撤销语义，需要各自动作适配。平台记账和远端副作用不伪称同一数据库事务。

## 6. 对当前模块的候选增量

| 模块                         | 当前可复用                                       | 候选新增与责任                                               |
| ---------------------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| agents / skills / tools      | 员工、标准方法、目录、凭据和逐工具授权           | 绑定关系；明确自动化可用身份和受门禁约束的操作               |
| execution / agent_runtime    | Run、队列、动作、预算、取消和普通 Agent 工具循环 | 接受流程节点的准备/授权/发布适配，不让宿主认识每种业务       |
| workflows（拟新增）          | 当前没有独立持久流程所有者                       | 模板版本、绑定、实例、节点状态、人工决定和提交意图           |
| workflows 内的触发与扩展入口 | 当前没有正式事件接受入口                         | 事件验签/去重、绑定查找、专业校验与动作映射；不拆成独立服务  |
| auth                         | 用户、角色、会话和资源检查                       | 服务主体与自动化发布/撤销权限，区分事件来源和实际执行身份    |
| conversations 与页面         | 对话、消息、SSE 和现有成果展示                   | 手动选择流程、输入和确认卡片；后台任务不强造一条用户聊天消息 |

`workflows` 是候选模块名称，不是当前目录事实。它调用统一执行入口并通过适配回调发布状态；业务扩展由装配入口注册，execution 不反向导入每个业务模块。流程不再增加另一套执行进程、调度器或秘密库；存在持久等待不表示要立刻迁入外部基础设施。

PR 可以保留专业校验与类型化输出，但不默认每份流程建一组表、一套模型循环或一个微服务。专业数据需要独立查询、约束或保留期时再决定领域存储。现有 CI 诊断保持原功能，待两种流程验证后再判断迁移收益，不在脑暴阶段承诺自动通用化。

## 7. 产品入口候选

员工页增加「工作流程」装配区，选择模板，再填模板声明的真实业务参数、账号、触发方式和确认人。模板输入 schema 属于平台工作流配置，区别于标准 Skill 的元数据；不能假称所有标准 Skill 自动携带这些表单字段。

能力库可以在同一入口明确区分 Skill、MCP 和平台流程模板，也可以先保留模板管理的次级入口；是否新增顶级导航或 Tab 尚未决定。流程实例页展示当前目标、步骤、证据、等待人和提交回执。对话作为一种工作入口，可展示实例摘要及跳转，但不是后台工作唯一生命周期容器。

## 8. 建议验证顺序与未定项

1. 先用 PR 手动触发验证结构化审查、受控提交及持久人工确认；不要一开始同时建设完整 Webhook、多种服务账号和拖拽编辑器。
2. 将模板与员工/仓库绑定分开，用另一位员工和另一仓库验证不复制流程。
3. 加入第二类真正不同的业务模板，验证已有节点和审批门禁的复用，记录哪些地方仍需业务代码。
4. 再增加事件接受与服务身份，验证重放、重复、乱序、目标变化、撤权、重启和取消。
5. 依据使用反馈决定开放多少配置能力、是否需要并行/循环和外部工作流引擎。

关键验收：人工等待释放 Run；等待中重启可恢复；双击确认只接受一次；目标/正文/规则变化后旧确认无效；外部结果未知不重复写；停用绑定阻止后续动作；提示注入不能改变流程和权限；多个模板/员工共享机制但数据、账号与范围各自受控。

尚未决定：是否作为下一轮实施目标、模板编辑权限与发布方式、第二个验证业务、首版固定节点范围、人工确认角色、实例独立入口和后台触发身份的具体模型。当前只授权设计讨论，不据此创建迁移、部署自动化或向 GitHub 提交任何 review。
