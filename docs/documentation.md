# 文档组织与维护规范

项目文档在 docs，模块说明与源码相邻。现行说明必须对应已实现行为；未实现方案不能作为能力或验收证明。公开版本只收录已核对的代码、配置、操作及业务契约。

## 职责

| 位置              | 内容                                     |
| ----------------- | ---------------------------------------- |
| 根 README         | 产品范围、首次运行、验证及阅读入口       |
| docs/product      | 当前功能、角色与操作流程                 |
| docs/architecture | 当前协作、生命周期、依赖与限制           |
| docs/reference    | 业务、权限、数据及外部契约               |
| docs/guides       | 启动、部署、配置、迁移、备份与排查       |
| docs/engineering  | 共享与端内工程约定                       |
| 模块 README       | 模块作用、流程、文件归属、依赖及维护入口 |
| docs-site         | 阅读与静态发布应用，正文继续在原位置维护 |

类型、字段、常量和可执行规则由代码及工具维护；文档解释含义、原因、边界和可观察结果。局部竞态与执行顺序写在附近注释。相同规则只保留一个详细维护位置。

## 维护与验证

1. 修改行为时同时核对实现、测试和现行契约；发现冲突先辨明原因，再修正对应内容。
2. 模块说明先讲作用与正常流程，再说明存储、协作、文件职责和失败边界；不复制完整 API 或逐函数列举。
3. 新增行为先明确目标、范围、未定项、失败及验收方式；生效后合入当前正文。开发讨论与历史证据不混入公开能力说明。
4. 仓库内使用相对链接；移动或删除内容时同步索引、引用和文档站发布清单。
5. 运行 make check-docs 检查本地文件、章节及索引可达性；使用前端 Prettier 格式化 Markdown；影响站点时执行 make check-docs-site。
6. 实际交付说明已运行的检查与未覆盖范围，离线替身不能证明外部服务可用，历史通过不能代替当前验证。

所有示例使用虚构数据或占位符。环境文件、数据库、日志、密钥、账号与私人执行内容不属于文档资源。发布清单及链接检查不能代替敏感信息审查。
