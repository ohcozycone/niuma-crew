# 平台持续委托

设计状态：讨论草案，尚未整体采纳。实施状态：未实施。更新：2026-11-08。范围：未来工作入口、任务/成果、触发、人工确认、等待与交付；不改变现行Run、Conversation或权限。

## 目标与现有边界

当前Run处理一次输入并可靠保存成果，业务另行接纳；尚没有跨多次Run的正式任务、持久人工等待或自动交办产品。候选目标是让持续委托有明确拥有者、进度、成果及验收，并保留外部动作未知结果的责任。

## 与平台架构的关系

整体架构与图源统一维护在[系统架构](../architecture/overview.md#模块分工)。主图已明确任务管理与编排位于业务应用层，计划调度属于该模块的内部机制；虚线框只表示职责位置，不代表能力已实施。

本方案继续维护持续委托的业务状态、授权、等待和交付设计。现有 Run 与应用接纳规则以[后端架构](../architecture/backend.md)和[执行契约](../reference/runtime.md)为准，不在这里重复维护总图。

## 待评审的共同模型

- 业务任务与一次Run分开；来源对话用于追溯，不要求每个任务新建专用对话
- 输入版本、成果和验收属于业务，执行循环继续复用当前引擎和动作门
- 触发、模板、人审和外部提交是独立语义；账号授权及后台身份不能由提示词提供
- 等待与恢复需明确持久位置、重复resume和取消的判定，未知副作用不自动重放
