## 接入方式：OpenSandbox＋Docker＋gVisor

接入链路为：现有 `create_agent` → 统一工具授权与预算入口 → `FilesystemMiddleware` / 沙箱后端 → OpenSandbox Python SDK → 受信 OpenSandbox 服务 → Docker 的 `runsc` 容器。Agent 循环和模型调用留在应用后端，获准的文件操作、脚本、测试命令在沙箱中执行；无需把整个应用放进沙箱，也不另建一套 Agent 循环。此能力走原生后端协议，不要求先包装成 MCP。

平台内部由 `sandboxes` 持有环境申请、远端身份和生命周期 SDK，`agent_runtime` 适配侧将同一已登记环境装配成 Deep Agents 文件/命令后端，`files` 保存取回的持久产物。沙箱管理凭证由受信适配侧按连接身份解析，不向模型或沙箱工作负载传递。具体实现均由 bootstrap 注入，不让资源模块接管执行宿主。

**部署与适配顺序：**

1. 在目标 Linux 主机安装 Docker Engine 和 gVisor，向 Docker 注册 `runsc`；腾讯云虚拟机优先验证 gVisor 的 `systrap` 平台，无需以 `/dev/kvm` 或嵌套虚拟化为前提。先确认内核、架构及所需系统调用兼容，再启动受信 OpenSandbox 服务。
2. 按 OpenSandbox 的 Docker 配置显式选择 gVisor，锁定服务、SDK、`execd`、工作负载镜像与 `runsc` 的已验收版本。配置片段如下；镜像占位符须替换为已验证的 tag/digest，不能直接用于部署。运行时缺失或验证失败时，代码连接不就绪，不能自动降级为 `runc` 或宿主 Shell。

   ```toml
   [runtime]
   type = "docker"
   execd_image = "<已验收的 execd 镜像及 digest>"

   [secure_runtime]
   type = "gvisor"
   docker_runtime = "runsc"
   ```

3. OpenSandbox 的管理端点仅向应用后端开放：同机使用回环地址，不同机使用受防火墙限制的内网和加密连接；配置 API Key。应用还需能访问 SDK 返回的文件/命令服务端点，不能只验证生命周期 API。Docker socket 仅交给受信控制服务，既不暴露公网，也不挂进 Agent 工作负载。
4. 优先复用 OpenSandbox 官方示例收录的第三方包 `langchain-sandbox-opensandbox`，其导入名为 `langchain_opensandbox.OpenSandboxBackend`，接到现有 `FilesystemMiddleware`。核对到的 `0.1.2` 声明 `deepagents>=0.7.0,<0.8.0`、`opensandbox>=0.1.15`，与工程 `deepagents==0.7.30` 的声明范围相容，运行兼容仍待实测。实施时显式声明并锁定实际依赖，验证文件、命令和异常行为；它不是 LangChain 内置的官方后端。
5. SDK 示例使用 `SandboxSync`；同步创建、文件传输、执行和销毁须通过受控线程/异步适配进入现有异步 Runner，验证取消后仍能回收，不能阻塞事件循环。若第三方包不能满足现有契约，平台在同一后端协议下补薄适配；不复制容器管理实现，也不要求使用者自行编写适配器。

服务端的 `[secure_runtime]` 是部署级配置，不能由模型在创建沙箱时改写。平台就绪检查必须确认实际容器的 Docker runtime 为 `runsc`，并完成目标主机冒烟；收到普通 HTTP 成功响应不足以证明隔离成立。未配置或未就绪时只关闭代码能力，搜索和文件阶段仍可独立使用。

**文件与权限：** 代码能力开启的 Run 使用一份独占沙箱，从首次文件操作前即将 `/inputs/`、`/workspace/`、`/outputs/` 装入同一工作副本；文件工具也通过该沙箱后端访问。`/skills/`、`/sources/` 仍由只读快照后端路由。使用 `CompositeBackend` 时以沙箱为 default，只读前缀作为专门路由；同步适配前缀剥离与现有技能 `files` 键格式。创建时装入获准输入，结束前取回输出并校验哈希；不能在 StateBackend 写文件、再在另一份沙箱文件中执行。代码需要来源文本时，通过获准文件工具读取后显式写入工作区；不假定虚拟来源路径在 Shell 中存在。

文件工具的路径检查约束不了任意 Shell。输入只读、命令执行身份、工作目录可写和挂载范围须由实际容器权限或已验收的只读挂载保证，不能仅靠中间件拒绝 `write_file`。工作负载不得使用特权模式、宿主网络/PID 命名空间，不得包含应用数据库、`.env`、主密钥、模型/搜索凭证、宿主 Docker socket 或业务数据目录。文件传输与产物收集也要拒绝通过符号链接逃逸允许目录，并验证跨 Run 无法读写。

**网络与资源：** 默认配置用于离线计算，命令网络出口与 SDK 管理通道分别限制和验收。需要联网安装依赖或访问业务 API 时，部署者另建经验证的出口白名单配置；策略须在受信网络层执行，阻断绕过代理的直连和到宿主、非许可内网、云元数据的访问，并覆盖 IPv6 等旁路。不能把“容器网络”“域名列表”或提示词当成已实现的出口隔离。建议将 Python、Node、Git 和常用库预装进固定镜像，减少运行时联网安装。

CPU、内存、进程数、磁盘、单命令时限、沙箱 TTL 和并发均需有部署上限，员工只能在其中选择已批准的执行配置。磁盘硬配额取决于目标文件系统/存储驱动，不能假定 Docker 默认具备；实施时验证所选机制，达不到必需上限则不标记该配置就绪。代码并发独立于现有 Run 并发，单机首轮从 1 个沙箱实测，保留应用自身资源；这不是修改当前默认并发。命令时限不超过 Run 剩余时间，stdout/stderr 和文件传输均有字节上限。

**生命周期与失败：**

1. 接受 Run 时冻结连接身份、执行配置修订、镜像及输入引用；创建前保存资源申请，创建后保存沙箱 ID、归属 Run、服务端点身份、到期时间和待清理状态。验证创建 API 的幂等/可查询归属能力，处理“已创建但未保存 ID”的窗口；不能遇到超时就盲目再建，也不能只把 ID 放在内存或 checkpoint。
2. 每次文件/命令调用仍走共享授权与持久预算；受控记录退出码、截断的 stdout/stderr 和结果引用。结束执行后终止残留命令/子进程，有界取回需要交付的输出并可靠保存，再销毁工作副本；最终下载仍走平台鉴权，沙箱路径或直连地址不交给用户充当下载链接。
3. 成功、失败、撤权、取消和超时都终止工作负载并销毁沙箱，验证子进程一并结束。调用 SDK `destroy` 或等价销毁 API，不能用关闭 HTTP 客户端替代进程终止。销毁失败保留租约、重试记录和告警，并依赖服务端 TTL、定期扫描及应用启动核对回收孤儿资源；TTL 是补偿，不能代替及时停止。
4. 重启按已保存的连接身份与归属清理本平台资源，不误删其他部署的沙箱；不重放未知命令。首版不做跨 Run 容器复用、快照恢复或热池，避免把前一轮数据和进程带入下一轮。代码写入/测试可在获准工作副本中执行；仓库推送、提交 PR 等外部写入仍需另行设计明确授权，沙箱本身不附送仓库凭证。

## 开源交付：平台与使用者的分工

下表是目标交付分工，尚未实现。部署维护者、员工配置者和技能作者是职责称呼，具体操作沿用现有管理员/成员权限，不借此新增角色体系。

| 能力       | 平台开源代码应内置                                                                                                | 使用者负责配置或提供                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 工具接入   | 原生工具注册、已支持传输/认证范围内的 MCP 客户端、目录审核及统一调用协议；提供已验收的 Tavily 与 OpenSandbox 接线 | 选择已支持服务，填写 MCP 地址、认证方式与凭证；支持范围内接入标准 MCP 不要求逐服务改代码              |
| 沙箱适配   | OpenSandbox 后端、文件/命令封装、错误转换及健康/就绪检查，保留替换后端的协议边界                                  | 部署 OpenSandbox、Docker、gVisor，提供内网地址/API Key 和实际主机资源；其他沙箱服务后续按同一协议适配 |
| 部署资料   | 版本锁定的单机示例、配置模板、镜像构建示例、启动/停止及兼容性验证说明                                             | 按系统安装依赖、拉取/构建镜像、配置防火墙、磁盘与运维监控；平台不自动接管其云账号                     |
| 执行配置   | 约束配置格式、校验、安全默认值及上限执行，缺少必需隔离时禁止启用代码能力                                          | 管理员选择受信镜像、可用语言/依赖、CPU/内存/磁盘/进程/并发、时限、TTL 与网络白名单                    |
| 许可与预算 | 连接和员工许可独立、原子复核与扣减、修订冻结、撤权和取消；实际能力取部署上限与员工许可的交集                      | 管理员决定哪些员工能用哪些工具、输入/输出范围和额度；业务配置只能收紧，不能突破部署上限               |
| 密钥       | 凭证加密与实例级解析、脱敏、模型/日志/沙箱隔离；管理凭证只由宿主使用                                              | 提供并轮换模型、搜索、MCP 与沙箱服务凭证，维护平台加密主密钥；服务费用按其所选提供者承担              |
| 文件与产物 | 输入归属检查、不可变引用、路径/大小限制、传输、暂存/发布、鉴权下载及过期清理                                      | 选择本地存储位置/容量及保留策略，显式上传或引用资料；需要其他存储时增加已支持的配置/适配              |
| 运行可靠性 | Run/动作记录、结果引用、有界输出、资源租约、重启核对、清理重试与明确的 unknown/interrupted                        | 设定可承受额度，监控磁盘/清理失败并维护主机；不能要求使用者自己补取消、回收和越权检查                 |
| 业务内容   | 标准 Skill 的加载与兼容检查、工具独立授权，附少量可验证示例                                                       | 定义技能方法、提示词、业务参数、测试/构建命令及专用镜像依赖；执行配置须由管理员批准                   |

部署配置负责运行环境与全局上限；连接保存可公开的端点/执行配置引用和独立密文凭证；员工许可选择已批准配置并收紧范围；Run 冻结本轮有效值。继续复用 `tool_connections` 的 `public_config` 与秘密分离机制及 `agent_tool_grants`，字段在现有草案中按实施需要补齐，不另建一套连接/许可体系。涉及密钥或部署隔离的原始 Docker 参数不作为模型工具参数或普通业务表单暴露。

平台应随代码交付可运行的基础适配与配置样例；开源使用者主要配置服务和业务内容。只有超出已支持协议、认证或后端能力的新集成才需要开发适配，并继续经过相同的授权、预算和生命周期入口，不能通过自定义 Skill/配置绕开它。工作流、表单、报告组织方式仍按后续讨论推进，不因开放配置而前置建设。
