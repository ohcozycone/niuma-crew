## 5. 判断、瓶颈与剩余边界

**保留这轮结果交付改造有价值，但不宣布整体质量/实际费用验收通过。** 官方移存替换重复逻辑，完整JSON不再被切坏；在最终隔离样本中，额外补读和较大工具上下文的重复携带减少，性能门槛已达到。没有因此增加结果服务、复制正文或提高运行预算。

主案例每Run模型动作耗时均值由20.89秒降至12.71秒；工具动作合计均值由0.039秒降至0.028秒。当前隔离链路约99%的时间仍在模型动作，结果文件保存不是主要卡点。输入均值减少17,903.8 tokens，其中15,853.3是缓存输入，约88.5%；即使大部分被重复处理的输入能命中缓存，减少轮次仍有条件成本收益。最终一轮模型耗时均值约4.44秒，剩余时间还包括发现、操作规划及偶发额外调用，不能把全部延迟都归因于最后回答。

旧固定预览与二次截断是交付功能问题；页面/文章、未知/零、满页/截断的混淆是提示与模型理解问题。两者已分别取得实际证据，不能用结果保存层的再次裁剪或业务字段猜测去修复后者。本轮到此收敛，不追加隐藏答案修复模型、正则纠错或统计工具；下一阶段若要求严格证据边界零错误，应单独验证回答约束与真实来源能力，不把它包装为本次已通过。

限制：MCP为固定合成回包，时间不含真实上游网络；使用同一合成输入的新轨迹复验，并非未见数据集泛化证明。缓存未人为清空、模型修订未独立锁定，只使用真实usage，不声称严格控制冷/热缓存。真实MCP写操作、真实沙箱、完整阅读全文任务和引用UI未验收。沙箱只读别名投递是在真实模型虚拟工作区测试后补齐的独立支路，已有假沙箱回归，不冒充真实沙箱验收。源码依据见[指纹](data/工具结果交付改造源码指纹.json)。


## 6. 长单行结果触发任务丢失的补充修复

2026-11-10，用户提供的新执行 `100000000170` 共 6 次模型请求、5 次工具动作、81,796 tokens。只读核对实际请求证据后确认：前五次请求仍带原始 Notion 计数问题；第六次只剩系统说明、摘要占位、一次文件读取请求及其反馈。占位原文是 `Previous conversation was too long to summarize.`，没有发生真正的摘要模型请求。最终回答与模型返回一致，原始用户输入仍在 Run 中，丢失发生在框架消息状态替换阶段。

根因是当前 SDK 的摘要前默认 4,000-token 裁剪：从末尾选取并要求起点是用户消息，长工具历史可能使可摘要列表为空；随后 SDK 不调用自定义摘要入口，直接用占位文本替换已选历史。此前工程验证和真实对照没有覆盖这条组合路径。最近一轮超时、重复限次和知识限次清理未修改该摘要参数；超时或预算耗尽也不符合本次全部动作成功、模型仅用 6/8 次的证据。

另一个交付缺口：本次上游正文是 22,884 字符的单行 JSON；两次 `read_file` 反馈完全相同，只显示其中 15,948 字符，行数改小也无法到达单行尾部。原始归档存在，字符读取工具也存在，但反馈只给文件路径，没有给对应 result_id。上游空查询还明确未执行，后续关键词匹配不能证明工作区文章总数。

本次修复只改三处生产文件：

1. `agent/model_calls.py` 使用官方参数 `trim_tokens_to_summarize=None`，让选定历史进入既有受管摘要入口，由原有字节、授权和次数检查约束。超限明确停止，不生成“无法摘要”的替代历史。
2. `builtin_tools/result_files.py` 根据已有路径关联生成字符读取入口，提供真实 result_id、字符 offset=0 和 next_offset 用法。
3. `agent/tool_calls.py` 在 MCP 结果移存及原生读取的最终文本反馈中附上该入口，然后规范化和保存实际反馈；仅展示本轮真正提供且来源受支持的能力，不向知识或工作区结果承诺字符工具可用。原始协议、正文、JSON 顺序、SDK 行窗口及旧字符游标均不变，未增加另一份正文、另一套分页工具或工具发现逻辑。

新增端到端回归在修改前稳定复现占位替换，修改后实际调用摘要，摘要输入包含原问题，后续模型请求保留任务目标；另验证从实际返回的编号通过现有字符工具读到单行末尾，下载归档与原文逐字一致。超出摘要输入字节上限时，在请求模型之前失败，原消息未替换。样本使用合成正文与 8,000-token 触发值复现同一裁剪路径，不声称精确重现生产环境的触发估值。另将本次已保存检查点中被选中的 9 条真实历史，完整回放给本地假摘要模型，验证收到原问题并实际调用摘要一次；没有将真实资料发送给供应商。

本次独立回归共 132 项通过：结果交付、摘要超限、能力入口约束、执行线程、结果保存/读取、工具执行和运行记忆共 64 项；能力运行、工具检查、基础工具和工具发现共 68 项。后端静态、格式与 48 文件类型检查通过。实际请求的非正文摘要与哈希见[复现证据](data/长结果摘要丢失任务复现.json)。本次没有付费模型或远端 MCP 重放，没有修改业务库、既有回答或已保存的旧摘要；修复后真实模型的答案质量与性能尚未重新验收。

## 7. 补充修复后的真实回归失败

2026-11-10，用户报告新对话失败。以下是实际执行的只读核对，不是同一回包的受控 A/B；本节没有继续修改生产代码、重跑模型或修改业务库。证据与参数见[两次执行对照](data/Notion两次执行回归对照.json)。

| 指标 | 对话 100000000165／执行 167 | 对话 100000000171／执行 173 |
| --- | --- | --- |
| 执行结果 | 成功返回，文章总数仍未知 | 失败，tool_arguments_invalid |
| 模型调用 | 3 次普通调用 | 7 次普通调用、1 次摘要 |
| 工具调用 | 发现、搜索，共 2 次 | 发现、3 次搜索、文件读取、2 次字符补读和 grep，共 8 次 |
| 总 tokens | 29,072 | 103,639 |
| 查询路线 | 查询“文章”，取得 8 个匹配页面后说明限制 | 空查询未执行，改查“的”和“the”，大结果触发读取及摘要 |

两次首轮模型 HTTP JSON 请求逐字段相同（哈希已保存），Notion 搜索参数定义也相同；因此不能把最初查询路线的分歧直接归因于新增补读提示。新提示实际进入了后续补读链路：模型拿到 result_id 后成功读取 offset=15000 的一页，随后又请求 offset=0、limit=15000。

直接失败原因是既有字符读取实现的隐藏限制：模型可见 Schema 的 limit 只有 integer 和默认值 6000，没有最大值；后端另行拒绝超过 12000 的值，异常经工具门传播为整次 Run 失败。实际输出又另受 8000 字节限制。对真实归档做本地探针，limit=15000 稳定失败，limit=12000 只读到 end=5237，next_offset=5237，正文总长22884；并不等于读出12000字符。

仅修 limit 仍不足以救回该执行：失败工具来自第8次模型请求，持久模型预算已满；即使工具返回成功，第9次形成回答的请求仍会被 agent_budget_exceeded 拒绝。摘要这次确实执行并保留了目标，但额外提出宽泛关键词去重估算、jq、继续分页等步骤，还把 read_file 写成字符偏移；后续 grep 的 count 返回的是匹配行数1，不是页面数量。此前占位丢任务的修复成立，不能据此宣称任务规划、工具理解或完整成本已通过。

本次结论是该版尚未通过真实任务回归。上节132项组件与工程回归只证明限定边界，不证明模型能以合理轮次完成任务。后续必须同时回放较短的关键词结果和本次长结果，并验收总轮次、实际回答、预算结束及缓存折算用量；不能只修一个参数报错后宣布完成，也不能靠增加模型次数掩盖读取链路的问题。
