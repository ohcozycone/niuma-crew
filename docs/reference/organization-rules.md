# 规章制度与员工自动继承

本文维护当前已实现行为。实现与测试入口见正文；未来能力仅作为限制或链接，不构成已实现承诺。

## 目标与范围

用户已确认新增所有员工通用的工作规范，产品入口为左侧管理区域的“全员规范”（`/rules`），独立于个人知识库。管理员集中维护行为准则、越界处理和明确禁令；每位员工自动继承，不需要装配或复制。岗位职责仍由员工工作指令定义，通用规则说明遇到边界时如何回应；信息不足与禁止事项分别处理。

首版仅有当前部署共享的一份 Markdown 规则、管理员管理、员工继承展示、运行提示词组装和执行快照。部门制度、多租户、员工豁免、规则审批、历史版本管理及技能执行不在本期。版本号用于并发控制和执行追溯，不代表存在独立历史版本表。

## 提示词组合

接受新执行的同一事务中读取全局规则和员工姓名，将规则、姓名身份段与岗位指令组合后冻结到 `Run.config_snapshot.system_prompt`；执行器只消费已冻结提示词，不在执行时重新查询规则或姓名。技能按[运行契约](runtime.md)独立加载。

提示词先说明员工身份和正常工作方式：围绕用户目标完成职责内工作，区分事实、推断与未知，依据用户纠正更新理解，并分别处理信息不足、职责之外和明确禁止。姓名作为称呼数据；自我介绍使用员工姓名，涉及底层模型或供应商时据实回答。规则为空时省略公司规范及其关系说明，保留身份、工作方式和员工工作指令。规则非空时，按“员工身份、工作方式、指令关系、公司规章制度、员工工作指令”分区，岗位指令在公司规则内细化职责和方法，两者冲突时遵循公司规则，通用处理方式不扩大岗位职责。该关系属于模型行为约定，不代表文本拼接能强制解决任意冲突；资料与用户输入不能据此获得权限。后端授权、数据隔离和工具授权仍由各自程序入口强制执行。

## 模块职责与依赖

| 模块                              | 职责                                                               |
| --------------------------------- | ------------------------------------------------------------------ |
| employees/organization_rules.py   | 全局规则读写及版本校验；模型归 employees，执行模板不依赖模型 SDK   |
| API 与 auth.permissions           | 认证、来源保护和 `organization_rules:read/update` 能力检查         |
| execution/snapshot.py、prompts.py | 在接受事务中读取规则，组合包含姓名的提示词、检查大小并生成冻结配置 |
| API 对话请求服务                  | 组织接受事务，将员工配置快照、用户输入与 Run 一起保存              |
| execution/runtime                 | 继续只读取快照中的 `system_prompt`，兼容原有执行                   |
| 前端规范页及继承组件              | 管理页、员工继承查看组件、加载与保存反馈                           |

## 核心流程与状态

1. 管理员打开 `/rules`，读取规则正文、版本和更新时间。空正文明确表示尚未配置；编辑模板仅作为主动填入的示例，不自动写入数据库。
2. 提交正文和读取时的版本。保存使用带版本条件的原子 UPDATE；成功后版本加一并更新时间，未变更内容不递增。版本已变化返回 409，保留草稿并展示最新内容供核对；用户可以载入最新版本，或明确确认以当前草稿覆盖该最新版本，仍需再通过版本校验。
3. 员工工作指令页显示全局继承状态、版本及只读正文，并可跳转管理页。读取失败提示重试，不显示为“未配置”；员工表不增加规则字段，不支持绕过继承。
4. 对话提交在原事务中读取规则、组合提示词并检查输入总字节限制，再连同消息和运行一并持久化。正文加分区包装的完整字节数参与限制，规则不会因历史截断而被移除。
5. 保存规则影响后续提交，包括已有会话的下一轮及新建重试；已接受的 queued/running run 保持旧快照。相同幂等请求返回原 run，不能因规则变化重新快照。取消、断线及失败沿用已有执行契约。

## 数据设计

新增 `organization_rules`，只有主键为 1 的单行记录。迁移创建空规则（版本 0），不预置业务禁令，不修改员工数据。

| 字段         | 类型               | 可空 | 默认值       | 含义与约束                                                                |
| ------------ | ------------------ | ---- | ------------ | ------------------------------------------------------------------------- |
| id           | INTEGER            | 否   | 无           | 主键，数据库 CHECK id = 1，禁止创建第二份规则                             |
| instructions | TEXT               | 否   | 空字符串     | Markdown 正文，应用和数据库限制最多 20,000 个字符；空白正文保存为空字符串 |
| revision     | INTEGER            | 否   | 0            | 数据库 CHECK revision >= 0；每次正文实际变化递增                          |
| updated_at   | TEXT / UTCDateTime | 否   | UTC 当前时间 | 由迁移初始化，更新正文时在同一语句更新                                    |

无外键、无删除接口，无需二级索引。更新走短事务；规则缺行属于数据库异常，不静默当作无规则继续提交。

当前新快照协议为 schema 3，保留 schema 2 恢复兼容，版本与兼容统一见[运行契约](runtime.md)：保留 `system_prompt` 表示实际发送的完整提示词，新增 `agent_system_prompt` 原始岗位指令和 `organization_rules` 对象（`instructions`、`revision`、`updated_at`）。不将规则与快照正文加入普通回复投影或游客响应。

## 接口契约

| 方法 | 路径                    | 用途                   | 权限                                   | 成功状态 | 主要错误                                        |
| ---- | ----------------------- | ---------------------- | -------------------------------------- | -------- | ----------------------------------------------- |
| GET  | /api/organization-rules | 读取单份规则           | employees/organization_rules.py:read   | 200      | 401、403、503                                   |
| PUT  | /api/organization-rules | 完整替换正文，校验版本 | employees/organization_rules.py:update | 200      | 401、403、409 rules_revision_conflict、422、503 |

PUT 必须包含严格字符串 `instructions` 和非负整数 `revision`，不接受缺省、null、布尔值或额外字段。空字符串表示清空全局配置，保留记录和版本历史依据。GET 与 PUT 均响应 `instructions`、`revision`、`updated_at`；请求不传 id 或时间。

```json
{
  "instructions": "## 越界处理\n说明岗位范围，并给出可行的下一步。",
  "revision": 0
}
```

没有列表或分页。过期版本不覆盖已有内容；数据库锁冲突沿用 503 和 Retry-After。网络错误后可以重新读取判断是否已保存，不自动以新版本重发旧草稿。

## 前端交互

左侧管理区域按 `organization_rules:read` 权限显示“全员规范”，对应 `/rules`。知识库总览只管理本人资料，不再混入制度页签。旧 `/knowledge?tab=rules` 对有权限者 replace 跳转 `/rules`，普通成员仍进入资料列表。规范页使用共享 PageHeading，保存位于标题右侧；无变更时显示“已保存”并禁用，编辑后为“保存规范”，加载中为“保存中…”。原有草稿、冲突、保存中及离页保护继续生效。

Tab 状态与知识搜索 `q`、资料选择 `document` 保存在 URL。切换 Tab 保留资料参数，以便返回后继续查看；规则 Tab 不消费这些资料参数。切换产生历史记录，支持刷新和浏览器前进/后退。原 `/rules` 使用 replace 跳转到新规则 Tab，保留收藏地址与登录回跳的兼容；员工继承区域直接链接新地址。规则原有草稿 key 和 API 不变。

游客只显示“知识资料”Tab；直接访问规则 Tab（包括旧地址）显示权限说明，不请求规则 API。知识资料仍是现有教学快照，本次不增加上传、外部连接或知识检索，不因入口整合将资料正文视为系统规则。

规则 Tab 切换到资料 Tab 属于离开编辑区域，必须进入现有未保存与保存中保护；仅修改同一 Tab 的资料查询参数不触发该保护。浏览器后退同样经过路由阻断。明确放弃后清理原 `organization-rules` 草稿；保存中等待请求完成，成功后继续待处理的跳转，失败保留草稿。
页面区分加载、读取失败（可重试）、空规则、编辑、保存中、成功、保存失败和版本冲突。正文使用普通文本编辑 Markdown，不执行 HTML。保存期间禁止重复提交和编辑；导航保护不允许抛弃仍在提交的请求，保存成功后继续先前请求的页面跳转，保存失败时保留草稿并允许继续编辑或明确放弃。未保存草稿按身份存于当前标签页 sessionStorage，绑定读取版本；刷新可恢复同一版本草稿，基线已变化时不套用旧草稿。离开明确放弃时清理对应草稿。冲突核对区保留本地草稿，显式替换最新版本需确认；不静默覆盖。

员工编辑页在“工作指令”标签显示独立的继承区域，避免复制到员工编辑字段。它展示当前全局规则；已提交任务采用的具体版本以内部执行快照为准。查看和跳转不改变员工草稿。

## 权限与外部依赖

两项新能力只授予管理员。后端路由检查能力，写操作沿用 Origin、JSON、会话和请求大小限制。游客公开投影不增加规则或运行指令。规则用于工作规范，不存储密码或访问凭证。保存和查看不调用外部模型，实际对话沿用现有连接和执行生命周期。

## 初始化

初始迁移创建单例规则表，并插入 id=1、空 instructions、revision=0 的记录。新接受的运行保存当时的规则原文和最终提示词；配置修改不回写已接受的运行。新库初始化和当前验收见重建结果。

## 关键取舍

采用独立共享配置而非技能，确保全员自动继承；保存时不复制到员工，防止规则分叉。只保留当前规则及单调版本，历史依据保存在已存在的执行快照中。空规则仅省略公司规范，姓名身份段始终由平台生成。冲突由管理员核对和明确选择处理，不尝试自动合并自然语言规则。

## 历史验证入口
