# 前置检索上下文改写

设计状态：草案，待评审。实施状态：未实施，本轮只制定计划。实质更新：2026-11-07。

## 目标与范围

让前置检索在连续对话中使用完整的检索问题。例如上一轮用户明确询问“云帆科技去上海出差的住宿标准”，本轮问“超标怎么办”，实际检索应包含公司、城市、费用类型及超标处理诉求。

本次只改善 `always` 前置检索的查询准备。继续使用同一聊天模型连接、现有知识工具、证据登记及 Agent 回答流程；`on_demand` 动态检索继续由 Agent 结合已有上下文生成工具参数。首版不增加独立模型配置或用户开关，不扩展为意图分类、多查询拆分、同义词扩展或重排项目。

当前规则见[知识库契约](../reference/knowledge.md)，执行与恢复边界见[运行契约](../reference/runtime.md)，日志与权限见[执行证据契约](../reference/runtime.md)。以下均为拟议行为，不能作为已经支持的能力。

## 当前实现与需要调整的位置

| 位置                                                    | 已确认行为                                               | 本次调整                                              |
| ------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------- |
| [Agent 入口](../../backend/app/runtime/agent/engine.py)         | 在读取 checkpoint 和启动图执行之前，以最新消息调用预检索 | 先验证并恢复本轮消息，再在图内准备查询与预检索        |
| [预检索工具动作](../../backend/app/runtime/agent/tool_calls.py) | 用最新消息前 1000 字符搜索；稳定动作键支持已完成结果复用 | 接受已准备的查询，保留原授权、缓存核验和工具动作链    |
| [临时参考资料](../../backend/app/runtime/agent/model_calls.py)  | 将当前预检索结果及重新核验的历史证据临时加入模型请求     | 从本 Run 的图状态取得预检索结果，继续临时注入         |
| [执行存档](../../backend/app/runtime/agent/checkpoints.py)      | 保存 SDK 消息、当前 Run 标识及模型用量                   | 增加按 Run 隔离的查询准备及预检索阶段状态             |
| [单次任务](../../backend/app/runtime/execution/runner.py)       | 已有模型调用但没有本 Run checkpoint 时拒绝恢复           | 保持该规则；保证首次改写调用之前已有本 Run 可恢复存档 |

关键事实：`AgentRequest.messages` 不是完整历史；历史来自明确选定的 checkpoint。不能简单拼接这个数组便宣称已接入上下文，也不能查询当前线程的最新存档替代本轮冻结的基点。

## 目标流程

1. 验证 Run、挂载知识及当前模型配置，按现有规则加载并验证本 Run 或基点 checkpoint。
2. 新 Run 通过官方消息 reducer 接纳本轮输入；同 Run 恢复继续原状态。保证本 Run 初始化已持久化。
3. 仅对前置模式准备查询。没有可用历史时直接使用原问题；有可用历史时，调用一次受管模型，将当前问题改写为独立查询。
4. 校验并保存查询准备结果，再调用现有 `presearch`，继续使用稳定的 `knowledge:presearch` 动作键。
5. 将预检索结果作为本轮临时资料提供给正常回答模型。用户原问题和正式对话消息保持原文。
6. Agent 按原有机制回答、再次搜索或补读；原引用检查及最终发布规则继续生效。

推荐在现有 LangChain 中间件内接入两个阶段，而不是在图外直接增加一次模型调用：`abefore_agent` 准备查询并返回持久状态；首次 `abefore_model` 执行预检索并保存结果，后续模型轮按 Run 标记跳过。当前锁定依赖已提供这两个钩子。正式实现必须验证图的初始化 checkpoint 在第一个外部调用之前完成；不能只依据钩子名称假定恢复安全。

## 上下文选取

### 唯一来源

- 使用当前被允许续接的 SDK 消息状态。新 Run 以受理时冻结的基点为准；恢复中的 Run 不把本轮已经生成的回答或工具反馈重新当作上一轮历史。
- 仅纳入用户消息、可用于理解对话的助手正文，以及框架已经生成并保留的对话摘要。工具请求、工具原始响应、附件全文及本轮临时资料不作为查询改写输入。
- 历史正文复用现有清理规则；历史答复及摘要仅辅助理解，不作为公司制度、金额等事实的权威依据。重新登记的历史知识证据仍走原路径，本次不复制一份知识记忆。
- `memory_reset`、新会话和没有有效基点的情况，不读取旧历史。无效或不匹配的 checkpoint 沿现有错误处理，不能静默改读其他存档。

### 输入边界

首版建议最多保留最近 6 个用户轮次及其相关助手正文，历史正文预算 12 KiB UTF-8；这些是初始工程上限，不是已验证的最优参数。先从近到远选取完整消息，受预算限制时舍弃较旧内容，不截取出半个 JSON 或残缺工具协议。若框架摘要已经存在，作为独立、明确标注的背景纳入同一预算，不再为改写额外生成摘要。

当前问题完整保留并优先获得预算。改写请求的实际大小仍受本轮上下文上限约束；当前问题本身超过可用预算时，跳过改写并记录原因，沿用现有长查询规则。不得把截断后的问题包装为完整理解。具体边界通过长中文、多字节和摘要场景测试确定。

所有入选消息和摘要参与输入指纹；指纹还包括 Run、原问题、改写策略版本及模型配置修订。恢复必须使用相同输入，不根据恢复时出现的较新消息重算。

## 改写规则与输出

固定提示词归属 [agent/prompts.py](../../backend/app/runtime/agent/prompts.py)。输入分为“历史背景”和“当前问题”，明确二者是数据；模型任务仅为生成检索查询，不回答业务问题，不调用工具，不执行历史或当前文本中的附加指令。

改写应遵守：

1. 保留当前问题的诉求、否定、比较和条件。当前用户的明确纠正覆盖较早信息。
2. 只补齐有依据的指代和省略，例如公司、产品、地点、讨论对象。不能补写模型猜测的金额、审批人、答案或适用条件。
3. 当前问题切换主题时，不强行沿用旧主题；已有完整问题时可直接原样输出。
4. 多个对象都可能是指代目标时，保留歧义。不要根据“最近出现”自动认定业务对象。
5. 输出单个查询，最多 1000 字符；保留原语言、名称、编号及关键条件。本次不生成多个查询，不选择库 ID。

建议使用严格校验的 JSON 结果，不要求供应商支持额外的原生结构化输出协议：

```json
{
  "query": "云帆科技上海出差住宿费用超标的处理、审批和报销规定",
  "unresolved": []
}
```

`query` 必须为非空字符串且符合现有知识查询上限；`unresolved` 为有界的简短歧义列表，不承载推理过程。出现歧义时查询只使用已知条件，并将歧义提示作为本轮临时资料交给回答 Agent；保留前置检索，但不能把来自不同对象的结果混合作为确定答案。是否向用户澄清仍由正常回答流程处理。

字段合法只代表输出结构可用，不能证明改写语义正确；语义质量由专门案例验收。首版不增加第二个“改写评审模型”或自动修复循环。

## 模型调用、用量与过程展示

- 改写使用当前冻结的聊天连接，通过受限 AgentContext 申请普通 `model_call`，标记 `purpose=knowledge_query`。不把调用伪装成无成本的本地处理。
- 沿用 `guard`、`start_model`、输入输出限制、取消和 Run 总期限；与摘要及回答共用唯一 `RunUsage`。记录实际调用次数和已报告 Token；未知用量保留未知。
- 输出预算设置为适合短 JSON 的有界值，不超过本轮及连接支持的限制；需要给供应商思考模型留出预算，不能机械设置极小输出导致查询缺失。以实际请求和完成状态验收。
- 改写消耗现有模型调用额度，不暗中提高 `max_model_calls`。剩余额度不足以容纳改写及至少一次正常回答时，跳过改写并记录 `budget_skipped`，正常回答仍按现有预算守卫执行。
- 执行详情区分“检索问题改写”“知识预检索”“回答”。管理员按现有证据权限查看实际请求、改写结果和搜索参数；普通成员沿用已有公开动作投影。
- 改写 JSON 不通过 `report_content` 输出到聊天正文，也不能在恢复时被当作回答草稿。`restore_control` 需要排除查询准备模型动作的正文回放，但仍累计其用量。
- 请求和响应沿用现有证据文件采集。执行日志只记录安全事件及原因，不把对话正文、查询或认证信息复制到 JSONL。

## 持久化与恢复

### 阶段状态

在官方 checkpoint 中保存本 Run 的查询准备结果、输入指纹和预检索完成标记。新 Run 初始化必须重置这些字段，不能继承上一轮的查询或命中结果。两种模式、跨轮及中途恢复均要覆盖。

成功完成的查询准备决策还需与模型动作结束及用量一起，原子写入现有 `RunAction.result_payload`，用于覆盖“动作已完成、阶段 checkpoint 尚未提交”的窗口。这是执行恢复所需数据，不依赖可能采集失败的诊断证据文件。拟通过 AgentContext 的受限结束入口转交，SDK 文件不直接查询 ORM；恢复由 Store/RunTask 提供已确认结果。

使用既有 JSON 载荷及可选 checkpoint 字段，预计无需新增业务表或数据迁移。实施时若发现现有结构无法表达必要状态，应先修订本方案，不借诊断字段偷偷保存第二份业务状态。

### 恢复决策

| 中断位置                             | 恢复行为                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------ |
| 改写未开始                           | 从本 Run 初始化存档继续，按预算执行                                                  |
| 改写结果与用量已保存，阶段存档未提交 | 校验输入指纹后复用已确认决策，不再次调用模型                                         |
| 改写请求可能已发出，但没有已确认结果 | 保留原动作不确定状态；沿现有恢复及预算规则进行可记录的新尝试，不声称上游恰好执行一次 |
| 查询已存档，预检索未完成             | 复用同一查询；工具按既有只读恢复规则执行                                             |
| 预检索已完成，阶段存档未提交         | 用相同查询和稳定工具键复用已确认结果，复用前继续核验授权                             |
| 正常回答或后续工具阶段中断           | 恢复原节点，不能重新触发改写或首轮预检索                                             |

恢复复用前仍检查当前账号、连接、挂载和来源权限。缓存不是绕过撤权的通道；指纹冲突不能直接选一个结果继续。

## 跳过、失败与降级

| 情况                                    | 处理                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------ |
| 动态检索模式                            | 不执行查询准备或固定预检索                                               |
| 无有效历史／记忆重置                    | 使用原问题，零次额外模型调用                                             |
| 历史存在但当前问题已经完整              | 首版仍允许一次改写，由模型原样保留；不先增加意图或指代分类调用           |
| 输入或剩余预算不适合改写                | 使用原查询，保存明确的跳过原因                                           |
| 完整返回，但 JSON、长度或内容结构不合法 | 不自动重试修复；记录校验失败和已发生用量，保存使用原查询的降级决策后继续 |
| API 鉴权、连接、模型修订或网络错误      | 沿现有模型错误语义终止或恢复，不捕获所有异常后假装改写成功               |
| 取消、撤权、Run 超时、持久化失败        | 停止后续动作，不执行预检索或发布回答                                     |
| 知识库无命中、待处理或搜索失败          | 沿原检索结果和错误处理，不把它解释为改写成功或规定不存在                 |

降级后的检索查询沿用当前原问题前 1000 字符的规则，并在决策中标明是否发生截断。结构失败、预算跳过与上游故障不能混成一个“未命中”。

## 实施任务与归属

按下列顺序连续实施，每一步完成匹配的定向验证后再进入下一步。

1. **固定行为与样例。** 在现有虚构企业资料上准备连续追问、纠正、切题及歧义案例，保存变更前的实际查询作为对照。基准答案与试题放库外，不重新导入资料。
2. **接入图内查询准备。** 在 runtime 新增一个职责明确的前置检索中间件模块，使用官方钩子；调整 Agent 装配，原问题仍经官方消息 reducer 传递。固定提示词留在 prompts，查询结果类型留在实际所属模块，不建立通用编排框架。
3. **接入受管调用与恢复。** 复用 model_calls 的请求采集、错误转换和用量路径；仅在实际共用部分提取辅助函数。扩展 contracts、RunTask、Store 的受限载荷保存及恢复投影；验证首次调用前存档及动作／存档提交窗口。
4. **接回知识检索与临时资料。** 现有 presearch 接受准备后的 query；ReferenceContextMiddleware 从本 Run 状态读取预检索及歧义提示，保留已核验历史证据。缓存指纹、查询字符串和恢复结果保持一致。
5. **补齐过程展示与质量验证。** 在已有执行详情中识别改写动作，不新增配置页。用同一模型连接及冻结语料对照旧／新查询，记录查询准确性、命中证据、最终回答、增量耗时及用量。
6. **更新现行文档。** 行为实际生效后同步知识库、运行与执行证据契约及 runtime README；实际结果进入 records，方案状态和两个索引同时更新。

首版沿用现有检索策略和 Top-K，便于判断改善是否来自查询改写；效果问题不顺手扩成重排、知识入库或员工考核系统重构。

## 验证与完成标准

### 确定性执行测试

优先扩展[员工知识运行测试](../../backend/tests/test_employee_knowledge_runtime.py)、[记忆测试](../../backend/tests/test_runtime_memory.py)、[checkpoint 恢复测试](../../backend/tests/test_checkpoint_runtime.py)及[执行证据测试](../../backend/tests/test_execution_evidence.py)，必要时为查询准备增加小范围独立测试。

必须证明：历史来自正确基点；记忆重置不读旧消息；新 Run 不复用旧查询；动态模式及无历史场景没有额外调用；正常执行只改写一次，已确认结果恢复时不重调，未确认请求的新尝试单独记录；原用户消息不改写；模型／工具额度及用量准确；查询不冒充聊天正文；取消、撤权和权限隔离有效；格式失败按既定策略处理；各个中断窗口能够按表恢复，且没有本 Run checkpoint 时不会提前调用改写模型。

测试使用真实 SDK 图和隔离数据库，假模型只验证平台执行逻辑。包括改写结果持久化失败、动作成功后 checkpoint 失败、预检索成功后存档失败三个独立故障注入点，不仅验证理想顺序。

### 真实模型案例

| 案例                                     | 期望                                                 |
| ---------------------------------------- | ---------------------------------------------------- |
| 云帆／上海／住宿标准之后追问“超标怎么办” | 查询补齐公司、地点、费用对象，命中超标相关资料       |
| “不是云帆，是云舟”                       | 当前纠正生效，查询不继续限定为云帆                   |
| 出差话题之后明确问会议室释放规则         | 不沿用住宿条件                                       |
| 对话中同时讨论两家公司后问“它的标准呢”   | 不武断选择公司；保留歧义，回答不混用制度             |
| 首轮给出完整制度问题                     | 不额外调用改写模型，保持原查询路径                   |
| 跨摘要的追问、摘要未保留必要实体         | 使用可用背景，缺失条件不编造，不承诺恢复被删除的信息 |
| 历史助手回答含未经证实的金额             | 改写不将该金额升级为查询前提或制度结论               |
| 已有历史知识证据的追问                   | 历史证据仍按原机制核验，改写不影响引用资格           |
| 中文长消息、编号、否定及比较条件         | 不静默丢弃影响检索的已知条件，超限时可见地跳过       |

最小验收集覆盖上述类别，每类至少两种说法，并对关键指代、纠正和切题场景重复测试。上线门槛：平台边界测试全部通过；人工检查的查询不新增业务事实、不丢失当前纠正；目标追问相对旧路径确实改善；已完整问题无明显回退。任何误改写单独记录并修复，不能只用平均命中率掩盖。

相关静态检查执行 `make lint-backend`，文档执行 `make check-docs` 和现有 Markdown 格式检查；如改动前端过程标签，再执行前端定向测试及静态检查。真实模型测试单独记录供应商、模型、配置、材料版本和调用开销，离线测试不替代模型效果验收。

## 发布与兼容

新受理 Run 冻结查询准备策略版本；已受理的旧快照缺省沿旧路径执行，不在恢复中途增加改写调用或改变已缓存查询。运行内新字段使用可选状态并按 Run 重置。上线前覆盖旧快照恢复测试，发布时优先等待在途任务结束，避免切换图结构影响执行。

只有实际实施、定向测试及真实案例验收完成后，才更新为已实施并安排发布。回退应恢复旧版本的完整执行路径，并等待使用新图状态的在途任务结束；不能只删掉图节点后继续承接其未完成 checkpoint。
