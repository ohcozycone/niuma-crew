## 1. 标准、框架与平台的分工

| 层次                       | 负责                                                             | 不自动提供                                                         |
| -------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------ |
| Agent Skills               | 技能目录、SKILL.md 元数据与正文、支持文件的组织约定              | ZIP 安装接口、网页编辑器、账号绑定、统一装配参数表单、脚本运行环境 |
| Deep Agents                | SkillsMiddleware、按需披露、文件 Backend、显式指定技能等运行能力 | 本平台的上传存储、业务权限、共享资产编辑、文件向沙箱的自动分发     |
| MCP / LangChain MCPAdapter | 工具发现、参数结构与调用；由底层 FastMCP 处理传输和连接          | 平台用户所有权、员工许可、容器配额、第三方包在宿主的隔离           |
| 本平台                     | 能力库、员工装配、账号密文、允许范围、持久文件、执行和发布记录   | 不能通过一个配置文件声明尚未实现的运行能力                         |

Agent Skills 是目录格式，选择 ZIP 作为网页导入载体是平台产品决定。[标准](https://agentskills.io/specification)定义格式；[客户端接入指南](https://agentskills.io/client-implementation/adding-skills-support)定义发现、披露、激活及资源加载的常见路径。平台内自定义管理字段不是协议违规，但不能把它们当成所有外部包都具备的字段。

## 2. 当前创建表单与标准的对应

| 当前字段                     | 对应标准                               | 当前与目标差异                                           |
| ---------------------------- | -------------------------------------- | -------------------------------------------------------- |
| 技能名称                     | `name`，但当前 UI 是展示名称           | 标准名有格式约束并与目录同名；建议分开可读展示名与协议名 |
| 技能简介                     | `description`                          | 标准为必填，需描述用途和触发场景；当前允许空值           |
| 工作指引                     | SKILL.md Markdown 正文                 | 当前已进入运行快照                                       |
| 所需输入、交付内容、示例任务 | 没有同名标准元数据字段；可写为正文段落 | 当前保存展示，但未进入通用运行快照，应在迁移时合入正文   |
| 分类                         | 平台管理字段                           | 可保留在数据库；不是标准必填项                           |
| 启用、修订、装配人数         | 平台状态                               | 不属于 Skill 文件必需格式                                |
| 装配参数 JSON Schema         | 平台扩展                               | 标准没有统一的员工参数表单或变量替换协议                 |

标准另有可选的 license、compatibility、metadata 和实验性的 allowed-tools；不把它们作为上传即获取权限的依据。框架自己的 `metadata.include_tools` 等扩展也不等于跨平台通用授权格式。

当前实现并非完全没有使用标准：它将数据库记录临时生成为只有 SKILL.md 的技能目录，交给官方 SkillsMiddleware。缺口在多文件资产管理与完整正文转换，不能称为已支持任意标准技能包。

## 3. 导入与在线创建统一为同一份技能资产

### 3.1 资产结构

目标支持下面的技能目录，目录为拟议示例，不代表当前已有文件：

```text
report-analysis/
├── SKILL.md
├── scripts/
│   └── analyze.py
├── references/
│   └── calculation-rules.md
└── assets/
    └── report-template.html
```

scripts 是真实代码；references 是参考材料；assets 是模板、图片、数据等。资源可以随包保存，不因用户选择在线创建就失去这些能力；`resources/` 可作为附加目录存在，但不是必须使用的标准目录名，也不要与 MCP 的 resources 接口混淆。

### 3.2 导入步骤

1. 上传 ZIP 到临时区，不启动 Agent 或沙箱，不执行包内脚本及安装钩子。
2. 校验压缩前后大小、文件数、重复路径与路径逃逸；拒绝绝对路径、越界 `..`、链接和特殊文件。明确解析一个技能根；多个技能时列出选择，避免悄悄只装其中一个。
3. 安全解析 YAML 元数据，检查 SKILL.md；诊断格式错误及依赖环境。无法解析的必需内容拒绝导入，不擅自执行文件修复程序。
4. 显示预览：名称、简介、文件树、脚本及资源数量、环境要求、兼容警告。未知扩展字段与文件可保留原始内容，但不得因此激活额外工具、命令或权限。
5. 用户确认后，写入不可变文件目录与清单，再提交数据库引用。失败时不在能力库出现半份资产，孤立文件通过清理任务收敛。
6. 列表出现能力后仍需员工主动装配。仅声明“需要 Bash/某 MCP”不自动授予相应能力；缺少平台支持的要求，显示就绪问题。

### 3.3 轻量存储

继续用本机或服务器数据目录，无需新增存储微服务。默认文件放在可配置 DATA_DIR 下，数据库保存资产 ID、元数据、文件相对路径、大小和哈希等索引。底层字节读写可复用现有存储能力；技能文件引用和清理规则由 skills 拥有，不能直接套用仅面向个人附件/Run 的下载授权。

建议按 skill ID 和内容摘要保存完整目录；每次提交得到一份不可变内容依据，当前技能记录指向它。员工引用同一个技能 ID，Run 冻结内容摘要，防止运行中修改脚本导致一半新一半旧。这是技能文件一致性机制，不是复制员工或为每个使用者创建一套版本。

同一套配置在 Mac 和 Ubuntu 指向各自数据目录；导出恢复标准目录结构。备份包含数据库和技能文件，沙箱销毁不影响资产原件。

### 3.4 在线创建与编辑

在线创建先生成最小 SKILL.md，随后进入与导入相同的编辑页：基本元数据、SKILL.md 正文、文件树。支持新增脚本/参考文档、编辑文本、上传二进制资源及导出；图片等二进制先提供预览/替换，不假装可用文本框编辑。

简单表单可作为创建向导，将输入、输出、步骤和示例编成 Markdown；生成后以 SKILL.md 为内容来源。不同时维护一份可任意编辑的 Markdown 和一组要求自动双向解析的表单字段，否则会产生两个互相覆盖的真相来源。旧记录先明确编译为完整正文，保留原技能 ID 和装配关系。

员工参数继续作为平台装配数据独立注入，不覆写共享包，不把账号 Token 写入技能资产。参数 Schema 没有就不生成专用输入框。

## 4. 从标准包到实际执行

1. Run 准备：按员工装配与用户权限捕获技能 ID、内容依据、目录位置及非秘密参数。
2. 目录披露：先给模型名称、简介和可读取路径；只披露本次获准技能，不把所有完整正文和脚本塞进系统提示。
3. 激活：模型读取 SKILL.md；用户明确指定时，复用已有 pinned skills 流程。指令中的相对路径按技能根解析，读取 supporting files 时仍校验这份包的范围。
4. 只需文字推理或远程 MCP 时，不启动沙箱。需要执行代码时，通过平台 execute 工具申请沙箱。
5. 在首次实际执行前，把已激活包的脚本、模板及依赖文件复制或只读挂载到沙箱中约定的位置。模型的文件工具路径与 Shell 内的实际路径必须有明确一致的映射，不能把虚拟 `/skills` 路径当成已经存在的磁盘目录。
6. 脚本只在隔离环境运行，工作文件写到 workspace，成果写到 outputs。包原件保持只读，不自动把运行产生的修改写回所有员工共享的技能。
7. 保存 stdout、stderr、退出码和成果引用；有实际结果后交给模型继续回答，最后保存成果再回收环境。

官方 [Deep Agents Skills](https://docs.langchain.com/oss/python/deepagents/skills#sandbox-scripts)已经提供按需加载和 Backend 扩展；官方文档也明确，沙箱外的文件需要平台同步进去。保留当前 create_agent 加 middleware 的组装方式即可，不要求为了标准包改成整套另一种 Agent。

`compatibility` 是环境说明，不是可执行的依赖锁。requirements、package 清单、系统包等需由平台选定的镜像或明确的沙箱准备流程提供，上传时不自动安装。能力不满足时说明缺什么，不能回退到后端宿主运行。

## 5. stdio 复用官方实现

核查环境已有 LangChain 1.4.7、FastMCP 4.1.4，其 MCPAdapter 可以接收 StdioTransport。早期教程常见的 langchain-mcp-adapters 不是当前工程必须再引入的第二套实现。[当前官方 MCP 接入](https://docs.langchain.com/oss/python/langchain/mcp)与 [FastMCP transport](https://gofastmcp.com/clients/transports)分别解释适配层和传输层。

下面仅为可信隔离运行器内的 SDK 构造示意，包名与版本均为占位，不在本次执行：

```python
from fastmcp.client.transports import StdioTransport
from langchain.mcp import MCPAdapter

transport = StdioTransport(
    command="npx",
    args=["-y", "@vendor/mcp-server@1.2.3"],
    env={"SERVICE_TOKEN": selected_account_token},
    keep_alive=False,
)
async with MCPAdapter(transport) as adapter:
    tools = await adapter.list_tools()
```

直接把这段放在后端会在后端所在环境起进程，SDK 不自动为本平台创建容器。平台新增的是隔离启动与流连接，不是重写 MCP 协议：程序/参数用结构化配置，秘密来自选定账号；SDK 与进程在可信管理的运行边界里通信，再接回现有授权和结果记录。

脚本执行沙箱和 MCP Server 可以共享底层容器资源管理，但进程生命周期不同。MCP 的 stdio 是持续协议通道，不能当作执行一次脚本拿 stdout 文本；不同账号/会话的进程复用策略明确配置，资源满额排队，退出清理，恢复不重放副作用操作。选择会话持久化需要显式管理 transport 生命周期，不能只依赖 SDK 默认 keep_alive。

### 5.1 什么时候启动，以及一份实例包含什么

保存一个 stdio 配置只登记程序、参数、运行环境和账号需求，不创建常驻环境。首次目录发现需要临时启动实例，完成读取后关闭；后续普通列表读取已保存快照。真正调用时按需取得执行实例，同一受控 MCP 会话的多个工具调用复用进程和通信通道，不按工具数量起容器。

一个 MCP Server 可以提供五项或更多工具：仍然是一份 Server 进程，而非每项工具一份沙箱。配置数量、进程数量、隔离环境数量、活动任务数量是不同计数，不能相互等同。

stdio 协议本身只规定进程与通信，不强制容器隔离。[FastMCP transport](https://gofastmcp.com/clients/transports)管理子进程，但不自动提供本平台的租户隔离。云平台隔离由平台的运行策略决定。

### 5.2 首版按执行实例隔离，避免全平台共箱

建议首版以“实际使用者/信任范围 + 具体账号连接及凭证修订 + MCP 配置/包版本 + 运行会话”为隔离依据。账号是运行时解析出的本人或明确共用连接，不能拿创建者的模板账号代替使用者。

默认在同一 Run 内为实际使用的每个 stdio 连接建立独立实例，多次调用复用，Run 结束关闭；目录检查使用独立的短期发现会话。绑定账号相同也不自动在不同 Run 之间复用有状态进程。以后验证了服务无会话状态或实现了明确隔离后，再增加受限的空闲复用。

| 分配方式                                | 判断                                                            |
| --------------------------------------- | --------------------------------------------------------------- |
| 每登记一个 MCP 就常驻一个容器           | 不采用；登记不等于需要运行，闲置配置不应占用容量                |
| 按 MCP 包名全平台共用一个环境           | 不采用；同包可能有不同用户、凭证和文件范围                      |
| 所有 stdio 共用一个环境                 | 不作为多用户默认；进程、文件、凭证及资源相互影响                |
| 每个实际活动的账号/运行会话实例独立环境 | 首版建议，边界清晰；代价是增加环境数量和冷启动                  |
| 同一信任范围内多个受信 MCP 共用环境     | 可选后续优化；必须主动选择，不能仅靠分目录或不同 env 宣称强隔离 |

任务脚本环境与带凭据的 MCP 环境默认分开。同一容器、同一权限的进程可能读取其他进程文件或凭据；不能因为属于一个 Run 就自动认为两者可以安全混用。若选择共箱，需要独立证明进程、身份、文件与秘密边界，这不是现有沙箱文件路径检查所能提供的保证。

### 5.3 与两三个容量的任务沙箱方案如何结合

保留一个底层环境提供方和容量账本，上层区分两类用途：

| 用途           | 所有者与结束条件                         | 是否复用                                  |
| -------------- | ---------------------------------------- | ----------------------------------------- |
| 任务文件与脚本 | Run；保存成果并结束任务后清理            | 同一 Run 内连续命令复用                   |
| stdio MCP 进程 | 受控 MCP 会话；首版随 Run 或发现会话关闭 | 同一会话的工具调用复用，不默认跨 Run 共享 |

容量包含两类用途、创建中、清理中及结果未知资源。可以设置全局上限和用途上限；例如总量三份、任务至多两份、MCP 至多一份，只是小机器的示例，不是经压测的默认值。按逻辑隔离环境计数，网络等辅助容器及 CPU/内存仍纳入整机预算。

目录发现、任务环境和 MCP 实例都需经过准入；清理不等待业务名额。任务可能同时需要脚本和多份 MCP，会形成多资源依赖。调度器必须预留所需资源集合，或采用不会持有互相等待资源的分阶段策略；不能让所有任务各占一份脚本环境后，再永久等待没有剩余额度的 MCP。未知需求不足时应有界拒绝/重新调度，不能靠超额创建解围。

这沿用[沙箱容量方案](sandbox-service.md)的配额、队列、租约和清理原则，但扩展资源用途、账号身份和会话生命周期。逻辑隔离与独立微服务部署是两件事，首版可以在当前后端中维护模块边界，不要求先增加一套独立网络服务。

### 5.4 当前代码需要的实际增量

现有 SandboxResource 的 run_id 是必填、外键且唯一；SandboxService.acquire 按 Run 建环境，满额立即报错；sweep 在 Run 不活动时销毁。它适合当前一轮任务一份文件/脚本环境，不是通用 MCP 会话池。

stdio 实施需增加可登记的 MCP 执行实例和会话引用，保留账号、包/镜像、凭证修订、归属 Run（如有）、租约、远端资源、停止与清理状态。不能把账号 ID 冒充 Run ID 写进旧表，也不能让多个独立实例共用同一个唯一 run_id。任务与 MCP 各自维护生命周期，底层创建与总量控制统一复用。

当前默认 max_concurrency=1，沙箱等待队列与 stdio 均未实现；“两三个容量加排队”仍是目标方案。不能把已有 Run 队列当成沙箱资源队列，也不能直接把当前每次 invoke 打开 HTTP 会话的逻辑复制成每次工具调用启动新的 npx 进程。

### 5.5 运行器后端不必绑定 OpenSandbox

2026-10-29 选型补充，属于建议，未进行 Docker 或 Gateway 部署验证。区分协议客户端、隔离底座和资源管理产品：stdio 由官方 MCP 客户端处理，Docker 是可选的隔离底座，OpenSandbox 是环境管理与操作接口。MCP 托管不以采用 OpenSandbox 为前提。

| 路径                           | 适用情况                                              | 取舍                                                                                   |
| ------------------------------ | ----------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 官方 StdioTransport 直接子进程 | 本机自用、已信任的程序                                | 最少组件；继承宿主运行权限，不能作为云平台用户代码的默认隔离                           |
| 专用 Docker stdio 运行器       | 当前单机平台托管 stdio 服务                           | 保持原生输入输出通道，组件可较少；需要受信控制端管理限制、身份、容量、停止和清理       |
| OpenSandbox 托管 MCP 环境      | 已部署并验证统一环境平台，或有远程环境/多节点治理需求 | 可复用环境 API；仍需专用 MCP 会话及协议通道，不能复用有限命令输出当成 stdio            |
| 现成 Docker MCP Gateway        | 希望复用 MCP 容器生命周期和路由                       | 可作为运行器候选；需验证平台个人 Token、会话隔离、目录与授权映射，不能直接替代业务边界 |

对当前轻量开源平台，建议保留 OpenSandbox 处理 Agent 文件与脚本，stdio 采用专门的容器运行器接口，首个候选后端为 Docker stdio。它不一定是新增微服务，但 Docker 管理权限应放在受信控制端，不把 socket 交给 Agent 工作负载或由用户任意决定 Docker 参数。若现有部署要求业务后端不接触 Docker 控制面，应保留该边界，由控制服务提供窄接口；这项成本需纳入与 OpenSandbox 方案的比较。

技术上可由 SDK 启动受控的 docker 命令，保留交互 stdin，避免 TTY，分别处理协议 stdout 与诊断 stderr；[Docker run](https://docs.docker.com/reference/cli/docker/container/run)和 [attach](https://docs.docker.com/reference/cli/docker/container/attach/)提供标准流连接。使用固定并预先准备的镜像，进程 EOF 或 SDK 退出后仍由控制端核对容器终止，不能把结束 docker CLI 当成确认容器已销毁。

当前 SandboxFileBackend 的 execute 把 stdout/stderr 合并为日志，命令上限 60 秒；collect_outputs 会停止 UID 1000 的工作进程。这套任务操作语义不适合直接管理持续的 MCP 协议。需要复用 OpenSandbox 时，应创建独立的 MCP 执行 profile 和会话适配，通过受控双向通道或桥接访问，而非复用任务 execute。

共享的是镜像/部署策略、资源预算、观测和清理原则，不要求共用同一个生命周期对象。若 Docker 与 OpenSandbox 两个后端并存，必须显式合并资源记账或分配不会超出整机预算的用途配额，不能让两边分别独占同一份总预算。直接 Docker 也不会自动继承当前 OpenSandbox 的网络、runsc 和权限策略，需要独立配置与验收；更少的管理层不代表隔离强度自动相同。

Docker 官方 [MCP Gateway](https://docs.docker.com/ai/mcp-catalog-and-toolkit/mcp-gateway/)与[开源仓库](https://github.com/docker/mcp-gateway)提供容器化服务、路由与生命周期管理，可在锁定版本后做小范围 PoC。官方独立安装说明覆盖 Docker Engine 场景，不应要求 Ubuntu 用户安装 Docker Desktop；但本次未验证其个人凭证和多用户模式，不将它写成平台已支持的默认依赖。OpenSandbox 自己提供的 MCP Server 是“把沙箱操作开放为 MCP 工具”，也不能等同于“通用托管任意 stdio MCP”。

## 6. 当前不稳定的原因与证据层级

### 6.1 已确认的实现缺口

| 发现                                                         | 影响                                             | 对应改进                                               |
| ------------------------------------------------------------ | ------------------------------------------------ | ------------------------------------------------------ |
| 三项 Skill 输入/输出/示例字段没有进入通用快照                | 页面写了要求，模型却未必看到                     | 编译为完整 SKILL.md，并对编译结果与快照做定向测试      |
| 当前技能只生成 SKILL.md，没有多文件资产投影与沙箱分发        | 标准包中的脚本和相对引用无法完整运行             | 包清单、只读文件读取、按需物化到沙箱                   |
| 工具选择交给模型，返回非空正文即可进入成功发布路径           | 模型可能不调用工具就声称完成外部操作             | 对明确的外部任务建立执行要求与结果核验；不要只加提示词 |
| 工具结果模型预览前 18,000 字节，后续仅在有来源读取权限时可读 | 已保存全量结果不代表模型看到了尾部               | 有界分页读取或已有只读来源通道；明确结果覆盖范围       |
| 目录别名与补充说明只用于展示                                 | 修改中文说明不会改善模型的工具选择               | 文案说明用途；模型指引需单独设计并进入冻结依据         |
| 部分来源标签由工具名和非空内容判定                           | 取得正文不等于完整加载整页，更不等于语义回答正确 | 分开记录提取成功、模型实际读取范围与答案引用           |

2026-10-29 [复核](../../records/mcp-review-and-stdio-boundaries.md)另外确认：SDK 可以接收服务级 instructions，但平台只保存工具目录，未捕获服务说明，也未传给模型；已保存的 SDK metadata 在重新创建模型工具时也不继续携带。工具 description 和 input schema 的传递正常。output schema 保留在 raw_descriptor 中，并非完全丢失，但它不构成任务语义完成的证明。

建议把可选服务说明作为有来源、长度上限和确认依据的连接级内容捕获，再与工具说明及平台统一规则一起组织上下文。它属于上游内容，不能覆盖平台身份、权限和执行规则，也不能仅靠放进 LangChain metadata 就假定模型收到。服务不提供 instructions 时仍可接入；本次并未证明真实 Tavily 是否返回此字段，以及它是否导致了当时的漏调用。

这些是不同层次的问题，不能统一归咎于 MCP 或 Skill 非标准。当前远程 MCP 使用官方协议实现并有目录、账号与权限约束；当前 Skill 的可移植资产管理尚未完成。

### 6.2 需要评测的因素

模型的工具选择能力、第三方 OpenAI 兼容接口对工具/流式参数的支持、历史答复对当前判断的影响、相似工具描述的重叠，都可能影响行为。已有成功调用说明当前模型至少具备部分工具能力，但不能证明所有参数和多轮情景都兼容。本轮没有进行模型 A/B 或重复在线调用，不能把这些因素宣布为已定位根因。

## 7. 可靠性实施路径

### 7.1 先分清四种成功

1. 接入成功：能读取工具目录或识别技能元数据。
2. 触发成功：本轮确实激活所需技能或请求相应工具。
3. 执行成功：请求通过权限，目标工具取得可确认结果，脚本正常退出或上游业务成功。
4. 任务达成：结果覆盖用户目标，答案与实际结果一致，成果已保存。

页面和日志分别表达，不能用 Run 技术上 succeeded 代表四层都满足。

### 7.2 根据任务明确执行要求

自由对话保留模型的自主选择。产品提供明确的“读取网页”“分析附件”等任务入口时，由后端根据任务类型生成可验证要求，例如指定 URL 必须有成功提取结果、附件分析需对应输入和可确认输出；执行仍走相同授权、预算和审计入口。

对话中的自然语言意图可辅助分类，但不能只用正则“出现 URL 就强制读取”，也不能把另一次模型分类当成确定事实。用户明确选中的 Skill 直接 pin，减少重复猜选；未指定时用清晰的 description 与精简的工具集合辅助发现。

对于“读取网页”的明确任务，可采用读取节点后再进入模型总结的流程，避免是否调用完全靠语言模型；这是一类通用流程，不为每个站点写专用后端。

### 7.3 以真实记录核验交付

- 发布前核对任务要求与本轮记录的工具、目标参数、成功状态和来源 ID。不依赖模型自己声称已执行。
- 工具失败、账号缺失、结果截断或部分读取分别返回清楚状态；缺少必要结果时进行一次有界补执行，仍不满足则交付限制说明，不发布“已完成”的状态。
- 引用只能指向本轮或明确授权复用的实际来源；校验来源 ID 只能防止虚构引用，不能证明每一句内容都忠实，仍需质量评测。
- 提示词保留“不得假装执行”等规则，但不把它们当作强制执行机制。也不对所有问题强制 tool_choice=required，避免普通问答误调用和反复调用。

### 7.4 建立小而固定的行为评测

保留单元/集成测试验证权限和协议，再为模型行为建立固定任务集：普通聊天不调用、明确 URL 使用提取而非只搜索、要求尾部时读到尾部、网络失败如实说明、缺个人账号提示连接、显式 Skill 激活、Skill 内脚本执行、无脚本权限不运行。

每个情景记录模型与适配器版本、工具清单摘要、激活/调用轨迹、结果覆盖、最终回答和耗时；同题重复测试并比较模型，统计漏调用、错调用与无依据声称成功。LangChain 的 [Agent Evals](https://docs.langchain.com/oss/python/langchain/test/evals)支持轨迹匹配和质量评估；断言关键调用及参数比仅检查生成一段文字更有用。

## 8. 模块改动与验收

以下是拟议职责，不预先创建空实现文件：

| 模块                                    | 增量                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------ |
| skills                                  | 包导入/导出、元数据与清单、内容依据、在线文本/资源编辑；保持技能 ID 和装配关系 |
| files / 存储基础设施                    | 复用字节存储；新增技能资产引用与保留条件，不混用个人附件下载权限               |
| agents                                  | 捕获完整技能内容依据与装配数据；继续只授权已声明且获准的工具                   |
| agent_runtime.skill_loading / workspace | 文件发现、正文与资源读取、完整路径、一致内容与显式激活                         |
| sandbox 管理                            | 按需物化包文件、只读原件、隔离执行和成果保存                                   |
| tools / managed process                 | stdio 配置、官方 transport、隔离进程、生命周期与账号资源隔离                   |
| conversations / publication             | 明确任务的执行要求、结果覆盖核验和准确的完成状态                               |
| 前端技能与工具页                        | 同一包编辑器、目录展示草稿、准确的加载/执行状态，不制造按厂商定制表单          |

建议顺序：先修正文投递和结果可读性、建立行为评测 → 标准包存储与只读加载 → 在线多文件编辑与沙箱执行 → 受管理 stdio。页面密度与保存交互可沿[页面方案](capability-library-and-assembly-ui.md)并行整理，不以页面改版替代执行能力验收。

验收必须覆盖：旧 Skill 转换不丢字段/关系；ZIP 越界与超限拒绝；上传不执行；导入/在线创建导出结构一致；资源与 Shell 路径一致；共享原件不被 Run 改写；无授权执行被拒绝；取消与失败清理资源；stdio 多次调用/退出/身份隔离；明确读取任务无结果时不会宣告完成。数据库迁移和真实 Mac/Linux、外部模型/MCP 联调单独留证。
