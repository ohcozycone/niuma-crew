# 文档组织与维护

`docs/`按读者的问题组织产品、契约、架构与操作；源码旁README只解释独立实现机制。项目总入口是根README，任务入口是本文档目录。源码目录独立，不代表必须配一篇README。

## 正文的职责

| 位置              | 主要问题                           | 详细内容的边界                                           |
| ----------------- | ---------------------------------- | -------------------------------------------------------- |
| 根README          | 平台做什么、怎样启动、从哪里读     | 不累计近期变更和未来功能                                 |
| docs/product      | 建设目标、组织资产、员工设计与使用 | 解释资产复用与岗位装配；操作另列步骤，不讲底层算法       |
| docs/architecture | 系统协作、技术机制与工程取舍       | 解释部署、依赖和取舍，必要代码链接替代逐文件清单         |
| docs/reference    | 外部行为必须满足什么               | 权限、输入输出含义、状态、幂等、错误、兼容与限制         |
| docs/engineering  | 怎样开发和选择验证                 | 规则、原因、例外、工具实际覆盖                           |
| docs/guides       | 怎样运行、部署、备份和排错         | 可执行步骤、观察点、失败与恢复                           |
| docs/design       | 全站怎样保持一致                   | 设计语义和交互规范；数值仍由CSS/spec维护                 |
| 源码旁README      | 非显然的机制怎样实现               | 跨存储发布、恢复、SDK适配或自定义协调，不能重复契约      |
| docs/proposals    | 有效未实施增量是什么               | 当前差异、采纳程度、未定项、实现和验收计划               |
| docs/records      | 什么决定或验证值得追溯             | 少量决定、迁移恢复及关键质量证据；普通流水由变更说明承担 |
| backend/datasets  | 样本从哪里来、怎样审核与使用       | 保留来源、许可、题目/答案隔离及数据版本                  |

类型、字段、空值、默认和外键由schema、ORM、正式迁移和OpenAPI维护。文档解释业务含义与跨对象约束，不复制完整类型表。局部竞态、顺序及释放原因写在实现附近，并由对应测试约束。

## 什么时候保留README

源码旁README需要解释一个独立的实现问题，而且不能由当前契约、架构摘要或局部注释充分覆盖。普通CRUD、组件属性、路由和文件列表不单独支撑一篇文章。保留文档先讲正常输入到结果，再讲对象协作、原因和关键失败；不要求每篇套相同章节。

独立文档应用的构建发布入口，以及随数据分发的来源和许可说明，按各自读者保留。前后端开发统一从根命令进入，不再分别维护运行手册。

## 当前、未来与历史

当前正文描述已经实现的行为。方案注明设计状态、实施状态、实质更新日期与范围；部分完成应列剩余增量。记录注明日期、环境/源码依据、方法、实际结果及未覆盖范围。采纳不等于实现，源码接线不等于真实服务或部署已验收。

用户有效需求决定应有行为。发现文档和代码冲突，先区分需求、实际实现和差异，再修正相应一方；模型假设、旧建议和已否定方案不自动成为需求。历史通过结果不能代替当前验证。

## 修改和发布

1. 找到唯一详细维护位置。同一规则在其他文档只保留必要摘要和链接。
2. 新能力或实质边界变化先明确可实施增量；普通修复和视觉微调直接更新现行正文，不机械新建方案与验收文件。
3. 生效规则回写正文，完成或撤回的方案退出活动目录；原始研究、图、日志和历史恢复包按需进入独立`niuma-crew-archive`，不成为构建或理解当前行为的前置。
4. 调整正文、路径或章节时同步全部引用和文档站发布清单。设计文档在docs/design维护，CSS、组件和真实示例仍在源码中；生成目录不人工维护。
5. 运行`make check-docs`和匹配的格式检查；站点映射变化运行`make check-docs-site`。链接检查覆盖文件、锚点和导航，不证明业务事实。归档默认只计数，按需用检查脚本的`--check-archive`核对本机归档。

## 写作与方案骨架

中文Markdown使用一个一级标题；代码标识保留原文，代码围栏标注语言。仓库内链接使用相对路径，代码入口不维护易变行号。目录树使用text围栏与tree字符。示例使用虚构数据，不含秘密。

方案按实际复杂度说明：状态与范围、有效需求和当前差异、所有者和主流程、重要失败/兼容、可交付增量与验收、未定项。无关章节省略。图文一起维护，目标图明确未实施，不能由图中的模块名推断当前架构。

## 主题与命名

正文链接用于补充更具体的操作、规则或实现；返回概览和同级切换交给导航，不在每篇重复安排阅读入口。

根 README、本文档索引和文档站沿用同一套主题名称。主标题和导航使用准确的中文，代码标识及必要技术名称在正文首次出现时对应说明，不用抽象口号代替具体问题。建设中方向先在对应主题列问题与状态，有足够实现或实验依据后再独立成篇。

架构图与流程图沿用现有平台图的字体、日夜语义配色、线型和层次。图只在有助于说明职责或流转时补充，图源与正文一起维护；目标图明确区分未实施部分。
