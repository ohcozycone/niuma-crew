# 前端架构

前端以页面和用户操作组织数据。后端负责业务规则和运行，前端负责表单、导航、历史阅读、操作反馈及观察连接。二者通过面向用户操作的 API 协作，不按后端模块一一复制 Hook。

## 业务架构：从用户入口进入

| 用户入口       | 页面模块            | 给用户的结果                                                   | 对应后端能力                                            |
| -------------- | ------------------- | -------------------------------------------------------------- | ------------------------------------------------------- |
| 登录           | pages/signin        | 管理员密码或 GitHub 登录，建立当前身份                         | auth 与 API Cookie 适配。                               |
| 数字员工       | pages/agents        | 搜索岗位、编辑配置、选择能力、进入对话                         | agents，以及技能/模型/工具的选择数据。                  |
| 能力库         | pages/skills        | 检索技能和 MCP 服务，导入、编辑或同步技能                      | capability_catalog、skills；MCP 管理由 tools 页面接续。 |
| 大脑配置       | pages/brains        | 维护共享模型连接，检查连接可访问性                             | model_connections。                                     |
| 工具与本人连接 | pages/tools         | 管理服务/账号、确认工具清单，为员工绑定本人账号                | tools；员工许可及个人绑定归 agents。                    |
| 知识库         | pages/knowledge     | 本人资料库、文本上传、来源阅读和 BM25 检索；管理员维护全员规则 | knowledge 及文件接口；规则另调用 organization_rules。   |
| 对话记录       | pages/conversations | 提交、看进展、读历史、停止、重试和下载成果                     | conversations 及观察/文件 API；不直接连接模型 SDK。     |

路由定义在 [router.tsx](../../frontend/src/router.tsx)，工作台共享外壳在 [Layout.tsx](../../frontend/src/Layout.tsx)。帮助页解释操作；设计系统和头像页用于工程展示，正式业务不读取它们的演示数据。

开发热更新时，[main.tsx](../../frontend/src/main.tsx)通过 Vite 的模块生命周期数据复用同一个 React 根，避免入口重执行后留下两套页面外壳；路由模块替换时释放旧 router 的历史监听与在途导航。普通页面在主内容区滚动，对话在消息区滚动，外层始终只有一个工作台。

## 工程架构：状态从哪里来

| 位置                 | 用通俗语言说明职责                                      | 主要文件与依赖方向                                                                   |
| -------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| main、router、Layout | 启动应用、决定 URL 打开哪个页面，提供共同导航及访问边界 | 路由装配页面；Layout 组合身份、工作台数据、工具栏及编辑保护。                        |
| pages                | 完成具体用户操作                                        | 页面私有组件和 Hook 就近组织，依赖共享组件、状态和 API，不把私有实现变成跨业务接口。 |
| components           | 多个页面共用的展示和交互                                | ui 适配基础控件；业务组件可读相应共享能力，基础控件不负责登录或业务流程。            |
| state                | 让具有共同生命周期的数据保持一致                        | 身份、主题、工作台数据、编辑保护各自管理，作用域不同，不集中成一个全局表单对象。     |
| hooks                | 复用没有特定页面归属的 React 行为                       | 如 URL 条件与草稿；业务私有 Hook 留在页面模块。                                      |
| lib/api、lib/models  | 发请求、转换接口数据、提供普通类型和规则                | 不反向依赖 React 页面、Provider 或 Hook；调用者管理显示和生命周期。                  |
| design-system        | 为文字、颜色、空间和控件外观提供共同含义                | 组件消费令牌，展示页验证效果，数值只维护一个来源。                                   |

例如收藏一位员工时，页面调用员工数据对象提交目标值，数据对象处理请求、版本和共享记录，目录及侧栏订阅同一员工摘要。页面不分别维护两套收藏事实。具体代码由[共享数据说明](../../frontend/src/state/README.md)展开。

### 两类主要交互怎样落到代码

配置编辑沿「页面表单 → 所属数据操作或 API 客户端 → 后端业务服务 → 已确认结果」完成。URL 保存筛选/分页，表单持有未保存输入，编辑保护协调离页；服务端版本冲突不能靠覆盖本地缓存解决。

对话沿「页面 → ConversationProvider → 会话控制器与传输接口 → 接受确认/快照/SSE → 消息订阅」完成。`useConversation` 提供当前会话操作和消息顺序，`useMessage` 只读指定消息及其操作资格。持续变化的正文按消息更新，不让整个历史列表承担每段文字的重渲染。实现见[对话模块](../../frontend/src/pages/conversations/README.md)。

### 为什么采用当前分层

页面按用户工作组织，便于把表单、URL 和反馈放在同一处理解；共享数据按真实记录及身份作用域组织，便于目录、侧栏和编辑结果一致；HTTP 客户端独立于 React，便于核对协议和测试转换。代价是新增共享数据时必须声明更新关系，复杂交互也仍需要取消、版本和旧请求保护。

并非全部资源都已经进入工作台共享数据。大脑和工具等页面仍有自己的读取/编辑状态；共享范围变化时沿现有标准接入，不凭目录相似强行归并。技术选择及取舍见[系统架构](overview.md#技术选型及当前取舍)，具体代码约束见[工程手册](../engineering/frontend.md)。

## 当前实现与目录

React 页面位于 pages，共享业务展示位于 components，HTTP 客户端与普通数据转换位于 lib/api，具有明确共享范围的身份、主题、工作台共享数据和编辑保护位于 state。具体工程规则见[前端手册](../engineering/frontend.md)。

员工、方法分别使用 agents/skills API 客户端；导航查询归 navigation，身份值归 identity，安全返回地址归 navigation。配置摘要类型与完整编辑类型分开，摘要没有工作指令等必填保存字段。

## 页面、身份与状态

[工作台共享数据](../../frontend/src/state/README.md)采用 Context 提供固定实例、普通 TypeScript 对象管理数据与操作、useSyncExternalStore 按记录或查询订阅。员工目录与侧栏共用按 ID 的摘要和收藏查询；技能目录、详情、能力库及搜索复用读取生命周期。写操作由所属数据模块统一处理，跨业务更新关系集中在 WorkspaceData；页面 Hook 负责 URL、表单、离页保护和展示组合。收藏只提前切换星标，服务端确认后同步记录及筛选成员；刷新与失败保留已有卡片。业务交互见[员工模块](../../frontend/src/pages/agents/README.md#目录读取与收藏同步)。

失败沿`ApiError → Failure → 原状态拥有者 → lib/failures → FailureState/FailureNotice`传递，保留来源、状态和安全诊断。展示组件不拥有请求或自动恢复；刷新、草稿、身份撤权和会话核对继续由原模块负责，具体边界见[访问异常标准](../reference/failures.md)。

编辑器通过 useEditingRegistration 注册 dirty、saving、同步状态判断和丢弃回调。外壳统一处理页面离开和 beforeunload，调用编辑器自己的回调清草稿，不从 URL 猜测草稿键。展示使用订阅快照，实际导航与退出判断通过 isDirty/isSaving 读取当前登记状态，避免保存确认后仍使用上一次渲染的脏标记。登录身份变化会重建工作台作用域，旧请求结果不能写入新身份。

知识库上传由身份作用域的 `KnowledgeUploadQueue` 持有文件、固定目标库和请求控制，Layout 挂载非模态浮层。路由或浮层订阅结束不取消上传；退出身份则清队列并尽力中止在途请求，忽略迟到响应。刷新、关闭浏览器仍可能中断未确认传输，不能据此认定服务器没有保存；处理批次另由服务器持久执行，见[知识库契约](../reference/knowledge.md)。

## 对话读取与提交确认

useConversation 负责整段交互，useMessage 负责一条消息的稳定读取和操作。内部 useConversationController 组合待确认提交、历史与回复观察；useResponseSubscription 只观察一个助手回复，不创建工作。

页面通过 ConversationTranscript 接入正文与问答导航。其私有阅读逻辑统一维护节点登记、可见组与历史定位后的滚动/聚焦；消息行显式登记归属，导航只消费会话标识、可见问题 ID 和定位控制。目录/预览读取与正文窗口保持独立，定位失败只来自历史层，不另建全局状态或重复网络生命周期。接入与清理约束见[模块说明](../../frontend/src/pages/conversations/README.md#问题导航与消息窗口)。

首屏使用同事务 snapshot。历史、接受结果、请求核对、单回复 GET 与 SSE 使用同一种助手读取格式；正文由服务端选好，页面不再在 result、current_model 和 assistant_content 之间判断。对话摘要版本和回复版本分别合并，迟到结果不能回退当前活动目标。

待确认存储位于 pendingSubmissionStorage。网络结果未知时用原键核对或重发；显式重试失败回复使用新键。旧版尚未接受的 Run 目标重试不能自动转换时保留记录并只读核对。

## 开发和生产

开发使用 Vite 3000 和后端代理；完整启动器会把实际后端地址传入 Vite。生产由后端 frontend_delivery 显式接收构建目录进行同源交付。URL 按页面组织，API 按操作组织，内部目录调整不要求同步重命名所有页面。

## 工程标准与验证

ESLint 检查依赖、组件与 Hook 归属；TypeScript 验证摘要/详情和回复结构。

## 执行过程展示

消息行展示正文、状态、用量与错误，执行过程展示已保存的真实动作。UI 可折叠和分页步骤，但不会把工具请求的过程文字作为最终答复。历史回复是否能重试以服务端 can_retry 和当前消息状态共同判断；已退役试验只读，不恢复报告入口或重新执行。
