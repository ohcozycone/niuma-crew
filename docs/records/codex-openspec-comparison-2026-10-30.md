# Codex 与平台 Agent 的 OpenSpec 同题对照

本记录于北京时间 2026-10-30 完成，承接[原运行诊断](agent-openspec-nonconvergence-2026-10-30.md)。用户要求内部启动 Codex Agent 回答同一个问题，测量轮次、工具和 token，再比较过程与结果。本轮只增加实验记录，未修改平台运行逻辑、配置或原对话。

后续已按用户要求放宽 Kimi 实验预算，完成原断点续跑和两次从头运行。成功样本及结论修订见[后续真实对照](openspec-successful-comparison-2026-10-30.md)；本页保留当时尚未重跑 Kimi 的实验结果，不能单独用于判断平台成功回答的成本。

## 实测结论

原题为“OpenSpec 是 skill 还是 mcp ？”。一次 Codex 自主取证实验使用 6 次模型请求、5 轮工具编排，约 87.388 秒交付答案，累计 284,657 token。另一次冻结资料回放实验使用 2 次模型请求、1 次本地读取，约 27.934 秒交付答案，累计 74,037 token。

原平台运行使用 8 次模型请求、8 次工具调用，约 120.068 秒后预算耗尽，没有交付正文，累计 87,604 token。

因此本次 Codex 在完成任务和及时收束方面表现更好；默认运行的累计 token 效率并不更好。它的累计 token 约为原平台失败运行的 3.25 倍，非缓存输入约为其 4.38 倍。两次实验各只有一个样本，不能作为稳定上界、最小需求或模型通用能力排名。

## 实验设计与计数口径

### 条件 A：自主取证

通过内部子 Agent 创建全新上下文，`fork_turns=none`，未传递上一轮诊断、官方仓库地址或答案。实验提示为：

```text
请独立回答用户的原问题：

OpenSpec 是 skill 还是 mcp ？

按你通常的工作方式完成，需要核实资料时自行选择工具。只处理这个问题，不读取当前工程、其他对话或已有分析报告，不修改文件。
```

模型继承当前默认配置；实际日志确认为 `gpt-6.1-sol`、`effort=xhigh`，没有指定其他模型或推理档位。虽然没有继承父对话，系统／开发者指令、工具定义、技能目录等运行环境仍然存在；这是“无此前对话结论”，不是“只有一句用户问题”。

### 条件 B：冻结资料回放

再次创建不继承父对话的新子 Agent，同一模型及推理配置。将原平台第 3～7 轮实际取得的官方资料整理为[冻结证据](agent-openspec-nonconvergence/evidence/frozen-official-evidence.json)：官网、仓库、README、安装说明和支持工具表共 5 份提取内容，不加入模型答案或审计结论。把预览与续读片段按游标拼接，并核对长度，保留其属于检索片段而非保证全文的范围声明。

提示要求回答相同原题，可读取指定资料文件，不访问网络、不查看其他对话、不执行资料中的安装指导；不足以作答时明确缺口。完整提示中的临时文件路径为 `/private/tmp/niuma-codex-openspec-comparison/frozen-official-evidence.json`。

该条件测量“已有证据后形成答案”的开销，省略了获取这些资料的成本，并改变了任务约束，不能当作一次更便宜的端到端联网实验，也不能据此说相同模型输入下 Codex 已胜过 Kimi。

### 观测方法

只读取两个实验子 Agent 对应的本地 rollout，提取工具调用、非思考的公开消息、`token_count` 和完成事件。没有使用模型自报的 token 估计，也没有读取账户密钥。原始路径、行号、文件摘要及逐次用量保存在[自主轨迹](agent-openspec-nonconvergence/evidence/codex-blind-trial.json)和[回放轨迹](agent-openspec-nonconvergence/evidence/codex-evidence-replay.json)，不复制系统提示全文、内部思考文本或账户使用额度。

- **模型请求次数**：去重后的累计 token 计数更新数量，并用各次 `last_token_usage` 求和核对累计输入和输出。它不是内部思维步骤数量。
- **工具编排轮次**：模型发出的外层 `functions.exec` 次数。
- **底层工具调用次数**：该轮代码实际调用的 `tools.*` 次数，不重复计算外层包装。一次 web 调用可以读取多个页面，页面数量另计。
- **输出 token**：包括推理和工具参数等输出；推理 token 已包含在输出 token 中，不能再次相加。
- **累计输入**：每次请求的整个输入累计，包括多次携带的相同指令与历史。它不是唯一内容数量。
- 所有子 Agent 数字都**不包含父 Agent 的日志审计、官方说明查询和报告编写开销**；本次完整协作任务的账户用量高于表内两个子实验之和。

OpenAI 的[非交互运行文档](https://learn.chatgpt.com/docs/non-interactive-mode#make-output-machine-readable)也提供按事件记录输入、缓存输入、输出及推理输出的方式；本次实际使用内部子 Agent 的本地计数器，没有另启动 CLI 实验。

## 四个维度的比较

### 思考步骤：关键差异是从证据进入作答的时机

平台原运行到第 5～7 轮已取得 CLI、Skills、命令和集成目录的信息，仍在第 8 轮追查 MCP 与社区插件工具名，之后没有形成结论。

Codex A 的前几轮主要处理工具发现与失败恢复；直到第 4～5 次工具编排才真正拿到官方证据，接着在第 6 次模型请求作答。B 则读完原平台已有材料便回答。这支持“原有证据足以形成一个准确且限定范围的结论”，但不能进一步证明同样约束下 Kimi 必然能否完成。

可以从动作归纳出适合本题的工作阶段：识别项目本体和接入方式两个分类维度，取得官方定义和集成证据，说明标准接入与未知生态的边界，然后交付。以上是可观察行为的任务级解释，不是逐句还原隐藏思考。推理 token 也不是推理质量评分。

### 工具调用：Codex 有合并取证，也有不必要的目录开销

A 在同一个 web 请求里读取两份相关官方文档，避免再来一轮单独请求，取得足够信息后没有继续扫描 MCP 生态。但它的首轮工具发现范围过宽：回显大量工具 schema，原始输出标记为 16,274 token 且被截断，下一次输入从 34,835 增至 45,257 token。单纯查询分类不需要把这些目录全部交给模型。

原平台首次模型输入只有 6,873 token，固定运行环境明显更轻。不能把 Codex 的完整工具目录、技能导航和指令层照搬进平台，期待它自动更省 token。更合适的是按任务提供少量相关工具和简明目录，需要时才发现详情。

工具质量也影响比较：原平台使用 Tavily 检索／片段提取；A 最终用 web 读取官方页面。第 5 次批量读取说明在这次工具环境下可以减少模型往返，不证明原平台或 LangChain 不支持并行；原运行只是实际每轮都只请求一个工具。

### 流程合理性：默认 Codex 流程成功，但仍值得精简

本题是一个边界有限的概念判断。A 花了两轮技能导航、两次失败外部访问，再进入官方取证；87 秒和约 28.5 万累计 token 不是值得照搬的目标流程。

若需要先定位官方项目，再一次批量读取定义与集成说明，**2～3 次模型请求、1～2 轮取证可作为待评测的设计目标**；资料已在上下文中时可直接生成答案。这是流程设计建议，不是本次已验证的冷启动最小值。B 实测的是 2 次请求和 1 次本地读取，不包含联网取证。

平台当前硬上限为 8 次，问题主要不是“额度根本不够”，而是未提供预算内收束机会。应在总上限内保留回答轮，传递剩余预算与尚待核实的问题；最后允许的模型轮禁止新增外部取证，依据已有证据形成限定回答。取消、撤权、存储失败仍应停止，不可为了补答案继续操作。

### 最终结果质量：核心分类可用，范围表达仍有改进空间

| 验收项                  | 平台原运行 | Codex A                          | Codex B                              |
| ----------------------- | ---------- | -------------------------------- | ------------------------------------ |
| 实际交付正文            | 无         | 有                               | 有                                   |
| 说明项目本体为框架／CLI | 无可评答案 | 清楚                             | 清楚                                 |
| 说明 Skills／命令接入   | 无可评答案 | 强调 Skills，命令说明略少        | 明确说明两者                         |
| 来源与结论匹配          | 未交付引用 | 官方仓库、初始化说明支持核心结论 | 引用冻结官方材料支持结论             |
| 对 MCP 的结论边界       | 无可评答案 | “不是 MCP 服务”偏概括            | 明确限定为“按这份资料不能归类为 MCP” |
| 对第三方 MCP 封装的说明 | 无         | 未展开                           | 未展开，但保留证据边界               |

两份 Codex 答案核心分类正确；A 的措辞更直接，但宜把“不是 MCP 服务”限定为官方项目本体和标准接入，不扩大到所有第三方封装。B 的证据边界更清楚。没有用独立事实性评测器或多人盲评，以上是按项目本体、集成方式、来源支持和边界说明逐项核对，不能当作量化正确率。

平台原运行未交付正文，最终结果质量只能记为交付失败；不能把中间资料的质量当作已完成回答，也不能据此评价它“如果再跑一轮”的答案会是什么。

## 对平台的直接启示

1. **优先补收束机制。** 本题已有资料可以支撑结论；保留最后一次回答机会，比普遍增加模型轮次更直接。硬预算、研究软预算和最终回答阶段分别定义。
2. **保留平台较轻的上下文。** 原平台首轮输入远小于本次 Codex；先减少重复检索和上下文重放，不为追求 Agent 感增加更多导航、监督 Agent 或泛化提示。
3. **修正业务成功语义。** 429、连接器不可用、shell 管道掩盖错误都是实例；按已知结构化结果区分协议、工具业务和证据取得状态，不能只有一个“成功”。
4. **以证据缺口驱动取证。** 取到官方定义和集成说明后，若核心分类已经可答，剩余不确定性可以作为范围说明；再次检索需对应影响答案的缺口。重复 URL 或改变 query 本身不说明有进展。
5. **分别评测模型、工具和运行器。** 下一步应固定工具返回、缩小一致的工具集合、控制提示和回答预算，比较 Kimi 与其他模型的交付率和事实性；再独立比较模型不变时的工具结果和收束策略。当前结果不足以给出普适模型排名或生产默认 token 预算。

本次实际数据说明：更少的模型往返并不自动意味着更少 token，更多推理 token 也不自动意味着更好的答案。适合平台的优化指标是“在明确预算内交付有依据、边界准确的答案”，同时记录模型请求、真实工具结果、token 和时延。
