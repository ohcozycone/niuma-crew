# 对话协作复盘与经验沉淀

设计状态：待评审方案。实施状态：未实施。更新：2026-11-08。范围：共享对话阅读、围绕执行证据讨论问题、Agent 独立分析、原发起者修正与验证，以及员工经验的整理和显式复用。本次只形成方案，不改变现行权限、数据和执行行为。

## 1. 目标、有效需求与首个验证场景

目标是让参与者共同检查一项工作的交办、执行和交付，把发现的问题转化为有依据的修正，再保留可复用的方法。收益看问题是否被发现、交付是否改善、同类错误是否减少，不以评论量和模型回复量衡量。

### 1.1 用户已明确的要求

1. 对话属于发起者，其他人能从列表进入阅读；只有发起者能在主对话发送。
2. 参与者可以针对用户要求、模型回复及执行过程提出问题，尤其关注绕路、工具调用或返回异常、交办方向偏差和模型理解错误。
3. Agent 能基于关联的上下文和评论参与分析；评论应帮助发起者发现问题、优化流程并形成经验。
4. 首先明确可实施的首版范围，本轮不写业务代码。

以下角色分工、共享证据方式、状态和发布规则是本方案的建议，不视为用户已批准实施。

### 1.2 首个完整用例

甲让员工统计一份名单。执行成功并交付了总数，但工具实际只返回第一页。乙在该工具动作下提出：“返回中还有 next_cursor，为什么这里按完整名单统计？”

预期链路：乙关联动作并提出问题 → 补齐可共享的参数及结果证据 → Agent 判断是否漏取分页并标明受影响结论 → 甲确认后补充修正要求 → 产生新的查询和统计结果 → 甲按完整性标准验证 → 整理“分页结果完整性检查”经验 → 后续同类任务显式引用。

同一链路还应覆盖“重复调用但最终结果正确”和“用户交办方向偏离目标”。不能只支持抛异常的失败 Run，也不能默认提出的问题一定成立。

## 3. 首版交付范围

### 3.1 必须一起交付

| 能力               | 首版边界                                                                                                                                                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 共享阅读与本人操作 | 全部有有效会话的访问者能看对话列表和正文；成员新增跨账号阅读；游客保持只读。正式关联的输入附件与交付文件随对话共享，原始工具 source 不因关联 Run 自动共享；个人知识库和账号管理权限不扩张。管理员也只能操作本人主对话 |
| 问题讨论           | 围绕已结束的对话 Run，支持整体交办、用户输入、最终回复和具体动作；根评论形成一个复盘问题，参与者可继续补证、回应和质疑                                                                                                |
| 协作证据           | 所有人可读已有公开动作信息；发起者可查看本人 Run 的工具证据，并选择摘录发布给讨论参与者。完整模型请求和技术日志继续使用原诊断权限                                                                                     |
| Agent 分析         | 在问题讨论中显式触发；使用原员工的当前可用模型连接，在独立复盘模式中分析已共享材料，不调用原任务工具或个人知识库                                                                                                      |
| 修正与验证         | 发起者确认问题、编辑修正草稿，在原对话新增一轮或显式新建关联对话；关联新执行及验收依据，保留原错误结果                                                                                                                |
| 经验沉淀与复用     | 基于已解决问题整理经验草稿，管理员审核发布；员工页可查看及按关键词查找，交办时显式引用生效版本                                                                                                                        |
| 可发现性           | 列表和员工页显示待处理问题数；发起者可筛选“我的对话中待处理的问题”；问题详情能跳回准确输入、回复或动作                                                                                                                |

“已结束”指 Run 已达终态，且对话接纳不再 pending；接纳失败也可复盘，并明确其成果尚未正常交付。首版不支持执行中打断或插入评论指令。甲的新一轮仍在运行时，乙可复盘前面已经结束的一轮。

### 3.2 首版不包含

- 实时多人接管主对话、委派其他人替发起者执行、修改历史输入或交付正文。
- 从旧动作或任意 checkpoint 回滚、编辑工具参数后重放某一步、自动重做外部操作。
- 自动扫描所有任务、每条评论自动唤醒模型、Agent 自发诊断自己的诊断。
- 源码检索、联网查证、后台自动修复、私有资料代查及高权限诊断结果自动公开。
- 经验自动召回、自动修改岗位/技能/全员规范、自动训练模型、完整记忆系统。
- 多租户、组织成员模型、私密/公开混合空间、评论附件上传、点赞排名和复杂工单流转。

首版面向当前单平台共享案例。历史对话在成员侧也将进入共享范围；实现时必须明确升级后的可见性变化，不能宣称旧数据仍按本人隔离。若部署中已有不能共享的历史，需要先完成数据筛选或迁移安排，再启用共享范围；本轮不擅自修改历史可见性。

## 4. 评论怎样关联执行过程

### 4.1 一个问题拥有稳定目标，可附多个证据引用

根评论建立复盘问题，后续评论、分析和修正围绕这个问题追加。首版建议一个问题只讨论一个主要缺陷；相关问题可互相引用，重复问题关闭时指向保留的问题。

问题类型可选“流程效率”“工具调用与结果”“交办与理解”“其他”，用于列表和经验筛选；不要求提问者先准确分类，也不靠类别直接推断根因。

| 评论入口           | 保存的主锚点                                    | 定位及解释                                                           |
| ------------------ | ----------------------------------------------- | -------------------------------------------------------------------- |
| 对话整体“发起复盘” | conversation_id ＋截止 run_id                   | 讨论交办目标或流程；明确分析截止哪次已结束执行，不随主对话继续而漂移 |
| 某次用户提问       | conversation_id ＋用户 message_id ＋对应 run_id | 适合指出目标、约束或验收口径有误；重试后仍指向当时选择的尝试         |
| 某条模型回复       | conversation_id ＋response_id/run_id            | 适合结论错误、遗漏和理解偏差；不能用“最后一条回复”代替标识           |
| 某个执行动作       | conversation_id ＋run_id ＋action_id ＋关注面   | 关注面区分动作本身、请求参数、返回结果；工具成功也能提出业务质量问题 |

服务端验证 conversation → input/response → run → action 的真实归属链。action_key、序号和父动作用于展示及辅助定位，数据库动作 ID 为稳定引用。不得接收任意 file_id 后直接读取证据。

文字引用首版保存原文摘录及其来源标识，不承诺字符范围批注。动作结果中的具体问题可附 JSON Pointer，例如 `/payload/next_cursor`，并记录原证据 hash、采集阶段和摘录；界面定位不到时仍能展示准确来源，不猜测新的位置。

### 4.2 原始证据与协作证据分开

已有 evidence 可能包含原始参数、个人资料或完整系统输入。现有脱敏只覆盖已知凭据字段与 Bearer 字符串，不能识别任意自然语言秘密。因此首版采用显式发布工具证据摘录，不把所有原始 evidence 开放给成员。

1. 已有公开动作摘要可直接用于评论；缺少具体参数或结果时，参与者在问题中请求补证，先保留待核实结论。
2. 新增“读取本人对话工具证据”的窄权限，仅允许原发起者读取该 Run 的 tool_request、tool_response 及必要的已保存工具反馈；不授予模型完整请求、全员规则或他人的诊断资料读取权。
3. 发起者从已采集的 JSON 选择与问题有关的字段/片段，预览共享副本并显式发布。发布记录保存发布人、来源 Run/动作、方向、JSON Pointer、来源 hash、脱敏版本及摘录字节；成员和游客只能经讨论关联读取该副本，不能借此下载原文件。
4. 自由文本补充标为“参与者陈述”。系统可验证的摘录标为“执行证据”；已保存恢复反馈另标“恢复记录”。三者不能混为真实上游结果。
5. 截断、证据未采集或来源不可读时明确显示限制；不把局部摘录称为完整返回，也不让 Agent 推断缺失页中具体有哪些数据。

大工具结果可能另存为 purpose=source 的文件，必须纳入同一规则：本人可经已验证的动作关联选取片段，其他人只读已发布片段；已有诊断权限继续按该权限读取。收紧现有“source 属于该对话的 Run 即可下载”的分支，不能只保护 evidence 接口而留下原始结果下载旁路。真正作为正式输入附件或交付文件发布的内容，按其明确的共享关系读取。

分页用例只需共享 page_size、next_cursor、实际返回条数和必要统计字段，无需公开整份名单。重复调用用例可共享两次参数及对应结果摘要。若无法共享判定所需证据，问题可以保持待核实或说明原因后关闭，不能生成“已确认根因”。

共享片段支持发布者撤回并保留占位和记录；依赖它的分析及经验标为依据已撤回，停止作为新分析或新交办的输入。含该片段内容的已生成分析和经验正文同步停止共享，待重新审阅后发布新版本。已经被人阅读、下载或发送给模型的内容无法收回，界面不承诺撤回能抹除这些副本。人的自由文本若包含应撤回内容，需撤回对应评论。

## 5. Agent 怎样参与分析

### 5.1 显式请求、独立执行

评论默认只保存，不触发模型。任何有讨论和执行权限的成员，包括原发起者，都能点击“请 Agent 分析”；游客不能触发。首版使用该对话原员工，不增加第二个专职诊断员工选择流程。

分析者显示为“某员工 · 复盘分析”，不声称复述当时的内部思考。使用该员工当前可用模型连接及当前有效的运行规则；原岗位、模型、技能版本和公开材料是分析对象，不能将当前配置反推成历史配置。员工停用、模型不可用或预算不足时，保留人的讨论及证据，分析单独失败。

每次分析新建 origin_kind=review 的 Run，owner 和发起会话属于点击分析的人；通过复盘业务关联原 conversation/run，不创建主对话 Message 或 ConversationRun，不改变主对话最近回复、活动占用、问答轮数和排序时间。该归属不能阻止其他有对话阅读权的人经复盘业务读取已共享分析。

每次分析使用独立执行线程，不继承原任务 checkpoint，也不继承其他人的工具、工作区、技能或个人知识。一个问题同时只允许一个活动分析，主任务与分析可独立运行；分析用量计入实际触发者的既有用户容量及独立 Run 预算。

### 5.2 固定并展示本次分析依据

服务端在受理事务确定问题修订及证据清单，保存以下有界输入：

- 根评论、明确选入的讨论及已有关联修正；Agent 旧分析标为建议，不能升级为原始证据。
- 目标用户输入、目标回复、截至锚点的相关已保存历史。默认从目标一轮开始，参与者可选择此前有关联的轮次；不自动带入后续主对话或全量历史。
- 目标 Run 的公开事实、相关动作及必要父子关系，以及显式共享的证据片段。
- 已知缺口：未授权、未采集、不可读、截断、未选入、配置版本差异等。

界面先预览输入来源；受理时重新核对引用和共享状态，保存标识、版本、hash 及实际发送内容。超过既有 context_bytes 时要求缩小范围或补充精确摘录，不静默截断关键参数。新评论和后来补证不会悄悄改变已经接受的分析；再次分析生成新 Run，并显示依据的变化。

第一版模型只分析送入的材料，没有通用查询工具、MCP、文件写入、沙箱或个人知识检索能力。固定复盘指令要求引用证据、区分事实与假设并指出验证条件；原任务文本、工具结果和评论属于待核对材料，不能覆盖分析模式或授予权限。该限制要由执行策略强制，不能仅靠提示词中的“请勿调用工具”。

现有 tools_enabled=False 可复用禁用业务装配的路径，但当前配置仍使用岗位指令，不能原样当作复盘模式。实施需新增受管的复盘指令组合及用途校验，并在受理、启动、模型动作与成果公开时复核。客户端不能自由提交工具开关、系统指令或运行身份。

### 5.3 分析输出及效力

| 输出       | 要求                                                                                  |
| ---------- | ------------------------------------------------------------------------------------- |
| 判断       | 分别说明有证据支持的问题、目前不成立的指控及仍待核实的部分；证据不足允许没有结论      |
| 事实与依据 | 每项指向用户输入、回复、动作或共享证据片段；校验引用确实属于本次材料，不能虚构动作 ID |
| 影响范围   | 具体哪些结论、文件或后续步骤受影响；绕路问题区分正确性与效率影响                      |
| 修正建议   | 可操作的补查、重算或交办调整；写明缺少的前提，不擅自执行                              |
| 验证方法   | 需要观察什么才能认定解决，哪些相反证据会推翻当前判断                                  |
| 经验候选   | 仅作为草案，不能直接标为已验证或发布                                                  |

输出采用有固定段落的分析报告及可校验的引用清单，不要求首版新增通用结构化成果框架。Run 成功只代表分析生成成功，不代表判断正确、问题已确认或任务已修复。

分析结果由复盘业务独立接纳。接纳失败只重试公开同一份结果，不再调用模型；超时、取消和服务重启使用现有执行规则，不能影响原任务的状态。新内容或新证据可再次分析，旧报告保留；不自动连续追问模型。

## 6. 原发起者怎样修正任务

### 6.1 问题状态与责任

| 状态   | 进入条件                                                            | 可执行者                       |
| ------ | ------------------------------------------------------------------- | ------------------------------ |
| 待核实 | 提出问题，或补充反证后重新打开                                      | 成员可提出；原发起者可重新打开 |
| 待修正 | 原发起者确认具体问题和预期修正，不要求 Agent 必须先分析             | 原发起者                       |
| 待验证 | 已关联一次修正执行，或待核验的非执行修正依据                        | 原发起者                       |
| 已解决 | 写明验证结论并关联可核对依据；需要执行时新 Run 已成功且交付接纳成功 | 原发起者                       |
| 已关闭 | 不成立、重复、证据不足或暂不处理，必须写原因；不计为解决            | 原发起者                       |

人的评论和 Agent 分析只能提供建议，不能自动推进问题状态。任何成员可在已解决问题下补充反证并请求复核；原发起者可重新打开，经验发布者或原发起者确认需要复核时，将相关经验标为“待复核”，在复核完成前不供新交办引用。普通质疑评论本身不自动停用已发布经验；来源撤回则由系统直接使依赖内容失效。已有复用记录保留其当时版本。

根评论和回应在提交后不覆盖修改，作者可撤回并重新补充；被引用评论撤回后保留定位占位，依赖分析按证据撤回规则失效。决策与状态变化追加操作者、时间、预期修订、理由和关联依据，避免两个标签页后写覆盖先写。

### 6.2 修正是新的交办

1. 原发起者点击“据此修正”。界面从已确认问题及选中的分析生成可编辑草稿，包含原目标、已确认偏差、修正范围、约束和验收方法；不直接发送。
2. 发起者检查草稿，尤其确认是否仍需调用外部工具、是否要重新读取数据、哪些结论需要替换。只有人显式提交才启动新工作。
3. 默认在原对话追加用户消息及新 Run。保存问题到修正输入/Run 的关联，但不覆盖原消息，不改旧 Run 的成功/失败状态，也不复用原请求键。
4. 新执行复核原发起者当前委托资格，使用员工当前配置、固定工作连接及知识范围。需要明确补查和重算时在新输入中说明；旧的工具结果仍可能存在于正常续聊上下文，不能把追加一句“已修正”视为重新取得了数据。
5. 发起者按验收方法核对新结果，在问题中确认验证结论。其他参与者可检查修正记录并提出反证；新 Run 成功不能自动关闭问题。

修正提交前检查对话版本、最新回复及活动占用。原对话又有新消息时要求重读和重新确认草稿；有活动执行时等待或由发起者按现有规则停止，不让复盘入口绕过单活动限制。未知网络结果用原修正提交键核对，幂等重放先于版本与容量检查。

现有失败重试保持原语义，只适用于最后一次失败/停止尝试；即使原 Run 技术上成功，只要内容或流程有误，也能通过新的用户输入修正。旧步骤不能在原处编辑后重放。

若原对话无法合法续接 checkpoint，或方向变化较大，首版提供“新建关联对话修正”：由原发起者显式选择，预览复制的原目标、允许使用的历史和修正要求，再经正常首条提交创建新对话，并原子保存修正关联。不能在续接失败后自动退化重做，也不能把原 SDK 状态复制给新线程。该分支只处理修正问题，不扩展为通用多分支对话。

### 6.3 修正结果和原成果同时可见

原回复旁显示“存在待处理问题”或“已有修正结果”，并能跳到相应问题与新回复；不只把纠错藏在讨论里。多个问题或多次修正分别关联，某个问题解决不表示整份成果都已正确。

重复调用问题需要在任务正确性保持的前提下比较有效调用数、耗时及用量；分页问题要核验数据完整性及重新统计结果；方向问题要由发起者确认新交付是否满足修订后的目标。人工补充数据、修改共享技能或修复工具服务也可作为修正依据，但要链接可核对版本/记录，不伪装为已经运行过的新 Run。

## 7. 解决问题的经验怎样沉淀

### 7.1 从已验证问题提炼，保留适用条件

问题已解决后，任何成员可“整理为经验”。可以手动填写，也可以复用独立分析执行生成草稿；自动生成需要显式触发和单独记账。Agent 给出的原因假设不自动成为经验事实。

经验草稿至少说明：

- **场景与信号**：什么任务、看到什么现象时需要这条经验。
- **已验证原因**：确认到哪一层；未确定根因时只记录已验证的处理方法。
- **处理步骤**：具体检查、补充输入或执行方法。
- **适用条件与例外**：工具、技能或数据版本，以及不应该照搬的情形。
- **验证方法**：怎样确认处理有效，不能只写“重新运行成功”。
- **来源**：原问题、原执行/动作、修正执行或非执行依据、验证人和日期。

例如：“当工具返回非空 next_cursor 时，当前页不能作为全量数据统计。按该工具协议继续取页，直到结束条件满足；若服务提供可信的全量聚合接口，可直接使用该接口。核验重复记录、累计条数和统计口径。”这比“以后注意分页”更容易应用，也没有把某个工具的分页方式推广到所有工具。

### 7.2 发布、修订与撤回

首版经验挂在原员工下，属于平台共享经验，由草稿提交人维护来源，管理员使用现有员工配置管理资格审核并发布。原发起者负责案例验证，管理员负责检查是否值得跨任务复用；管理员发布不等于模型判断被证明正确。

状态只保留草稿、已发布、已撤回；已发布记录另有“待复核”标记。修改已发布正文产生新修订并重新发布，旧任务继续引用旧修订。撤回、待复核或来源已撤回的经验不进入新任务选择，但保留历史引用占位、原因及审计关系。

同一经验可能需要三个不同落点：

| 落点             | 适用情况                                       | 首版处理                                                         |
| ---------------- | ---------------------------------------------- | ---------------------------------------------------------------- |
| 经验记录         | 与场景有关、需要人判断是否适用的方法           | 本方案实现发布和显式引用                                         |
| 岗位指令或 Skill | 已稳定验证、应在该员工后续工作中普遍采用的步骤 | 管理员经现有配置编辑发布，经验关联目标及修订；不自动改写         |
| 工具或平台代码   | 分页、参数校验等可以由程序稳定保证的行为       | 形成具体工程修改入口，修复与测试另行实施；记录只链接实际交付依据 |

### 7.3 首版就能在下一次交办中使用

员工页增加“经验”入口，支持标题/正文关键词、已发布状态和问题类型筛选；对话交办区提供“引用经验”，首版手动选择，不做向量检索或自动推荐。

提交前展示所选经验全文、适用条件及来源。服务端在正常发送事务中复核发布/待复核状态，保存经验 ID、修订及实际注入内容。经验以明确标识的参考材料进入本次输入，不覆盖用户要求、全员规则或工具权限。UI 显示本轮实际引用了哪些经验，不把“员工名下存在经验”说成本轮已经使用。

经验作为往轮参考材料可能保留在正常 SDK 历史中，但不自动升级为所有后续任务的固定规则。普通正文优化生成新修订，已受理工作保留已冻结版本；显式撤回、待复核或旧修订被标为失效时，才触发依赖失效处理。此时需要像知识/工具变更一样检查继承关系，禁止仅从新注入列表删除却继续使用旧 checkpoint 中失效的内容。首版保守重置受影响的执行记忆，重新提供当前允许的材料；排队和运行中的工作在启动、动作及成果公开时复核引用修订仍有效。

这条显式复用链路属于首版；自动检索、个人偏好和跨员工记忆继续留在[长期记忆方案](长期记忆.md)，不作为首版依赖。

## 8. 页面、业务对象与实施接点

### 8.1 页面入口

- 对话列表保留“查看对话”，显示作者、待处理问题数和最近复盘活动。主对话时间仍表示主任务活动；讨论活跃度独立展示，不能冒充新回复。
- 主对话只有发起者显示输入框；其他人看到作者及只读说明，仍可从用户输入、回复和执行步骤发起复盘。服务端返回 can_send、can_stop、can_retry、can_review 等操作资格，写入时独立复核。
- 复用当前对话辅助栏增加“复盘”视图，列出问题与状态；从动作进入时保留原执行详情并打开关联问题。直接访问问题链接应加载必要历史窗口和准确动作，不依赖全部消息或动作已在内存。
- 问题详情展示原目标、证据、人的讨论、Agent 分析、修正和验证。发起者看到确认、修正、验证、关闭入口；其他成员可补充和请求分析。
- 发起者可在列表筛选本人待处理问题，标识新问题及补证请求。首版通过页面刷新/进入时读取，不做邮件、站外推送或完整通知中心。
- 经验列表进入员工主页，经验详情回链原问题及修正；原对话旁也能看到沉淀出的经验。

### 8.2 业务所有者与最小新增事实

建议新增 reviews 业务模块，拥有问题、评论、共享证据、分析接纳、修正关联和经验。它调用 conversations、execution、files 及 employees 的公开操作，不把这些记录塞入普通 Message 或 RunAction。具体表名和 DTO 在实施时设计，不在方案复制整套字段字典。

| 事实           | 最小内容及约束                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 复盘问题与评论 | 作者、原对话/截止执行、主锚点、追加内容、问题状态/修订、决策记录；引用始终经原资源关联授权     |
| 共享证据       | 公开片段、来源标识/hash/阶段、发布者、撤回状态；保留文件依赖，不借 evidence 下载入口放开原文件 |
| 分析关联       | 问题、触发人、独立 Run、输入清单与版本、结果接纳状态；同问题单活动分析；来源撤回可影响公开资格 |
| 修正关联       | 一到多个问题、明确修正输入、新对话/Run、验证结论和验证者；不能关联他人的执行或不相干员工       |
| 经验与引用     | 草稿/发布/撤回、修订、适用条件、来源链、发布者、待复核标记；新任务捕获具体经验修订和实际内容   |

同一修正可处理多个问题，但每个问题分别核验是否解决；同一问题可有多次失败或部分有效的修正。修正关系不复用 retry_of_run_id，后者继续只表达同一输入的重试。

### 8.3 建议 HTTP 操作分组

路径为提案，最终 schema 和 OpenAPI 随实现维护。所有入口继续使用现有来源检查、身份、错误包络和 no-store，不提供通用 Run 提交接口。

| 操作入口                                     | 责任                                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------------ |
| `/api/conversations/{id}/reviews` 及单个问题 | 分页列表、创建、读取、按预期修订追加决策；创建时校验目标链及终态                     |
| 问题下的 `/comments`、`/evidence`            | 追加/撤回回应、发布/撤回可核验工具片段；下载共享副本时重新授权                       |
| 问题下的 `/analyses`                         | 预览材料、显式受理、核对未知请求、读取进度、精确停止及新尝试；只读取本问题绑定的 Run |
| 对话下的 `/corrections`                      | 原子保存新的修正输入、Run 与问题关联；显式新对话分支也经同一业务操作组织首条提交     |
| `/api/agents/{id}/experiences` 及经验详情    | 列表、草稿、修订、发布/撤回、来源及复用记录；普通发送可提交允许的经验引用            |

新增写入使用客户端请求键和摘要去重；分析受理及关联在同一短事务提交。未知结果可按原键核对，不能因重新打开弹窗生成第二份分析。首版分析使用有界串行轮询读取，终态停止，不为了复盘新建另一套通用 SSE 系统。

停止分析需要“当前分析由本人触发”及 runs:cancel，不能从“所有人能读问题”推导其他人能停止。经验草稿整理属于该问题的新分析用途，同样只读共享材料；发布、撤回和问题决策使用独立的业务操作资格。

## 9. 关键失败、迁移与验收

### 9.1 必须明确的失败行为

| 情况                                             | 行为                                                                       |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| 伪造其他对话的 message/run/action 或任意 file_id | 受理前拒绝，不读取或发送相应材料                                           |
| 管理员尝试向他人主对话发送、停止、重试或提交修正 | 拒绝；管理员诊断读取资格不等于任务操作资格                                 |
| 评论/共享片段撤回与分析并发                      | 受理、启动和结果公开复核依赖；受影响结果不公开，不把冻结副本当永久授权     |
| 分析模型服务不可用或生成失败                     | 原问题、证据和人工处理照常可用；保留失败尝试，显式再次请求才能新建 Run     |
| 原任务已经继续，修正草稿依据过时                 | 返回冲突并保留草稿，重读后由发起者确认；不插队或回滚主线程                 |
| 修正调用工具成功但交付接纳失败                   | 仍待验证，不能宣称已解决；接纳重试不得重做已发生的工具操作                 |
| 经验撤回/更新与排队、运行或续聊并发              | 当前依赖复核；停止使用失效修订，不从旧 checkpoint 静默继承；原历史不被改写 |
| 问题被关闭/重开或多次点击生成经验                | 使用修订和幂等保护；重复请求返回原记录，未解决问题不能直接发布已验证经验   |

### 9.2 迁移与发布

新增问题、分析及经验记录使用增量迁移，保留当前用户、对话归属、消息、Run、动作、文件与 checkpoint；不得通过重建数据库来获得新结构。空库和含真实结构的旧库都应验收外键、索引、原数据可读性及新增约束。

先完成读写权限拆分，再开放共享列表和复盘入口；不能出现“列表已经共享，但写入口仍按 resources:all 放行”的中间发布状态。历史可见性迁移是独立确认点，不能根据本篇待评审方案直接在线执行。

若新执行输入或用途策略需要变更快照版本，按现行运行版本契约处理旧活动 Run，发布前排空或明确中断；不能未经验证允许旧存档自动恢复。当前后台仍依赖触发人的会话，不新增离线服务身份，退出或会话失效的行为与现行执行规则一致。

### 9.3 首版验收集合

| 用例                      | 验收重点                                                                                                                   |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| A：成功 Run 的遗漏分页    | 成员能定位动作并请求补证；共享有限字段后 Agent 引用正确证据；发起者补查、重算并确认；原答案保留且显示修正入口              |
| B：成功 Run 的重复调用    | 区分必要复核与无效重复；在结果正确性相同的前提下核对调用数及成本；不能仅凭两次参数相同断言浪费                             |
| C：交办方向或理解偏差     | 定位到用户输入/回复；分析区分目标不清与模型偏离；发起者编辑修正目标，其他人不能替其发主消息                                |
| D：错误指控或证据缺失     | Agent 不迎合评论者；保留反证或未知，关闭时说明原因，不形成已验证经验                                                       |
| E：技术失败与接纳失败     | 能复盘失败/取消/中断及接纳错误；保留原尝试；分析和修正互不改写原状态                                                       |
| F：多用户与跨资源越权     | member 共享读取但无他人写权；admin 同样不能跨本人主操作；guest 只能读；个人账号/知识原件和非公开 evidence 不能从新入口泄露 |
| G：幂等、并发、重启及撤回 | 双击只受理一次；原主任务可与独立分析并行；同问题分析互斥；结果接纳可重扫；来源撤回不产生迟到公开                           |
| H：经验的实际复用         | 已解决案例生成并发布经验；新任务显式选入并显示版本；相似任务能正确应用，反例中不误用；撤回和待复核后不再新引用             |

确定性校验覆盖权限、锚点、状态、事务、幂等和恢复；离线假模型覆盖流程；真实模型样本检查证据引用、诊断判断和适用性。业务质量不能只用模型裁判或 Run succeeded 证明。

试点按有复盘和无复盘的同类案例比较有效问题发现率、修正完成率、问题到验证的耗时、同类错误复发及新增分析成本。记录每项分母、人工核验依据和任务复杂度；首轮先建立基线，不编造收益阈值。经验是否被真正用于后续交办，以及应用后是否有效，是沉淀链路的必要指标。

## 10. 实施顺序、待评审选择与本次交付

### 10.1 按依赖推进，完整闭环后称为首版

1. **共享阅读与操作隔离**：确认升级共享范围，补本人写入校验、作者和操作资格；统一查询出口。
2. **问题与证据**：稳定锚点、讨论、工具证据摘录、撤回及待处理入口；先能人工检查和确认。
3. **独立分析与修正验证**：复盘 Run、固定材料、独立接纳、修正受理及验收关联；用分页和方向偏差完成端到端验证。
4. **经验发布与显式复用**：从已解决案例整理、审核发布、下次交办引用、失效依赖处理及效果记录。

以上是同一首版的实施切片。只有评论列表、模型回复或经验存档，都不构成本方案要求的闭环。每个切片可独立验证，但不能省略最后的修正验证和后续使用。
