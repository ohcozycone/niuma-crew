# NiumaCrew 与 StaffDeck 产品及技术对比

日期：2026-11-01。本文是一份基于当前源码的产品研究记录，覆盖功能、实现机制、适用边界和发展建议。建议尚未成为工程需求，也未实施。

**核心判断：StaffDeck 已覆盖更完整的数字员工运营流程；NiumaCrew 已建立较细的工具授权、执行记录和知识证据机制。你最值得优先验证的方向，是让员工稳定完成「有来源、可核对、能下载成果」的知识工作，再向需要人工确认的业务流程延伸。**

这个判断有三个依据：

1. 两者都能配置员工、装配技能和工具、调用模型并保存执行记录。你的工程已经超出了简单的角色聊天应用，个人多库问答也已接入正式聊天。
2. StaffDeck 的明显增量集中在 SOP、跨会话记忆、团队协作、定时任务、人工接管、企业渠道，以及反馈后的版本改进。这些功能大多能找到实际入口和调用链。
3. 功能覆盖不等于效果已经得到验证。StaffDeck 的内置记忆并非按问题做向量召回，「自进化」的候选评估目前主要是结构检查；你现有的引用校验也只能验证来源身份，不能证明回答确实被原文支持。下一步应围绕实际任务质量建立优势。

## 2. 两款产品的共同点与产品重心

### 2.1 共同点

两者都把数字员工建模为可复用配置：员工有职责和工作指令，引用模型，按需使用技能、知识和工具。员工不是登录账号，也不等于一台专属常驻机器。同一员工可服务多个用户，真正工作发生在某次运行中。

两者也都把执行控制放在模型之外：平台组织资源、保存进度并检查调用；模型负责理解、选择工具和形成回答。两者均有本地 SQLite 持久化和单实例运行约束，均不能仅凭「有后台任务」就视作分布式执行平台。

### 2.2 产品重心的区别

| 维度         | NiumaCrew 当前形态                                    | StaffDeck 当前形态                                         | 对你的启示                                         |
| ------------ | ----------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------- |
| 项目定位     | README 明确用于交流学习；当前主要围绕配置和对话工作台 | 官方定位为面向企业的数字员工平台，并带默认岗位和运营功能   | 可借鉴闭环设计；客户定位和商业价值仍需你自己验证   |
| 核心使用路径 | 选员工 → 提需求 → 观察执行 → 取得回复或文件           | 建员工 → 装配资源/SOP → 多入口服务 → 人工介入 → 反馈和修订 | 你已有执行基础，缺少较多持续运营环节               |
| 默认业务样例 | 有教学资料和能力接线；示例不代表自带成熟业务员工      | 分发清单提供 IT、人事、行政、财务、法务默认员工及关联资源  | 用户第一次进入时，应更容易完成一个真实小任务       |
| 组织复用     | 共享员工、共享技能、个人账号、个人知识装配            | 员工资源绑定、市场资源、员工分支和版本、团队               | 组织能力复用需要发布和升级规则，不能只增加分享按钮 |
| 工作持续性   | 一次次对话与 Run                                      | 对话之外还有 SOP 状态、计划任务、团队任务和人工等待        | 长流程需要业务实例，不能靠拉长单次 Run 代替        |
| 质量治理     | 详细动作、用量、来源和发布检查；暂无正式反馈改进产品  | 轨迹、反馈归因、候选改进、审核发布与回滚                   | 可先补任务评测，再考虑自动生成改进建议             |

## 4. Agent 怎样工作

### 4.1 NiumaCrew 是平台宿主加 SDK 循环

一次对话的主要路径为：

1. 对话准备服务读取员工、模型、全员规章、技能、工具和当前用户的知识装配，形成固定配置快照。
2. 对话模块接受请求并保存输入，执行宿主把 Run 放入队列。
3. `execute_agent()` 使用 LangChain 的 `create_agent()` 创建模型—工具循环；DeepAgents 提供技能发现和文件相关中间件。
4. 每次模型和工具动作经过宿主检查，记录预算、状态和结果；知识工具与外部 MCP 都走受控入口。
5. SDK 返回候选回答和成果文件引用，发布事务再次核对授权、来源及文件归属，再保存正式消息。

因此，准确说法是「使用 LangChain Agent 循环和 DeepAgents 能力」，而不是直接采用 `create_deep_agent()` 的全部默认配置。当前没有接入子 Agent 委派、SOP 状态机或长期记忆模块。

这一结构的价值是业务规则仍由你的代码控制，SDK 不拥有最终消息和授权事实。代价是取消、恢复、结果归一和上下文控制都需要平台自己维护。

源码：[对话准备](../../backend/app/conversations/preparation.py)、[Agent 循环](../../backend/app/agent_runtime/langchain.py)、[中间件](../../backend/app/agent_runtime/middleware.py)、[发布](../../backend/app/conversations/publication.py)。

### 4.2 StaffDeck 是模块装配加独立 Harness 引擎

当前默认启动路径会组装 Harness v3。平台把员工、资源、权限和行为模块编译成本轮装配快照；桥接层通过 Python SDK、stdio JSON-RPC 与 Node 引擎进程通信。

平台生成的引擎配置明确关闭引擎原生文件、Shell、网页、子 Agent、待办和目标工具，再挂上 StaffDeck 的本地 MCP 能力服务。模型主要看到稳定代理，例如：

| 代理                  | 实际作用                              |
| --------------------- | ------------------------------------- |
| `capability_describe` | 查询当前资源及其具体参数结构          |
| `knowledge_search`    | 检索当前获准知识                      |
| `general_skill_read`  | 读取当前获准技能包                    |
| `tool_invoke`         | 按工具 ID 调用 HTTP、MCP 或其他 Agent |
| `sandbox_execute`     | 请求平台受控文件/命令能力             |
| `capability_invoke`   | 调用版本化扩展操作                    |

每次请求仍回到平台，检查本轮范围、当前权限、调用账本和结果策略。人设、记忆和 SOP 当前步骤通过执行前的钩子进入模型上下文。引擎原生子 Agent 被关闭，不影响平台用自己的团队模块组织员工协作。

这不是一个纯提示词包装，也不是仓库里旧 `AgentLoop` 类的原样运行。当前桥接层仍复用部分 `app/core` 和业务服务，分析时必须沿启动和装配关系判断。

源码：[引擎进程与配置](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/bridge/worker.py)、[能力入口](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/capabilities/host.py)、[上下文钩子](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/interactions/pipeline_host.py)。

### 4.3 两种技术路线的实际取舍

| 问题                   | 你的实现                                                             | StaffDeck 实现                                     | 判断                                                                                               |
| ---------------------- | -------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 如何让模型知道工具参数 | 每个 MCP 操作生成独立 `StructuredTool`，把实际参数结构直接提供给模型 | 稳定代理配合资源目录和参数描述，再按 ID 调用       | 直接暴露容易选用；大量工具会占上下文。代理减少固定接口种类，但可能需要额外查询，嵌套参数也需要检查 |
| 如何增加运行能力       | 在现有宿主和中间件边界接入                                           | 通过模块清单、插槽、装配编译、钩子和 provider 接入 | 对外部可替换模块很多的产品，后者有价值；对你当前规模，全套复制会增加开发和排错成本                 |
| 引擎部署               | Python 应用内运行 SDK，外部工具/沙箱另连                             | Python 平台加 Node 引擎进程及桥接协议              | StaffDeck 引擎隔离更明确，也多了安装、版本匹配、进程池和协议恢复成本                               |
| 能否保证模型完成任务   | 有调用、时限、上下文和成果检查                                       | 有动作限制、结构化完成、SOP 检查等机制             | 都不能只凭循环框架保证任务质量；需要同题评测                                                       |

**建议保留当前 Agent 主循环。** 优先借鉴按任务需要缩小能力范围、清晰的完成契约和统一结果表达，而不是为了功能对齐更换引擎。

## 5. 工具接入与权限

### 5.1 你的实现把接入拆成四层

以「员工读取用户自己的业务资料」为例：

1. **服务定义**：登记 MCP 地址或可信程序，以及允许配置哪些字段。
2. **账号连接**：用户提供自己的凭据，平台加密保存，记录配置和凭据修订。
3. **确认目录**：发现服务提供哪些操作、参数和使用说明，先保存候选，确认后才供员工装配。
4. **员工许可**：指定员工可以调用哪些操作、访问哪些路径或参数范围，并选择个人或共用账号方式。

运行时固定这些依据，但调用前继续检查当前授权、连接、目录和范围。用户绑定自己的账号不会扩大岗位权限；没有个人绑定也不会悄悄借用创建者账号。远端服务修改参数结构后，旧确认依据不能自然变成新授权。

HTTP 接入还会核对域名、DNS 解析地址和实际请求目标；私有地址需要部署配置明确允许。可信 stdio 则是运行宿主程序，部署者必须明确启用，不能把它当成隔离沙箱。

源码：[工具模块](../../backend/app/tools/README.md)、[员工许可](../../backend/app/agents/tool_grants.py)、[实际调用](../../backend/app/tools/invocation.py)、[网络策略](../../backend/app/tools/network.py)。

### 5.2 StaffDeck 的接入面更宽

它的业务工具记录可以是普通 HTTP、MCP 或 A2A。HTTP 工具直接保存方法、地址、输入输出结构和认证配置；MCP 工具关联 MCP Server，Server 管理传输、地址或程序参数；A2A 则通过专门客户端对接外部 Agent 任务。

员工和 SOP 节点选择资源后，本轮装配只给相应资源范围；实际调用仍经权限检查和当前资源校验。它也有「快照加当前权限」两层控制，不能把你的快照检查写成它完全没有的能力。

两者的一个具体差别是凭据模型：你有明确独立的「服务定义—个人账号连接—员工绑定」关系；本次核查的 StaffDeck 核心 HTTP/MCP 工具路径主要从工具或 Server 配置解析认证，并非同一套个人连接模型。若多人共用一个员工但必须访问各自账号，你的现有拆分值得保留。

源码：[工具数据结构](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/db/models.py)、[协议客户端](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/tools/mcp_client.py)、[工具执行](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/tools/tool_executor.py)、[受控业务入口](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/capabilities/facade.py)。

### 5.3 外部操作失败后怎么办

假设员工请求创建工单，请求发出后网络断开。此时「平台没收到结果」不能说明「工单没创建」。

你的当前策略较保守：装配了外部 MCP 或沙箱的运行通常不允许自动 checkpoint 恢复；未知动作保留为未知，不盲目自动重放。StaffDeck 则有更通用的持久调用账本：

| 账本状态               | 含义与后续行为                                 |
| ---------------------- | ---------------------------------------------- |
| `completed`            | 相同逻辑副作用键可以返回缓存结果，避免再次提交 |
| `failed`，且确定未发出 | 释放占用，允许按规则重试                       |
| `outcome_unknown`      | 可能已经发生，阻止自动重放，等待核对           |
| `denied` / `cancelled` | 记录被拒绝或取消的调用状态                     |

这是你以后做业务写入时值得借鉴的机制。不过账本不能单独实现外部系统的「恰好执行一次」，仍需要上游幂等键、状态查询或人工对账。

源码：[你的恢复控制](../../backend/app/execution/store.py)、[StaffDeck 调用账本](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/capabilities/ledger.py)。

### 5.4 MCP Apps 是一个额外产品能力

StaffDeck 可以读取 MCP 的界面资源，在对话中显示工具视图，并把界面操作回传给后端。其 App 回调对非只读操作要求 `confirm_side_effect`；这个局部确认不能扩大解释为平台已完成全部高风险工具的细粒度审批。

你的平台暂未接入对应正式入口。未来若要支持「模型生成表格后，用户筛选、编辑再提交」，交互结果页可能比继续增加聊天文字更有价值；首版也可以先用自己控制的结构化表格和表单验证，不必立刻兼容全部 MCP Apps。

## 6. 技能包与 SOP

### 6.1 技能包的基础已经接近

两者都支持 `SKILL.md` 方法包及支持文件，并让模型按需读取。你的实现还包括 ZIP 路径和容量检查、内容摘要寻址、旧资源保留及接受时的技能快照；导入不会自动运行脚本或安装依赖。

StaffDeck 的当前通用技能入口会把包投递到工作区并提供读取信息。源码中兼容的 `execute` 操作会安全降为 `read`；需要实际运行脚本时，再经过沙箱能力。因此，不能因为仓库里存在旧的「生成代码—修复—再执行」Runner，就把它描述成所有正式聊天的默认技能运行方式。

源码：[你的技能包](../../backend/app/skills/packages.py)、[技能装配快照](../../backend/app/agents/execution_config.py)、[StaffDeck 技能接入](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/capabilities/facade.py)。

### 6.2 StaffDeck 的 SOP 是真正的业务状态

「按以下五步处理」写在技能正文里，只是在要求模型遵循方法。StaffDeck 另保存结构化流程：节点、连接边、开始和结束节点、需要收集的信息、允许动作，以及本节点可使用的工具、知识和技能。

例如一个内部服务流程可以这样工作：

1. 当前节点收集申请对象和原因；资料不足时保存等待状态并追问。
2. 信息齐备后，平台检查可走的后继节点，再进入查询或提交步骤。
3. 该步骤只装配对应资源；模型不能因为另一步有写入工具，就在当前节点获得同样许可。
4. 需要负责人判断时建立人工请求，保存当前节点和信息，待回复后继续。
5. 完成不仅看模型是否说「处理好了」，还检查流程位置、必填信息和提交结果。

它也支持子流程、待处理任务切换和版本分支。模型提交结构化步骤结果出错时，当前实现另有无工具的格式修复阶段，最多进行两次修复模型尝试；它只应修复结构，不应重新执行业务。

这能减少遗漏固定步骤，但分支条件、信息提取和回答内容仍可能由模型判断。SOP 的结构检查不等于业务正确性证明，也不等于成熟 BPM 系统的全部能力。

源码：[流程结构](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/skills/skill_schema.py)、[流程生命周期](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/sop/lifecycle.py)、[状态保存](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/sop/state.py)、[格式修复](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/runtime/result_repair.py)。

## 7. 知识库怎样入库、检索和引用

### 7.1 你的知识库已经接入正式问答

当前实际路径是：上传 Markdown/TXT 原件 → 手动提交后台处理 → 解析和切分 → 逐文件发布正文、来源和关键词索引 → 按需显式构建向量 → 用户为员工装配本人多个库 → 正式聊天检索及引用。

这里有三个已经实现、不能低估的细节：

1. 上传与入库分开，未处理资料不会直接进入模型；处理失败保留旧的可用内容，不拖垮同批其他文件。
2. 切分保留 Markdown 标题路径和原文位置，可合并同父短章节；处理前能预览规则的实际结果。
3. 同一个共享员工，不同用户可装配不同私库；装配设置不写共享员工指令，也不自动分享给其他成员。

根 README、部分产品流程和架构摘要仍有「员工知识绑定/向量/问答待接入」的旧说明，与当前源码及[现行知识契约](../reference/knowledge.md)不一致。本报告采用正式代码链路，没有把旧摘要当成现状。本次只新增研究记录，未顺带重写这些正文。

### 7.2 检索技术有实质区别

| 环节         | NiumaCrew 正式链路                                               | StaffDeck 内置链路                                                          |
| ------------ | ---------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 文件解析     | UTF-8 Markdown/TXT；PDF/DOCX 的实验依赖不等于正式上传支持        | 文本、Markdown、HTML、PDF、DOCX；旧 `.doc` 明确要求转换                     |
| 文档结构     | 固定正文、标题路径、来源区间和片段                               | 文档、章节、主题桶、片段，另有 OKF Wiki 概念及关联                          |
| 关键词路线   | jieba 分词，SQLite FTS5 的 BM25                                  | 概念、文档、主题及片段的词法评分                                            |
| 语义路线     | BGE-M3 生成 1024 维归一化向量，保存在 SQLite，精确计算余弦相似度 | 当前内置主链用模型选择文档和主题桶，没有发现相同的 Embedding 加向量索引主线 |
| 合并与扩展   | BM25 与向量按 RRF 融合；跨库也按名次组织，不直接比较不同分数     | 先选文档和主题，再展开章节、排序片段、补关联内容和证据包                    |
| 模型参与检索 | BM25 不需要模型；向量/混合需要问题向量；最终回答另调用聊天模型   | 配有模型时，文档和主题路由会调用模型；不可用时可带轨迹回退词法路径          |
| 检索时机     | `on_demand` 由模型决定，`always` 在首轮进图前预检索；后续可补读  | 暴露知识检索能力，SOP 可以绑定本步知识范围和必要资源                        |

**BM25** 可以理解为擅长找词语；**向量**擅长找近似含义；**RRF**按各路线的排名合并，避免把不相同的分数直接相加。StaffDeck 的**主题桶**则是按文档结构和主题组织出的导航入口，帮助模型先决定去哪里找。

你的正式实现没有使用常驻 Chroma 服务。`knowledge/retrieval.py` 中的 Chroma 相关接口属于 POC，产品实际向量链在 `vectors.py`，不能混用两套实现做结论。

源码：[你的正文与 BM25](../../backend/app/knowledge/service.py)、[正式向量与 RRF](../../backend/app/knowledge/vectors.py)、[跨库检索](../../backend/app/knowledge/employee.py)、[StaffDeck 解析](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/knowledge/parser.py)、[结构检索主链](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/knowledge/service.py)。

### 7.3 各自适合什么资料

对于「规定中的某个准确金额、编号、产品名」，关键词路线通常值得保留；对于「换了一种说法描述同一问题」，向量路线提供补充。对于长手册、章节依赖明显的制度或操作文档，StaffDeck 的导航和章节展开思路值得借鉴。这些是机制上的适用推断，本次没有测出哪款产品的准确率更高。

StaffDeck 的模型路由增加了理解目录的机会，也增加调用成本和选错文档的风险；你的片段召回更直接，但可能丢失跨章节约束。未来可以在现有混合检索上增加邻近章节补读和文档目录导航，不必先推翻整个索引方案。

两者也都有边界：StaffDeck 用 `pypdf` 提取 PDF 文字，不代表扫描件 OCR、复杂表格和版面还原已经完成；你的正式产品目前每文件 128 KiB、每库 200 文档/5000 片段，向量构建为显式整体构建，后台增量向量尚未接入。扩大资料规模前，需要先测更新耗时、查询延迟和内存，而不是只把上限调大。

### 7.4 引用可靠性应分成两个问题

第一个问题是「这个引用是否来自本轮允许使用的真实资料」；第二个问题是「这段资料是否支持这句话」。

你的实现对第一个问题有明确控制：检索后登记本轮证据，保存来源片段快照；后续动作和发布重新检查库归属、装配修订及片段状态；回答中的知识编号与地址必须配对。未知编号、错配地址或伪造路径会阻止正式发布。历史来源要在新一轮重新核验和登记后才能继续用。它仍允许普通的非资料性回答，不能据此声称每句话都强制带引用。

StaffDeck 主要从检索结果收集引用元数据，提供来源卡，并对回答里的数字引用去重、重编号；不存在于元数据的编号会被去除。本次探针确认：如果输入有来源元数据，但回答没有引用编号，其整理函数仍可能保留来源卡。因此，显示来源卡不能单独证明正文逐句使用了这些来源。

**两者都没有仅凭上述机制解决第二个问题。** 一条「来源真实但结论误读」的回答仍可能出现。这是你未来做引用支持度评测、冲突发现和人工复核的直接机会。

源码：[你的引用检查](../../backend/app/knowledge/employee.py)、[发布事务](../../backend/app/conversations/publication.py)、[StaffDeck 引用处理](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/knowledge/citations.py)、[最终回复整理调用](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/core/turn_coordinator.py)。

## 8. 记忆与上下文

### 8.1 你的历史和 checkpoint 还不是长期记忆

当前平台从同一对话中选择成功历史进入上下文，并保存 Run 的执行存档，知识问答也能重新核验历史证据。但没有看到把用户事实或偏好提炼成独立记录、在新对话里召回的正式模块。

因此，在同一对话里继续讨论资料可以成立；「另开对话后仍自动记得你偏好三列表格」尚无独立长期记忆机制保证。把所有旧聊天塞进提示词既增加成本，也会把旧假设和已纠正信息继续带入新任务。

### 8.2 StaffDeck 内置记忆怎样读写

1. 本轮开始时，按租户、用户和员工范围读取记忆。
2. 当前 provider 只把 `profile`、`preference`、`fact` 三类作为记忆上下文，读取结果按更新时点组织；执行前钩子注入最多 20 条。
3. 对话后提交后台提炼任务。提炼模型读取本轮历史、已有记忆和结果，输出增量。
4. 增量按稳定 key 执行新增/更新或删除，保存原因、来源和员工关联。
5. 用户可查看和清除自己的记忆；管理权限允许的范围也有查看入口。

例如「以后默认用中文」可以成为偏好；后面改成「这个岗位用英文」，提炼器可按 key 更新或删除旧项。但提炼仍是模型判断，不保证每次都能正确识别范围和纠错。

一个关键实现细节是 `MemoryService.recall()` 显式丢弃 `query` 和 `limit`，最终调用范围内的 `context_memories()`。所以它当前更接近**保存个人事实并选择最近记忆注入**，而不是「根据当前问题进行语义记忆检索」。`importance` 字段存在也不等于当前召回按重要性排序。

渠道上下文还受到额外限制：当前记忆 provider 存的是账号级个人记忆，渠道会话的使用资格不会自动授予这个更大的范围；相关授权分支会跳过可选召回和提炼。不能仅凭账号合并就宣称所有渠道可无条件共享记忆。

源码：[记忆存取与提炼](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/memory/service.py)、[后台提炼](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/memory/jobs.py)、[记忆授权与 provider](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/memory.py)、[上下文注入](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/interactions/pipeline_host.py)。

### 8.3 你的记忆首版应先保证可控

建议先支持「用户明确保存的个人偏好和项目事实」，每条记录包含所有者、作用员工或项目、来源消息、修订和有效状态。用户能查看、改正、删除，也能控制是否用于当前任务。

读取时先按身份和作用范围筛选，再限制条数或上下文预算；只有条目规模和测试证明需要时，再加入向量召回。提炼结果先作为候选或只自动保存低风险明确偏好，避免把模型猜测直接变成长期事实。权限、凭据和业务审批不进入记忆授权体系。

验收重点应是：新对话能复用；换用户/员工不串用；更正覆盖旧值；删除后缓存及后台迟到任务不能重新写回；与当前明确指令冲突时以当前指令为准。这些比一开始搭建多层「记忆架构」更重要。

## 9. 定时、协作与人工介入

### 9.1 定时任务需要一套持久业务状态

你的 Runner 能处理已经接受的队列，却没有保存「每周一上午执行」这类计划定义。队列扫描与定时业务是两个层次。

StaffDeck 保存计划定义及每次计划运行，支持单次、每日、每周和每月，使用 IANA 时区计算下一次时间；到期任务通过数据库条件更新领取，然后经调度入口进入员工执行。它还有两组明确策略：

| 策略                | 用户可理解的含义                           |
| ------------------- | ------------------------------------------ |
| `forbid` / `allow`  | 上一次没结束时，本次禁止重叠或允许另跑一份 |
| `coalesce` / `skip` | 停机错过的触发合并处理或跳过               |

当前结构不是任意 cron 表达式引擎。计划依赖常驻 worker 和可用模型、连接、执行身份；计划成功触发也不等于结果已经完成交付。

你若增加「每周资料变化检查」，应保存计划所有者、员工、时间规则、执行范围、上次比较依据和结果投递位置。到期前重新检查权限和连接；没有变化时安静结束，有变化再给出差异和证据。首版先支持固定频率，避免先构建完整调度产品。

源码：[StaffDeck 计划结构](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/scheduled_tasks/schema.py)、[领取与执行](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/scheduled_tasks/service.py)、[调度 worker](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/scheduled_tasks/worker.py)。

### 9.2 团队协作已经存在，但不宜直接照搬全部机制

StaffDeck 当前有团队页面、成员与负责人、团队任务、任务依赖、共享黑板、任务竞标、负责人验收及重做/升级处理。执行结果和任务事件写入数据库，唤醒逻辑推进后续工作。

一个可理解的例子是：负责人把材料拆给两名员工 → 员工提交各自结果 → 负责人要求其中一份重做 → 满足依赖的任务继续 → 负责人汇总。共享黑板保存团队认可的信息，避免所有员工都读取所有对话。

这类协作由平台的团队状态和任务服务组织，不能简单等同于引擎原生 `subagent`。README 路线图仍将群聊和分工列为未完成，但代码已经有相应入口，因此本报告把它列为「有实现、效果待实测」。

对你来说，团队协作的直接价值应由任务验证：单员工无法覆盖不同资料范围、需要独立复核，或确有可并行的工作。如果只是让几名员工轮流改写同一份回答，会增加模型成本、错误传播和汇总负担。

建议先做「一名主员工产出、一名复核员工检查」的受限实验，固定输入和产出，比较有无复核的质量、耗时及成本。验证有效后再考虑通用团队、竞标和动态分工。

源码：[团队任务与状态](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/teams/service.py)、[任务唤醒](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/teams/wakeup.py)、[团队运行适配](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/runtime/team_host.py)、[团队页面](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/frontend-enterprise/src/pages/TeamsPage.tsx)。

### 9.3 人工接管与审批应分别设计

StaffDeck 的人工接管有持久请求、处理人指派、通知、回复、恢复和关闭。它解决的是「员工处理不了或流程需要人判断时，如何带上下文交给某个人」，而不是只在聊天中输出「请找管理员」。

你的当前追问仍主要属于普通对话，尚无持久人工工单及处理人收件箱。若发展为业务助理，这是一项必要增量：等待时保留资料、问题和当前业务实例，人回来后继续新一轮执行。

审批则多一个约束：**批准的必须是某一份具体内容、目标和版本。** 例如批准提交报告 A 后，模型又改了 A，就不能沿用旧批准。StaffDeck 的业务转人工和局部 App 确认可以参考，但不能替代这一整套版本绑定审批。

源码：[人工接管内核](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/handoff/core.py)、[业务接管服务](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/core/human_handoff_service.py)。

### 9.4 渠道接入的难点主要在身份与可靠投递

StaffDeck 有微信、企业微信、飞书和钉钉适配，渠道后台处理连接、接收、路由和投递；账号可以挂载员工，部分链路还支持团队。平台同时维护渠道身份关联、收件去重、发送记录和重试。

例如把员工接入群聊之后，需要回答的不只是「能否收到消息」，还包括：谁有资格调用哪个员工、群成员是否看得到私库内容、同一消息重投是否会再次执行、外部账号属于谁、机器人发送失败怎样补发。你已经建立的个人账号和私库边界必须延续到渠道入口。

建议只在试用团队明确使用某个渠道时接入一个，先固定员工与身份映射，再扩展自动路由。不要同时承担四种渠道的协议、凭据、附件和消息格式维护。

## 10. 文件交付、执行恢复与部署

### 10.1 文件写出来与成果交付是两个阶段

你的工作区区分输入、来源、中间文件和正式输出；运行返回输出引用后，发布事务检查文件是否属于本 Run、本用户、正确用途和内容摘要，再关联到正式消息。这样可以避免「模型说文件生成了，但页面没有可下载成果」的假成功。

StaffDeck 也有工作区、技能文件投递、工具执行和成果发现/发布服务。它更贴近本机运行，命令通过 SRT 或 Bubblewrap 等本地操作系统隔离机制执行；你的计算接线使用独立 OpenSandbox 环境。

| 问题           | 你的现状                                                 | StaffDeck 现状                                                                              | 取舍                                                        |
| -------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 没有计算环境时 | 可做获准的有界虚拟文件处理；命令能力需要已配置并验收沙箱 | 视管理员配置、平台和可用后端决定                                                            | 不应把普通文件工作区当作任意计算环境                        |
| 隔离在哪里     | 代码工作负载经 OpenSandbox 服务管理                      | 通常是宿主上的 OS 沙箱进程                                                                  | 前者多一套服务运维；后者更依赖宿主权限和平台特性            |
| 隔离失败       | 正式执行需满足沙箱配置和验收约束                         | 当前 Windows 命令分支在后端不可用或初始化失败时可退为无沙箱执行；管理员关闭隔离也可直接运行 | 不能仅凭「sandbox」名称比较安全性，要检查实际后端和失败分支 |
| 输出验证       | 文件归属、摘要、正式消息关联                             | 记录和发布成果，受平台能力入口控制                                                          | 两者都还需要验证文件内容是否正确、能否打开                  |

StaffDeck 的 Windows 回退由实际 `command.py` 执行分支确认，并非仅根据诊断文案推断。此处是特定平台条件，不能扩大成它在所有系统都无隔离。

源码：[你的成果发布](../../backend/app/conversations/publication.py)、[你的沙箱模块](../../backend/app/sandboxes/README.md)、[StaffDeck 命令执行](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/harness/command.py)、[沙箱后端](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/harness/sandbox.py)。

### 10.2 恢复语义不相同

你的启动恢复会把满足版本及安全条件的 Run 重新排队，利用同步 checkpoint 继续 SDK 状态；不满足条件的运行转为中断。外部 MCP 或沙箱能力会使自动恢复范围收窄。用户重新尝试失败任务则是另一次 Run，不能把它和原运行继续混为一谈。

StaffDeck 的孤儿运行恢复会终止丢失执行器的尝试，保留 SOP 节点、已填信息和任务状态，并保存失败回复，提示用户重新发送以继续。它的任务租约、调用账本、SOP 进度和引擎状态分别承担不同职责。

因此，不宜写「StaffDeck 支持任意任务自动断点续跑，你不支持」。更准确的比较是：**你在安全范围内恢复执行图；它强调保留业务流程位置并关闭失联尝试，后续再继续。** 外部写入仍需核对结果。

源码：[你的启动恢复](../../backend/app/execution/store.py)、[SDK 状态恢复](../../backend/app/agent_runtime/langchain.py)、[StaffDeck 孤儿执行恢复](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/core/harness_recovery.py)。

### 10.3 两者都需要正视容量与常驻成本

你的默认运行配置是 2 个并发 Run、20 个排队项、单账号 2 个活动 Run、180 秒运行时限、8 次模型调用、32 次工具调用，以及 128 KiB 的序列化输入预算。它们是代码默认值，可被环境覆盖；本次未读取部署环境，因此不是当前实例的实际参数报告。字节预算也不是模型 token 数。

这些限制可防止失控，但某些资料研究会在取证完成、最后综合前触顶。已有[预算放宽的历史对照](openspec-successful-comparison-2026-10-30.md)提供线索；不能据此认定所有问题只需增加调用次数。更值得做的是按任务预留总结机会，明确剩余预算，保留已读证据，并在停止时准确交付当前可确认结果。

StaffDeck 的桥接请求默认期限是 600 秒，属于引擎阶段期限，不能直接与上述 Run 总时限视作同一指标。它还包含模型路由、记忆提炼、反馈分析、流程格式修复等额外调用。某次回答背后可能不只有「回答模型」这一项成本。比较成本时应汇总这些阶段，而不只比较最终回复 token。

部署方面，两者默认业务存储均为 SQLite；你的 Runner 用文件锁限制同一数据目录的宿主，StaffDeck 也有数据库级运行实例锁，渠道还要求文件 SQLite 的单实例锁。租约和后台线程并不自动带来跨主机扩容。StaffDeck 有桌面安装与 CLI，是交付形式上的增量；你的代码和工具链当前更贴近开发环境。

StaffDeck 包含 `OSS_LOCAL` 和 `BUSINESS_BASE` 权限适配，但当前分发清单使用 `OSS_LOCAL`，框架管理功能被发行开关关闭。企业权限中心接口存在，不证明本次公开分发已经具备所有企业后台；租户字段也不证明租户注册、计费、配额及完整隔离均已形成 SaaS 产品。

源码：[你的预算](../../backend/app/execution/config.py)、[你的调度](../../backend/app/execution/scheduler.py)、[StaffDeck 运行锁](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/runtime_lock.py)、[产品开关](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/src/staffdeck_harness/product_features.py)、[分发配置](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/distribution/manifest.json)。

## 11. 反馈、评测与版本改进

### 11.1 StaffDeck 的闭环做到哪一步

它的反馈分析会结合回复和执行轨迹，归类为模型问题、技能指令问题、SOP 触发/信息/流转/资源问题、知识缺口或运行故障。模型给出归因、依据和建议，不能把这个自动分类直接当成已确认根因。

在此基础上，改进服务能针对 SOP 或通用技能生成候选版本，保存差异和反馈依据，交由人工审核；发布时保存旧快照，支持回滚。员工分支还允许局部修改而不直接覆盖市场原件。

但当前 `evaluate()` 的模式是 `static_v1`：SOP 检查结构和嵌套；技能检查正文有效性及是否有变化。源码明确标记基线/候选回放尚待接入。因此，准确评价是**有可审查的改进流程，还没有完整的效果验证闭环**。

源码：[反馈归因](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/feedback/service.py)、[候选、评估、审核与回滚](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/evolution/service.py)、[员工资源分支](https://github.com/OpenBMB/StaffDeck/blob/fcc28c003ef188e6d0a11596d44fdfb3723b275b/backend/app/agents/branching.py)。

### 11.2 你更值得先补「改动有没有用」的证据

现有动作、模型用量、来源快照和技能摘要，已经可以支撑问题定位。下一步可以让用户标记「结论错、证据不足、没用工具、文件不可用」，关联到具体回复和 Run；再把高价值案例整理成固定题集。

每次改模型、技能、切分或检索方式，用相同输入和资料分别运行旧配置与新配置，比较可交付率、关键事实、引用支持度、文件正确性、模型成本和人工修改量。先有这个机制，自动生成候选版本才有判断好坏的依据。

工程里的单元测试可以检查权限、状态和边界，但不能替代真实模型任务评测。相反，某次真实任务回答正确，也不能代替越权、重试、撤销和恢复测试。

## 12. 三个相同任务下的实际区别

以下是依据源码推导的使用过程，不是本次已经跑出的产品成绩。它们帮助判断哪些能力与你的目标有关。

### 12.1 「查阅两份规则，说明冲突并生成核对表」

| 阶段         | NiumaCrew                                               | StaffDeck                                        |
| ------------ | ------------------------------------------------------- | ------------------------------------------------ |
| 准备资料     | 正式接受 Markdown/TXT；PDF 需要先转换；处理后可预览片段 | 可直接处理文字型 PDF/DOCX 等，形成章节和主题索引 |
| 配置员工     | 选择本人多库及按需/先检索模式                           | 为员工或节点绑定知识资源                         |
| 查找依据     | 关键词与向量混合召回，必要时补读已登记证据              | 文档和主题路由、章节展开、证据片段               |
| 给出冲突判断 | 模型依据证据综合；引用身份受强检查                      | 模型综合，引用元数据与来源卡配合展示             |
| 生成文件     | 需要员工具备文件许可，并通过正式成果发布                | 需要相应工作区和成果能力                         |
| 仍需验证     | 是否找全互相冲突的条款、表格是否准确、引用是否支持结论  | 同样需要验证，还要观察目录路由是否遗漏关键文档   |

你的机会是把「答案和可核对材料一起交付」做完整：冲突条款、各自版本、原文位置、待人工判断项和下载文件。现有证据和成果边界正好能复用。

### 12.2 「每周检查资料更新，有重要变化再提醒我」

你的员工当前可以在用户发起时执行获准查询，但没有正式计划、版本比较和持续提醒闭环。StaffDeck 已有定时触发和渠道投递相关基础；真正「只在重要变化时提醒」仍需要任务定义、比较依据和通知规则，不能从「支持定时」直接推出。

你的增量应是监测任务和比较状态，复用已有 Run 执行。每次成功保存新比较依据；失败不覆盖旧基准；连续相同内容不重复提醒；暂停或撤权后不再调度。这比做一个每天固定输出长总结的功能更有明确验收标准。

### 12.3 「分析材料，等我批准后才提交到业务系统」

你目前能做分析和获准工具操作，但缺少跨运行的批准状态。StaffDeck 可通过 SOP、人工接管和工具调用组织流程；其现有局部确认也不能直接证明任意审批都锁定了最终提交内容。

你的可挖掘方向是保存「待提交操作」：具体目标、内容摘要、预期版本和提交身份。批准后重新检查这些条件；材料变化或凭据变更要求重新核对；网络超时进入结果未知，查询业务系统后再决定是否重试。这个能力可以跨多个业务复用，价值在于把授权和实际动作连接起来。

## 13. 未来方向与优先级

### 13.1 推荐的产品切入点

推荐先验证：**面向小团队知识工作的数字员工，让资料研究、规则核对和结构化材料整理能留下证据并交付成果。**

这是基于现有工程复用程度和与 StaffDeck 的功能差异提出的定位假设，不是市场调研得出的需求规模结论。它的优点是你已有私库、混合检索、来源核验、受控工具和正式文件交付；需要补的主要是默认体验、任务评测和资料更新，而非重建运行底座。

后续可延伸到带人工确认的业务助理。若真实客户的核心问题是客服分流、固定问答和复杂组织流程，StaffDeck 已有较多对应基础；此时应先比较采用或集成它的成本，再决定自建范围。

### 13.2 值得挖掘的八个方向

优先级表示建议顺序，非已采纳排期；投入大小为相对复杂度，不是工期承诺。

| 优先级与方向                | 对用户的具体价值                                 | 可复用基础                           | 关键新增                                                  | 投入/主要不确定性                          |
| --------------------------- | ------------------------------------------------ | ------------------------------------ | --------------------------------------------------------- | ------------------------------------------ |
| P0 默认能力包与稳定交付     | 新用户配置少量连接就能查资料、整理文本和下载成果 | 技能、MCP、目录、文件、运行快照      | 官方装配配方、就绪检查、结果归一、预算收束、验收样例      | 中；依赖真实服务、模型和任务难度           |
| P0 任务质量与引用支持度评测 | 判断一份回答能否放心采用；配置升级有依据         | Run、动作、用量、来源快照、历史对照  | 固定题集、期望事实、对照执行、人工标注和结果报告          | 中；题集是否代表真实工作决定价值           |
| P1 资料更新与可追溯分析     | 新资料及时可用，旧结论能解释依据，新旧规则能比较 | 原件、摘要、处理批次、片段版本、引用 | PDF/DOCX 正式解析、文档修订、增量向量、版本对照和失效提示 | 中到大；解析质量、版本保留与权限需一起设计 |
| P1 受控提交与人工等待       | 员工准备好内容，人批准后再执行                   | 工具许可、Run、正式成果、版本检查    | 业务实例、批准记录、待提交操作、幂等键、结果未知核对      | 大；业务副作用和目标系统能力差异大         |
| P2 可管理个人记忆           | 新对话复用稳定偏好，减少重复说明                 | 身份、员工、消息、运行上下文         | 记忆记录、范围、来源、修订、编辑删除、候选提炼            | 中；错误记忆和隐私范围比检索算法更先要解决 |
| P2 变化监测与定时任务       | 资料或目标变化时主动给出差异                     | 队列、知识/工具查询、历史成果        | 计划、持久领取、时区、比较基准、通知策略                  | 中到大；需要常驻执行和可靠投递             |
| P2 员工发布与团队资源复用   | 一组验证过的岗位可被他人安全复用和升级           | 共享员工、技能摘要、资源目录         | 包含依赖的员工模板、版本、兼容检查、升级预览和回退        | 中到大；不能把私人凭据或私库一起复制       |
| P3 独立复核与有限协作       | 对高价值成果增加独立检查或并行取证               | 多员工配置、Run 与文件证据           | 子任务关系、固定交付结构、复核意见、父级预算和取消        | 大；质量收益是否抵得过额外调用需实测       |

### 13.3 方向一：先把现有能力做成用户能完成的工作

可以直接沿用[官方基础能力包方案](../proposals/skills-and-mcp/foundation-capability-packages.md)，它当前是未实施草案，不需要再创建另一套能力数据库。

首版只需形成三种可检查组合：

1. 信息查证：搜索、提取相关正文、保存来源、形成有依据的回答。
2. 文件整理：读取获准的文本/CSV/JSON，生成并交付用户能打开的成果。
3. 计算处理：只有沙箱经过目标环境验收时才开放，要求保存可核对计算结果。

技术增量应落在原有职责内：`agents` 提供装配预览，`skills` 管方法包，`tools` 把供应商响应转换为统一来源和错误，`agent_runtime` 组织阅读及收束，`conversations` 继续负责交付。目录只汇总就绪状态，不成为另一份授权事实。

一次验收要覆盖正常成功、资料不足、服务超时、长结果续读、预算将尽和成果不存在。指标分别记录任务完成率、来源支持度、文件可用率、用量及耗时，不把它们压成一个模糊分数。

### 13.4 方向二：把知识来源变成可持续维护的依据

首版可以围绕「同一份资料更新后，怎样重新回答和核对旧结论」展开，分三步实施：

1. **扩大输入但保留来源。** PDF/DOCX 解析进入后台处理，保存页码、段落或表格位置及解析诊断；扫描件无文字时明确失败或提示转换，不用空结果冒充入库成功。
2. **增加正式修订。** 区分「某份业务文档」与「它的某个版本」，让处理任务和片段引用固定版本。替换文件产生新修订；旧回答标明当时版本，是否仍可打开原件另按保留与权限规则决定。
3. **增量更新和比较。** 按文件/片段摘要识别变动，只为新内容生成向量；完整校验后发布新索引。比较结果列出新增、删除、冲突和受影响结论，避免只生成一段「已更新」的文字。

要守住的失败条件包括：旧处理任务迟到、重切后的片段 ID 改变、用户删除资料、向量服务故障和任务重启。不能为了展示旧来源绕过当前访问控制，也不能把新版片段拼到旧回答里冒充原依据。

验收可用固定样例：修改一个关键数值、删除一条规则、移动章节但不改内容、上传同名不同内容、上传无可提取文字的 PDF。检查是否正确识别变化、有没有读到错误版本，以及重建成本是否下降。

### 13.5 方向三：小范围业务流程与可靠提交

首版建议只支持四种节点：员工分析、确定性检查、人工决定、受控操作。继续使用[现有流程草案](../proposals/configurable-workflows.md)的模板与实例边界。

需要新增的核心事实可以控制在以下范围，具体表名待设计时确定：

| 业务对象         | 保存什么                                   | 为什么现有 Run 不足以表达                |
| ---------------- | ------------------------------------------ | ---------------------------------------- |
| 流程模板版本     | 节点、允许连接、输入输出和资源要求         | Run 是一次尝试，不是可复用业务定义       |
| 流程实例         | 当前节点、目标、输入版本、等待或终态       | 同一业务可能跨数天、多次 Run             |
| 人工决定         | 决定人、批准内容摘要、目标版本、有效期     | 聊天里的「同意」缺少明确绑定对象         |
| 待提交操作与回执 | 规范化参数、连接身份、逻辑幂等键、结果状态 | 工具动作完成与业务系统已落实不总是一回事 |

执行顺序应为：生成候选成果 → 保存并校验 → 发起人工决定 → 决定绑定该版本 → 新 Run 重新核对权限、身份和目标 → 提交 → 保存回执。审批期间原 Run 可以结束；批准不意味着整个员工永久获得更大权限。

必须验证：重复点击批准只提交一次；批准后修改材料需要重新批准；撤权后不能继续；外部系统成功但回传丢失时进入结果未知；拒绝和过期都不产生写入。先在无真实副作用的测试服务中验证，再接具体业务。

### 13.6 建议的三阶段交付顺序

| 阶段                 | 可以交给用户的成果                                           | 进入下一阶段的条件                                           |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 第一阶段：任务可完成 | 少量官方员工/能力组合、明确就绪检查、成果下载、固定评测报告  | 同一题集可反复运行，失败原因可解释；新配置的质量和成本有对照 |
| 第二阶段：资料可维护 | 结构化解析、修订和更新对照、增量向量；按试用场景补可控记忆   | 资料更新不混版本，原引用和权限边界可验证；用户确实反复使用   |
| 第三阶段：流程可持续 | 一条带人工决定和受控提交的流程；再按实际需要加计划或一个渠道 | 等待、重启、撤权、重复提交和结果未知均有明确处理             |

工期需要结合开发人数、目标环境和试用场景另估。本次没有这些信息，因此不提供「几周做完」的假精确承诺。

## 14. 如何验证产品方向，而不是只验证代码能跑

建议选一组真实但可脱敏的资料，建立 30 道首轮题集。这个数量是便于启动的建议，不是统计意义上的充分样本。题目可包含准确查找、同义表达、跨文档冲突、无依据问题、资料更新和文件交付，先保证每类有可核对答案。

比较你的旧配置、新配置与 StaffDeck 时，要固定输入资料、问题、模型版本和可用工具；无法固定的差异明确记录。StaffDeck 自带岗位或流程可另列「默认体验组」，避免把默认资源差异误当成运行引擎差异。

| 评估问题         | 记录方法                                           | 防止什么误判                 |
| ---------------- | -------------------------------------------------- | ---------------------------- |
| 任务真正完成了吗 | 按预先定义的交付物逐项判断，区分完整、部分和失败   | 模型说「完成」就计成功       |
| 事实与判断可靠吗 | 人工核对关键事实、冲突项和遗漏项                   | 答案流畅就计正确             |
| 引用支持结论吗   | 抽取关键结论，检查引用原文是否足以支持             | 来源真实就计推理正确         |
| 文件可采用吗     | 实际打开、检查结构和数据，核对下载归属             | 有链接或有文件名就计交付     |
| 成本和速度如何   | 记录所有模型阶段、向量请求、工具次数、总时长和重试 | 漏算路由、提炼和修复调用     |
| 失败是否可恢复   | 断网、进程重启、撤权、修改资料和重复提交的定向检查 | 把重新跑一遍称作安全续跑     |
| 用户愿意持续用吗 | 观察再次使用、人工改动量和完成同类工作所需时间     | 注册或试用一次就认定需求成立 |

第一轮先建立基线，再根据试用团队对错误的容忍度设通过门槛。不同任务不必共用同一门槛：辅助草稿允许人工修改，自动提交则必须满足更严格的授权和回执条件。

## 15. 当前值得保留、需要补齐与暂缓的选择

**值得保留的基础**是宿主与模型分工、个人账号和员工许可拆分、知识证据登记、快照与当前授权并行检查、成果文件正式发布。它们能降低运行过程与最终交付不一致的风险。要把这些变成产品优势，还需要用户能理解的结果展示和任务质量数据；不能仅凭代码设计声称整体比 StaffDeck 更安全或更可靠。

**优先补齐的缺口**是默认可用任务、检索与成果的实际质量、资料格式和更新体验，以及必要的模型接入范围。当前聊天预设比较集中，会限制不同成本和模型能力的对照；增加预设时仍应保留凭据版本、协议适配和实际连接验收，不能只把任意 URL 文本框开放出来。

**暂缓大规模投入**通用流程画布、员工竞标、全渠道、完整模块 SDK、自运营市场和多层自动记忆。StaffDeck 的实现说明这些方向有工程内容，也说明维护面会迅速扩张。等真实使用暴露对应问题，再逐项建设，能让投入与用户价值保持联系。
