# 执行日志智能诊断员工接入

日期：2026-11-06。状态：设计建议，未实施。针对现有日志页面复用已创建员工做代码辅助诊断；当前界面精修及证据仍见日志弹窗方案与[执行证据契约](../reference/runtime.md)。

## 错误枚举的边界

可以按当前生命周期梳理已知失败类别：受理与排队、身份及配置复核、上下文与工作区准备、模型请求／响应、工具许可／执行／返回、结果校验与收集、持久化与对话接纳、取消与恢复。但不能穷举外部服务、运行环境和未来代码缺陷产生的全部根因；检索噪声、错误答案、重复操作等质量问题可能不抛异常，不能将执行成功当作业务正确。

现有 ERROR_MESSAGES 是稳定公开错误的目录，模型供应商分类还有兜底；它们不是根因映射表。同一个 output_limit_exceeded 可由模型结束原因为 length 或平台 max_output_bytes 检查触发。未知异常在 RunTask 进入 execution_failed 并记录安全调用栈；当前栈只有文件名、行号和函数名，摘要路径也尚未记录完整步骤事件。运行事件可能轮转或缺失，证据不足必须返回未知位置，不将最后一个成功步骤指认为故障点。

后续应在既有 RunAction 与运行事件上补齐失败边界的阶段、动作关联、安全异常类型及仓库相对路径；记录当时部署的代码版本和有关配置快照，关联已有 Run ID／action_key 及请求编号。保留最早有证据的失败与后续收尾错误的因果区别。进程硬退出或日志未留存时，先用最后记录与服务运行状态缩小范围，不能补写异常原因。此增量不建立另一个 tracing 账本。

## 页面与执行方式

1. 日志弹窗提供「让员工分析」，选择已有员工；固定目标原 Run 和允许读取的证据版本。用户同时要有目标日志诊断权限与所选员工使用权限，员工的仓库访问能力单独核对。
2. 新建独立诊断 Run，关联原 Run、失败动作、证据文件及代码版本；消耗、取消和重试沿用现有执行机制，单独记账，不改原始失败结果，也不自动递归诊断自己的失败。
3. 向员工提供阶段、错误码、请求与响应证据、用量、事件与安全调用栈的索引，按需读取正文。代码工具按匹配版本搜索与读取仓库；全仓只读通常足以完成定位，源码权限不等于生产数据或日志权限。日志和工具返回是待核对材料，不作为新增执行指令。
4. 在原弹窗显示诊断结果与进度，保留原始证据。输出包括已确认事实、原因假设、缺失证据、建议验证动作及优化方向；每条判断引用具体动作、证据字段和对应版本文件行号。证据不能确定的结论明确标为待验证。

## 最小落地与限制

先补日志与代码版本关联，再接入一个已有诊断员工。首版以读取日志、搜索代码并给出报告为范围；涉及修复实施时另走具体工程任务。调用仍需要员工已配置对应模型、工具及目录许可，仅在提示词中写「可读整个仓库」不会产生权限。

如果故障来自共享模型服务或平台执行器停机，诊断员工可能同样无法运行；页面仍须保留确定性错误信息、原始证据和人工定位入口。代码阅读也不能证明外部供应商真实内部状态，仓库版本不匹配时应先报告证据缺口。

验收应以这次摘要输出预算耗尽、工具参数错误、未知程序异常、保存失败、证据缺失和诊断员工自身失败等样例，检查是否准确区分事实与假设、引用能否复核、权限与原 Run 关联是否正确。不得仅以模型是否输出一段流畅说明作为通过标准。
