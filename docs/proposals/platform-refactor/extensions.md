# 后续能力：什么时候值得增加新概念

本页说明[重构方案](README.md)如何接住后续能力，不把未来功能当成本次必须建立的目录和表。具体业务仍由对应专题维护。

## 1. 增加结构前先问四个问题

1. 当前是否已有真实操作和使用者？
2. 它是否有独立 ID、数据、规则或生命周期，现有记录放不下？
3. 不增加它，是否会重复保存状态、丢失必要事实或破坏边界？
4. 能否先用现有用例和明确函数完成，而不创建通用框架？

只有出现实际职责和验收场景，才确定文件树。旧版预设96个后续文件的清单撤回；不是删除未来能力，而是避免把尚未确定的实现误写为施工要求。

## 2. 一次模型输出、动作、步骤与计划

一次模型调用可能返回正文，也可能提出工具请求。实际执行工具后，再次请求模型仍属于同一 Run。

RunAction 记录已经开始的动作；模型提出但尚未执行的请求是调用结果的一部分，不能标成已完成动作。

“读取日志、找出原因、给出建议”是一份计划。计划项可能对应多个实际动作，也可能在执行中改变；不能用计划勾选取代真实动作与用量。

当前只需显示模型产生的计划文字时，可以作为回复内容，不增加 Plan 表。需要编辑、版本、逐项确认或跨处理引用后，再建立独立计划记录。

## 3. 计划模式

计划模式首先是本次运行的行为限制与产出约定：

- 允许使用哪些操作；
- 哪些写入必须拒绝；
- 输出的是建议还是已经执行的结果；
- 用户如何开始后续执行。

不能只靠提示词声称只读。新增具有副作用的工具前，需有实际调用边界实施限制。当前没有任意写工具，不提前建设完整审批系统或 mode 继承框架。

计划模式不是新 Run 上面的一层对象；接受时冻结本次模式，发布时明确其产出含义即可。

## 4. 执行中追加输入与人工等待

当前运行中不接收新的 start。未来要增加补充输入，需规定：

- 补充给哪个准确 Run；
- 下一个受控边界何时消费；
- 已开始工具使用哪份参数；
- 输入如何排序、去重与记录已消费位置；
- 停止和追加竞争如何决定。

这些事实不能靠覆盖 Run.input_snapshot 表达。真正需要时新增输入记录和消费序号，不复用观察 revision。

等待用户回答或审批也需要持久原因、到期、恢复与界面操作；只加 waiting 枚举不算实现。审批与业务验收分别设计。

## 5. 正式任务与交付验收

只有产品需要明确目标、交付要求、负责人、成果版本和验收状态时，才值得建立 Task。

Task 可以发起多次 Run，调用共同的执行能力；Run 成功只说明处理正常交付，不说明任务已经被用户验收。对话可以关联任务，但不把 Conversation 直接改造成任务状态机。

新来源由自己的关联与共享发布流程承接，不让 execution 反向读取 Task ORM。确有第二个实际来源后，再提取重复的接受和发布协作。

## 6. 持续目标与定时触发

Goal 决定一次 Run 结束后是否再开始下一次，拥有累计预算、继续条件、暂停和停止。它不代替 Task 的业务要求，也不占用一个永不结束的 Run。

Schedule 负责何时触发和记录触发结果。跨登录持续运行需要明确授权依据，不能假定原用户会话永远有效。

当前不创建 GoalController、ScheduleService 或通用 workflow 引擎。先有一个具体持续任务和停止验收，再选择实现。

## 7. 标准方法与通用工具

[技能与 MCP 专题](../skills-and-mcp/README.md)继续维护方法资产、连接与权限的业务方向。

方法告诉员工怎么做，工具连接提供技术访问，员工许可决定能否使用。方法文本不能授予凭证权限。只有当前 CI 专用访问被提炼出实际复用，才建立通用连接与调用模块。

通用能力接入不能丢掉 CI 的来源、引用、范围和覆盖校验。先通过等价验收，再决定是否替换专业执行器，不在本次承诺统一自由循环。

## 8. 知识、评测与后台作业

[知识专题](../knowledge-assistant/README.md)继续定义资料导入、版本、发布和检索；现有静态标题/正文筛选仍是教学能力，不改称真实检索。

文档解析、索引构建和批量评测通常有自己的长作业进度、失败项和重建规则，不因为它们在后台运行就全部塞进 Agent Run。

检索通过受限调用返回有来源和版本的片段；回答运行记录实际使用的资料依据。评测需要固定数据和评分，Run succeeded 不能充当质量合格。

## 9. 规模变化

当前使用单执行宿主和 SQLite。只有实测出现多进程调度或容量需要，才设计租约、分布式队列、跨进程取消与恢复。

增加新的基础设施要保留同样的业务约束，并写清原子性如何实现，不能把“以后可接消息队列”当作已经解决。

本次完整目标树只展开当前能力重构所需的文件；未来专题保留在现有文档中，新增代码以具体实施方案为准。
