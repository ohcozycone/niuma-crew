# 能力接入、装配与运行实施验收

日期：2026-10-29。依据[最终实施计划](../proposals/skills-and-mcp/execution-plan.md)，在当前共享工作树实施；仓库尚无可引用提交。本记录只证明下述实际范围，不把 SDK 能力、历史测试或模型自报当成验收。

## 独立评审结论

三个独立 Agent 分别审查 MCP 生命周期与身份、Skill 资产与运行、前端装配和保存边界。设计结论：保留模块化单体与现有 OpenSandbox；不增加独立 Sandbox Service、通用插件框架、员工复制或上传微服务。stdio 使用可信子进程，不能宣传为安全隔离。

| 发现                                          | 处理                                                                       |
| --------------------------------------------- | -------------------------------------------------------------------------- |
| 普通 tools:update 不能代表有权提交宿主程序    | stdio 定义单独要求管理员，部署默认关闭；账号只能填声明的环境凭据           |
| 环境变量能改变程序搜索、解释器加载或代理      | 拒绝启动控制键，结构化 argv、私有 cwd、最小继承环境                        |
| SDK 可能遗漏主程序退出后留下的后代            | 独立进程组内的薄启动器兜底；真实 PID/孙进程退出检查通过                    |
| Run 关闭后迟到调用可能重新开进程              | caller 与客户端关闭状态不可逆，补关闭后调用拒绝测试                        |
| 沙箱回收异常跳过 MCP 清理                     | 嵌套 finally；故障注入确认 MCP 仍关闭且保留原异常                          |
| Skill 共用个人附件 TTL 会误删共享资产         | 独立内容寻址目录；Run 冻结清单，不复制员工，不自动清除旧 blob              |
| 标准源文与 description 可分别改成两份事实     | 标准包从 SKILL.md 投影描述；拒绝独立旧字段覆盖，legacy API 兼容            |
| 已装配 Skill 依赖当前搜索页，丢名称与参数规范 | 按已装配 ID 独立取真实详情；候选搜索和分页只在选择器                       |
| MCP 导入模板看似已配置凭据                    | 保留变量键、空值/模板转待填输入；账号保存必须填写实际值                    |
| 长结果核验可能混入旧 Run 游标、意图识别过宽   | 只处理当前 Run 来源；网页目标识别限定明确读取指令，普通 URL 讨论不强制检索 |

交叉代码评审完成后，上述发现均已处理。管理员信任同时包括 stdio 程序暴露的工具行为；若登记宿主 Shell 执行器，平台无法从工具 schema 通用判断参数中的代码。该情况不属于内置沙箱执行的保护范围。

## 落地范围

- 能力库统一入口、搜索/类型/数量/刷新/添加菜单，MCP 和 Skill 紧凑卡片；内置工具独立次要入口。
- MCP HTTP/stdio 定义、通用导入预览、个人/明确共用账号密文、目录与说明确认、中文别名保留原始名、员工逐工具装配。
- 大脑移入员工基本信息；工具与 Skill 摘要、添加选择器及配置侧栏，面板完成只改草稿，员工主保存同事务提交。
- 标准 Skill ZIP 预览/导入、完整 SKILL.md、脚本/参考/二进制文件的统一保存和导出；旧输入/输出/示例完整进入模型。
- Skill 文件按冻结清单读取，已激活包在 execute 前投递当前 Run 沙箱的相同路径；平台内置执行不回退宿主。
- MCP 服务说明进入来源标明的运行指导；结果持久保存、受原工具许可约束的本轮分页读取；明确网页读取任务缺证据时准确失败。

OAuth、员工广场/复制、容器 stdio、Docker Gateway、独立沙箱重建与跨节点队列未实施。它们不属于本轮有效实施范围。

## Context7 真实 stdio 接入补验（2026-10-29）

用户反馈手填与导入 Context7 均无法接入，核对本机后端配置发现 `TOOL_MCP_STDIO_ENABLED` 未开启；两种入口共用 `validate_stdio`，因此都会在安装或协议握手之前被拒绝。此次按用户要求只在本机 `backend/.env` 开启可信 stdio，并触发开发后端重载；项目默认关闭策略不变。健康检查恢复成功。

从官方 npm 查询并运行固定版本 `@upstash/context7-mcp@4.4.4`，宿主 Node.js `24.18.0` 满足最低 `20.18.1`。直接使用平台 `StdioMCPClient`，不注入 API Key，真实发现 `resolve-library-id`、`query-docs`；分别查询 React 库与 useEffect 清理文档，均返回 `success`，内容包含实际库标识和带来源的文档片段。`finally` 关闭 SDK 会话，不保留常驻测试进程。

通过现有 `McpDefinitionService.import_config/create` 与 `ToolService.create/discover/approve` 在本机能力库登记 Context7 固定程序、个人匿名连接，并确认两项工具目录；未修改员工许可。导入预览、服务定义、账号、候选与批准均走原有代码，无 Context7 厂商适配器或表结构变更。本次没有调用聊天模型；带真实个人 API Key、其他宿主及云上部署未验证，匿名成功不保证后续额度。配置与完整操作见[部署指南](../guides/agent-tools.md#可信本机-mcp)。
