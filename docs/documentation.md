# 文档组织与维护规范

适用于本工程的开发者与 AI。项目级文档按用途集中在 `docs/`，模块实现说明与源码相邻；同一规则只保留一个详细维护位置。入口是[文档索引](README.md)，运行命令由根 Makefile 提供。

## 代码、注释与文档如何分工

| 信息                                           | 主要维护位置与验证                                 | 文档或注释补充什么                                                       |
| ---------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| 签名、DTO 类型、必填和可空、外键、默认值       | 类型、Pydantic、ORM、正式迁移与测试                | 业务含义、缺省与清空、兼容和生命周期；不复制整份 OpenAPI 或逐函数清单    |
| 命名、格式、可稳定判定的导入边界               | 实际启用的 Ruff、ESLint、TypeScript 配置及配置回归 | 工程手册解释意图、适用范围与例外；安装工具不代表启用规则                 |
| 权限、事务、幂等、状态转移、敏感字段隔离       | 服务和数据库中的强制检查，以及拒绝、竞争和故障测试 | reference 定义跨入口契约，模块 README 解释实现协作；文字不能代替代码检查 |
| 局部反直觉实现、竞态、顺序、资源释放、兼容处理 | 实现附近的短注释、针对风险的测试                   | 为什么必须这样做、何时可移除；不逐句翻译代码                             |
| 跨模块依赖方向、所有权和共用工程要求           | architecture、engineering 与模块入口               | 解释协作原因、例外和检查方式；可自动检查的部分同步落到工具               |
| 启动、备份、迁移、排错                         | guides，链接实际脚本和配置                         | 前提、步骤、可观察结果、失败与恢复，不另存一份可执行脚本                 |
| 尚未实施的行为与结构                           | proposals                                          | 有效需求、假设、增量方案、未定项和验收，不作为当前实现证据               |
| 一次评审、实验与验收                           | records 及原始证据                                 | 日期、适用版本或快照、方法、结果与限制，不作为永久通过的证明             |

例如：SQLite 零匹配 UPDATE 为什么必须早于读取，由事务工具旁的注释和竞争测试解释；哪些检查与配置必须原子保存，由业务契约定义。`omitted_field()` 的机制由代码维护，PATCH 省略、显式空值和并发冲突的对外含义由现行接口契约维护。

先查现有维护位置。代码与短注释不足以表达跨文件协作、外部契约或重复操作时再增加 docs 正文。内部辅助函数、工具已完整表达的格式细节和临时排查过程不单独建文档。关键行为既要有实现证据，也要让维护者理解应保持的约束；两者承担不同职责。

## 目录与职责

| 位置                        | 负责内容                                               | 边界                                                                                                |
| --------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 根 README                   | 项目定位、功能地图、首次阅读顺序、启动与主要入口       | 新读者可先了解平台，再进入流程及架构；不复制完整配置或 API                                          |
| 根及端内 AGENTS             | 适用任务的必读导航与执行入口                           | 人与 AI 共用正文，不重复一套工程标准                                                                |
| docs/README.md              | 按任务和主题检索                                       | 当前文档优先，方案与记录单列                                                                        |
| docs/documentation.md       | 本规范                                                 | 组织与维护规则的唯一详细来源                                                                        |
| docs/product/               | 当前产品概念、功能作用、用户操作、结果及执行链路       | 面向陌生读者；不把实验和未来规划写成可使用功能，详细接口和部署参数链接原维护位置                    |
| docs/architecture/          | 当前模块、部署、生命周期、协作与领域术语               | 未采纳结构进入方案；历史图明确标记                                                                  |
| docs/engineering/           | 共享、前端、后端工程标准与验证选择                     | 不累计实施流水账或复制业务契约                                                                      |
| docs/reference/             | 现行业务、接口、数据、权限及界面契约                   | 按业务主题归属；较小时一份文件即可，复杂后再拆                                                      |
| docs/guides/                | 开发、配置、迁移、备份和排错操作                       | 参数只维护一个完整定义位置，链接实际代码                                                            |
| docs/learning/              | 学习路线、代码阅读和练习                               | 学习掌握标准与功能实施状态分开                                                                      |
| docs/codebase/              | 源码调查、实际调用链、状态归属、依赖及验证边界         | 标明调查时点与证据；作为代码导航，不替代 architecture、reference 和工程手册；更新调查时重新核对实现 |
| docs/proposals/             | 未实施增量、设计取舍、开发任务和验收计划               | 生效细则合入 reference；保留动机与剩余增量                                                          |
| docs/records/               | 重要评审、取舍与实际验收                               | 只证明记录时的范围；未落实建议需核对后进入方案                                                      |
| docs/templates/             | 按用途裁剪的模板                                       | 不要求填写无关章节                                                                                  |
| 前后端 README               | 端内入口、专项操作和模块导航                           | 工程标准链接手册，详细操作链接指南                                                                  |
| 源码旁模块 README           | 产品作用、正常流程、设计原因、文件职责、依赖与维护入口 | 先建立业务理解再说明实现；不逐函数罗列，不复制字段/API，不累计多轮验收                              |
| frontend/src/design-system/ | 当前视觉、组件状态、令牌用途与维护入口                 | 数值由 CSS 和机器配置维护，历史验收进入 records                                                     |
| backend/datasets/           | 示例资料、题目、答案与审核数据                         | 属于应用或教学数据，不作为工程规范，不默认送入模型                                                  |

只创建已有内容需要的目录。模块 README 按独立业务或公共职责建立，不要求每个子目录都有。图与可编辑源相邻或通过明确链接关联，标明当前、拟议或历史用途；图中出现模块不代表已实现。

临时产物写入系统临时目录。大型截图、日志、母版等长期证据继续保存在同级 `niuma-crew-archive/`；主工程保留完整可读的文字结论。归档是可选历史依据，不能成为运行、构建或理解当前规则的前置。

## 人与 AI 的阅读入口

1. 首次运行从根 README 开始，按需进入开发或数据库指南。
2. 初次了解平台从产品与功能说明开始，再读使用流程、系统架构、前后端架构及相关模块；代码用于继续核查，不能成为理解模块基本作用的前置。
3. 修改已有功能，读取适用工程手册、现行契约、模块说明及相关代码和测试。
4. 新能力或边界变化先确认当前行为，再阅读或新增对应方案，明确未定项后连续设计、实现和验证。
5. 排错优先查看当前代码、配置、日志和测试，旧记录作为限定版本的线索。

AGENTS 只提供导航，具体任务按影响范围继续读取。视觉任务同时读设计系统，纯后端任务无需加载视觉细则。现行文档、方案和记录不得互相替代。

## 面向新读者的说明深度

平台说明回答「给谁解决什么问题、有哪些功能、它们怎样组合、当前可用范围」。流程说明按真实操作解释前提、输入、正常处理、用户结果及主要失败恢复；需要跨模块理解时，用时序图或流程图连接页面、业务和执行。

模块 README 分为产品和设计两个维度，章节按实际复杂度裁剪，不要求机械填同一套表格。

1. 产品维度先用普通语言说明作用及一个适用例子，定义必要业务对象，并描述从输入到用户结果的正常过程。无独立界面的公共模块说明它支撑的用户行为。
2. 设计维度展开核心对象怎样存储、主流程怎样在实现文件间推进，以及事务、状态和资源为何这样划分。设计图中的节点和箭头对应实际对象、文件及交换内容；正文解释图中的机制和取舍，不能只列边界或换成目录方框。设计理由来自代码/契约事实或明确的工程推断，不能虚构历史动机。
3. 文件职责优先使用带注释的目录树，一行一个实际文件。注释用完整动词说明处理什么及产生什么结果，例如「提供岗位配置的创建、查询、修改和删除接口」，避免拼接「员工、技能、账号」等对象名。相关文件在正文中按机制一起解释，树负责定位，不替代设计说明。空包标记、生成文件和测试按类别说明。
4. 依赖说明谁调用本模块、本模块使用谁、交换什么，并区分源码导入、注入回调和同库数据关系。图中的箭头注明是调用、数据流还是部署关系，不能让职责图暗示已拆服务。
5. 在正常流程之后解释权限、版本、事务、取消、失败和恢复等实际相关边界，给出契约、实现及验证入口。历史阶段编号只有在理解当前兼容行为确有必要时才出现。

验收时让一个未读过源码的读者尝试解释模块作用、对象关系、正常流程、文件分工及依赖方向。链接用于继续深入，不能代替本篇最小背景。架构图以自包含 SVG 为可编辑源，PNG 是同内容导出；结构变化时一起更新图与说明。

改写模块说明时，将新信息合入它影响的机制并删除重复前言。当前 README 连贯描述完整设计，阶段编号、补充经过及验收流水不承担设计主线。

为避免架构漂移，新增或调整能力先核对当前产品目标、数据/生命周期所有者及已生效边界；接口、权限、事务或部署变化进入相应正文。尚未实施的方向留在方案，AI 不能从未来模块名推导当前架构。

## 状态与冲突

| 类型                     | 开头应说明                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------- |
| 现行架构、契约、模块说明 | 适用范围、实现和测试入口、已知限制；不要求设计状态表                                                     |
| 工程规范                 | 范围、规则、例外、实际工具覆盖和人工评审边界                                                             |
| 方案                     | 设计状态（草案、已采纳、已撤回或已取代）、实施状态、实质更新日期、范围与入口；部分实施列明完成和剩余增量 |
| 记录                     | 日期、适用版本或可复现快照、来源、实际方法与结果、未覆盖范围；历史原文明确其时点                         |

已采纳不等于已实现，一次测试通过不等于持续通过。配置数量、演示和模型自报不能证明执行完成。代码与迁移提供实现证据，是否部署及真实上游是否可用需要另验。

用户有效需求决定应有行为。文档与代码冲突时，分别说明需求、当前实现和差异，判断是实现缺陷还是说明过时后修正；不能仅按更新时间或静默选择一方。模型建议、假设和已否定方案不自动成为需求；历史旧行为不向当前正文扩散。

## 格式与内容深度

- UTF-8 Markdown、中文说明，代码标识保留原文；一个一级标题，后续按二、三级标题组织。
- 文件名使用有意义的小写短横线。当前文档不用 final、日期或版本副本；记录可用日期标识独立事件。重命名更新引用，历史由版本管理追踪。
- 仓库内用相对链接，代码入口链接文件而非易变行号。移动段落同时更新锚点引用，代码块中的示例路径也需核对。
- 目录结构统一使用 `text` 代码围栏和 `├──`、`│`、`└──` 的 tree 风格，一行一个实际节点；拟议结构明确标注，不用缩进清单冒充目录树。
- 字段表按需包含类型、空值、默认、含义和约束，区分数据库、应用与展示规则；API 说明权限、成功及主要错误、幂等和例子，不复制完整 OpenAPI。
- 跨端契约说明 DTO 映射、状态生命周期及展示控制与后端授权的关系。常量和派生值优先链接源定义，不维护第二套数值表。
- 方案至少说明目标、范围、当前与目标差异、职责、主流程、失败与验收；数据、权限、外部依赖、迁移在涉及时展开。拟议 SQL 留在方案，正式迁移目录只放执行代码。
- 注释、README 和 docs 重点解释原因、边界和可观察行为，不逐句翻译代码、复制目录或保留无效讨论。
- 示例使用虚构数据或占位符，不含密码、Cookie、token、API Key 或隐私。

## 维护与验收

1. 定位权威正文与影响范围。小修复直接更新相关说明，新能力或边界变化先写可实施增量方案，不为每次改动新建整套文件。
2. 已授权范围内连续完成设计、实现和验证，不因写文档额外增加审批；真实关键需求缺失时再澄清。
3. 实施时同步修正方案，保留有效取舍、撤销失效假设。生效规则合入当前正文，方案链接它并维护剩余增量。
4. 实际验收进入记录，当前规则与历史记录分开；交付更新索引、模块入口与全部引用。
5. 运行 `make check-docs` 检查项目 Markdown 文件与章节链接、docs 索引可达性；工具生成缓存（如 `.impeccable`）不进入项目文档扫描。归档默认仅报告数量，可用检查脚本的 `--check-archive` 在本机核对；不访问外网，也不判断业务语义。
6. Markdown 排版使用前端现有 Prettier 配置；代码和检查工具改动执行匹配的静态检查与定向测试。仅文档改动不机械重跑全量业务测试，交付说明实际结果及未覆盖范围。
