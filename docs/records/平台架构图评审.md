# 平台架构图评审

日期：2026-11-08。范围：当前工作区的目标架构图、后端职责及执行接纳链路。方法：阅读现行文档和关键源码，对照 C4、arc42 及端口与适配器原始资料。本次未修改执行行为、未运行业务测试；下文命名和绘图建议反映初版评审时点，后续采纳结果以系统架构正文为准。

本记录评审的是初版模块分区图。后续图示统一维护在[系统架构](../architecture/overview.md#模块分工)，当前以一张逻辑职责图表达受理、应用与执行；绘图调整不代表相关业务能力已实施。

## 结论与图的用途

原图保留了“业务应用使用公共执行、再独立接纳结果”这条正确主线，但同时表达平台总览、后台模块和局部实现，展开深度不一。入口分类混用了渠道、协议、触发机制和内部工具适配；资源分组缺少内聚依据；基础设施适配与实际存储重复出现。仅修改名称和曲线不足以解决这些问题。

先确定图要回答的问题，再决定粒度。平台总览回答“通过哪些应用和系统提供服务”；后台组件图回答“业务由哪些模块负责、怎样复用执行”；运行协作图回答“一次对话或业务任务怎样受理、执行和交付”。这三个问题可以分别用图说明，不能要求一张图同时承担全部细节。

C4 的容器图以应用和数据存储为主要元素；组件图聚焦一个容器的内部职责，可把相连的外部应用作为配角。不是禁止不同类型元素同图出现，而是需要明确边界、类型和展开层级。参见[容器图](https://c4model.com/diagrams/container)、[组件图](https://c4model.com/diagrams/component)。

## 用问题检验分组

### 入口回答“从哪里来”，还是“要做什么”

浏览器、IM 是交互渠道，HTTP 是协议，Webhook 是事件交付方式，时间调度负责识别到期。它们不对应互斥的业务：HTTP 可以提交对话、管理计划、查询状态；Webhook 可以创建工作，也可以推进已有工作。SSE 主要承担进度观察和结果传输，不决定执行哪一种任务。

平台对外提供的是业务能力，例如提交对话、创建或管理任务、确认某项动作、查询进度及取消。入口把不同来源转换为这些应用请求；业务目标、归属和完成条件由应用模块解释。已登记的事件订阅还需把事件映射到用户委托和工作规则，不能把任意 Webhook 载荷直接当成获准执行的模型指令。

总览可用“交互与触发来源”表达驱动方式，在其中区分平台 Web 界面、外部调用方和时间触发。组件图再展开请求接入、事件接入和时间调度。内置定时器属于平台内部，不能仅因它提供触发信号就放到外部系统边界之外。

用户关于“同一服务可由对话或其他方式驱动”的理解，与端口与适配器的基本思路一致：应用能力通过稳定入口供不同驱动方式使用，而不是为每种技术入口复制业务。参见[原始文章](https://alistair.cockburn.us/hexagonal-architecture/)。这不代表当前代码已完整采用该架构模式。

### 管理工具适配为什么会出现在主入口旁

它只对应一种具体接线：用户在对话中要求“每天九点整理新闻”，Agent 调用创建计划工具，由适配把结构化参数交给任务管理入口。创建计划与执行某一期新闻工作是两件事。

这个适配与 Webhook、HTTP 不在同一分类维度。它是运行时可调用的某个业务工具实现，不应作为总体接入中的第三个主模块。下一版主图建议省略；在“对话创建计划”的局部协作图中，说明由应用装配工具、执行内核只依赖通用工具接口即可。

### 左右位置是否表达了不同层级

原图将业务应用放左、执行放右，是为了表达使用者到提供者的调用方向。这个布局本身成立，但没有充分说明它表达模块协作，容易被理解为同层功能并列。

如果本图的核心是“应用复用执行基座”，应用在上、执行在下更容易读懂。这只是阅读布局选择，不自动成为严格源码分层。静态依赖与完成结果的流向需要分别定义；不能用一个向上箭头同时代表返回值、回调和具体模块导入。C4 的[绘图检查表](https://c4model.com/diagrams/checklist)要求明确图类型、范围、元素类型及箭头含义；[动态图](https://c4model.com/diagrams/dynamic)用于另行说明特定场景的运行协作。

### 持续工作是不是定时任务或外部触发的总称

不是。触发方式和业务生命周期是两个维度。

| 场景                 | 触发           | 需要保存的业务状态                    |
| -------------------- | -------------- | ------------------------------------- |
| 人工提交一次资料分析 | 手动           | 可能只有一次 Run，也可能需要任务验收  |
| 每天整理新闻         | 时间           | 计划、某一期工作、对应 Run 及交付结果 |
| PR 更新后生成评审    | 事件           | 订阅、目标版本、评审实例及提交状态    |
| 人工批准后继续发布   | 人工决定或回调 | 原实例的等待状态、批准依据与后续步骤  |

人工交办也可能跨天等待；定时触发的工作也可能仅执行一步。“持续工作服务”没有充分说明对象与责任，候选名称可改为“任务管理与编排”，其中明确业务任务、计划或订阅、实例进度及交付。这里的业务任务不等于内部执行协调对象 `RunTask`。

首个场景只需要计划、发生记录和 Run 关联时，可以先做轻量实现；不能因采用“编排”一词就预建完整工作流引擎。场景负责定义目标、风险规则及验收，编排机制负责保存和推进状态。

### 对话、考核与任务能否并列

可以按业务对象与生命周期所有权并列，而不是因为它们恰好各有一个页面。

| 模块                   | 拥有的事实                           | 执行后还要负责什么               |
| ---------------------- | ------------------------------------ | -------------------------------- |
| 对话                   | Conversation、消息和 Run 关联        | 接纳为正式回复，关联可下载成果   |
| 考核                   | 批次、题目、答卷和评分规则           | 接纳答卷并评分，完成批次         |
| 任务管理与编排（候选） | 工作定义、计划或订阅、任务实例和步骤 | 等待、推进、交付及验收           |
| 执行子系统             | Run、动作、预算、状态与执行成果      | 完成受控执行，不替应用作业务验收 |

考核已独立使用执行服务，并非对话的一个样式；见[考核服务](../../backend/app/evaluations/service.py)。任务模块仍属拟议能力，不能从考核的实现直接推导已经有通用任务管理。

### 资源模块能否因为“都被上层使用”而合并

仅凭共同使用者不足以形成模块边界。需要继续问：它们管理什么对象、谁可以改变、哪些修改要一起成功、失败后由谁恢复，以及能否独立演进。

| 原节点            | 判断                                                                         |
| ----------------- | ---------------------------------------------------------------------------- |
| 身份与授权        | 管理用户、资格和撤销，是共享安全能力；与内容资产不同                         |
| 员工配置与装配    | 管理岗位、规则及资源选择关系；引用技能或连接，不取得它们的所有权             |
| Skill、知识、记忆 | 都与内容有关，但方法发布、资料入库、记忆纠错各有规则，不能视为同一种资源对象 |
| 模型与工具连接    | 模型和工具可合并展示接入职责，内部仍有各自协议、凭据及修订规则               |
| 文件与执行环境    | 管理持久成果和临时环境，保留、回收及故障核对不同于内容事实治理               |

这些可以作为独立技术模块出现在同一级组件视图，但不因此组成一个统一的“资源业务领域”。总图可按共享领域能力、运行资源、安全能力分区；分区是阅读组织，不宣称每区对应一个新服务或统一事务。需要展开时仍按各自所有者说明。

模块粒度不按代码行数或方框大小决定。独立权限、状态和恢复责任是拆分依据；只是同一个对象上的几个查询或保存操作，不必再拆新模块。arc42 建议采用一致的内聚标准组织构件，而非仅按谁会调用它们分组，见[内聚性原则](https://docs.arc42.org/tips/5-17/)。

### 两处基础设施和两处索引是否重复

原“基础设施适配”中，“数据与文件访问”按访问对象分，“模型/工具协议”按集成技术分，“存档/索引/观测”又合并了恢复、检索和诊断，切分维度不统一。下方再列存储与外部系统，同时引入了代码适配和运行依赖两种视角。

适配代码与实际存储可以同时画，但要明确谁调用哪个接口、哪个框是代码、哪个框是存储。原图没有给出这些对应关系，也让聚合框看起来像一个必须经过的统一服务。下一版主图建议删除泛化的“基础设施适配”中转框，直接标注必要的存储和外部系统依赖；具体客户端、存储访问与索引适配在相应模块展开。

图里的两处“索引”不是有意设计的两套同名服务。上方原意是索引访问的代码，下方是实际索引存储。当前关键词索引为 SQLite FTS，向量索引使用 Chroma；知识模块管理来源、有效成员及发布资格。见[知识模块](../../backend/app/knowledge/README.md#正式向量检索)。可以分别写“知识处理与检索”及“全文/向量索引存储”，不应两处都只写“索引”。

## 必须保留的执行主线

1. 应用校验并保存业务输入，提交一次 Run，保存业务关联。
2. Execution 管理受理、调度、取消和执行事实；Worker / Task 驱动 Agent 运行时，完成模型和获准工具操作。
3. 执行服务核验并保存成果与 Run 终态。
4. 应用读取或收到可恢复的完成提示，独立接纳成果，判断继续、交付或结束。

Run 是持久记录，不是主动执行主体。一份业务任务可关联多次 Run；一个 Run 内又可多次请求模型和工具。“Run 事务管理”应理解为执行生命周期及关键短事务，不能把等待模型、网络调用或人工确认包进一个长期数据库事务。

当前[RunService](../../backend/app/execution/service.py)在调用方事务中受理，在完成事务中保存成果与终态；[对话接纳](../../backend/app/conversations/acceptance.py)独立处理发布及重试，不改写已成功 Run，也不因接纳失败重跑模型。执行成功与业务完成的分离，是下一版应最清楚表达的边界。

## 下一版绘制依据

先以“后端服务组件架构”作为主图口径，主要节点为职责明确的模块，浏览器和外部系统作为相连参与者。应用使用执行服务的关系突出展示，资源与安全依赖按需展开，不把所有目录都画成主模块。平台管理、资料入库等请求仍有自己的服务入口，不能把平台所有请求都导向 Run。

平台总览只保留前端、后端、主要存储和外部系统；Execution 内部再单独展开运行管理、Agent 运行时、动作控制及成果保存。用一张局部运行协作图解释提交、执行、结果接纳与任务推进，避免总图同时承担时序职责。

arc42 的[构件视图](https://docs.arc42.org/section-5/)采用逐级展开，并要求说明职责、接口及拆分原因。这里采用这一绘制原则；不把 C4 层级、逻辑模块层次和部署进程混为一谈，也不为满足版式增加无实际责任的中转模块。
